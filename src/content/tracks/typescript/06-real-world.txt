## What can go wrong is part of the type

In JavaScript, any function may throw anything, and nothing in its signature says so. TypeScript doesn't change that: there's no `throws` clause, and a caught value is `unknown` (Module 1). This lesson shows how professionals make failures **visible and checkable** anyway.

## Custom error classes

Error subclasses (JavaScript course, Module 7) become more useful with typed fields:

```ts
class HttpError extends Error {
  override name = "HttpError";

  constructor(
    readonly status: number,
    message: string,
    options?: { cause?: unknown },
  ) {
    super(message, options);
  }

  get retryable(): boolean {
    return this.status >= 500;
  }
}

class ValidationError extends Error {
  override name = "ValidationError";

  constructor(readonly fields: Record<string, string>) {
    super(`Invalid: ${Object.keys(fields).join(", ")}`);
  }
}

function handle(error: unknown): string {
  if (error instanceof ValidationError) return `fix ${Object.keys(error.fields).join(" and ")}`;
  if (error instanceof HttpError) return error.retryable ? "try again later" : `request failed (${error.status})`;
  if (error instanceof Error) return `unexpected: ${error.message}`;
  return `unknown failure: ${String(error)}`;
}

console.log(handle(new ValidationError({ email: "missing", age: "too low" })));
console.log(handle(new HttpError(503, "unavailable")));
console.log(handle("oops"));
```

`instanceof` narrows `unknown` to each error class, giving typed access to `fields` or `status`. The final `String(error)` branch handles code that throws non-errors (strings, objects), which JavaScript allows. The `cause` option chains a low-level error to the one you rethrow, keeping the original for debugging.

## Results: errors as values

Exceptions are invisible in types. For failures the **caller is expected to handle** (invalid input, "not found", a declined payment), many TypeScript codebases return a **result** instead, a discriminated union:

```ts
type Result<T, E = string> = { ok: true; value: T } | { ok: false; error: E };

const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
const err = <E>(error: E): Result<never, E> => ({ ok: false, error });

function parseAge(input: string): Result<number> {
  const n = Number(input);
  if (input.trim() === "" || !Number.isInteger(n)) return err(`"${input}" is not a whole number`);
  if (n < 0 || n > 150) return err(`${n} is not a realistic age`);
  return ok(n);
}

for (const input of ["36", "abc", "200"]) {
  const result = parseAge(input);
  console.log(result.ok ? `age ${result.value}` : `error: ${result.error}`);
}
```

The caller **can't** use `result.value` without first checking `result.ok`, so failures can't be forgotten. `Result<number, never>` (from `ok`) is assignable to `Result<number, string>` because `never` fits everywhere: that's the bottom type from Module 5 at work.

## Typed error unions

Results shine when the error is itself a discriminated union, so callers can handle each failure differently, with exhaustiveness checking:

```ts
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

type WithdrawError =
  | { kind: "insufficient-funds"; shortBy: number }
  | { kind: "account-frozen" }
  | { kind: "limit-exceeded"; limit: number };

function withdraw(balance: number, amount: number, frozen: boolean): Result<number, WithdrawError> {
  if (frozen) return { ok: false, error: { kind: "account-frozen" } };
  if (amount > 500) return { ok: false, error: { kind: "limit-exceeded", limit: 500 } };
  if (amount > balance) return { ok: false, error: { kind: "insufficient-funds", shortBy: amount - balance } };
  return { ok: true, value: balance - amount };
}

function message(e: WithdrawError): string {
  switch (e.kind) {
    case "insufficient-funds": return `You need ${e.shortBy} more`;
    case "account-frozen": return "Your account is frozen";
    case "limit-exceeded": return `The daily limit is ${e.limit}`;
  }
}

const r = withdraw(100, 130, false);
console.log(r.ok ? r.value : message(r.error));
```

Add a new failure kind and every `switch` that doesn't handle it stops compiling: the types now document every way the operation can fail.

## When to throw, when to return

A common, practical split:

- **Throw** for bugs and truly exceptional situations the immediate caller can't do anything sensible about (a broken invariant, a missing configuration file at startup, programmer errors). Let them travel up to a top-level handler that logs them.
- **Return a result** for expected failures that are part of the domain (validation, "not found", business rules), especially across module or API boundaries.

Libraries such as `neverthrow` and `Effect` provide rich result types with chaining helpers; a ten-line `Result` type like the one above is often enough.

type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

type TransferError =
  | { kind: "same-account" }
  | { kind: "invalid-amount"; amount: number }
  | { kind: "unknown-account"; id: string }
  | { kind: "insufficient-funds"; available: number };

function transfer(accounts: Map<string, number>, from: string, to: string, amount: number): Result<Map<string, number>, TransferError> {
  const fail = (error: TransferError): Result<Map<string, number>, TransferError> => ({ ok: false, error });
  if (from === to) return fail({ kind: "same-account" });
  if (!(amount > 0) || Math.round(amount * 100) !== amount * 100) return fail({ kind: "invalid-amount", amount });
  const fromBalance = accounts.get(from);
  if (fromBalance === undefined) return fail({ kind: "unknown-account", id: from });
  const toBalance = accounts.get(to);
  if (toBalance === undefined) return fail({ kind: "unknown-account", id: to });
  if (fromBalance < amount) return fail({ kind: "insufficient-funds", available: fromBalance });
  const next = new Map(accounts);
  next.set(from, fromBalance - amount);
  next.set(to, toBalance + amount);
  return { ok: true, value: next };
}

function describe(e: TransferError): string {
  switch (e.kind) {
    case "same-account":
      return "cannot transfer to the same account";
    case "invalid-amount":
      return `invalid amount ${e.amount}`;
    case "unknown-account":
      return `unknown account ${e.id}`;
    case "insufficient-funds":
      return `only ${e.available} available`;
    default:
      return e satisfies never;
  }
}

=== lesson ts-async | Typing asynchronous code | 85
## Promise<T>

An `async` function always returns a `Promise`, and TypeScript types it as `Promise<T>`, where `T` is what the promise **resolves to**:

```ts
async function getGreeting(name: string): Promise<string> {
  await new Promise((resolve) => setTimeout(resolve, 50));
  return `Hello, ${name}`;
}

const pending = getGreeting("Ada");
const text = await pending;
console.log(text.toUpperCase());
```

`pending` is a `Promise<string>`; `await pending` is a `string`. Forget the `await` and TypeScript catches it: `pending.toUpperCase()` is an error (a Promise has no such method), which in plain JavaScript would be a confusing run-time crash. The same goes for `if (isAdmin(user))` when `isAdmin` is async: the `typescript-eslint` rule `no-misused-promises` flags it, because a Promise is always truthy.

`new Promise<T>(...)` takes a type argument when there's nothing to infer it from:

```ts
function delay<T>(ms: number, value: T): Promise<T> {
  return new Promise<T>((resolve) => setTimeout(() => resolve(value), ms));
}

console.log(await delay(30, { ready: true }));
```

## Typing fetch responses

`response.json()` returns `Promise<any>`: TypeScript can't know what a server will send. The safest habit is to treat it as `unknown` and **check** it (next lesson), or, at minimum, to state the expected type in one place:

```ts
interface User {
  id: number;
  name: string;
  email: string;
  city: string;
}

async function getJson<T>(url: string): Promise<T> {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`${response.status} ${response.statusText} for ${url}`);
  return (await response.json()) as T;
}

const users = await getJson<User[]>("https://api.example.com/users");
console.log(users.map((u) => `${u.name} (${u.city})`).slice(0, 2));
```

That `as T` is an honest, contained cast: one function, clearly documented, where you **trust** the server's contract. In production, APIs change, so validating at this boundary (with a schema, next lesson) is better. (`api.example.com` is DevQuest's built-in demo API, as in the JavaScript course.)

## Combining promises

`Promise.all` keeps each position's type when given a tuple, so parallel requests stay precisely typed:

```ts
const wait = <T>(ms: number, value: T) => new Promise<T>((r) => setTimeout(() => r(value), ms));

const [count, label, flags] = await Promise.all([wait(30, 42), wait(10, "items"), wait(20, [true, false])]);
console.log(count + 1, label.toUpperCase(), flags.length);

const settled = await Promise.allSettled([wait(5, "fine"), Promise.reject(new Error("broken"))]);
for (const r of settled) console.log(r.status === "fulfilled" ? r.value : (r.reason as Error).message);
```

`count` is a `number`, `label` a `string`, `flags` a `boolean[]`. `Promise.allSettled` returns `PromiseSettledResult<T>` values, a discriminated union on `status` (`"fulfilled"` with `value`, `"rejected"` with `reason: any`).

## Typing callbacks and async functions as values

A function type can return a promise: `type Loader<T> = (id: number) => Promise<T>`. Generic helpers built on that are common in real code, for example a retry wrapper:

```ts
async function retry<T>(task: () => Promise<T>, attempts: number, delayMs = 10): Promise<T> {
  let lastError: unknown;
  for (let attempt = 1; attempt <= attempts; attempt++) {
    try {
      return await task();
    } catch (error) {
      lastError = error;
      await new Promise((r) => setTimeout(r, delayMs * attempt));
    }
  }
  throw new Error(`Failed after ${attempts} attempts`, { cause: lastError });
}

const result = await retry(async () => {
  const response = await fetch("https://api.example.com/flaky");
  if (!response.ok) throw new Error(`status ${response.status}`);
  return (await response.json()) as { ok: boolean; attempt: number };
}, 5);
console.log(result);
```

`retry` returns whatever the task returns: `T` flows from the callback to the result. (The demo `/flaky` endpoint fails twice before succeeding.)

## Async iteration and cancellation

Two more typed tools you'll meet:

- **Async generators** (`async function*`) return `AsyncGenerator<T>`, consumed with `for await`; useful for paginated APIs.
- **`AbortSignal`** cancels fetches and timers; pass `{ signal }` options through your functions, typed as `AbortSignal`.

```ts
interface Page { page: number; items: { id: number; name: string; price: number }[]; nextPage: number | null }

async function* allProducts(signal?: AbortSignal): AsyncGenerator<Page["items"][number]> {
  let page: number | null = 1;
  while (page !== null) {
    const response = await fetch(`https://api.example.com/products?page=${page}`, { signal });
    const data = (await response.json()) as Page;
    yield* data.items;
    page = data.nextPage;
  }
}

let total = 0;
for await (const product of allProducts()) total += product.price;
console.log(`Total stock value: ${total}`);
```

## Typed messages between threads

Web Workers (browser) and `worker_threads` (Node.js) run code in parallel, communicating only by **messages**, which arrive untyped (`event.data` is `any`). A discriminated union for each direction turns the message channel into a checked protocol, the same idea as typed events:

```
type ToWorker =
  | { type: "resize"; imageId: string; width: number }
  | { type: "cancel"; imageId: string };

type FromWorker =
  | { type: "progress"; imageId: string; percent: number }
  | { type: "done"; imageId: string; url: string }
  | { type: "failed"; imageId: string; error: string };

const worker = new Worker(new URL("./resize.worker.ts", import.meta.url), { type: "module" });
const send = (message: ToWorker) => worker.postMessage(message);

worker.addEventListener("message", (event: MessageEvent<FromWorker>) => {
  const message = event.data;
  switch (message.type) {
    case "progress": showProgress(message.imageId, message.percent); break;
    case "done": showImage(message.imageId, message.url); break;
    case "failed": showError(message.imageId, message.error); break;
  }
});

send({ type: "resize", imageId: "a1", width: 800 });
```

Both files import the same two types, so a change to the protocol breaks the build on both sides. (`MessageEvent<FromWorker>` is a promise about the data rather than a check; for messages from code you don't control, validate them like any other boundary.)

=== lesson ts-runtime-validation | Validating data at the boundaries | 95
## The boundary problem

Types disappear at run time (Module 1). Everything **inside** your program is checked, but data that **enters** it is not: HTTP responses, request bodies, `JSON.parse`, `localStorage`, environment variables, files, form fields, messages from other services. If you just declare that such data has a type (`as User`), a wrong assumption travels deep into your code before failing.

The professional answer: **validate at the boundary**. Data enters as `unknown`, a validator checks it, and only checked data gets a precise type. Inside, you can trust your types again.

## Hand-written validation

You already know the basic tool: a type guard (Module 2). For anything bigger, writing guards by hand becomes long and repetitive, and the guard and the type can drift apart:

```ts
interface Settings {
  theme: "light" | "dark";
  fontSize: number;
}

function isSettings(value: unknown): value is Settings {
  return (
    typeof value === "object" && value !== null &&
    "theme" in value && (value.theme === "light" || value.theme === "dark") &&
    "fontSize" in value && typeof value.fontSize === "number"
  );
}

const saved: unknown = JSON.parse('{"theme": "dark", "fontSize": "14"}');
console.log(isSettings(saved) ? `font ${saved.fontSize}` : "invalid settings, using defaults");
```

The bug is caught (`fontSize` is a string), but notice the duplication: every property is described twice, once in the interface and once in the guard.

## Schemas: one description, two uses

**Schema libraries** solve this. You describe the data **once**, as a value; the library gives you both a run-time validator and the TypeScript type, **inferred** from the schema. The most popular is **Zod**:

```
import { z } from "zod";

const Settings = z.object({
  theme: z.enum(["light", "dark"]),
  fontSize: z.number().int().min(8).max(32),
  email: z.string().email().optional(),
});

type Settings = z.infer<typeof Settings>;
// { theme: "light" | "dark"; fontSize: number; email?: string | undefined }

const result = Settings.safeParse(JSON.parse(text));
if (result.success) {
  useSettings(result.data); // typed as Settings
} else {
  console.log(result.error.issues); // what was wrong, and where
}
```

Valibot, ArkType and TypeBox work the same way (TypeBox also produces JSON Schema, which OpenAPI tools use). Frameworks build on them: tRPC, Hono and Astro validate request inputs with them, and React Hook Form validates forms.

## How do they do it? Build a tiny one

There's no magic: a schema is an object with a `parse` method, and the type is inferred with the generics and conditional types from Modules 3 and 5. Here's a working miniature:

```ts
type Schema<T> = { parse(value: unknown, path?: string): T };
type Infer<S> = S extends Schema<infer T> ? T : never;

class SchemaError extends Error {}

const string = (): Schema<string> => ({
  parse(value, path = "value") {
    if (typeof value !== "string") throw new SchemaError(`${path} should be a string`);
    return value;
  },
});

const number = (): Schema<number> => ({
  parse(value, path = "value") {
    if (typeof value !== "number" || Number.isNaN(value)) throw new SchemaError(`${path} should be a number`);
    return value;
  },
});

function object<Shape extends Record<string, Schema<unknown>>>(shape: Shape): Schema<{ [K in keyof Shape]: Infer<Shape[K]> }> {
  return {
    parse(value, path = "value") {
      if (typeof value !== "object" || value === null) throw new SchemaError(`${path} should be an object`);
      const out: Record<string, unknown> = {};
      for (const key of Object.keys(shape)) out[key] = shape[key].parse((value as Record<string, unknown>)[key], `${path}.${key}`);
      return out as { [K in keyof Shape]: Infer<Shape[K]> };
    },
  };
}

const User = object({ name: string(), age: number() });
type User = Infer<typeof User>;

const good: User = User.parse(JSON.parse('{"name": "Ada", "age": 36, "extra": true}'));
console.log(good);
try {
  User.parse(JSON.parse('{"name": "Bob", "age": "old"}'));
} catch (error) {
  console.log(error instanceof SchemaError ? error.message : error);
}
```

`type User` is computed from the schema: `{ name: string; age: number }`. Add a property to the schema, and both the validation and the type follow. (The two casts are contained inside the library, which is where such code belongs. Unknown properties like `extra` are dropped from the result, as Zod does by default.)

## Where to validate

Validate **once, at each entry point**, then pass typed data inward:

- **API handlers** (server): request body, query and route parameters;
- **API clients** (front end): responses from servers you don't control, or that may be a different version;
- **configuration**: environment variables at startup (fail fast with a clear message);
- **storage**: `localStorage`, files and caches, which may hold data from an older version of your app.

Inside the program, don't re-validate data that's already typed: that's what the types are for. And prefer `safeParse`-style results (a `Result`, previous lessons) where invalid input is expected, such as forms, and throwing `parse` where it means a bug or misconfiguration.

function literal<const L extends string | number>(expected: L): Schema<L> {
  return {
    parse(value, path = "value") {
      if (value !== expected) throw new SchemaError(`${path} should be ${JSON.stringify(expected)}`);
      return expected;
    },
  };
}

function optional<T>(schema: Schema<T>): Schema<T | undefined> {
  return {
    parse(value, path = "value") {
      return value === undefined ? undefined : schema.parse(value, path);
    },
  };
}

function array<T>(item: Schema<T>): Schema<T[]> {
  return {
    parse(value, path = "value") {
      if (!Array.isArray(value)) throw new SchemaError(`${path} should be an array`);
      return value.map((v, i) => item.parse(v, `${path}[${i}]`));
    },
  };
}

function union<T extends Schema<unknown>[]>(...options: T): Schema<Infer<T[number]>> {
  return {
    parse(value, path = "value") {
      for (const option of options) {
        try {
          return option.parse(value, path) as Infer<T[number]>;
        } catch (error) {
          if (!(error instanceof SchemaError)) throw error;
        }
      }
      throw new SchemaError(`${path} does not match any option`);
    },
  };
}

const Order = object({
  id: number(),
  status: union(literal("new"), literal("paid"), literal("shipped")),
  items: array(object({ sku: string(), qty: number() })),
  gift: optional(boolean()),
});

## The DOM is fully typed

TypeScript ships with type declarations for the whole browser API (`lib.dom.d.ts`): every element, event and method. That's why the editor can autocomplete `addEventListener("` with every event name. The types form a hierarchy: `HTMLInputElement` extends `HTMLElement`, which extends `Element`, then `Node`, then `EventTarget`.

In DevQuest, pages can use TypeScript with **`<script lang="ts">`**: the script is type-checked (a page with type errors doesn't run), then its types are stripped. (In a real project, a bundler such as Vite does this for `.ts` files.)

```html
<label>Name <input id="name"></label>
<p id="out">Type your name</p>
<script lang="ts">
const input = document.querySelector<HTMLInputElement>("#name");
const out = document.getElementById("out");
if (input === null || out === null) throw new Error("page is missing elements");

input.addEventListener("input", () => {
  out.textContent = input.value.trim() ? `Hello, ${input.value.trim()}!` : "Type your name";
});
console.log(input.tagName, input.value === "");
</script>
```

Three typing points in that small script:

- `querySelector` returns `Element | null`. With a **tag name** (`querySelector("input")`) TypeScript knows the element type automatically; with a CSS selector like `"#name"` it can't, so you give it as a type argument: `querySelector<HTMLInputElement>("#name")`. (That type argument is an unchecked promise, like `as`; if unsure, check with `instanceof`.)
- Elements may be missing, so the result includes `null`, and you must handle it once. After the `throw`, both are narrowed.
- Inside the listener, `input` and `out` stay narrowed: they're `const`, and the arrow function is created after the check. (A `function` declaration wouldn't keep the narrowing, because declarations are hoisted and could run before the check.)

## Events

Event listeners receive precisely typed events, chosen by the event name:

```html
<button id="add">Add</button> <span id="count">0</span>
<input id="key" placeholder="press a key here">
<script lang="ts">
const button = document.getElementById("add");
const count = document.getElementById("count");
const keyInput = document.getElementById("key");

if (button && count && keyInput) {
  let clicks = 0;
  button.addEventListener("click", (event) => {
    clicks += event.shiftKey ? 10 : 1;
    count.textContent = String(clicks);
  });
  keyInput.addEventListener("keydown", (event) => {
    console.log(`key: ${event.key}`);
  });
}
</script>
```

`event` is a `MouseEvent` for `"click"` (so `shiftKey` exists) and a `KeyboardEvent` for `"keydown"` (so `key` exists), thanks to overloads on `addEventListener`.

One common trap: `event.target` is typed as `EventTarget | null`, not as the element, because with **event delegation** (JavaScript course, Module 11) the target can be any descendant. Narrow it with `instanceof`:

```html
<ul id="list"><li><button data-id="1">Delete 1</button></li><li><button data-id="2">Delete 2</button></li></ul>
<script lang="ts">
const list = document.getElementById("list");
list?.addEventListener("click", (event) => {
  const target = event.target;
  if (!(target instanceof HTMLButtonElement)) return;
  console.log(`delete item ${target.dataset.id}`);
  target.closest("li")?.remove();
});
document.querySelector<HTMLButtonElement>("[data-id='2']")?.click();
</script>
```

`instanceof` checks the real element at run time and narrows its type: the safe way to handle `target`.

## React with TypeScript

React projects are mostly TypeScript today (`npm create vite@latest my-app -- --template react-ts`). Components are functions whose **props** are typed with an interface or type, and JSX is checked against them. React's own types come from the `@types/react` package, which DevQuest doesn't include, so these examples are shown rather than run:

```
import { useState, type ReactNode } from "react";

interface ButtonProps {
  label: string;
  variant?: "primary" | "secondary";
  disabled?: boolean;
  onClick: () => void;
  children?: ReactNode;
}

function Button({ label, variant = "primary", disabled = false, onClick }: ButtonProps) {
  return <button className={variant} disabled={disabled} onClick={onClick}>{label}</button>;
}

interface Todo { id: number; text: string; done: boolean }

function TodoList({ initial }: { initial: Todo[] }) {
  const [todos, setTodos] = useState<Todo[]>(initial);
  const [draft, setDraft] = useState("");

  function add(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    setTodos((list) => [...list, { id: Date.now(), text: draft, done: false }]);
    setDraft("");
  }

  return (
    <form onSubmit={add}>
      <input value={draft} onChange={(e) => setDraft(e.target.value)} />
      <Button label="Add" onClick={() => {}} />
      <ul>{todos.map((t) => <li key={t.id}>{t.text}</li>)}</ul>
    </form>
  );
}
```

What TypeScript adds:

- **Props are checked at every use**: `<Button label="Add" />` without `onClick` is an error, as is `variant="danger"`.
- **`useState` infers** from the initial value (`useState("")` is a string state); give a type argument when the initial value doesn't show the full type: `useState<Todo[]>([])`, `useState<User | null>(null)`.
- **Event handlers are typed** by the JSX attribute: in `onChange={(e) => ...}` on an `<input>`, `e.target.value` is known to be a string. Written separately, the type is `React.ChangeEvent<HTMLInputElement>`.
- `ReactNode` is the type of anything renderable (for `children`).

Everything else in this course applies directly: discriminated unions for component state ("loading" / "error" / "loaded"), generics for reusable components (`function List<T>({ items, render }: { items: T[]; render: (item: T) => ReactNode })`), and validated API data.

## Modules in TypeScript

TypeScript uses standard ES modules (JavaScript course, Module 11). Types can be exported and imported like values:

```ts
// file: models.ts
export interface Product {
  sku: string;
  name: string;
  priceCents: number;
}
export type Currency = "EUR" | "USD" | "GBP";
export const DEFAULT_CURRENCY: Currency = "EUR";

// file: format.ts
import type { Currency, Product } from "./models.ts";

export function price(p: Product, currency: Currency): string {
  return `${p.name}: ${(p.priceCents / 100).toFixed(2)} ${currency}`;
}

// file: main.ts
import { DEFAULT_CURRENCY, type Product } from "./models.ts";
import { price } from "./format.ts";

const lamp: Product = { sku: "L-1", name: "Desk lamp", priceCents: 3500 };
console.log(price(lamp, DEFAULT_CURRENCY));
```

- **`import type`** imports only types: the whole statement is erased from the output. Inline `type` markers (`import { DEFAULT_CURRENCY, type Product }`) do the same for single names.
- With the compiler option **`verbatimModuleSyntax`** (recommended), imports that are only used as types **must** be marked with `type`, so every tool (Node, esbuild, Vite) can strip them without type information.

## File extensions in imports

How you write import paths depends on what runs the code:

- **Node.js running `.ts` files directly** (type stripping) needs the real file name: `import { price } from "./format.ts"`. (`tsc` accepts this with `allowImportingTsExtensions`, or rewrites it with `rewriteRelativeImportExtensions`.)
- **`tsc` compiling to JavaScript for Node** (`"module": "NodeNext"`) expects the name of the **output** file: `import { price } from "./format.js"`, which looks odd in a `.ts` file but is what Node will load after compilation.
- **Bundlers** (Vite, webpack) accept either, and also extension-less paths (`"./format"`), with `"moduleResolution": "Bundler"`.

DevQuest accepts all three, so use whichever matches the project you're working in.

## Module mode and script mode

A file with at least one top-level `import` or `export` is a **module**: its declarations are private unless exported. A file without any is a **script**: its top-level declarations are **global**, visible in every other script of the project (and two scripts declaring the same `const` clash). That's why an otherwise empty `export {};` sometimes appears at the end of a file: it turns a script into a module. The compiler option `"moduleDetection": "force"` treats every file as a module, which is what you want in modern projects (and what DevQuest does).

## Namespaces: you'll meet them in older code

Before ES modules existed, TypeScript had its own way to group code: **namespaces** (originally called "internal modules").

```
namespace Geometry {
  export const TAU = Math.PI * 2;
  export function circumference(radius: number): number {
    return TAU * radius;
  }
}

console.log(Geometry.circumference(1).toFixed(3));
```

A namespace compiles to an object built by a function, so it isn't erasable syntax: Node's type stripping refuses it, and so does DevQuest (it strips types the same way). Today, **use modules instead**: a file is already a namespace. You'll still see `namespace` in declaration files (the types of libraries that expose a global object, such as `declare namespace google.maps { ... }`) and in older codebases.

## CommonJS and dynamic imports

Many npm packages are still CommonJS (`module.exports = ...`). With `"esModuleInterop": true` (on by default with `NodeNext`), you can import them with normal `import` syntax: `import express from "express"`. Declaration files describe such modules with `export = something;`, and very old TypeScript code imports them with `import fs = require("fs")`.

**Dynamic imports** (`await import("./charts.ts")`) load a module on demand, for example to make a web app's first load faster; their result is fully typed as the module's exports.

## Declaration files (.d.ts)

A **declaration file** contains only types: no code. It describes the shape of JavaScript that exists somewhere else. You meet them in three ways:

1. **Built-in**: `lib.dom.d.ts`, `lib.es2023.d.ts`... the types of the platform.
2. **Bundled with libraries**: most modern npm packages ship `.d.ts` files next to their JavaScript (look for `"types"` in their `package.json`).
3. **DefinitelyTyped**: for packages written in JavaScript without types, the community maintains types in separate `@types/...` packages: `npm install --save-dev @types/node @types/express`.

When a package has no types at all, write a minimal declaration yourself:

```ts
// file: slugify.js
export function slugify(text, separator = "-") {
  return text.toLowerCase().trim().replace(/[^a-z0-9]+/g, separator).replace(new RegExp(`^${separator}|${separator}$`, "g"), "");
}

// file: slugify.d.ts
export declare function slugify(text: string, separator?: string): string;

// file: main.ts
import { slugify } from "./slugify.js";
console.log(slugify("  Hello, TypeScript World! "));
```

`declare` says "this exists at run time; here's its type". A `.d.ts` file next to a `.js` file with the same name is picked up automatically. For an npm package, put `declare module "package-name" { ... }` in a `.d.ts` file in your project (a common place is `src/types/`).

Libraries written in TypeScript generate `.d.ts` files with `tsc --declaration`, so their users get types for free.

## Ambient declarations and globals

Some values exist without being imported: globals injected by a script tag, a bundler (`import.meta.env` in Vite), or a runtime. Declare them with `declare`:

```ts
declare const __APP_VERSION__: string;
declare function analytics(event: string, data?: Record<string, unknown>): void;

function about(): string {
  return typeof __APP_VERSION__ === "undefined" ? "development build" : `version ${__APP_VERSION__}`;
}
console.log(about());
```

(Here `__APP_VERSION__` isn't actually defined, so the `typeof` check matters: a `declare` is a promise TypeScript can't verify.)

## Types for JavaScript files: JSDoc

TypeScript can check plain JavaScript too, using **JSDoc comments** for types. With `"allowJs": true` and `"checkJs": true` (or `// @ts-check` at the top of a file), the editor checks `.js` files:

```
// @ts-check
/**
 * @param {number[]} values
 * @returns {number}
 */
export function average(values) {
  return values.reduce((a, b) => a + b, 0) / values.length;
}
```

This is how some projects (Svelte's own source, webpack) get type checking without a build step, and how large JavaScript codebases migrate gradually.

## Triple-slash directives

Occasionally you'll see special comments at the top of a declaration file: `/// <reference types="vite/client" />` pulls in a package's global types (here, the type of `import.meta.env`), and `/// <reference path="./globals.d.ts" />` includes another file. In application code, the `types` compiler option and imports do the same job more visibly, so you rarely write them yourself.

## tsconfig.json in depth

Module 1 introduced `tsconfig.json`. Here's what professionals tune, and why.

### The strict family

`"strict": true` turns on a set of flags, each of which you can also set individually:

| Flag | Catches |
|---|---|
| `noImplicitAny` | parameters and variables silently typed `any` |
| `strictNullChecks` | using possibly `null`/`undefined` values |
| `strictFunctionTypes` | unsafe function parameter types (contravariance, Module 5) |
| `strictBindCallApply` | wrong arguments to `bind`, `call`, `apply` |
| `strictPropertyInitialization` | class fields never initialised |
| `noImplicitThis` | `this` with an implicit `any` type |
| `useUnknownInCatchVariables` | `catch (e)` typed `any` instead of `unknown` |
| `alwaysStrict` | emits `"use strict"` |

Beyond `strict`, these are worth turning on in new projects:

- **`noUncheckedIndexedAccess`**: `array[i]` and `record[key]` include `undefined` (Module 2);
- **`exactOptionalPropertyTypes`**: `email?: string` means "absent or a string", not "may be set to `undefined`";
- **`noImplicitOverride`**: `override` is required (Module 4);
- **`noFallthroughCasesInSwitch`**, **`noImplicitReturns`**: classic control-flow mistakes;
- **`verbatimModuleSyntax`** and **`erasableSyntaxOnly`**: code that any type-stripping tool can handle (Node, esbuild, swc).

### Output and environment

| Option | Meaning |
|---|---|
| `target` | JavaScript version emitted (ES2022 is a safe modern choice) |
| `lib` | which built-in declarations are available (`["ES2023", "DOM"]` for browsers, without DOM for Node) |
| `module` / `moduleResolution` | `NodeNext` for Node packages; `ESNext` + `Bundler` for Vite and other bundlers |
| `types` | which `@types` packages are loaded automatically (`["node"]`, `["vite/client"]`) |
| `outDir`, `rootDir`, `declaration`, `sourceMap` | where output goes; emit `.d.ts`; source maps |
| `noEmit` | check only (when another tool builds) |
| `isolatedModules` | each file must be compilable alone (required by esbuild, swc, Vite) |
| `incremental` / `composite` | faster rebuilds; project references for monorepos |
| `paths` | import aliases like `@/components/*` (the bundler must be told too) |

Configurations can share settings with **`extends`** (`"extends": "@tsconfig/node22/tsconfig.json"`): the `@tsconfig/bases` packages hold recommended settings for each runtime.

## The toolchain

A modern TypeScript project typically uses:

- **`tsc`** for type checking (`tsc --noEmit`, or `tsc -b` with project references); TypeScript 7's native compiler makes this much faster on large codebases;
- **a fast transpiler** for building and running: Vite (esbuild and Rollup) for front ends, `tsx` or Node's type stripping for scripts and servers, `tsup` or `tsdown` to bundle libraries;
- **typescript-eslint** for lint rules that use type information: `no-floating-promises` (forgotten `await`), `no-misused-promises`, `no-unsafe-assignment` (spreading `any`), `switch-exhaustiveness-check`, `consistent-type-imports`;
- **Prettier** (or Biome) for formatting;
- **Vitest** (or Jest with ts-jest, or Node's `node:test`) for tests, written in TypeScript;
- **CI** running `tsc --noEmit`, the linter and the tests on every pull request.

Type-level tests also exist: Vitest's `expectTypeOf(value).toEqualTypeOf<...>()` checks types like the `Expect<Equal<...>>` checks used in this course, and `tsd` does the same for library authors.

## Building and shipping

- **Project layout**: source in `src/`, compiled output in `dist/` (`rootDir` and `outDir`), tests next to the code or in `test/`; output files are never committed.
- **Source maps** (`sourceMap`, plus `declarationMap` for libraries) map compiled JavaScript back to your TypeScript, so stack traces, debuggers and **error monitoring** services (Sentry and similar, which receive your source maps during deployment) show your original lines.
- **Project references** (`"composite": true` and `"references"` in `tsconfig.json`, built with `tsc -b`) split a large repository or monorepo into projects that build incrementally, each with its own settings.

**Publishing a library** to npm needs three things in addition to the compiled JavaScript: `"declaration": true` (emit `.d.ts` files), a `package.json` whose `"exports"` field lists the entry points with a `"types"` condition, and a check that the published types work for users, for example with the `@arethetypeswrong/cli` tool:

```
{
  "name": "@acme/money",
  "type": "module",
  "exports": {
    ".": { "types": "./dist/index.d.ts", "default": "./dist/index.js" }
  },
  "files": ["dist"]
}
```

## Migrating a JavaScript project

A proven, gradual path:

1. Add `tsconfig.json` with `allowJs: true`, `checkJs: false` and `strict: false`; make the build pass.
2. Rename files from `.js` to `.ts` one at a time, starting with leaf modules (utilities, models); fix the errors in each.
3. Install `@types/...` for dependencies; write small `.d.ts` files for the rest.
4. Turn on `noImplicitAny`, then `strictNullChecks` (usually the biggest batch of fixes, and the most valuable), then full `strict`.
5. Add typescript-eslint rules to stop new `any`s creeping in.

At no point does the application stop working: TypeScript was designed for this gradual adoption.

interface TsConfig {
  kind: "node" | "browser";
  compilerOptions: {
    target?: string;
    module?: "NodeNext" | "ESNext" | "Preserve" | "CommonJS";
    moduleResolution?: "NodeNext" | "Bundler" | "Node10";
    lib?: string[];
    strict?: boolean;
    noUncheckedIndexedAccess?: boolean;
    noEmit?: boolean;
    outDir?: string;
  };
}

function lintConfig(config: TsConfig): string[] {
  const o = config.compilerOptions;
  const warnings: string[] = [];
  if (o.strict !== true) warnings.push("enable strict");
  if (o.noUncheckedIndexedAccess !== true) warnings.push("enable noUncheckedIndexedAccess");
  if (o.module === "NodeNext" && o.moduleResolution !== undefined && o.moduleResolution !== "NodeNext") {
    warnings.push("module NodeNext needs moduleResolution NodeNext");
  }
  if (o.moduleResolution === "Bundler" && o.module !== "ESNext" && o.module !== "Preserve") {
    warnings.push("moduleResolution Bundler needs module ESNext or Preserve");
  }
  if (config.kind === "browser" && o.lib !== undefined && !o.lib.some((l) => l.toLowerCase() === "dom")) {
    warnings.push("a browser project needs the DOM lib");
  }
  if (o.noEmit === true && o.outDir !== undefined) warnings.push("noEmit with outDir is contradictory");
  return warnings;
}

function recommended(kind: "node" | "browser"): TsConfig {
  const base = { target: "ES2022", strict: true, noUncheckedIndexedAccess: true };
  return kind === "node"
    ? { kind, compilerOptions: { ...base, module: "NodeNext", moduleResolution: "NodeNext" } }
    : { kind, compilerOptions: { ...base, module: "ESNext", moduleResolution: "Bundler", lib: ["ES2023", "DOM"], noEmit: true } };
}

::solution
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

interface AppConfig {
  port: number;
  databaseUrl: string;
  logLevel: "debug" | "info" | "warn" | "error";
  features: string[];
}

const LEVELS = ["debug", "info", "warn", "error"] as const;

function isLevel(value: string): value is AppConfig["logLevel"] {
  return LEVELS.some((level) => level === value);
}

function loadConfig(env: Record<string, string | undefined>): Result<AppConfig, string[]> {
  const errors: string[] = [];

  const portText = env.PORT ?? "3000";
  const port = Number(portText);
  if (portText.trim() === "" || !Number.isInteger(port) || port < 1 || port > 65535) errors.push("PORT must be an integer from 1 to 65535");

  const databaseUrl = env.DATABASE_URL;
  if (databaseUrl === undefined || databaseUrl === "") errors.push("DATABASE_URL is required");
  else if (!databaseUrl.startsWith("postgres://")) errors.push("DATABASE_URL must start with postgres://");

  const level = env.LOG_LEVEL ?? "info";
  if (!isLevel(level)) errors.push(`LOG_LEVEL must be one of ${LEVELS.join(", ")}`);

  const features = (env.FEATURES ?? "").split(",").map((f) => f.trim()).filter((f) => f !== "");

  if (errors.length > 0 || databaseUrl === undefined || !isLevel(level)) return { ok: false, error: errors };
  return { ok: true, value: { port, databaseUrl, logLevel: level, features } };
}

::hints
- Collect messages in an `errors` array instead of returning at the first problem.
- A type guard `isLevel(value: string): value is AppConfig["logLevel"]` narrows the log level without `as`.
- At the end, TypeScript needs to know that `databaseUrl` is defined and `level` is valid: re-checking them in the final `if` (cheap) narrows them for the success branch.
