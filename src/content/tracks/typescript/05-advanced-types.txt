## Types are sets of values

The most useful mental model for TypeScript's type system: **a type is a set of values**.

- `boolean` is the set `{ true, false }`; the literal type `"red"` is a set with one value; `string` is the infinite set of all strings.
- A union `A | B` is the **union** of two sets: values in either.
- `never` is the **empty set**: no value has type `never`.
- `unknown` is the set of **all** values. It's called the **top type**; `never` is the **bottom type**.

"A is **assignable** to B" then simply means **A is a subset of B**: every value of A is also a value of B. `"red"` is assignable to `string`, `string` is assignable to `string | number`, and everything is assignable to `unknown`. A type that's a subset is called a **subtype**; the larger one is a **supertype**.

This model explains things that look odd at first. An object type `{ name: string }` is the set of **all objects that have a string `name`**, including those with more properties. So `{ name: string; age: number }` is a *smaller* set (more requirements, fewer values): it's a subtype, even though it has more properties.

## Intersection types

An **intersection** `A & B` is a value that is **both** an A and a B: it has all properties of both.

```ts
type Timestamps = { createdAt: string; updatedAt: string };
type Article = { title: string; body: string };
type StoredArticle = Article & Timestamps & { id: number };

const post: StoredArticle = {
  id: 1, title: "Types as sets", body: "...",
  createdAt: "2026-01-01", updatedAt: "2026-01-02",
};
console.log(Object.keys(post).length, post.title);
```

Intersections combine object types like `interface ... extends` does (`interface StoredArticle extends Article, Timestamps { id: number }` is the equivalent). Two differences: `&` works with any types, including unions; and conflicting properties don't produce an error at the declaration, but a property of type `never` (`{ id: string } & { id: number }` has `id: never`, because no value is both). `extends` reports the conflict immediately, which is one reason to prefer interfaces for object hierarchies.

Intersecting **primitives** makes the set smaller: `string & number` is `never`, and `string & { __brand: "Email" }` is the branded string from Module 4.

~~~check

~~~

## unknown and never in unions and intersections

The set model predicts how the special types behave:

| Expression | Result | Why |
|---|---|---|
| `T \| never` | `T` | adding the empty set changes nothing |
| `T & unknown` | `T` | intersecting with everything changes nothing |
| `T \| unknown` | `unknown` | the union with everything is everything |
| `T & never` | `never` | nothing is in the empty set |

`never` showing up in a union where it disappears is the basis of many advanced types (the conditional types lesson uses it to filter unions).

## Variance: when is a container of A a container of B?

If `Dog` is a subtype of `Animal`, is `Dog[]` a subtype of `Animal[]`? Is a function taking a `Dog` usable where a function taking an `Animal` is expected? These questions are about **variance**:

- **Covariance** (same direction): `Dog[]` is assignable to `Animal[]`, and a function returning `Dog` fits where one returning `Animal` is expected. Producers can be more specific.
- **Contravariance** (opposite direction): a function **taking** an `Animal` fits where a function taking a `Dog` is expected, **not** the other way round. Consumers can be more general.

```ts
interface Animal { name: string }
interface Dog extends Animal { bark(): string }

const feedAnimal = (a: Animal) => `${a.name} fed`;
const walkDog = (d: Dog) => `${d.name} walked, ${d.bark()}`;

const dogHandlers: ((d: Dog) => string)[] = [feedAnimal, walkDog];
const rex: Dog = { name: "Rex", bark: () => "woof" };
console.log(dogHandlers.map((handle) => handle(rex)));
```

`feedAnimal` can handle any animal, so it can certainly handle a dog. The reverse, using `walkDog` where any animal might arrive, would call `bark()` on a cat. With `strict` (`strictFunctionTypes`), TypeScript rejects it.

One known hole: arrays are covariant even though they're mutable. You can assign a `Dog[]` to an `Animal[]` variable, then push a cat into it. TypeScript accepts this for convenience; `readonly` arrays (where nothing can be pushed) are genuinely safe to treat covariantly. Methods declared with method syntax (`walk(d: Dog): void` in an interface) are also checked more loosely ("bivariantly") than function-typed properties (`walk: (d: Dog) => void`), for historical compatibility.

## satisfies: check without widening

You often want to check a value against a type **without** losing the more precise type TypeScript inferred. An annotation replaces the inferred type; **`satisfies`** checks it and keeps the inferred type:

```ts
type Colour = string | [r: number, g: number, b: number];

const annotated: Record<string, Colour> = { primary: "#3178c6", accent: [255, 128, 0] };
const checked = { primary: "#3178c6", accent: [255, 128, 0] } satisfies Record<string, Colour>;

console.log(checked.primary.toUpperCase(), checked.accent[0]);
```

With the annotation, `annotated.primary` is `Colour` (string or tuple), so `.toUpperCase()` would be an error, and `annotated.anything` is allowed (any string key). With `satisfies`, TypeScript still verifies every value is a valid `Colour` (a typo like `[255, 128]` is caught), but `checked.primary` remains a `string`, `checked.accent` a tuple, and only the two real keys exist. Use `satisfies` for configuration objects and lookup tables: you get both the check and the precision.

=== lesson ts-type-operators | Type operators and utility types | 90
## Computing types from other types

Professional TypeScript avoids writing the same information twice. Instead of maintaining several similar types by hand, you **derive** them with type operators, so they can never drift apart.

### typeof: the type of a value

In a type position, `typeof x` gives the type TypeScript inferred for the value `x`:

```ts
const defaults = { theme: "dark", fontSize: 14, showTips: true };
type Settings = typeof defaults;

function update(changes: Partial<Settings>): Settings {
  return { ...defaults, ...changes };
}
console.log(update({ fontSize: 16 }));
```

### keyof: the property names

`keyof T` is the union of `T`'s keys:

```ts
interface Product { id: number; name: string; price: number }
type ProductKey = keyof Product;

function sortBy(products: Product[], key: ProductKey): Product[] {
  return products.toSorted((a, b) => (a[key] < b[key] ? -1 : a[key] > b[key] ? 1 : 0));
}

const items: Product[] = [{ id: 2, name: "Pen", price: 2 }, { id: 1, name: "Lamp", price: 25 }];
console.log(sortBy(items, "name").map((p) => p.name));
```

`ProductKey` is `"id" | "name" | "price"`, and stays correct when `Product` changes. `keyof typeof obj` gives the keys of a value.

### Indexed access types: T[K]

`T["name"]` is the type of a property; a union of keys gives a union of their types; `T[number]` gives an array's element type:

```ts
type Order = { id: number; customer: { name: string; email: string }; lines: { sku: string; qty: number }[] };

type Customer = Order["customer"];
type Line = Order["lines"][number];
type IdOrCustomer = Order["id" | "customer"];

const line: Line = { sku: "A-1", qty: 2 };
const who: Customer = { name: "Ada", email: "ada@example.com" };
const key: IdOrCustomer = 42;
console.log(line, who.name, key);
```

(Note that indexed access uses brackets and string literal types: `Order.customer` isn't valid type syntax.)

## Built-in utility types

TypeScript ships a set of generic **utility types**, all built from these operators (you'll build several yourself in the next two lessons):

| Utility | Result |
|---|---|
| `Partial<T>` | every property optional |
| `Required<T>` | every property required |
| `Readonly<T>` | every property readonly |
| `Pick<T, "a" \| "b">` | only those properties |
| `Omit<T, "a">` | all properties except those |
| `Record<K, V>` | an object with keys K and values V |
| `Exclude<U, X>` | members of union U not assignable to X |
| `Extract<U, X>` | members of union U assignable to X |
| `NonNullable<T>` | T without null and undefined |
| `ReturnType<F>` / `Parameters<F>` | a function type's return type / parameter tuple |
| `Awaited<P>` | what a Promise resolves to (recursively) |
| `InstanceType<C>` | the instance type of a class type |

```ts
interface User {
  id: number;
  name: string;
  email: string;
  passwordHash: string;
  createdAt: string;
}

type PublicUser = Omit<User, "passwordHash">;
type NewUser = Pick<User, "name" | "email">;
type UserPatch = Partial<Omit<User, "id" | "createdAt">>;

function toPublic({ passwordHash, ...rest }: User): PublicUser {
  return rest;
}

const user: User = { id: 1, name: "Ada", email: "ada@example.com", passwordHash: "x9!", createdAt: "2026-01-01" };
const patch: UserPatch = { email: "ada@new.example" };
const signup: NewUser = { name: "Grace", email: "grace@example.com" };
console.log(toPublic(user), patch, signup);
```

A single source of truth (`User`) and several derived **views** of it: add a field to `User` and every derived type follows. This is the everyday use of type operators: API request and response types, form types, database rows.


## Utility types for functions

`ReturnType`, `Parameters` and `Awaited` let you reuse the types of functions you don't control, such as a library function whose result type isn't exported:

```ts
async function fetchProfile(id: number, withPosts = false) {
  return { id, name: "Ada", posts: withPosts ? ["Hello"] : [] };
}

type Profile = Awaited<ReturnType<typeof fetchProfile>>;
type FetchArgs = Parameters<typeof fetchProfile>;

const args: FetchArgs = [7, true];
const profile: Profile = await fetchProfile(...args);
console.log(profile);
```

`Profile` is `{ id: number; name: string; posts: string[] }`, worked out from the function itself.

## Unions of keys, Exclude and Extract

```ts
type Event =
  | { type: "click"; x: number; y: number }
  | { type: "key"; key: string }
  | { type: "scroll"; delta: number };

type EventType = Event["type"];
type PointerEvent = Extract<Event, { type: "click" }>;
type NotScroll = Exclude<EventType, "scroll">;

const e: PointerEvent = { type: "click", x: 1, y: 2 };
const t: NotScroll = "key";
console.log(e, t);
```

`Event["type"]` collects the tags of a discriminated union (`"click" | "key" | "scroll"`), and `Extract<Event, { type: "click" }>` picks one member by its tag. These two are used constantly in reducers and event systems.

=== lesson ts-mapped-types | Mapped types | 90
## Transforming every property

A **mapped type** builds a new object type by looping over keys:

```ts
type Flags<T> = { [K in keyof T]: boolean };

interface Features {
  darkMode: string;
  beta: number;
  analytics: object;
}

const enabled: Flags<Features> = { darkMode: true, beta: false, analytics: true };
console.log(enabled);
```

`[K in keyof T]` is like a `for...of` over the keys of `T`: for each key `K`, the new type has a property `K` of the type after the colon. Typically that type uses `T[K]`, the original property's type:

```ts
type Nullable<T> = { [K in keyof T]: T[K] | null };
type Getters<T> = { [K in keyof T]: () => T[K] };

interface Point { x: number; y: number }

const blank: Nullable<Point> = { x: null, y: 4 };
const lazy: Getters<Point> = { x: () => 1, y: () => 2 };
console.log(blank, lazy.x() + lazy.y());
```

## Modifiers: readonly and ?

Mapped types can add or remove the `readonly` and `?` modifiers with `+` and `-` (`+` is the default). This is exactly how the built-in utilities are written:

```ts
type MyPartial<T> = { [K in keyof T]?: T[K] };
type MyRequired<T> = { [K in keyof T]-?: T[K] };
type MyReadonly<T> = { readonly [K in keyof T]: T[K] };
type Mutable<T> = { -readonly [K in keyof T]: T[K] };

interface Config { readonly host: string; port?: number }

const full: MyRequired<Config> = { host: "localhost", port: 80 };
const editable: Mutable<Config> = { host: "a" };
editable.host = "b";
console.log(full, editable);
```

Mapped types over `keyof T` like these are **homomorphic**: they keep the original modifiers (a property that was optional stays optional, unless you use `-?`).

## Mapping over any union of keys

The keys don't have to come from `keyof`. Any union of string literals works, which is how `Record` is defined:

```ts
type MyRecord<K extends PropertyKey, V> = { [P in K]: V };

type Permission = "read" | "write" | "admin";
const defaults: MyRecord<Permission, boolean> = { read: true, write: false, admin: false };
console.log(defaults);
```

(`PropertyKey` is the built-in `string | number | symbol`: everything that can be an object key.)

## Key remapping with as

Since TypeScript 4.1, `as` in a mapped type renames keys, or **filters them out** by mapping them to `never`:

```ts
type Setters<T> = { [K in keyof T as `set${Capitalize<string & K>}`]: (value: T[K]) => void };
type OnlyStrings<T> = { [K in keyof T as T[K] extends string ? K : never]: T[K] };

interface Person { name: string; age: number; city: string }

const setters: Setters<Person> = {
  setName: (v) => console.log("name ->", v),
  setAge: (v) => console.log("age ->", v.toFixed(0)),
  setCity: (v) => console.log("city ->", v),
};
setters.setAge(37);

const text: OnlyStrings<Person> = { name: "Ada", city: "London" };
console.log(text);
```

`` `set${Capitalize<string & K>}` `` is a **template literal type** (two lessons on), turning `"name"` into `"setName"`. `T[K] extends string ? K : never` is a **conditional type** (next lesson): keys whose values aren't strings become `never` and disappear.


## Recursive mapped types

A mapped type can refer to itself, to transform nested objects:

```ts
type DeepReadonly<T> = { readonly [K in keyof T]: T[K] extends object ? DeepReadonly<T[K]> : T[K] };

interface Settings {
  theme: { colours: { primary: string }; font: string };
  volume: number;
}

const settings: DeepReadonly<Settings> = { theme: { colours: { primary: "#000" }, font: "serif" }, volume: 5 };
console.log(settings.theme.colours.primary);
```

`settings.theme.colours.primary = "#fff"` is now a compile error at every level; built-in `Readonly<T>` only protects the top level. (Functions are objects too, so a fully general version handles them separately; libraries such as `type-fest` contain carefully tested versions of such helpers.)

## If-then-else for types

A **conditional type** chooses between two types based on a test:

```ts
type IsString<T> = T extends string ? "yes" : "no";

type A = IsString<"hello">;
type B = IsString<42>;

const a: A = "yes";
const b: B = "no";
console.log(a, b);
```

`T extends U ? X : Y` reads "if `T` is assignable to `U`, then `X`, otherwise `Y`". The `extends` here is the same assignability (subset) test as in generic constraints.

A practical example: a function whose return type depends on its input type, without overloads:

```ts
type Parsed<T extends string | number> = T extends string ? number : string;

function convert<T extends string | number>(value: T): Parsed<T> {
  return (typeof value === "string" ? Number(value) : String(value)) as Parsed<T>;
}

const n = convert("42");
const s = convert(7);
console.log(n + 1, s.padStart(3, "0"));
```

(TypeScript can't check that the implementation's `typeof` test matches the conditional type, hence the `as`. Conditional return types are a power tool: overloads are often clearer for two or three cases.)

## Distribution over unions

When a conditional type is applied to a **union**, it's applied to each member separately, and the results are joined. This is called **distribution**, and it's what makes conditional types able to filter unions:

```ts
type MyExclude<T, U> = T extends U ? never : T;
type MyExtract<T, U> = T extends U ? T : never;

type Status = "draft" | "published" | "archived";
type Live = MyExclude<Status, "archived">;
type Draftish = MyExtract<Status, "draft" | "deleted">;

const live: Live = "published";
const d: Draftish = "draft";
console.log(live, d);
```

`MyExclude<"draft" | "published" | "archived", "archived">` becomes `("draft" extends "archived" ? never : "draft") | ...`, which is `"draft" | "published" | never`, and `never` disappears from unions (lesson 1 of this module). These are exactly the built-in `Exclude` and `Extract`. `NonNullable<T>` is `T & {}` today, but was once `T extends null | undefined ? never : T`.

Distribution only happens when the checked type is a **naked type parameter** (`T extends ...`). To test the union as a whole, wrap both sides in brackets: `[T] extends [string] ? ...`.

~~~check
- `never`
~~~

## infer: extracting types

Inside the `extends` clause, **`infer X`** declares a type variable that TypeScript fills in by pattern matching:

```ts
type ElementOf<T> = T extends readonly (infer E)[] ? E : never;
type Unpromise<T> = T extends Promise<infer V> ? V : T;
type MyReturnType<F> = F extends (...args: any[]) => infer R ? R : never;
type FirstArg<F> = F extends (first: infer A, ...rest: any[]) => any ? A : never;

type E = ElementOf<string[]>;
type V = Unpromise<Promise<number>>;
type R = MyReturnType<() => boolean>;
type P = FirstArg<(id: number, name: string) => void>;

const values: [E, V, R, P] = ["a", 1, true, 2];
console.log(values);
```

"If `T` looks like an array of *something*, call that something `E` and give me `E`." That's how `ReturnType`, `Parameters`, `Awaited` and `InstanceType` are implemented.

## Recursive conditional types

Conditional types can call themselves, which allows types that process nested structures:

```ts
type Flatten<T> = T extends readonly (infer E)[] ? Flatten<E> : T;
type DeepAwaited<T> = T extends Promise<infer V> ? DeepAwaited<V> : T;

type F = Flatten<number[][][]>;
type W = DeepAwaited<Promise<Promise<string>>>;

const f: F = 3;
const w: W = "done";
console.log(f, w);
```

`DeepAwaited` is essentially the built-in `Awaited`. TypeScript limits recursion depth (to about a thousand levels with tail-recursive conditional types), which is plenty for real code.

## Where conditional types are used

You'll write conditional types rarely in application code and read them often in library types: React's prop helpers, ORMs that compute query result types, validation libraries such as Zod (`z.infer<typeof schema>`), and router libraries that type URL parameters. Knowing how to read `T extends X ? Y : Z` and `infer` lets you understand those error messages, and occasionally write a small helper that removes a lot of duplication.

## String types built from strings

**Template literal types** use the backtick syntax of JavaScript template strings, at the type level:

```ts
type Size = "sm" | "md" | "lg";
type Colour = "red" | "blue";
type ButtonClass = `btn-${Colour}-${Size}`;

const cls: ButtonClass = "btn-blue-lg";
console.log(cls);
```

With unions inside, TypeScript generates every combination: `ButtonClass` is a union of six strings (`"btn-red-sm" | "btn-red-md" | ...`). A typo like `"btn-blu-lg"` is a compile error.

Placeholders can also be general types: `` `${number}px` `` matches `"12px"` and `"1.5px"`, and `` `#${string}` `` any string starting with `#`.

```ts
type Pixels = `${number}px`;
type CssVar = `--${string}`;

function setStyle(name: CssVar, value: Pixels): string {
  return `${name}: ${value};`;
}
console.log(setStyle("--gap", "12px"));
```

## Intrinsic string types

Four built-in types transform string literal types: `Uppercase<S>`, `Lowercase<S>`, `Capitalize<S>` and `Uncapitalize<S>`.

```ts
type Method = "get" | "post";
type Upper = Uppercase<Method>;
type HandlerName = `handle${Capitalize<Method>}`;

const m: Upper = "POST";
const h: HandlerName = "handleGet";
console.log(m, h);
```

## Combining with mapped types

Template literal types are most useful together with key remapping (the mapped types lesson). The classic example: deriving event handler names from an object's properties.

```ts
type ChangeHandlers<T> = {
  [K in keyof T & string as `on${Capitalize<K>}Changed`]: (value: T[K]) => void;
};

interface FormValues { email: string; age: number; subscribed: boolean }

const handlers: ChangeHandlers<FormValues> = {
  onEmailChanged: (v) => console.log("email", v.toLowerCase()),
  onAgeChanged: (v) => console.log("age", v + 1),
  onSubscribedChanged: (v) => console.log("subscribed", !v),
};
handlers.onAgeChanged(36);
```

(`keyof T & string` keeps only string keys: `Capitalize` can't work on number or symbol keys.)

## Parsing strings with infer

`infer` works inside template literal types, which lets types **parse** strings. Web frameworks use this to type URL parameters from a route pattern:

```ts
type RouteParams<Path extends string> =
  Path extends `${string}:${infer Param}/${infer Rest}`
    ? Param | RouteParams<`/${Rest}`>
    : Path extends `${string}:${infer Param}`
      ? Param
      : never;

type Params = RouteParams<"/users/:userId/posts/:postId">;

function link<P extends string>(pattern: P, params: Record<RouteParams<P>, string>): string {
  return pattern.replace(/:(\w+)/g, (_, name: string) => (params as Record<string, string>)[name]);
}

const p: Params = "postId";
console.log(p, link("/users/:userId/posts/:postId", { userId: "7", postId: "42" }));
```

`RouteParams` matches "anything, a colon, a parameter name, a slash, the rest", collects the name, and recurses on the rest. Forget `postId` in the call to `link` and the compiler tells you. That's how libraries such as Express's types, React Router and Hono type route parameters.

## Limits

Template literal types are checked at compile time against **literal** strings. A plain `string` variable (from user input, for example) isn't assignable to `` `${number}px` ``, because TypeScript can't know its contents: you validate it at run time first (with a type guard, Module 2). And very large combinations (unions of thousands of strings) slow the compiler down; TypeScript refuses unions above 100,000 members.

## Enums

An **enum** gives names to a set of constants. It's one of the few TypeScript features that exist at run time:

```ts
enum Direction {
  Up,
  Down,
  Left,
  Right,
}

enum LogLevel {
  Debug = "debug",
  Info = "info",
  Error = "error",
}

function move(d: Direction): string {
  return `moving ${Direction[d]} (${d})`;
}

console.log(move(Direction.Left), LogLevel.Error, Object.keys(LogLevel));
```

- A **numeric enum** numbers its members from 0 (`Up = 0`, `Down = 1`...), and also creates a reverse mapping (`Direction[2]` is `"Left"`).
- A **string enum** gives each member a string value, which reads better in logs and JSON.

Enums are compiled into real objects, so they're **not erasable syntax** (Node's type stripping and `erasableSyntaxOnly` reject them). They also have quirks: numeric enums accept any number in some situations, and enums are nominal (a string can't be passed where a string enum is expected, even with the right value).

For these reasons many teams prefer a **union of string literals**, possibly with an `as const` object for named access:

```ts
const LogLevel = {
  Debug: "debug",
  Info: "info",
  Error: "error",
} as const;
type LogLevel = (typeof LogLevel)[keyof typeof LogLevel];

function log(level: LogLevel, message: string): string {
  return `[${level}] ${message}`;
}

console.log(log(LogLevel.Info, "started"), log("error", "failed"));
```

This gives the same `LogLevel.Info` syntax, accepts plain strings, and is erasable. (Declaring a value and a type with the same name is legal: they live in separate namespaces. This **companion object pattern** is also used to pair a type with its helper functions: `type Money = {...}` and `const Money = { add, format }`, imported together by one name.) You'll still meet enums in many codebases and frameworks, so know both.

## Type assertions: as

`value as Type` tells the compiler "trust me, this is a `Type`". It changes nothing at run time:

```ts
interface Config {
  port: number;
  host: string;
}

const saved: unknown = JSON.parse('{"port": 8080, "host": "localhost"}');
const config = saved as Config;
console.log(config.port + 1, config.host.toUpperCase());

const broken = JSON.parse('{"port": "eighty"}') as Config;
console.log(broken.port + 1);
```

The first assertion happens to be right. The second compiles just as happily and prints `eighty1`: the assertion **didn't check anything**, and the wrong data travels on until something misbehaves far from the cause (here `broken.host.toUpperCase()` would crash). Another everyday example is `document.querySelector("#email") as HTMLInputElement`, which also silently removes the possibility of `null`. TypeScript only allows assertions between types that overlap; `"hello" as number` is an error (you can force it with `as unknown as number`, which is a strong code smell).

Safer alternatives, in order of preference:

1. **Narrow** with a check (`if (el === null) throw ...`, `instanceof`, a type guard), or validate outside data (Module 6).
2. **`satisfies`** when you want to check, not override.
3. **`as`** in small, well-understood places (tests, a validated value, the inside of a typed helper).

## The non-null assertion: !

`value!` is a shorthand assertion that removes `null` and `undefined`:

```ts
const scores = new Map([["ada", 90]]);
if (scores.has("ada")) {
  console.log(scores.get("ada")! + 5);
}
```

`has` doesn't narrow `get`, so `!` is common here. But `const s = scores.get("ada"); if (s !== undefined) ...` is just as short and checked. Each `!` is a place where a "Cannot read properties of undefined" can come back.

## Definite assignment assertions

A third kind of assertion tells TypeScript that a variable or field **will** be assigned before use, even though it can't see where: `let x!: number;` or, in a class, `name!: string;`. It's used with frameworks that fill fields in for you (Angular's `@ViewChild`, ORMs that create entities), and in tests that set things up in a `beforeEach`:

```ts
class Report {
  title!: string;

  init(title: string): this {
    this.title = title;
    return this;
  }
}

console.log(new Report().init("Q3 sales").title);
```

Without `!`, strict mode reports *Property 'title' has no initializer*. As with every assertion, if you're wrong, `title` is `undefined` at run time while its type says `string`; prefer a constructor parameter when you can.

## any: the ultimate escape hatch

`any` turns checking off for a value, and spreads: anything derived from an `any` is also `any`. Legitimate uses are rare: migrating JavaScript code gradually, and a few generic type tricks (the mixin constructor in Module 4). When you need "any value", you almost always mean `unknown`.

Two compiler options and one lint rule keep `any` under control: `noImplicitAny` (part of `strict`) forbids accidental `any`; `typescript-eslint`'s `no-explicit-any` and `no-unsafe-*` rules flag explicit `any` and its spread.

## Comments that switch checks off

- `// @ts-expect-error` suppresses the error on the next line, and errors if there isn't one (Module 1). Use it in tests of types, and with an explanation for known compiler limitations.
- `// @ts-ignore` suppresses silently, forever. Avoid it.
- `// @ts-nocheck` at the top of a file disables checking for the whole file (sometimes used during migration).


## Declaration merging and module augmentation

Interfaces with the same name merge (Module 2). This lets you **add** properties to existing types, such as the browser's `Window` or a library's interfaces. In a web app:

```
declare global {
  interface Window {
    appVersion: string;
  }
}

window.appVersion = "1.4.0";
```

The same works for global variables (here runnable, because it doesn't need a browser window):

```ts
declare global {
  var appVersion: string;
}

globalThis.appVersion = "1.4.0";
console.log(appVersion);
```

The same mechanism can add methods to built-in types (`interface Array<T> { last(): T | undefined }` plus an assignment to `Array.prototype.last`), but changing built-in prototypes is discouraged: it affects every library in the program and can clash with future JavaScript features. Prefer a plain function such as `last(array)`.

`declare global` adds to the global scope from inside a module; `declare module "some-library" { interface Options { ... } }` does the same for a library's types (Module 6 covers declaration files). Use this sparingly: it changes a type for the whole project.

type ActionMap = {
  add: { id: string; text: string };
  toggle: { id: string };
  remove: { id: string };
  clearDone: undefined;
};

type Action = {
  [K in keyof ActionMap]: ActionMap[K] extends undefined ? { type: K } : { type: K; payload: ActionMap[K] };
}[keyof ActionMap];

type Todo = { id: string; text: string; done: boolean };

function reducer(state: readonly Todo[], action: Action): Todo[] {
  switch (action.type) {
    case "add":
      return [...state, { ...action.payload, done: false }];
    case "toggle":
      return state.map((t) => (t.id === action.payload.id ? { ...t, done: !t.done } : t));
    case "remove":
      return state.filter((t) => t.id !== action.payload.id);
    case "clearDone":
      return state.filter((t) => !t.done);
    default:
      action satisfies never;
      return [...state];
  }
}

function act<T extends keyof ActionMap>(type: T, ...payload: ActionMap[T] extends undefined ? [] : [ActionMap[T]]): Action {
  return (payload.length ? { type, payload: payload[0] } : { type }) as Action;
}

type Paths<T> = {
  [K in keyof T & string]: T[K] extends readonly unknown[] ? K : T[K] extends object ? `${K}.${Paths<T[K]>}` : K;
}[keyof T & string];

type PathValue<T, P extends string> = P extends `${infer Head}.${infer Rest}`
  ? Head extends keyof T
    ? PathValue<T[Head], Rest>
    : never
  : P extends keyof T
    ? T[P]
    : never;

function get<T, P extends Paths<T>>(obj: T, path: P): PathValue<T, P> {
  let current: unknown = obj;
  for (const key of path.split(".")) {
    current = (current as Record<string, unknown>)[key];
  }
  return current as PathValue<T, P>;
}
