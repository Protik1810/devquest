=== lesson ts-why | What TypeScript is (and isn't) | 60
## The bugs JavaScript lets through

You know JavaScript. You also know the bugs it allows without a word: a string where a number was expected (`"5" + 3` is `"53"`), a misspelt property that quietly gives `undefined`, a function called with the wrong arguments, a value that is sometimes `null`. JavaScript finds these only when that line runs, often in front of a user, and sometimes never finds them at all.

**TypeScript** is JavaScript with a **static type system**. You describe what kind of value each variable, parameter and return value holds; the TypeScript **compiler** checks your whole program against those descriptions **before it runs**, and reports every place where the code could do something impossible.

```ts
function totalPrice(price: number, quantity: number): number {
  return price * quantity;
}

console.log(totalPrice(9.99, 3));
```

That runs. Now press **✎ Edit**, change the call to `totalPrice("9.99", 3)` and press **▶ Run** again: instead of a mysterious `NaN` at run time, you get a precise message about line 5 before anything runs. In an editor such as VS Code, the same message appears as a red underline while you type. That instant feedback is the main reason professionals use TypeScript.

DevQuest checks every piece of TypeScript in this course with the real TypeScript compiler, in **strict** mode (the setting every new project should use). Code with type errors doesn't run, just like a project built with `tsc`.

## Compile time and run time

There are two separate moments in a TypeScript program's life:

1. **Compile time**: the compiler reads your code, checks the types, and produces plain JavaScript with all the type annotations **erased**.
2. **Run time**: that JavaScript runs in a browser or in Node.js, exactly like any other JavaScript. The types are gone.

```ts
type User = { name: string; admin: boolean };

const ada: User = { name: "Ada", admin: true };
console.log(ada, typeof ada);
```

At run time, `ada` is an ordinary object; nothing remembers that it was a `User`. This has two important consequences:

- **Types cost nothing at run time**: no slowdown, no extra code.
- **Types don't check anything at run time.** If data comes from outside your program (JSON from a server, a form, a file), TypeScript can't know what's really in it. You'll learn to validate such data in Module 6.

## Structural typing

TypeScript compares types by their **shape**, not by their name. Any value that has the right properties fits, wherever it came from:

```ts
type Point = { x: number; y: number };

function describe(p: Point): string {
  return `(${p.x}, ${p.y})`;
}

const somewhere = { x: 3, y: 4, label: "home" };
console.log(describe(somewhere));
```

`somewhere` was never declared as a `Point`, but it has `x` and `y` numbers, so it's accepted. This is the "duck typing" of JavaScript (Module 9 of the JavaScript course), now checked by the compiler. It's called **structural typing**, in contrast to the **nominal typing** of Java and C#, where a class must explicitly declare which types it is.

~~~check

+ They've been removed; only plain JavaScript runs
- They make the program slower
- They're turned into runtime validation

~~~

## Gradual typing: you can start anywhere

Every JavaScript program is (almost) valid TypeScript: TypeScript adds to JavaScript, it doesn't change how JavaScript works. Teams migrate existing projects file by file, and inside a file you only *need* to write types where the compiler can't work them out by itself (which turns out to be surprisingly rare: mostly function parameters).

## What TypeScript is not

- **Not a different language at run time.** It's JavaScript; everything from the JavaScript course still applies.
- **Not a guarantee of no bugs.** Wrong logic with correct types is still wrong. Tests (Module 7 of the JavaScript course) are still essential; types and tests catch different mistakes.
- **Not perfectly "sound".** A few escape hatches (`any`, type assertions) let you tell the compiler to trust you. This course shows when they're justified and how to avoid them.

## Who uses it, and which version

TypeScript was created at Microsoft in 2012 and is now the default for professional JavaScript: Angular is written in it, React, Vue and Node projects are increasingly TypeScript-first, and job adverts for front-end and full-stack roles mostly expect it. TypeScript 7 (2026) rewrote the compiler in Go, making it about ten times faster; TypeScript 6 was the last version written in JavaScript, and it's the one DevQuest runs inside the app. For everything in this course, they behave the same.

=== lesson ts-setup | Setting up a TypeScript project | 60
## Installing the compiler

TypeScript is an npm package, installed per project as a development dependency:

```
npm install --save-dev typescript
npx tsc --version
```

`tsc` is the TypeScript compiler. Start a configuration file with:

```
npx tsc --init
```

## tsconfig.json

`tsconfig.json` tells `tsc` which files make up the project and how strict to be. A good modern starting point:

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "NodeNext",
    "strict": true,
    "noUncheckedIndexedAccess": true,
    "outDir": "dist",
    "rootDir": "src",
    "sourceMap": true,
    "skipLibCheck": true
  },
  "include": ["src"]
}
```

| Option | Meaning |
|---|---|
| `target` | which JavaScript version to output (`ES2022` keeps modern syntax such as classes and `async` as they are) |
| `module` | which module system to output and how imports resolve (`NodeNext` for Node.js, `ESNext` with `"moduleResolution": "Bundler"` for Vite and other bundlers) |
| `strict` | turns on the whole family of strict checks; **always** on in new projects |
| `noUncheckedIndexedAccess` | `array[i]` and `record[key]` may be `undefined` (not part of `strict`, but worth it) |
| `outDir` / `rootDir` | where compiled `.js` files go, and where the source lives |
| `sourceMap` | maps compiled code back to your `.ts` lines for debugging |
| `skipLibCheck` | don't type-check library declaration files (faster builds) |

Module 6 goes through the configuration in depth.

## Compiling and running

```
npx tsc            # check and compile src/*.ts into dist/*.js
node dist/main.js  # run the output
npx tsc --watch    # recompile whenever a file changes
npx tsc --noEmit   # only check types, produce no files (common in CI)
```

You don't always need a separate build step any more:

- **Node.js 22.18 and later run `.ts` files directly** (`node src/main.ts`) by stripping the types, for code that only uses "erasable" TypeScript syntax (no `enum` or constructor parameter properties; the compiler flag `erasableSyntaxOnly` enforces that). Node doesn't type-check: you still run `tsc --noEmit` to find type errors.
- **Vite**, **tsx** (`npx tsx src/main.ts`) and test runners like **Vitest** also strip types on the fly.

That's the most common setup today: a fast tool strips types to run the code, while `tsc --noEmit` (in the editor, a pre-commit hook and CI) does the checking.

## The editor is the real tool

The compiler's biggest gift isn't the build: it's the editor integration. VS Code ships with TypeScript built in: hover over any name to see its type, get autocompletion that knows every property, rename a symbol across the whole project safely, and see errors as you type. A popular convention in documentation (used in this course's examples) shows a hover result with a comment:

```ts
const score = 42;
//    ^? const score: 42
let name = "Ada";
//  ^? let name: string
console.log(score, name);
```

(`const score` has the type `42`, because a `const` can never be anything else, while `let name` is a `string`, because it could change. The next lesson explains why.)

## Type checking in DevQuest

DevQuest runs the TypeScript 6 compiler with these settings: `strict`, target ES2022, ES modules with top-level `await`, the DOM types, and the globals the course uses (`assert`, `test`). Every example and exercise is checked, and code with type errors doesn't run.

=== lesson ts-basics | Types: the basics | 75
## Annotations

A **type annotation** is a colon and a type after a name:

```ts
let title: string = "DevQuest";
let level: number = 3;
let active: boolean = true;
let big: bigint = 9007199254740993n;

function greet(name: string): string {
  return `Hello, ${name}!`;
}

console.log(greet(title), level, active, big);
```

The primitive types are the JavaScript ones, in lowercase: `string`, `number`, `boolean`, `bigint`, `symbol`, `null` and `undefined`. (Avoid the capitalised `String`, `Number` and `Boolean`: those are the wrapper object types, almost never what you want.)

## Inference: let TypeScript work it out

You rarely need to annotate variables. TypeScript **infers** a type from the value:

```ts
let count = 10;
const greeting = "hi";
const items = ["pen", "book"];
const user = { name: "Ada", age: 36 };
count = count + 1;
console.log(count, greeting, items, user);
```

`count` is a `number`, `items` a `string[]`, `user` a `{ name: string; age: number }`. If you later write `count = "eleven"`, that's an error, exactly as if you had written `: number` yourself.

Where should you write annotations?

- **Function parameters**: always (the compiler can't guess what callers will pass).
- **Return types**: on exported and important functions, as documentation and a guard against accidentally returning the wrong thing.
- **Variables**: only when the inferred type isn't what you mean (for example a `let` that starts as `null` but will hold a `User` later).

## Literal types and widening

A `const` can never change, so TypeScript gives it the most precise type possible: the **literal type** of its value. A `let` can change, so its type is **widened** to the general type:

```ts
const direction = "north";
let heading = "north";
heading = "south";
console.log(direction, heading);
```

`direction` has the type `"north"` (only that exact string); `heading` has the type `string`. Literal types are the basis of some of TypeScript's most useful patterns, such as `"north" | "south" | "east" | "west"` (Module 2).

~~~check

- `any`

~~~

## any, unknown, void and never

Four special types complete the basics:

| Type | Means | Use it... |
|---|---|---|
| `any` | "don't check this at all" | almost never: it switches the type system off for that value, and the "any-ness" spreads |
| `unknown` | "could be anything; check before using" | for values from outside (JSON, errors, user input) |
| `void` | "returns nothing useful" | as the return type of functions that only do something |
| `never` | "this can't happen" | for functions that never return (always throw), and impossible branches |

The difference between `any` and `unknown` is crucial. Both accept any value, but `unknown` makes you **prove** what it is before using it:

```ts
const data: unknown = JSON.parse('{"name": "Ada"}');

if (typeof data === "object" && data !== null && "name" in data && typeof data.name === "string") {
  console.log(data.name.toUpperCase());
}
```

Inside the `if`, TypeScript has **narrowed** `data` step by step to "an object with a `name` that's a string", so `.toUpperCase()` is allowed. With `any`, `data.name.toUpperCase()` would compile even if `name` were missing, and crash at run time. Narrowing gets a whole lesson in Module 2.

```ts
function log(message: string): void {
  console.log(`[log] ${message}`);
}
function fail(message: string): never {
  throw new Error(message);
}
log("starting");
try {
  fail("stopped");
} catch (error) {
  console.log(error instanceof Error ? error.message : error);
}
```

Notice `catch (error)`: in strict mode, a caught error has the type `unknown` (anything can be thrown in JavaScript), so you check `instanceof Error` before reading `.message`.

## Arrays and objects, briefly

```ts
const scores: number[] = [90, 85];
const names: Array<string> = ["Ada", "Grace"];
const point: { x: number; y: number } = { x: 1, y: 2 };
scores.push(77);
console.log(scores, names, point);
```

`number[]` and `Array<number>` mean the same thing. Object types list properties with `;` (or `,`) between them. Module 2 covers both in depth.

## Type aliases

`type` gives a type a name, so you can reuse it:

```ts
type Money = number;
type Product = { name: string; price: Money };

function cheapest(products: Product[]): Product | undefined {
  return products.toSorted((a, b) => a.price - b.price)[0];
}
console.log(cheapest([{ name: "Pen", price: 2 }, { name: "Lamp", price: 25 }]));
```

The return type `Product | undefined` says "a product, or undefined" (for an empty list): a **union** type, Module 2's main topic.

=== lesson ts-reading-errors | Reading type errors | 60
## Errors are conversations with the compiler

Type errors are the compiler telling you, precisely, where your code doesn't match what you said it would do. Reading them quickly is a core professional skill, because most TypeScript work is a loop of "write, read the error, adjust".

Every error has three parts. In DevQuest:

```
Type error on line 2: Type 'string' is not assignable to type 'number'. (TS2322)
```

and in a terminal, from `tsc`:

```
src/cart.ts:2:1 - error TS2322: Type 'string' is not assignable to type 'number'.

2 total = "ten";
  ~~~~~
```

- the **location** (file, line and column);
- the **message**, which usually says what was given and what was expected;
- the **code** (`TS2322`), handy for searching.

## The errors you'll meet every day

```ts
let total: number = 0;
total = "ten";
```

**TS2322 "Type X is not assignable to type Y"**: a value of the wrong type went into a variable, property or return value. Read it as "you gave X where Y was promised".

```ts
function area(width: number, height: number): number {
  return width * height;
}
area(3);
area(3, "4");
```

**TS2554 "Expected 2 arguments, but got 1"** and **TS2345 "Argument of type X is not assignable to parameter of type Y"**: a function was called wrongly. The fix is usually at the call site.

```ts
const user = { name: "Ada", email: "ada@example.com" };
console.log(user.emial);
```

**TS2339 "Property 'emial' does not exist on type ..."**: a typo, or a property the type doesn't promise. When the name is close to a real one, the message adds "Did you mean 'email'?" (and the code becomes TS2551).

```ts
const prices = new Map<string, number>();
const price = prices.get("tea");
console.log(price.toFixed(2));
```

**TS18048 "'price' is possibly 'undefined'"** (TS2532 for "Object is possibly 'undefined'"): the value might not be there. This is TypeScript catching the JavaScript classic "Cannot read properties of undefined" **before** it happens. Handle the missing case: `price?.toFixed(2) ?? "not for sale"`, or check with `if (price === undefined)`.

Others you'll see often:

| Code | Message | Usual cause |
|---|---|---|
| TS7006 | Parameter 'x' implicitly has an 'any' type | a parameter without a type, in strict mode |
| TS2741 | Property 'y' is missing in type ... | an object without a required property |
| TS2353 | Object literal may only specify known properties | an extra (often misspelt) property in an object literal |
| TS2304 / TS2552 | Cannot find name 'x' | a typo, or something not imported |
| TS2367 | This comparison appears to be unintentional | comparing values that can never be equal (`"a" === 1`) |

## Long messages: read the last line first

When the mismatch is deep inside an object, TypeScript points straight at the innermost property:

```ts
type Address = { city: string; zip: string };
type Customer = { name: string; address: Address };

const c: Customer = { name: "Ada", address: { city: "London", zip: 12345 } };
console.log(c);
```

The error is on `zip`: it's a number but should be a string. When the value comes from a variable instead of being written in place, the compiler can't point inside it, so it explains the mismatch as a chain, from the outside in:

```
Type '{ name: string; address: { city: string; zip: number; }; }' is not assignable to type 'Customer'.
  The types of 'address.zip' are incompatible between these types.
    Type 'number' is not assignable to type 'string'.
```

The first line says where the mismatch starts; the **last** line says what's actually wrong. Read long errors from the bottom up.

~~~check

+ Where the function is called, by passing a number
- Inside the function, by changing its body
- In tsconfig.json
- By adding `any` to the parameter
> The function says it needs a number; the caller passed a string.
~~~

## Fix the cause, don't silence the messenger

It's tempting to make an error disappear with `any`, a type assertion (`as number`), or a `// @ts-ignore` comment. Each of these tells the compiler "trust me", and switches off the checking that just found a real problem. Fix the cause instead:

- **Wrong value?** Convert it properly (`Number(text)`, `String(n)`).
- **Missing case?** Handle `null` and `undefined` (`?.`, `??`, an `if`).
- **Wrong type description?** Fix the type, if the code was right and the type was wrong.

When you genuinely need to suppress an error (for example in a test that checks that misuse is rejected), use `// @ts-expect-error` on the line above: unlike `@ts-ignore`, it **reports an error itself if the line below stops being an error**, so it can't silently hide anything. DevQuest's hidden checks use it to make sure your types reject wrong code.

function parseScore(input: unknown): number | null {
  let n: number;
  if (typeof input === "number") n = input;
  else if (typeof input === "string" && input.trim() !== "") n = Number(input.trim());
  else return null;
  if (!Number.isInteger(n) || n < 0 || n > 100) return null;
  return n;
}

function averageScore(inputs: unknown[]): string {
  const scores = inputs.map(parseScore).filter((s): s is number => s !== null);
  if (scores.length === 0) return "no valid scores";
  const avg = scores.reduce((a, b) => a + b, 0) / scores.length;
  return `${avg.toFixed(1)} (from ${scores.length} score${scores.length === 1 ? "" : "s"})`;
}
