## Array types

An array type is the element type followed by `[]`, or the generic form `Array<T>`:

```ts
const temperatures: number[] = [18.5, 21, 19.75];
const tags: Array<string> = ["new", "sale"];
const matrix: number[][] = [[1, 2], [3, 4]];

temperatures.push(22);
console.log(temperatures.map((t) => t.toFixed(1)), tags.length, matrix[1][0]);
```

Arrays of mixed things need a union in brackets: `(string | number)[]` is "an array whose elements are each a string or a number". Without the brackets, `string | number[]` means "a string, or an array of numbers": a different thing entirely.

Inference handles most arrays. An empty array is the exception: write the element type, or TypeScript can't know what will go in it:

```ts
const names: string[] = [];
names.push("Ada");
console.log(names);
```

## Reading an index may give undefined

What's the type of `names[5]`? By default TypeScript says `string`, even though the array may be shorter. That's a deliberate trade-off for convenience, and a real source of bugs. The compiler option `noUncheckedIndexedAccess` makes every index read `T | undefined`, which forces you to handle the missing case. Many teams turn it on; either way, prefer methods that make the "maybe missing" explicit:

```ts
const queue = ["first", "second"];
const next = queue.at(0);
const last = queue.find((item) => item.startsWith("s"));
console.log(next?.toUpperCase(), last ?? "none");
```

`at()` and `find()` return `string | undefined`, so the compiler makes you deal with "not there".

## Tuples: fixed-length arrays with a type per position

A **tuple** is an array whose length and position types are fixed. They're useful for small groups of values where the order is the meaning, such as coordinates or a function returning two things:

```ts
type Point = [number, number];
type Entry = [name: string, score: number, passed?: boolean];

const origin: Point = [0, 0];
const result: Entry = ["Ada", 92];

function minMax(values: number[]): [min: number, max: number] {
  return [Math.min(...values), Math.max(...values)];
}

const [low, high] = minMax([4, 9, 1]);
console.log(origin, result, low, high);
```

The labels (`name:`, `score:`) are only documentation, shown by the editor. `passed?` is an optional element. You already know a famous tuple from React: `const [count, setCount] = useState(0)`.

There are also **rest elements** in tuples: `[string, ...number[]]` is "a string, followed by any number of numbers", like a CSV row with a label.

A tuple keeps its fixed types only when TypeScript knows it's a tuple. An array literal on its own is inferred as an array, so annotate tuples (or use `as const`, below).

## readonly arrays

Functions that receive an array often shouldn't change it. `readonly string[]` (or `ReadonlyArray<string>`) removes every mutating method from the type:

```ts
function total(prices: readonly number[]): number {
  return prices.reduce((sum, p) => sum + p, 0);
}

const cart = [3.5, 1.25, 10];
console.log(total(cart));
```

Inside `total`, `prices.push(1)` or `prices[0] = 0` would be a compile error, while `map`, `filter` and `reduce` still work (they return new arrays). Any normal array can be passed where a `readonly` one is expected, so this costs callers nothing: it's a promise the function makes. Like all types, `readonly` vanishes at run time; it doesn't freeze anything (that's `Object.freeze`).

## as const

`as const` tells TypeScript to infer the narrowest possible type for a literal: every value becomes a literal type, arrays become readonly tuples, and objects get readonly properties:

```ts
const sizes = ["S", "M", "L"] as const;
type Size = (typeof sizes)[number];

function label(size: Size): string {
  return `Size ${size}`;
}
console.log(sizes, label("M"));
```

`sizes` has the type `readonly ["S", "M", "L"]`, and `(typeof sizes)[number]` (the type of any element) is `"S" | "M" | "L"`. This is a common way to keep a runtime list of values and a type in sync: add `"XL"` to the array and the type follows. (`typeof` in a type position asks for the type of a value; `T[number]` gives an array's element type. Module 5 covers these "type operators" in depth.)

=== lesson ts-objects | Object types and interfaces | 80
## Describing an object's shape

An **object type** lists properties and their types:

```ts
type Book = {
  title: string;
  author: string;
  year: number;
  isbn?: string;
  readonly id: number;
};

const book: Book = { id: 1, title: "Dune", author: "Frank Herbert", year: 1965 };
book.year = 1966;
console.log(book, book.isbn ?? "no ISBN");
```

- `isbn?: string` is an **optional property**: it may be missing (its type, when read, is `string | undefined`).
- `readonly id` can't be reassigned after the object is created (`book.id = 2` is an error).

## interface

An **interface** is another way to name an object type:

```ts
interface Author {
  name: string;
  born: number;
  website?: string;
}

interface Novelist extends Author {
  novels: string[];
}

const herbert: Novelist = { name: "Frank Herbert", born: 1920, novels: ["Dune"] };
console.log(herbert.name, herbert.novels.length);
```

`type` and `interface` overlap almost completely for object shapes. The differences:

| | `interface` | `type` |
|---|---|---|
| object shapes | ✓ | ✓ |
| extend another shape | `extends` | intersection `&` (Module 5) |
| unions, tuples, primitives, computed types | ✗ | ✓ |
| **declaration merging** (two declarations with the same name combine) | ✓ | ✗ (an error) |

A common team convention, and the one the TypeScript team itself recommends: **use `interface` for object shapes** (especially public ones that others may extend), and **`type` for everything else** (unions, tuples, function types, computed types). Many teams just use `type` everywhere. Both are fine; consistency within a project matters more.

## Excess property checks

Structural typing allows extra properties (the previous module's `Point` example). But when you write an **object literal directly** where a type is expected, TypeScript checks for properties the type doesn't know, because they're almost always typos:

```ts
interface Options {
  title: string;
  color?: string;
}

function makeButton(options: Options): string {
  return `[${options.title}${options.color ? ` (${options.color})` : ""}]`;
}

console.log(makeButton({ title: "Save", color: "green" }));
```

Change `color` to `colour` in the call and TypeScript reports *Object literal may only specify known properties*. Without this check, the misspelt optional property would be silently ignored. (If the object is first stored in a variable, the check doesn't apply: it might have extra properties for other reasons.)

## Index signatures and Record

Sometimes an object is used as a dictionary with keys you don't know in advance:

```ts
const stock: { [product: string]: number } = { apples: 12, pears: 0 };
const prices: Record<string, number> = { apples: 0.5 };

stock.plums = 7;
console.log(stock, prices.apples);
```

`{ [key: string]: number }` (an **index signature**) and `Record<string, number>` mean the same thing: any string key, number values. With a union of keys, `Record` gives an object with **exactly** those keys, which is great for lookup tables:

```ts
type Weekday = "mon" | "tue" | "wed" | "thu" | "fri";
const openingHours: Record<Weekday, string> = {
  mon: "9-17", tue: "9-17", wed: "9-13", thu: "9-17", fri: "9-16",
};
console.log(openingHours.wed);
```

Forget `fri` and the compiler tells you. For true dictionaries whose keys come and go at run time, a `Map<string, number>` is usually better than an object (the JavaScript course, Module 6).

## Nested and optional data

Real data is nested. Optional chaining and `??` (from the JavaScript course) are how you read it safely, and TypeScript checks every step:

```ts
interface Profile {
  name: string;
  address?: { city: string; postcode?: string };
}

function postcodeOf(profile: Profile): string {
  return profile.address?.postcode ?? "unknown";
}

console.log(postcodeOf({ name: "Ada" }), postcodeOf({ name: "Grace", address: { city: "NYC", postcode: "10001" } }));
```

Remove the `?.` and the compiler stops you: `profile.address` is possibly `undefined`.

## Optional versus "may be undefined"

`nickname?: string` and `nickname: string | undefined` look similar, but differ: the first may be **left out**, the second must be **present** (possibly as `undefined`). Use `?` for genuinely optional properties; use `| undefined` (or `| null`) when the property must always be given, even if empty, so nobody forgets to think about it.

=== lesson ts-unions | Union and literal types | 80
## Either this or that

A **union type** `A | B` says a value is one of several types:

```ts
function formatId(id: string | number): string {
  return typeof id === "number" ? `#${id.toString().padStart(5, "0")}` : id.toUpperCase();
}

console.log(formatId(42), formatId("ab-17"));
```

With a union, you can only use what **all** members have in common, until you check which one you have. `id.toUpperCase()` directly would be an error (numbers don't have it); after `typeof id === "number"` TypeScript knows which member it's dealing with in each branch. That checking is called **narrowing**, the topic of the next lesson.

## Literal unions: a small set of allowed values

Unions of literal types are one of TypeScript's most used features. They replace "magic strings" with a checked list of allowed values:

```ts
type Theme = "light" | "dark" | "system";
type HttpMethod = "GET" | "POST" | "PUT" | "DELETE";
type DiceRoll = 1 | 2 | 3 | 4 | 5 | 6;

function setTheme(theme: Theme): string {
  return `Theme set to ${theme}`;
}

console.log(setTheme("dark"));
```

`setTheme("drak")` is a compile error, and the editor autocompletes the three allowed values. In plain JavaScript, that typo would just quietly not work.

## null and undefined in unions

In strict mode (`strictNullChecks`), `null` and `undefined` are **not** part of other types. A `string` is always a real string. If a value may be missing, say so with a union:

```ts
function findUser(id: number): string | null {
  return id === 1 ? "Ada" : null;
}

const user = findUser(2);
console.log(user === null ? "nobody" : user.toUpperCase());
```

This single rule removes an entire category of bugs, the one Tony Hoare (who invented null references in 1965) called his "billion-dollar mistake": every possibly-missing value is visible in the types, and the compiler makes you handle it.

Which to use for "nothing", `null` or `undefined`? JavaScript itself uses `undefined` for missing properties and array elements, and DOM methods return `null`. Pick one convention for your own APIs (many TypeScript codebases prefer `undefined`, and optional properties `?` are `undefined` anyway) and stay consistent.

## Discriminated unions

The most important pattern in this lesson: a union of object types that share a **literal "tag" property** (here `kind`):

```ts
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "rectangle"; width: number; height: number }
  | { kind: "triangle"; base: number; height: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
    case "rectangle":
      return shape.width * shape.height;
    case "triangle":
      return (shape.base * shape.height) / 2;
  }
}

console.log(area({ kind: "circle", radius: 1 }).toFixed(3), area({ kind: "triangle", base: 4, height: 3 }));
```

Checking `shape.kind` tells TypeScript exactly which member you have: in the `"circle"` case, `shape.radius` exists and `shape.width` doesn't. This is called a **discriminated** (or **tagged**) **union**, and it's how TypeScript code models "one of several kinds of thing": shapes, events, actions in a Redux store, API responses, states of a form, messages between services. Compare it with the class-based polymorphism of the JavaScript course: here, the data is plain objects (easy to send as JSON) and the behaviour lives in functions with a `switch`.

Notice that `area` has no `default` and no final `return`, and TypeScript doesn't complain: it knows the `switch` covers every possible `kind`. Add a `"square"` member to the union and `area` becomes an error ("Function lacks ending return statement") until you handle it. The next lesson makes this **exhaustiveness check** explicit.

## Modelling states instead of flags

Discriminated unions shine for **states**. Compare two ways to describe a data request:

```ts
type LoadingFlags = { loading: boolean; error?: string; data?: string[] };

type RequestState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "failed"; error: string }
  | { status: "loaded"; data: string[] };

function render(state: RequestState): string {
  switch (state.status) {
    case "idle": return "Press load";
    case "loading": return "Loading...";
    case "failed": return `Error: ${state.error}`;
    case "loaded": return state.data.join(", ");
  }
}

console.log(render({ status: "loaded", data: ["a", "b"] }), "|", render({ status: "failed", error: "timeout" }));
```

With `LoadingFlags`, nothing stops nonsense such as `loading: true` with an `error` and `data` at the same time, and every reader must guess which combinations are possible. `RequestState` makes **impossible states impossible to write**: data only exists when the status is `"loaded"`. This idea, "make illegal states unrepresentable", is one of the biggest design benefits of a type system.

## Narrowing

**Narrowing** is how TypeScript follows your checks: after an `if`, a `switch`, an early `return` or a `throw`, it knows more about a value's type. You've used it since Module 1. This lesson lists all the ways, then shows how to write your own.

```ts
function lengthOf(value: string | string[] | null): number {
  if (value === null) return 0;
  // here: string | string[]
  if (typeof value === "string") return value.length;
  // here: string[]
  return value.reduce((n, s) => n + s.length, 0);
}
console.log(lengthOf(null), lengthOf("hey"), lengthOf(["ab", "c"]));
```

The compiler performs **control-flow analysis**: it follows every path through the function, and each check removes possibilities for the code after it.

## The narrowing toolkit

| Check | Narrows to |
|---|---|
| `typeof x === "string"` (also number, boolean, bigint, symbol, undefined, function, object) | that primitive (careful: `typeof null` is `"object"`) |
| `x === null`, `x !== undefined`, `x == null` (both null and undefined) | without the missing values |
| truthiness: `if (x)` | removes null and undefined, but also `""`, `0`, `NaN` and `false`: use it with care for strings and numbers |
| `Array.isArray(x)` | the array member |
| `x instanceof Date` | that class |
| `"swim" in animal` | members that have that property |
| `x.kind === "circle"` | that member of a discriminated union |
| equality with a literal: `x === "auto"` | that literal |

```ts
type Fish = { name: string; swim: () => string };
type Bird = { name: string; fly: () => string };

function move(animal: Fish | Bird): string {
  if ("swim" in animal) return animal.swim();
  return animal.fly();
}

function when(value: Date | string | number): string {
  if (value instanceof Date) return value.toISOString().slice(0, 10);
  return new Date(value).toISOString().slice(0, 10);
}

console.log(move({ name: "Nemo", swim: () => "splash" }), when(0), when(new Date(Date.UTC(2026, 0, 15))));
```

## Type predicates: your own type guards

Sometimes a check is too complex to write inline, or you need it in many places. A function whose return type is **`value is Type`** is a **type guard**: when it returns `true`, TypeScript narrows the argument to that type.

```ts
interface User {
  id: number;
  name: string;
}

function isUser(value: unknown): value is User {
  return (
    typeof value === "object" &&
    value !== null &&
    "id" in value && typeof value.id === "number" &&
    "name" in value && typeof value.name === "string"
  );
}

const data: unknown = JSON.parse('[{"id": 1, "name": "Ada"}, {"id": "2"}, null]');
if (Array.isArray(data)) {
  const users = data.filter(isUser);
  console.log(users.map((u) => u.name));
}
```

`data.filter(isUser)` returns `User[]`: TypeScript understands that the guard removes everything else. Since TypeScript 5.5, simple arrow functions such as `(x) => x !== null` are inferred as type predicates automatically, so `[1, null, 2].filter((x) => x !== null)` is a `number[]`.

Be careful: TypeScript trusts a type predicate completely. If `isUser` returned `true` for something that isn't a user, the compiler would believe it. A guard is a promise you make; test it well.

## Assertion functions

A close relative: an **assertion function** throws if a condition is false, and its return type `asserts value is Type` (or `asserts condition`) narrows the value for the rest of the scope:

```ts
function assertIsString(value: unknown, label: string): asserts value is string {
  if (typeof value !== "string") throw new TypeError(`${label} must be a string`);
}

const input: unknown = "  hello ";
assertIsString(input, "input");
console.log(input.trim());
```

DevQuest's global `assert` (like Node's `node:assert`) is declared this way: after `assert(x !== null)`, TypeScript knows `x` isn't null.

+ When the function returns true, `value` is narrowed to User for the caller
- The function throws if value isn't a User
- value is converted to a User

## Exhaustiveness checking with never

When every member of a union has been handled, what remains is the type `never` ("no possible value"). That gives a neat trick to make the compiler check that a `switch` is **complete**:

```ts
type Light = "red" | "amber" | "green";

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

function next(light: Light): Light {
  switch (light) {
    case "red": return "green";
    case "green": return "amber";
    case "amber": return "red";
    default: return assertNever(light);
  }
}

console.log(next("red"), next("amber"));
```

If someone adds `"flashing"` to `Light`, the `default` branch receives a `"flashing"`, which isn't assignable to `never`: a compile error that points exactly at the `switch` that needs updating. (And if invalid data arrives at run time anyway, `assertNever` throws a clear error.) An equivalent shortcut is the `satisfies` operator: `default: light satisfies never;`. Use exhaustiveness checks for every `switch` over a union that will grow.

## Where narrowing gets lost

Narrowing applies to a specific variable at a specific place. It can be lost:

- **In callbacks**: a narrowed `let` variable (or a property) isn't trusted inside a function created later, because it might change before the callback runs. Copy it into a `const` first.
- **After calls that could change an object's property**: TypeScript is optimistic here, and keeps the narrowing.
- **Across separate checks stored in booleans**: `const isText = typeof x === "string"; if (isText) ...` works for `const` values since TypeScript 4.4, but not for more complex aliasing.

```ts
function shout(message: string | undefined): (() => string) | undefined {
  if (message === undefined) return undefined;
  const text = message;
  return () => text.toUpperCase();
}
console.log(shout("hi")?.());
```

::solution
type Config = { port: number; host: string; debug: boolean; mode: "dev" | "prod"; tags: string[] };

function parseConfig(text: string): Config {
  const config: Config = { port: 8080, host: "localhost", debug: false, mode: "dev", tags: [] };
  text.split("\n").forEach((raw, index) => {
    const line = raw.trim();
    if (line === "" || line.startsWith("#")) return;
    const fail = (message: string): never => {
      throw new Error(`line ${index + 1}: ${message}`);
    };
    const eq = line.indexOf("=");
    if (eq === -1) fail("expected key=value");
    const key = line.slice(0, eq).trim();
    const value = line.slice(eq + 1).trim();
    switch (key) {
      case "port": {
        const port = Number(value);
        if (value === "" || !Number.isInteger(port) || port < 1 || port > 65535) fail(`invalid port "${value}"`);
        config.port = port;
        break;
      }
      case "host":
        config.host = value;
        break;
      case "debug":
        if (value !== "true" && value !== "false") fail(`invalid debug "${value}"`);
        config.debug = value === "true";
        break;
      case "mode":
        if (value !== "dev" && value !== "prod") return fail(`invalid mode "${value}"`);
        config.mode = value;
        break;
      case "tags":
        config.tags = value.split(",").map((t) => t.trim()).filter((t) => t !== "");
        break;
      default:
        fail(`unknown key "${key}"`);
    }
  });
  return config;
}
::tests
assert.deepStrictEqual(parseConfig(""), { port: 8080, host: "localhost", debug: false, mode: "dev", tags: [] });
assert.deepStrictEqual(
  parseConfig("# server\nport = 3000\n\nhost=example.com\ndebug = true\nmode=prod\ntags = web, api , ,blue"),
  { port: 3000, host: "example.com", debug: true, mode: "prod", tags: ["web", "api", "blue"] },
);
assert.throws(() => parseConfig("port=80\ncolour=red"), { message: 'line 2: unknown key "colour"' });
assert.throws(() => parseConfig("\nport"), { message: "line 2: expected key=value" });
assert.throws(() => parseConfig("port=abc"), { message: 'line 1: invalid port "abc"' });
assert.throws(() => parseConfig("port=70000"), { message: 'line 1: invalid port "70000"' });
assert.throws(() => parseConfig("port="), { message: 'line 1: invalid port ""' });
assert.throws(() => parseConfig("debug=yes"), { message: 'line 1: invalid debug "yes"' });
assert.throws(() => parseConfig("mode = test"), { message: 'line 1: invalid mode "test"' });
const __c = parseConfig("mode=prod");
const __m: "dev" | "prod" = __c.mode;
::hints
- Start from a `Config` holding the defaults and fill it in line by line.
- A helper `fail(message: string): never` that throws makes TypeScript understand that code after a failed check doesn't continue.
- After `if (value !== "dev" && value !== "prod") return fail(...)`, `value` is narrowed to `"dev" | "prod"`, so it can be assigned to `config.mode` without `as`.
