## JavaScript classes, now with types

Everything you learnt about classes in the JavaScript course (Modules 8 and 9) still holds. TypeScript adds types for fields, parameters and methods, plus a few extra keywords for **access control** and **design**.

```ts
class BankAccount {
  readonly owner: string;
  private balance = 0;
  static readonly overdraftLimit = 100;

  constructor(owner: string, opening: number) {
    this.owner = owner;
    this.deposit(opening);
  }

  deposit(amount: number): void {
    if (amount <= 0) throw new RangeError("Deposit must be positive");
    this.balance += amount;
  }

  withdraw(amount: number): boolean {
    if (this.balance - amount < -BankAccount.overdraftLimit) return false;
    this.balance -= amount;
    return true;
  }

  get available(): number {
    return this.balance + BankAccount.overdraftLimit;
  }
}

const account = new BankAccount("Ada", 50);
console.log(account.withdraw(120), account.withdraw(100), account.available);
```

- **Fields are declared** in the class body with their types (`owner: string`). Under `strict`, every field must be initialised, either where it's declared (`balance = 0`) or in the constructor; otherwise TypeScript reports *Property 'x' has no initializer*.
- `readonly` fields can only be assigned in the declaration or the constructor.
- `static` members belong to the class itself (`BankAccount.overdraftLimit`), as in JavaScript.
- `get`/`set` accessors are typed like methods.

## private, protected, public and #private

TypeScript has three **access modifiers**:

| Modifier | Accessible from |
|---|---|
| `public` (the default) | anywhere |
| `protected` | the class and its subclasses |
| `private` | only the class itself |

`account.balance` outside the class is a compile error. But remember type erasure: `private` is a **compile-time** check only, and the property is an ordinary property at run time (visible in `console.log` and `JSON.stringify`, and reachable with `account["balance"]`).

JavaScript's own **`#private` fields** (JavaScript course, Module 8) are private **at run time** too:

```ts
class Token {
  #value: string;

  constructor(value: string) {
    this.#value = value;
  }

  matches(guess: string): boolean {
    return guess === this.#value;
  }
}

const token = new Token("s3cret");
console.log(token.matches("guess"), token, JSON.stringify(token));
```

Which to use? `#private` gives real encapsulation (nothing outside can read it); `private` is lighter and allows tests or subclasses to bend the rules with a cast. Many modern codebases prefer `#private` for anything genuinely secret; `private` remains very common, and `protected` has no `#` equivalent.

## Parameter properties

A TypeScript shortcut: put a modifier on a constructor parameter, and it becomes a field automatically:

```ts
class Point {
  constructor(
    public readonly x: number,
    public readonly y: number,
  ) {}

  distanceTo(other: Point): number {
    return Math.hypot(this.x - other.x, this.y - other.y);
  }
}

console.log(new Point(0, 0).distanceTo(new Point(3, 4)));
```

`public readonly x: number` declares the field and assigns it. It's concise and widely used (Angular code is full of it). It's also one of the few TypeScript features that **generate code**, so it isn't "erasable": Node's built-in type stripping rejects it, and the `erasableSyntaxOnly` option forbids it. Projects that run `.ts` files directly in Node write the fields out instead.

## Inheritance, abstract classes and override

```ts
abstract class Employee {
  constructor(public readonly name: string) {}

  abstract monthlyPay(): number;

  payslip(): string {
    return `${this.name}: ${this.monthlyPay().toFixed(2)}`;
  }
}

class Salaried extends Employee {
  constructor(name: string, private readonly salary: number) {
    super(name);
  }

  override monthlyPay(): number {
    return this.salary / 12;
  }
}

class Contractor extends Employee {
  constructor(name: string, private readonly rate: number, private readonly hours: number) {
    super(name);
  }

  override monthlyPay(): number {
    return this.rate * this.hours;
  }
}

const staff: Employee[] = [new Salaried("Ada", 60000), new Contractor("Bob", 50, 80)];
for (const person of staff) console.log(person.payslip());
```

- An **abstract class** can't be instantiated (`new Employee("x")` is an error); it exists to be extended. An **abstract method** has no body, and every concrete subclass **must** implement it (the compiler checks).
- **`override`** marks a method that replaces a parent's method. With the compiler option `noImplicitOverride`, it's required, which catches two classic bugs: a typo in the method name (it would silently create a new method instead of overriding), and a parent method being renamed (overrides would silently stop overriding).

Abstract classes are the "template method" pattern from the JavaScript course, now checked: `payslip` is written once, and each subclass fills in `monthlyPay`.

## Classes are also types

A class declaration creates two things: a **value** (the constructor function, used with `new`) and a **type** (the shape of its instances). So `staff: Employee[]` uses the class as a type. Because TypeScript is structural, any object with the same public shape matches that type, even if it wasn't created with `new` (as long as the class has no `private`, `protected` or `#private` members: those make a class type behave nominally, so only real instances match).

`typeof Employee` is the type of the **class itself** (its constructor and static members), which is what you need when passing classes around, for example to a factory.

    if (v === undefined) return undefined;
    this.#spots.delete(plate);
    return v.fee(hours);
  }
}

=== lesson ts-interfaces-structural | Interfaces, implements and structural typing | 85
## Programming to an interface

The JavaScript course taught "program to an interface, not an implementation" (Module 9), but JavaScript couldn't check it: an "interface" was just a convention. In TypeScript, it's real:

```ts
interface Logger {
  log(message: string): void;
}

class ConsoleLogger implements Logger {
  log(message: string): void {
    console.log(`[console] ${message}`);
  }
}

class MemoryLogger implements Logger {
  readonly lines: string[] = [];
  log(message: string): void {
    this.lines.push(message);
  }
}

function processOrder(id: number, logger: Logger): void {
  logger.log(`processing order ${id}`);
}

const memory = new MemoryLogger();
processOrder(1, new ConsoleLogger());
processOrder(2, memory);
console.log(memory.lines);
```

`implements Logger` asks the compiler to check that the class has everything `Logger` requires; forget `log` or give it the wrong parameter type and the error appears **on the class**, where it's easy to fix. `processOrder` depends only on the interface, so any logger works, including a test double.

A class can implement **several** interfaces (`class Cache implements Readable, Writable`), but extend only one class.

## implements is optional (structural typing)

Delete `implements Logger` from `MemoryLogger` above and the program still compiles: the class has the right shape, and that's all TypeScript cares about. `implements` only adds an **early check**. So why write it? It documents intent, and it reports mistakes at the class instead of at some distant call site.

Structural typing also means plain objects can satisfy interfaces, which makes testing easy:

```ts
interface Clock {
  now(): Date;
}

function greeting(clock: Clock): string {
  const hour = clock.now().getUTCHours();
  return hour < 12 ? "Good morning" : "Good afternoon";
}

const fakeClock: Clock = { now: () => new Date(Date.UTC(2026, 0, 1, 9)) };
console.log(greeting(fakeClock));
```

No mocking library needed: an object literal with a `now` method is a `Clock`.

## Interfaces for classes: what they can't describe

An interface describes the **instance** side: properties and methods. It can't require private members, constructors or static members. To describe a constructor ("a class whose instances are Loggers"), use a **construct signature**:

```ts
interface Logger {
  log(message: string): void;
}

type LoggerClass = new (prefix: string) => Logger;

class PrefixLogger implements Logger {
  constructor(private prefix: string) {}
  log(message: string): void {
    console.log(`${this.prefix} ${message}`);
  }
}

function createLogger(Kind: LoggerClass, prefix: string): Logger {
  return new Kind(prefix);
}

createLogger(PrefixLogger, ">>").log("ready");
```

## Assignability: when is A a B?

Structural typing has precise rules. A type `A` is **assignable** to `B` when every required property of `B` exists in `A` with an assignable type. Extra properties in `A` are fine (except in fresh object literals: the excess property check from Module 2). Some consequences:

- `{ name: string; age: number }` is assignable to `{ name: string }`, but not the other way round: more specific types (more properties) fit where less specific ones are expected. The "subtype" is the one with **more** requirements.
- Methods with **fewer parameters** fit where more are offered (Module 3).
- **`readonly` properties** don't stop assignment: a `{ readonly x: number }` can be assigned to `{ x: number }`, which then mutates it. `readonly` is a promise about one view of an object, not about the object.

```ts
interface Named { name: string }
interface Person { name: string; age: number }

const ada: Person = { name: "Ada", age: 36 };
const named: Named = ada;
console.log(named.name);
```

## Branding: when structural typing is too lenient

Sometimes you *want* two types with the same shape to be incompatible: a `UserId` and an `OrderId` are both strings, and mixing them up is a real bug. A **brand** adds a fake property that no plain string has:

```ts
type UserId = string & { readonly __brand: "UserId" };
type OrderId = string & { readonly __brand: "OrderId" };

function userId(raw: string): UserId {
  if (!/^u_\d+$/.test(raw)) throw new Error(`Invalid user id: ${raw}`);
  return raw as UserId;
}

function loadUser(id: UserId): string {
  return `user ${id}`;
}

console.log(loadUser(userId("u_42")));
```

`loadUser("u_42")` is now an error (a plain string isn't a `UserId`), and so is passing an `OrderId`. The only way to get a `UserId` is through `userId()`, which validates: a **smart constructor**. The brand exists only in the types (`&` creates an **intersection** type, Module 5); at run time it's still a plain string.

  get(key: string): string | undefined;
  set(key: string, value: string): void;
  delete(key: string): boolean;

class MemoryStore implements KeyValueStore {
  #data = new Map<string, string>();

  get(key: string): string | undefined {
    return this.#data.get(key);
  }

  set(key: string, value: string): void {
    this.#data.set(key, value);
  }

  delete(key: string): boolean {
    return this.#data.delete(key);
  }

  keys(): string[] {
    return [...this.#data.keys()];
  }

class PrefixedStore implements KeyValueStore {
  constructor(
    private readonly inner: KeyValueStore,
    private readonly prefix: string,
  ) {}

  get(key: string): string | undefined {
    return this.inner.get(this.prefix + key);
  }

  set(key: string, value: string): void {
    this.inner.set(this.prefix + key, value);
  }

  delete(key: string): boolean {
    return this.inner.delete(this.prefix + key);
  }

  keys(): string[] {
    return this.inner.keys().filter((k) => k.startsWith(this.prefix)).map((k) => k.slice(this.prefix.length));
  }
}

function migrate(from: KeyValueStore, to: KeyValueStore): number {
  const keys = from.keys();
  for (const key of keys) {
    const value = from.get(key);
    if (value !== undefined) to.set(key, value);
  }
  return keys.length;
}

=== lesson ts-oop-patterns | OOP patterns in TypeScript | 90
## this types: fluent APIs that survive inheritance

A method returning `this` (the **polymorphic `this` type**) returns "whatever class this object really is", which keeps fluent chains working in subclasses:

```ts
class QueryBuilder {
  protected parts: string[] = [];

  where(condition: string): this {
    this.parts.push(`WHERE ${condition}`);
    return this;
  }

  build(): string {
    return this.parts.join(" ");
  }
}

class PagedQueryBuilder extends QueryBuilder {
  limit(n: number): this {
    this.parts.push(`LIMIT ${n}`);
    return this;
  }
}

const sql = new PagedQueryBuilder().where("age > 18").limit(10).build();
console.log(sql);
```

If `where` returned `QueryBuilder`, then `.where(...).limit(10)` would be an error: a `QueryBuilder` has no `limit`. Returning `this` keeps the subclass type.

## Builder with typed steps

The builder pattern (JavaScript course, Module 9) gets stronger with types: required options can be enforced by the compiler.

```ts
interface Email {
  to: string[];
  subject: string;
  body: string;
  cc: string[];
}

class EmailBuilder {
  private email: Partial<Email> = { to: [], cc: [] };

  to(address: string): this {
    this.email.to?.push(address);
    return this;
  }

  cc(address: string): this {
    this.email.cc?.push(address);
    return this;
  }

  subject(text: string): this {
    this.email.subject = text;
    return this;
  }

  body(text: string): this {
    this.email.body = text;
    return this;
  }

  build(): Email {
    const { to = [], cc = [], subject, body } = this.email;
    if (to.length === 0 || subject === undefined || body === undefined) throw new Error("to, subject and body are required");
    return { to, cc, subject, body };
  }
}

const mail = new EmailBuilder().to("ada@example.com").subject("Hi").body("See you at 3").build();
console.log(mail);
```

(Advanced libraries go further, encoding "subject has been set" in the builder's type parameter so that `build()` doesn't even compile until every required step has run. It's elegant but complex; a checked `build()` is usually enough.)

## Mixins: reusable behaviour without deep hierarchies

A **mixin** is a function that takes a class and returns a subclass with extra behaviour. TypeScript types it with a constructor type:

```ts
type Constructor<T = object> = new (...args: any[]) => T;

function Timestamped<TBase extends Constructor>(Base: TBase) {
  return class extends Base {
    createdAt = new Date(Date.UTC(2026, 0, 1));
  };
}

function Taggable<TBase extends Constructor>(Base: TBase) {
  return class extends Base {
    tags = new Set<string>();
    tag(...names: string[]): this {
      for (const name of names) this.tags.add(name);
      return this;
    }
  };
}

class Note {
  constructor(public text: string) {}
}

const RichNote = Taggable(Timestamped(Note));
const note = new RichNote("Buy milk").tag("home", "urgent");
console.log(note.text, [...note.tags], note.createdAt.toISOString());
```

`RichNote` instances have `text`, `createdAt`, `tags` and `tag()`, all typed. (`any[]` in `Constructor` is one of the rare legitimate uses of `any`: TypeScript requires exactly this form for mixin constructors.) Mixins avoid deep inheritance trees ("a TaggableTimestampedNote extends TimestampedNote extends Note"); still, **composition** (an object that *has* a tag set) is often simpler. Reach for mixins when behaviour must appear on the class itself.

## Decorators

**Decorators** are functions applied to classes and class members with `@` syntax. TypeScript 5 implements the standard (ECMAScript) decorator proposal; frameworks such as Angular, NestJS and TypeORM rely on decorators (the older "experimental" version, enabled by `experimentalDecorators`). Here's what a method decorator looks like:

```
function logged<This, Args extends unknown[], Return>(
  method: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext<This, (this: This, ...args: Args) => Return>,
) {
  return function (this: This, ...args: Args): Return {
    console.log(`calling ${String(context.name)}(${args.join(", ")})`);
    return method.call(this, ...args);
  };
}

class Calculator {
  @logged
  add(a: number, b: number): number {
    return a + b;
  }
}
```

JavaScript engines don't run decorator syntax natively yet (browsers and Node are still implementing it), so it needs compiling by `tsc` or a bundler, and DevQuest can't run it directly. But a decorator is only a function that receives a method and returns a replacement. This is what `@logged` does, written by hand:

```ts
function logged<Args extends unknown[], Return>(name: string, method: (...args: Args) => Return) {
  return function (this: unknown, ...args: Args): Return {
    console.log(`calling ${name}(${args.join(", ")})`);
    return method.apply(this, args);
  };
}

class Calculator {
  add(a: number, b: number): number {
    return a + b;
  }
}
Calculator.prototype.add = logged("add", Calculator.prototype.add);

console.log(new Calculator().add(2, 3));
```

That's the "decorator" pattern from the JavaScript course (Module 9) applied to methods. Use decorators when a framework expects them; in your own code, plain higher-order functions are simpler and need no compiler support.

## Making illegal operations impossible: private constructors

A `private constructor` stops anyone outside the class from calling `new`. Combined with static factory methods, it guarantees every instance is valid:

```ts
class Percentage {
  private constructor(readonly value: number) {}

  static of(value: number): Percentage {
    if (value < 0 || value > 100) throw new RangeError(`${value} is not a percentage`);
    return new Percentage(value);
  }

  static fromRatio(ratio: number): Percentage {
    return Percentage.of(Math.round(ratio * 100));
  }

  toString(): string {
    return `${this.value}%`;
  }
}

console.log(`${Percentage.of(42)} ${Percentage.fromRatio(0.075)}`);
```

`new Percentage(500)` is a compile error outside the class. The same idea gives a **singleton** (a class with one instance, created by a static `instance()` method), though a module-level `const` is usually a simpler singleton in TypeScript.

## Classes or functions and types?

TypeScript supports both styles well:

- **Classes** fit stateful objects with behaviour and invariants (a bank account, a connection pool, a game entity), and frameworks built around them (Angular, NestJS).
- **Plain data types plus functions** (discriminated unions with `switch`, Module 2) fit data that crosses boundaries (JSON, messages), and functional styles (React with hooks, Redux).

Most real codebases mix them. The SOLID principles and design patterns from the JavaScript course apply to both; types make them checkable.

class RequestBuilder {
  protected request: { method: string; url: string; headers: Record<string, string>; body?: string };

  constructor(url: string) {
    this.request = { method: "GET", url, headers: {} };
  }

  method(m: "GET" | "POST" | "PUT" | "DELETE"): this {
    this.request.method = m;
    return this;
  }

  header(name: string, value: string): this {
    this.request.headers[name.toLowerCase()] = value;
    return this;
  }

  build(): { method: string; url: string; headers: Record<string, string>; body?: string } {
    return { ...this.request, headers: { ...this.request.headers } };
  }
}

class JsonRequestBuilder extends RequestBuilder {
  json(data: unknown): this {
    this.request.body = JSON.stringify(data);
    return this.header("Content-Type", "application/json");
  }

  override build(): { method: string; url: string; headers: Record<string, string>; body?: string } {
    if (this.request.body !== undefined && this.request.method === "GET") throw new Error("GET requests cannot have a body");
    return super.build();
  }
}

(`inject<T>` is the one place where a generic return type is a deliberate, documented unchecked cast: the caller states what it expects.)
::starter

  readonly dependsOn?: readonly string[];

}
::solution
interface Plugin {
  readonly name: string;
  readonly dependsOn?: readonly string[];
  setup(app: App): void;
}

class App {
  #plugins = new Map<string, Plugin>();
  #services = new Map<string, unknown>();

  use(plugin: Plugin): this {
    if (this.#plugins.has(plugin.name)) throw new Error(`plugin ${plugin.name} is already registered`);
    this.#plugins.set(plugin.name, plugin);
    return this;
  }

  provide<T>(key: string, value: T): void {
    this.#services.set(key, value);
  }

  inject<T>(key: string): T {
    if (!this.#services.has(key)) throw new Error(`nothing provided for ${key}`);
    return this.#services.get(key) as T;
  }

  start(): string[] {
    const done: string[] = [];
    const visiting = new Set<string>();
    const visit = (plugin: Plugin): void => {
      if (done.includes(plugin.name)) return;
      if (visiting.has(plugin.name)) throw new Error(`dependency cycle at ${plugin.name}`);
      visiting.add(plugin.name);
      for (const dep of plugin.dependsOn ?? []) {
        const required = this.#plugins.get(dep);
        if (required === undefined) throw new Error(`plugin ${plugin.name} needs ${dep}`);
        visit(required);
      }
      visiting.delete(plugin.name);
      plugin.setup(this);
      done.push(plugin.name);
    };
    for (const plugin of this.#plugins.values()) visit(plugin);
    return done;
  }
}
