=== lesson redis-intro | Keys, strings & counters | 50
**Redis** (REmote DIctionary Server) is an **in-memory data structure store**. It keeps data in RAM, which makes reads and writes take microseconds, and it's used as a **cache**, **session store**, **message queue**, **rate limiter** and **real-time leaderboard** by a huge share of web apps.

Everything is a **key** pointing at a value. The value can be a string, list, hash, set, sorted set or stream, and each type has its own commands. You talk to Redis with **`redis-cli`**, one command per line:

```
SET site:name "DevQuest"        → OK
GET site:name                   → "DevQuest"
GET nothing-here                → (nil)
INCR page:views                 → (integer) 1
MSET a 1 b 2                    → OK      (set several keys at once)
MGET a b                        → 1) "1"  2) "2"
DEL a b                         → (integer) 2  (how many were deleted)
EXISTS a                        → (integer) 0
```

**Key naming:** use `object:id:field` with colons, such as `user:42`, `user:42:sessions` or `cache:weather:london`. Consistent names make keys easy to find and expire.

**Why counters are safe:** Redis executes commands **one at a time** (single-threaded command execution), so `INCR` is atomic. A thousand clients incrementing `page:views` at once never lose an update, unlike "read, add 1, write back" in application code.

In DevQuest, your commands run on a **Redis practice engine** inside the app. Lines starting with `#` are comments (a DevQuest convenience; real redis-cli doesn't support them).

=== lesson redis-expiry | Expiry, TTL & caching | 55
Any key can **expire**: Redis deletes it automatically after a timeout. That's what makes Redis a great cache and session store.

```
SET weather:london "12C" EX 60     → OK        (expires in 60 seconds)
TTL weather:london                 → (integer) 60
EXPIRE user:42:token 3600          → (integer) 1
PERSIST user:42:token              → (integer) 1   (remove the timeout)
TTL no-such-key                    → (integer) -2  (-2 = missing, -1 = no expiry)
SET lock:job NX EX 30              → OK, or (nil) if the key already exists
```

**Cache-aside**, the most common caching pattern:
1. Look in Redis: `GET cache:product:7`.
2. On a **miss**, read from the database, then `SET cache:product:7 <json> EX 300`.
3. On writes to the product, `DEL cache:product:7` so the next read refreshes it.

Always give cache entries a TTL, so stale data and unused keys clean themselves up. Add a little randomness to TTLs ("jitter") so thousands of keys don't expire at the same second and stampede your database.

DevQuest's engine uses a simulated clock: **`DEBUG SLEEP 61`** moves time forward 61 seconds instantly. On a real server, `DEBUG SLEEP` would actually freeze Redis, so never run it in production.

--- cards

Cache-aside :: Read the cache; on a miss load from the database and SET it with a TTL; delete the cache entry when the data changes.

=== lesson redis-lists | Lists: queues & activity feeds | 55
A Redis **list** is an ordered sequence of strings with fast pushes and pops at both ends: a natural **queue** or **stack**.

```
RPUSH jobs email:1 email:2      → (integer) 2   (append to the right/tail)
LPUSH jobs urgent:9             → (integer) 3   (prepend to the left/head)
LRANGE jobs 0 -1                → all items (-1 = the last one)
LPOP jobs                       → "urgent:9"
LLEN jobs                       → (integer) 2
LTRIM feed:ada 0 99             → keep only items 0-99
```

**Job queue:** producers `RPUSH`, workers `LPOP` (or **`BLPOP`**, which *blocks* until a job arrives instead of polling).

**Reliable queue:** if a worker crashes after popping, the job is lost. **`LMOVE jobs processing LEFT RIGHT`** atomically moves the job into a `processing` list, and the worker removes it from there only when it's done.

**Capped feed:** for "the 100 latest activities", `LPUSH feed:user:42 <item>` then `LTRIM feed:user:42 0 99`. The list never grows beyond 100.
--- exercise code redis

2. Take the **oldest** job and move it, atomically, to the **end** of `jobs:done` (one command).
3. Push `p6` onto the **front** of `feed:ada`, then trim the feed to its **3 newest** items.
::starter

# 2. oldest job → jobs:done (LMOVE)

# 3. new feed item, keep the 3 newest
::solution

::setup

LPUSH feed:ada p1 p2 p3 p4 p5
::verify

::expected
1) "email:2"
2) "email:3"
3) "report:7"
1) "email:1"
1) "p6"
2) "p5"
3) "p4"
::hints
- The oldest job is at the left (head) of the list.
- `LMOVE source destination LEFT RIGHT` pops from the left of source and pushes to the right of destination.
- `LTRIM key 0 2` keeps items 0, 1 and 2.
--- cards
BLPOP :: Blocking pop: waits until a list has an item (or a timeout), so workers don't need to poll.
Capped list :: LPUSH a new item then LTRIM key 0 N-1 to keep only the newest N.

=== lesson redis-hashes | Hashes: storing objects | 50
A **hash** maps fields to values inside one key, which is perfect for objects like users, products or settings, without serialising JSON:

```
HSET user:42 name "Grace" role admin logins 0   → (integer) 3   (fields added)
HGET user:42 name                                → "Grace"
HINCRBY user:42 logins 1                         → (integer) 1
HGETALL user:42                                  → field, value, field, value…
HDEL user:42 role                                → (integer) 1
HEXISTS user:42 role                             → (integer) 0
```

**Hash or string with JSON?**
- **Hash:** read or update **individual fields** (`HINCRBY`, `HSET` one field) without rewriting the whole object; small hashes are also very memory-efficient.
- **JSON string:** the object is always read and written as a whole, or has nested structure.

Expiry applies to the **whole key**, not to single fields (recent Redis versions add per-field TTLs with `HEXPIRE`).

--- cards
Redis hash :: A key holding field → value pairs; ideal for objects whose fields are read or updated individually.
HINCRBY :: Atomically increments an integer field inside a hash.

=== lesson redis-sets | Sets: tags, uniques & mutual friends | 50
A **set** is an unordered collection of **unique** strings, and the set operations run on the server:

```
SADD tags:post:1 redis cache nosql   → (integer) 3   (new members added)
SISMEMBER tags:post:1 redis          → (integer) 1
SCARD tags:post:1                    → (integer) 3   (size)
SINTER friends:ada friends:linus     → members in BOTH sets
SUNION a b / SDIFF a b               → in either / in a but not in b
SINTERSTORE mutual friends:ada friends:linus   → saves the result as a new set
```

Typical uses: **unique visitors** per day (`SADD visitors:2026-03-01 <userId>`, then `SCARD`), **tags**, **"who liked this"**, **mutual friends** and **permissions**. For counting millions of uniques approximately in a few kilobytes, Redis also offers **HyperLogLog** (`PFADD` and `PFCOUNT`).

Real Redis returns set members in **no particular order**; DevQuest's engine prints them sorted so lesson output is stable.
--- exercise code redis

::starter

::hints

- `SINTERSTORE destination key1 key2` stores the intersection.
--- cards
Redis set :: Unordered collection of unique strings with server-side intersection, union and difference.
HyperLogLog :: Probabilistic structure (PFADD/PFCOUNT) that counts unique items approximately in ~12 KB.

=== lesson redis-zsets | Sorted sets: leaderboards & rankings | 60
A **sorted set** is a set where every member has a **score**, kept sorted by score. It's the go-to structure for **leaderboards**, rankings, priority queues and "top N" lists:

```
ZADD scores 120 ada 95 linus 150 grace     → (integer) 3
ZINCRBY scores 80 linus                    → "175"
ZREVRANGE scores 0 2 WITHSCORES            → top 3, highest first, with scores
ZREVRANK scores ada                        → (integer) 2   (0 = first place)
ZSCORE scores grace                        → "150"
ZRANGEBYSCORE scores 100 200               → members scoring 100..200
ZCARD scores                               → (integer) 4
```

Inserting, updating and ranking are all **O(log n)**, so a game with millions of players can show anyone's rank instantly. Members with equal scores are ordered alphabetically.

Other uses: **delayed jobs** (score = run-at timestamp, then `ZRANGEBYSCORE jobs -inf <now>`), **sliding-window rate limits** (score = request time), and **trending items** (score = popularity).
--- exercise code redis

# 2. add alan
::solution

::setup

::verify

::hints

- `ZADD key score member`
--- cards
Sorted set :: Unique members ordered by a numeric score; O(log n) inserts and rank lookups. Perfect for leaderboards.
ZREVRANK :: A member's position when sorted from the highest score (0 = top).

=== lesson redis-patterns | Rate limits, locks & transactions | 65
Small commands combine into powerful patterns:

**Fixed-window rate limiter:** "at most 100 requests per user per minute":

```
INCR rate:user7:202603011200        → (integer) 1, 2, 3 …
EXPIRE rate:user7:202603011200 60   (set when the counter is first created)
```

If the counter is above the limit, reject the request. The key name contains the minute, so each window starts fresh, and the expiry cleans old windows up.

**Distributed lock:** "only one worker may build this report":

```
SET lock:report worker-1 NX PX 30000   → OK = you hold the lock; (nil) = someone else does
```

`NX` sets the key only if it doesn't exist, and `PX` makes it expire, so a crashed worker can't hold the lock forever. Release it only if the value is still yours (check-and-delete, done atomically with a small Lua script).

**Transactions:** `MULTI` queues commands and `EXEC` runs them all at once, with no other client's command in between:

```
MULTI
DECRBY points:ada 25
INCRBY points:linus 25
EXEC
```

Redis transactions don't roll back if one command fails; they guarantee **isolation**, not undo. Use `WATCH` for optimistic locking, or a Lua script (`EVAL`) for logic that must be fully atomic.

--- cards
SET NX PX :: Set only if the key doesn't exist, with a millisecond expiry: the basis of a Redis lock.
MULTI/EXEC :: Queue commands and run them together without interleaving; no automatic rollback on errors.

=== lesson redis-production | Redis in production | 55
Running Redis well means knowing what happens to your data in memory.

**Persistence:**
- **RDB snapshots** save the whole dataset every N minutes: compact and fast to restart, but you can lose the last few minutes.
- **AOF (append-only file)** logs every write; with `appendfsync everysec` you lose at most about one second. Many setups use both.
- Treat Redis as a cache unless persistence is configured and tested.

**Memory limits:** set `maxmemory` and an **eviction policy**: `allkeys-lru` (evict least recently used keys, the classic cache choice), `allkeys-lfu`, `volatile-ttl`, or `noeviction` (writes fail when full, best for queues and data you can't lose).

**Scaling & availability:**
- **Replication:** replicas copy a primary and can serve reads.
- **Sentinel:** monitors the primary and promotes a replica automatically on failure.
- **Redis Cluster:** shards keys across nodes using **16,384 hash slots**. Multi-key commands need their keys in the same slot (use hash tags like `{user42}:cart`).

**Habits that keep it fast:** never run **`KEYS *`** on a big production instance (it blocks the server); iterate with **`SCAN`**. Avoid huge keys (a 10-million-item list). Use pipelining to batch many commands.

**Pub/Sub vs Streams:** `PUBLISH`/`SUBSCRIBE` is fire-and-forget (offline subscribers miss messages); **Streams** (`XADD`, `XREADGROUP`) persist messages with consumer groups and acknowledgements, like a lightweight Kafka.

**Security:** never expose port 6379 to the internet, require authentication (ACL users with least privilege), and enable TLS between hosts. In 2024 Redis changed its license, and the Linux Foundation's open-source fork **Valkey** is now a common drop-in alternative.
