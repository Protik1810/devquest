=== lesson mysql-intro | MySQL, databases & tables | 55
**MySQL** is the most widely deployed open-source relational database: it powers WordPress, Shopify-era stores, and the classic **LAMP** stack (Linux, Apache, MySQL, PHP). **MariaDB** is a community fork, largely compatible, created by MySQL's original author.

A MySQL server holds several **databases** (also called schemas), each with **tables**:

```sql
CREATE DATABASE shop;
USE shop;
CREATE TABLE books (
  id     INT AUTO_INCREMENT PRIMARY KEY,
  title  VARCHAR(200) NOT NULL,
  price  DECIMAL(6,2) NOT NULL DEFAULT 9.99,
  format ENUM('paper', 'ebook') NOT NULL DEFAULT 'paper'
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

SHOW TABLES;
DESCRIBE books;
```

**MySQL-flavoured details:**
- `AUTO_INCREMENT` numbers new rows automatically.
- `VARCHAR(n)` is text up to *n* characters; `DECIMAL(6,2)` is exact money up to 9999.99.
- `ENUM(...)` restricts a column to a list of values.
- **InnoDB** is the default storage engine: transactions, row locking, foreign keys and crash recovery.
- Always use **`utf8mb4`**: MySQL's old `utf8` stores only 3-byte characters, so emoji 😀 break it.
- Identifiers can be quoted with backticks: `` `order` ``.

In DevQuest your statements run on a **MySQL practice engine** inside the app: MySQL syntax is translated and executed on an embedded database. Query results match MySQL for these lessons, but server features (users, storage engines, exact error messages) aren't simulated.

=== lesson mysql-select | Filtering, sorting & LIMIT | 50
The everyday query shape:

```sql
SELECT name, price
FROM products
WHERE category = 'tech' AND price BETWEEN 20 AND 300
ORDER BY price DESC
LIMIT 10;
```

**MySQL specifics worth knowing:**
- **`LIMIT offset, count`**: `LIMIT 20, 10` skips 20 rows and returns 10 (page 3 of 10). `LIMIT 10 OFFSET 20` means the same.
- **`IF(cond, a, b)`** is a compact CASE: `IF(price >= 100, 'premium', 'standard')`.
- **`IFNULL(email, '(none)')`** replaces NULL (the standard `COALESCE` works too).
- **`LIKE 'Lap%'`**: `%` is any text and `_` is one character.
- String comparisons are **case-insensitive** by default (the default collation `utf8mb4_0900_ai_ci` is *case and accent insensitive*), so `WHERE name = 'ada'` finds "Ada". Use a `_bin` or `_cs` collation when case matters.
- `CONCAT(first, ' ', last)` joins strings. In MySQL, `||` means OR, not concatenation.

Tables today: `customers(id, name, city, email)`, `products(id, name, category, price)`, `orders(id, customer_id, ordered_on, status)`, `order_items(order_id, product_id, qty)`.

=== lesson mysql-joins | Joins, GROUP BY & GROUP_CONCAT | 60
Joins combine tables through their keys; `GROUP BY` then summarises each group:

```sql
SELECT c.name, COUNT(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;
```

`INNER JOIN` keeps only matching rows; `LEFT JOIN` keeps every customer, with NULLs when there's no order. MySQL has no `FULL OUTER JOIN`: emulate it with a `UNION` of a LEFT and a RIGHT join.

**`GROUP_CONCAT`**, MySQL's favourite aggregate, turns a group's values into one string:

```sql
GROUP_CONCAT(p.name ORDER BY p.name SEPARATOR ', ')   -- 'Keyboard, Mouse'
```

The result is truncated at `group_concat_max_len` (1024 bytes by default), which matters for big groups.

**ONLY_FULL_GROUP_BY:** MySQL 5.7+ rejects selecting a column that's neither grouped nor aggregated (older versions silently picked a random value). Group by every non-aggregated column.

**HAVING** filters groups after aggregation, for example `HAVING COUNT(o.id) > 1`.

=== lesson mysql-dates | Dates & built-in functions | 55
Reports are mostly about **time**. MySQL's date toolbox:

| Function | Example | Result |
|---|---|---|
| `DATE_FORMAT(d, fmt)` | `DATE_FORMAT('2026-03-07', '%Y-%m')` | `'2026-03'` |
| `YEAR(d)`, `MONTH(d)`, `DAY(d)` | `MONTH('2026-03-07')` | `3` |
| `DATEDIFF(a, b)` | `DATEDIFF('2026-03-07', '2026-02-27')` | `8` (days) |
| `DATE_ADD(d, INTERVAL n unit)` | `DATE_ADD('2026-01-31', INTERVAL 1 DAY)` | `'2026-02-01'` |
| `NOW()`, `CURDATE()` | | current datetime / date |

Format codes: `%Y` year, `%m` month (01-12), `%d` day, `%H:%i:%s` time, `%M` month name, `%W` weekday name.

Column types: `DATE`, `DATETIME` (no time zone, stored as written) and `TIMESTAMP` (converted to UTC and back using the session time zone). A common rule is to store UTC and convert in the app.

**Strings:** `UPPER`, `LOWER`, `CONCAT`, `SUBSTRING(s, start, len)`, `LEFT/RIGHT(s, n)`, `TRIM`, `REPLACE`, `LPAD`. **Numbers:** `ROUND(x, 2)`, `FLOOR`, `CEIL`, `ABS`.

Grouping by a formatted date (`GROUP BY DATE_FORMAT(ordered_on, '%Y-%m')`) is the classic monthly report. MySQL lets you `GROUP BY` the SELECT alias.

=== lesson mysql-upsert | Upserts, transactions & constraints | 60
**Insert or update** in one statement, MySQL style:

```sql
INSERT INTO inventory (sku, qty) VALUES ('KB-1', 2)
ON DUPLICATE KEY UPDATE qty = qty + VALUES(qty);
```

If the insert would break a PRIMARY KEY or UNIQUE index, MySQL updates the existing row instead. `VALUES(qty)` means "the value I tried to insert". MySQL 8.0.19+ also allows an alias form: `INSERT … VALUES ('KB-1', 2) AS new ON DUPLICATE KEY UPDATE qty = qty + new.qty`.

Relatives:
- `INSERT IGNORE` skips rows that would violate a key, silently, so use it carefully.
- `REPLACE INTO` deletes the old row and inserts the new one, which fires delete triggers and cascades.

**Transactions (InnoDB):**

```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
COMMIT;   -- or ROLLBACK;
```

MySQL runs with **autocommit** on: each statement is its own transaction unless you start one. The default isolation level is **REPEATABLE READ**, and InnoDB adds *gap locks* so ranges you read can't get new rows mid-transaction.

**Constraints:** PRIMARY KEY, UNIQUE, NOT NULL, FOREIGN KEY (InnoDB only), and `CHECK`, which is enforced since MySQL **8.0.16** (older versions parsed and ignored it).

=== lesson mysql-window | Window functions & CTEs (MySQL 8) | 60
MySQL **8.0** added the modern SQL features that used to require painful self-joins:

**CTEs (`WITH`)** name subqueries and support recursion (`WITH RECURSIVE`) for hierarchies.

**Window functions** compute across related rows without collapsing them:

```sql
SELECT category, name, price,
       RANK()       OVER (PARTITION BY category ORDER BY price DESC) AS price_rank,
       SUM(price)   OVER (PARTITION BY category)                     AS category_total,
       LAG(price)   OVER (ORDER BY price)                            AS cheaper_neighbour
FROM products;
```

- `ROW_NUMBER()` numbers rows 1, 2, 3; `RANK()` gives ties the same rank with gaps; `DENSE_RANK()` has no gaps.
- `PARTITION BY` restarts the calculation per group.
- To filter on a window result ("top 2 per category"), compute it in a CTE and filter outside: you can't use window functions in WHERE.

If you're stuck on MySQL 5.7, these queries need variables or self-joins, which is one good reason to upgrade.

=== lesson mysql-indexes | Indexes & InnoDB internals | 60
InnoDB stores every table as a **clustered index**: rows live inside the B-tree of the **primary key**, sorted by it. Every **secondary index** stores the indexed columns *plus the primary key*, then looks the row up through the PK. So:
- keep primary keys **short** (an INT/BIGINT, not a long string), because every secondary index copies them;
- auto-increment keys insert at the end of the tree, which is fast; random UUIDs scatter inserts all over it.

```sql
CREATE INDEX idx_orders_customer_date ON orders (customer_id, ordered_on);
CREATE UNIQUE INDEX uq_customers_email ON customers (email);
SHOW INDEX FROM orders;
```

**Composite indexes follow the leftmost-prefix rule:** `(customer_id, ordered_on)` helps `WHERE customer_id = 7` and `WHERE customer_id = 7 AND ordered_on > '2026-01-01'`, but **not** `WHERE ordered_on > …` alone. Put equality columns first and the range or sort column last.

A **covering index** contains every column a query needs, so MySQL never touches the table (EXPLAIN shows `Using index`).

**EXPLAIN** shows the plan: check `type` (`ALL` = full scan, bad on big tables; `ref`/`range`/`const` = good), `key` (the index chosen) and `rows` (estimated rows examined). `EXPLAIN ANALYZE` (8.0.18+) runs the query and shows real timings.

=== lesson mysql-production | MySQL in production | 55
Keeping MySQL healthy and safe:

**Replication:** the primary writes every change to the **binary log (binlog)**; replicas replay it. Use **GTIDs** (global transaction IDs) so failover and re-pointing replicas is simple. Replication is usually **asynchronous**, so replicas can lag; read-your-own-writes may need the primary. **Group Replication / InnoDB Cluster** add automatic failover.

**Backups:** `mysqldump` (logical SQL dump; fine for small databases), **Percona XtraBackup** or MySQL Enterprise Backup (fast physical hot backups), plus the binlog for point-in-time recovery. A backup you haven't **restored in a test** isn't a backup.

**Performance:** enable the **slow query log**, read it with `pt-query-digest`, and fix the worst queries with indexes. Size `innodb_buffer_pool_size` to hold the working set (often 50-75% of RAM on a dedicated server). Use a **connection pool** in the app.

**Schema changes** on big tables can lock them: use online DDL (`ALGORITHM=INPLACE`/`INSTANT`) or tools like gh-ost and pt-online-schema-change.

**Security:** never use `root` from the app; create a user per app with only the privileges it needs (`GRANT SELECT, INSERT, UPDATE ON shop.* TO 'app'@'10.0.%'`). Use parameterised queries against SQL injection, and TLS between app and database.

**MySQL or PostgreSQL?** Both are excellent. MySQL is simpler to operate at huge scale for straightforward OLTP workloads and has a vast hosting ecosystem. PostgreSQL offers richer SQL, extensions (PostGIS, pgvector), stricter defaults and powerful JSONB.
