## A different way to structure programs

You've written functional code since Module 5: pure functions, callbacks, `map`, `filter` and `reduce`, closures. **Functional programming** (FP) turns those habits into a style: build programs from small **pure** functions that take data and return **new** data, and combine them. JavaScript isn't a purely functional language, but FP ideas run through modern JavaScript: React components, Redux reducers, array pipelines and many libraries are built on them.

The core principles:

- **Pure functions**: output depends only on input; no side effects.
- **Immutability**: never change data; create new versions.
- **Functions as values**: pass them, return them, combine them.
- **Declarative code**: say *what* you want (`filter` the active users), not *how* to loop.

## Imperative versus declarative

```js
const orders = [
  { customer: "Ada", total: 120, paid: true },
  { customer: "Bob", total: 45, paid: false },
  { customer: "Cy", total: 300, paid: true },
];

// Imperative: how to do it, step by step
const bigPaid1 = [];
for (let i = 0; i < orders.length; i++) {
  if (orders[i].paid && orders[i].total > 100) {
    bigPaid1.push(orders[i].customer.toUpperCase());
  }
}

// Declarative: what we want
const bigPaid2 = orders
  .filter((o) => o.paid && o.total > 100)
  .map((o) => o.customer.toUpperCase());

console.log(bigPaid1, bigPaid2);
```

The declarative version has no index variable to get wrong, no array being mutated, and reads like the requirement.

## Composition: pipelines of functions

Small functions combine into bigger ones. `pipe` runs functions left to right (the order you read them); `compose` right to left (the mathematical order):

```js
const pipe = (...fns) => (input) => fns.reduce((value, fn) => fn(value), input);

const trim = (s) => s.trim();
const lower = (s) => s.toLowerCase();
const dashes = (s) => s.replaceAll(/\s+/g, "-");
const noPunctuation = (s) => s.replaceAll(/[^\w-]/g, "");

const slugify = pipe(trim, lower, noPunctuation, dashes);
console.log(slugify("  Hello, World! Learn FP  "));
```

`pipe` itself is a tiny `reduce`: start with the input and feed it through each function in turn. Each step is trivially testable on its own, and steps can be reused in other pipelines.

## Currying and partial application

**Partial application** fixes some of a function's arguments now, leaving a function that takes the rest later. **Currying** turns a function of several arguments into a chain of one-argument functions. They make functions fit nicely into pipelines and `map`:

```js
const multiply = (a) => (b) => a * b;
const double = multiply(2);
console.log([1, 2, 3].map(double));

const hasRole = (role) => (user) => user.roles.includes(role);
const users = [
  { name: "Ada", roles: ["admin", "dev"] },
  { name: "Bob", roles: ["dev"] },
];
console.log(users.filter(hasRole("admin")).map((u) => u.name));

const greet = (greeting, name) => `${greeting}, ${name}!`;
const hello = greet.bind(null, "Hello");
console.log(hello("Grace"));
```

`fn.bind(null, firstArg)` is JavaScript's built-in partial application.

## Immutability in practice

Changing shared data is where many bugs come from (Module 6: references). FP avoids it: functions return updated **copies**.

```js
const state = Object.freeze({
  user: Object.freeze({ name: "Ada", points: 10 }),
  history: Object.freeze(["joined"]),
});

const addPoints = (s, n) => ({
  ...s,
  user: { ...s.user, points: s.user.points + n },
  history: [...s.history, `+${n} points`],
});

const next = addPoints(state, 5);
console.log(state.user.points, next.user.points, next.history);
console.log(state.history === next.history, state.user === next.user);
```

The unchanged parts could even be **shared** between old and new versions; only the changed path is copied. That makes "undo" trivial (keep old states) and change detection fast (`===`).

Newer array methods help: `toSorted`, `toReversed`, `toSpliced` and `with(index, value)` all return new arrays.

## Memoization: caching pure functions

Because a pure function always gives the same output for the same input, its results can be **cached**:

```js
function memoize(fn) {
  const cache = new Map();
  return (arg) => {
    if (!cache.has(arg)) cache.set(arg, fn(arg));
    return cache.get(arg);
  };
}
let calls = 0;
const slowSquare = (n) => {
  calls++;
  return n * n;
};
const fastSquare = memoize(slowSquare);
console.log(fastSquare(9), fastSquare(9), fastSquare(9), "calls:", calls);
```

Only pure functions can be safely memoized: caching a function that reads the clock or a database would return stale answers.

## Where FP fits

FP shines for **data transformation**: turning API responses into view models, computing reports, reducers for state. Object-oriented design shines for **modelling things with identity and behaviour** (a bank account, a game character). Real JavaScript code mixes both: classes or modules on the outside, pure functions doing the work inside. Prefer whichever makes a given piece of code clearest.

## Patterns for text

A **regular expression** (regex) describes a **pattern** of text: "a sequence of digits", "something that looks like an email", "a word starting with a capital letter". They're used to validate input, search, extract parts and replace. Nearly every language has them with very similar syntax, so this is knowledge you'll keep.

```js
const date = /\d{4}-\d{2}-\d{2}/;
console.log(date.test("Due on 2026-10-14"));
console.log(date.test("Due tomorrow"));
console.log("Due on 2026-10-14".match(date)[0]);
```

A regex is written between slashes, `/pattern/flags`, or built from a string with `new RegExp("pattern", "flags")`.

## The building blocks

| Pattern | Matches |
|---|---|
| `abc` | the exact text "abc" |
| `.` | any one character (except a new line) |
| `\d`, `\w`, `\s` | a digit / a word character (letter, digit, `_`) / whitespace |
| `\D`, `\W`, `\S` | anything that is *not* a digit / word character / whitespace |
| `[aeiou]`, `[a-z]`, `[^0-9]` | one of these characters / a range / anything *except* these |
| `^` and `$` | the start and end of the text (or of a line, with the `m` flag) |
| `\b` | a word boundary |
| `a\|b` | `a` or `b` |
| `\.`, `\?`, `\(` | a literal `.`, `?` or `(` (special characters need a backslash) |

**Quantifiers** say how many times the previous item repeats:

| Quantifier | Means |
|---|---|
| `*` | 0 or more |
| `+` | 1 or more |
| `?` | 0 or 1 (optional) |
| `{3}`, `{2,4}`, `{2,}` | exactly 3, from 2 to 4, 2 or more |

```js
const checks = {
  zip: /^\d{5}$/,
  hexColour: /^#[0-9a-f]{6}$/i,
  username: /^[a-z][a-z0-9_]{2,15}$/,
  price: /^\$\d+(\.\d{2})?$/,
};
console.log(checks.zip.test("90210"), checks.zip.test("9021"));
console.log(checks.hexColour.test("#1E90FF"), checks.hexColour.test("#12345"));
console.log(checks.username.test("ada_99"), checks.username.test("9lives"));
console.log(checks.price.test("$12.50"), checks.price.test("$12.5"));
```

`^` and `$` anchor a pattern to the **whole** text; without them, `/\d{5}/` would also accept "abc123456xyz".

## Flags

| Flag | Effect |
|---|---|
| `i` | ignore case |
| `g` | global: find **all** matches (with `match`, `matchAll`, `replace`) |
| `m` | multiline: `^` and `$` match at every line |
| `s` | `.` also matches new lines |
| `u` | Unicode mode: correct handling of emoji and `\p{...}` classes (use it by default for text) |

## Groups: extracting parts

Parentheses make a **group**, which captures the part it matched. `(?<name>...)` gives the group a name:

```js
const text = "Order 1042 shipped on 2026-10-14 to Paris";
const m = text.match(/(?<year>\d{4})-(?<month>\d{2})-(?<day>\d{2})/);
console.log(m[0], m.index);
console.log(m.groups.day, m.groups.month, m.groups.year);

for (const match of "x=1, y=22, z=333".matchAll(/(\w)=(\d+)/g)) {
  console.log(match[1], "is", Number(match[2]));
}
```

- `str.match(re)` without `g` returns the first match with its groups (or `null`!); with `g`, an array of all matched texts, without groups.
- `str.matchAll(re)` (needs `g`) gives every match **with** its groups, for a `for...of` loop.
- `(?:...)` groups **without** capturing, just to apply a quantifier or `|`: `/(?:Mr|Ms|Dr)\. \w+/`.

## Replacing

```js
console.log("2026-10-14".replace(/(\d+)-(\d+)-(\d+)/, "$3/$2/$1"));
console.log("Smith, John".replace(/(?<last>\w+), (?<first>\w+)/, "$<first> $<last>"));
console.log("hello big world".replace(/\b\w/g, (letter) => letter.toUpperCase()));
console.log("Call 555-1234 or 555-9876".replaceAll(/\d{3}-\d{4}/g, "[hidden]"));
```

In the replacement text, `$1`, `$2`... (or `$<name>`) insert groups. A **function** as the replacement receives each match and returns its replacement: the most flexible option.

## Lookarounds

A **lookahead** `(?=...)` or **lookbehind** `(?<=...)` checks what comes next (or before) without including it in the match; `(?!...)` and `(?<!...)` are the negative versions. A classic use is "a password must contain a digit and a capital letter":

```js
const strong = /^(?=.*\d)(?=.*[A-Z]).{8,}$/;
console.log(strong.test("password1"), strong.test("Password1"));
console.log("Price: $42 and €17".match(/(?<=\$)\d+/)[0]);
```

## Pitfalls

- **`g` regexes remember their position.** A regex with the `g` flag has a `lastIndex`; calling `test` repeatedly on it continues from there, so the same call can alternate between `true` and `false`. Don't reuse a `g` regex for `test`; create the regex without `g` for yes/no checks.
- **Escape text you put into a regex.** Building `new RegExp(userText)` from user input breaks on special characters (`a+b`, `1.5`), and lets users inject patterns. Escape it first: `text.replace(/[.*+?^${}()|[\]\\]/g, "\\$&")`.
- **Catastrophic backtracking.** Nested quantifiers like `/(a+)+$/` can take exponential time on some inputs, freezing a page or a server (a "ReDoS" attack). Keep patterns simple, and avoid nesting `+` and `*` inside repeated groups.
- **Don't parse everything with regex.** HTML, JSON, programming languages and email addresses (fully) need real parsers. A regex for "looks roughly like an email" is fine; one for "is a valid email" doesn't exist.

## Unicode: characters versus code units

JavaScript strings are sequences of UTF-16 **code units**. Most characters are one unit, but emoji and many rare characters are **two** (a *surrogate pair*), and what a person sees as one character can be several code points (a thumbs-up plus a skin tone; a letter plus a combining accent):

```js
const s = "café 👍🏽";
console.log(s.length, [...s].length);
console.log("😀".charCodeAt(0), "😀".codePointAt(0), String.fromCodePoint(128512));
console.log("é".length, "é".normalize("NFD").length);
const graphemes = [...new Intl.Segmenter("en", { granularity: "grapheme" }).segment(s)];
console.log(graphemes.length);
```

- `.length` counts code units; `[...s]` (or `for...of`) iterates **code points**; `Intl.Segmenter` gives **grapheme clusters**, what users perceive as characters. Use it for "maximum 20 characters" limits on user names.
- `codePointAt` / `String.fromCodePoint` work with full Unicode values (use them instead of `charCodeAt` / `fromCharCode`, which only see code units).
- The same visible text can have different encodings ("é" as one code point, or "e" + an accent). `str.normalize()` makes them comparable; normalising and then removing accents with `/\p{Diacritic}/gu` makes accent-insensitive search possible.
- With the `u` flag, regexes understand Unicode classes: `\p{L}` (any letter, in any alphabet), `\p{Lu}` (uppercase letter), `\p{N}` (number), `\p{Emoji}`.

```js
console.log("Ünïcödé naïve café".normalize("NFD").replace(/\p{Diacritic}/gu, ""));
console.log("Grüße, Jürgen! 你好".match(/\p{L}+/gu));
```

const LINE = /^(?<date>\d{4}-\d{2}-\d{2}) (?<time>\d{2}:\d{2}:\d{2}) (?<level>[A-Z]+) \[(?<service>[\w-]+)\] (?<message>.*)$/;

function parseLog(text) {
  return text
    .split("\n")
    .map((line) => line.match(LINE))
    .filter((m) => m !== null)
    .map((m) => ({ ...m.groups }));
}

function errorsByService(text) {
  const counts = {};
  for (const entry of parseLog(text)) {
    if (entry.level === "ERROR") counts[entry.service] = (counts[entry.service] ?? 0) + 1;
  }
  return counts;
}

=== lesson js-dates-intl | Dates, times and internationalisation | 80
## Time is harder than it looks

Dates look simple until you meet time zones, daylight saving time, months of different lengths, leap years and the dozens of ways the world writes "14 October 2026". Most date bugs come from a handful of traps; this lesson shows them and the tools that avoid them.

## The Date object

A `Date` is a single moment in time, stored as the number of **milliseconds since 1 January 1970, 00:00 UTC** (the *Unix epoch*):

```js
const launch = new Date(Date.UTC(2026, 9, 14, 15, 30));
console.log(launch.getTime());
console.log(launch.toISOString());
console.log(launch.getUTCFullYear(), launch.getUTCMonth(), launch.getUTCDate(), launch.getUTCDay());
console.log(new Date("2026-10-14T15:30:00Z").getTime() === launch.getTime());
```

- `Date.now()` is the current time in milliseconds; `new Date()` the current moment as a `Date`.
- ⚠️ **Months count from 0**: `Date.UTC(2026, 9, 14)` is **October** 14. (Days of the month start at 1; days of the week run from 0 = Sunday.) This catches everyone.
- `toISOString()` gives the standard, sortable, unambiguous format `2026-10-14T15:30:00.000Z` (the `Z` means UTC). Use it to store and send dates; it's also what `JSON.stringify` produces.

## UTC versus local time

A `Date` has no time zone of its own; it's one instant. But methods like `getHours()` and `toString()` show it in the **computer's local time zone**, which differs between your users (and between your laptop and your server). The `getUTC...` methods use UTC, which is the same everywhere:

- **Store and compute in UTC** (timestamps, ISO strings).
- **Convert to local time only for display**, ideally with `Intl` (below).

Parsing has a trap too: `new Date("2026-10-14")` (date only) is read as **UTC** midnight, but `new Date("2026-10-14T09:00")` (date and time, no `Z`) as **local** time. Include the `Z` or an offset (`+02:00`) when you mean a specific instant. Invalid input doesn't throw; it gives an "Invalid Date" whose `getTime()` is `NaN`:

```js
const bad = new Date("next Tuesday");
console.log(bad.getTime(), Number.isNaN(bad.getTime()), String(bad));
```

## Date arithmetic

Add time by changing a part of the date; JavaScript rolls over months and years for you. Differences are millisecond subtractions:

```js
const day = 24 * 60 * 60 * 1000;
const start = new Date(Date.UTC(2026, 0, 30));
const later = new Date(start);
later.setUTCDate(later.getUTCDate() + 5);
console.log(later.toISOString().slice(0, 10));

const deadline = Date.UTC(2026, 11, 25);
const today = Date.UTC(2026, 9, 14);
console.log("Days left:", Math.round((deadline - today) / day));

const jan31 = new Date(Date.UTC(2026, 0, 31));
jan31.setUTCMonth(1);
console.log(jan31.toISOString().slice(0, 10));
```

The last line shows a famous surprise: "January 31 plus one month" asks for February 31, which rolls over to **March 3**. Month arithmetic needs a rule (clamp to the month's last day?) that you must choose. `Date` objects are also **mutable** (`setUTCDate` changes the object), so copy before changing: `new Date(original)`.

Also beware adding `24 * 60 * 60 * 1000` to a **local** date across a daylight-saving change: that day has 23 or 25 hours. Working in UTC avoids it.

## Formatting for people: Intl.DateTimeFormat

`Intl.DateTimeFormat` turns a date into text for any language and time zone, so you never assemble `"14/10/2026"` by hand:

```js
const when = new Date(Date.UTC(2026, 9, 14, 15, 5));
const full = new Intl.DateTimeFormat("en-US", { dateStyle: "full", timeStyle: "short", timeZone: "UTC" });
console.log(full.format(when));
console.log(new Intl.DateTimeFormat("en-GB", { dateStyle: "medium", timeZone: "UTC" }).format(when));
console.log(new Intl.DateTimeFormat("de-DE", { timeZone: "UTC" }).format(when));
console.log(new Intl.DateTimeFormat("ja-JP", { dateStyle: "long", timeZone: "Asia/Tokyo" }).format(when));
console.log(when.toLocaleTimeString("en-US", { timeZone: "America/New_York", hour: "numeric", minute: "2-digit" }));
```

Options choose the parts (`weekday`, `year`, `month`, `day`, `hour`...) and styles (`"long"`, `"short"`, `"numeric"`), and `timeZone` shows the moment as clocks read it in that place (Tokyo is already on the 15th). In a real app you'd usually leave out `timeZone` and the locale, so each user sees their own; the lessons fix them so everyone gets the same output.

## More of Intl

The `Intl` family handles everything that changes between languages and regions:

```js
const rtf = new Intl.RelativeTimeFormat("en", { numeric: "auto" });
console.log(rtf.format(-1, "day"), "|", rtf.format(3, "week"), "|", rtf.format(-2, "hour"));

const ordinal = new Intl.PluralRules("en-US", { type: "ordinal" });
const suffix = { one: "st", two: "nd", few: "rd", other: "th" };
console.log([1, 2, 3, 4, 11, 21, 22, 103].map((n) => n + suffix[ordinal.select(n)]).join(" "));

console.log(new Intl.ListFormat("en", { type: "conjunction" }).format(["tea", "coffee", "juice"]));
console.log(["Zoe", "émile", "adam", "Émilie"].sort(new Intl.Collator("fr").compare));
console.log(["file10", "file2", "file1"].sort(new Intl.Collator("en", { numeric: true }).compare));
```

- `RelativeTimeFormat`: "yesterday", "in 3 weeks", "2 hours ago".
- `PluralRules`: which plural form a number takes. English has two cardinal forms, but Arabic has six and Japanese one, so never hard-code `n === 1 ? "item" : "items"` in an app that will be translated.
- `ListFormat`: "a, b, and c" with each language's rules.
- `Collator`: alphabetical sorting that respects accents and languages, and **natural** number order (`file2` before `file10`).
- `NumberFormat` (Module 2) for numbers, currencies and units.

## The future: Temporal

`Date` has many design problems (mutable objects, 0-based months, no time zones). A modern replacement, **Temporal**, with separate types like `Temporal.PlainDate` and `Temporal.ZonedDateTime`, is arriving in browsers and Node.js. Until it's everywhere, many projects use a small library such as **date-fns** or **Luxon**. The rules above (UTC inside, local for display, ISO for storage) stay the same.

📚 **Go deeper:** MDN, "Date" and "Intl"; javascript.info, "Date and time" and "Intl"; tc39.es/proposal-temporal (the Temporal documentation).

=== lesson js-security-performance | Security and performance | 90
## Two things users never see, until they go wrong

Users don't notice security until their data leaks, or performance until the page freezes. Both are part of a professional's job from the first line of code, not an afterthought. This lesson collects the JavaScript-specific essentials.

## Never trust input

Everything that comes from outside your code is **untrusted**: form fields, URL parameters, API responses, uploaded files, even data in your own database (it came from users at some point). Validate it (type, length, format, range) where it **enters** your system, and remember that client-side checks are a convenience: the server must check again.

## Injection: when data becomes code

Most serious vulnerabilities share one cause: **text from a user is treated as code**.

- **XSS** (cross-site scripting): user text inserted as HTML (`innerHTML`) runs as script in other users' browsers. Use `textContent`, or escape HTML when you must build markup:

```js
function escapeHtml(text) {
  return text
    .replaceAll("&", "&amp;")
    .replaceAll("<", "&lt;")
    .replaceAll(">", "&gt;")
    .replaceAll('"', "&quot;")
    .replaceAll("'", "&#39;");
}
const comment = `<img src=x onerror="alert('hacked')">`;
console.log(`<p>${escapeHtml(comment)}</p>`);
```

  Frameworks like React escape text automatically; their escape hatches (`dangerouslySetInnerHTML`) are named to scare you. A **Content Security Policy** (an HTTP header) is a second line of defence: it tells the browser which scripts may run at all.
- **`eval` and `new Function`** run a string as JavaScript. With any user input involved, that's remote code execution. You'll almost never need them; linters forbid them.
- **SQL injection**: building a query by gluing in user text (`"... WHERE name = '" + name + "'"`) lets an attacker rewrite the query. Always use **parameterised queries** (`db.query("SELECT * FROM users WHERE name = $1", [name])`), which every database library supports. The same goes for shell commands built from user text.

## Prototype pollution

A JavaScript-specific attack: a "deep merge" or "set by path" function that copies keys from user-supplied JSON can be tricked with the key `__proto__`:

```js
function naiveMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (typeof source[key] === "object" && source[key] !== null) {
      if (typeof target[key] !== "object" || target[key] === null) target[key] = {};
      naiveMerge(target[key], source[key]);
    } else {
      target[key] = source[key];
    }
  }
  return target;
}
const attack = JSON.parse('{"__proto__": {"isAdmin": true}}');
naiveMerge({}, attack);
const someone = {};
console.log(someone.isAdmin);
```

Writing to `target["__proto__"]` reached `Object.prototype`, so **every object in the program** now has `isAdmin: true`. Defences: skip the keys `__proto__`, `constructor` and `prototype` when copying; use `Map` for user-keyed data; create dictionaries with `Object.create(null)`; validate input against a schema.

## Secrets and dependencies

- **Never put secrets in code** (API keys, database passwords): not in front-end JavaScript (anyone can read it in the browser), and not in a Git repository (history keeps them forever, and bots scan GitHub for keys within minutes). Keep them in **environment variables** (`process.env.API_KEY`), loaded from a `.env` file that's listed in `.gitignore`, and in your hosting platform's secret settings.
- **Dependencies are code you run.** Prefer few, well-maintained packages; run `npm audit`; update regularly; review what a new package pulls in (Module 11).
- **Use HTTPS everywhere**, set cookies with `HttpOnly`, `Secure` and `SameSite`, and never store passwords: servers store **hashes** made with a slow password-hashing function (bcrypt, scrypt, Argon2), never plain text or a fast hash.

The OWASP Top 10 (owasp.org) lists the most common web security risks; every web developer should read it once.

## Performance: measure first

The first rule of performance: **don't guess, measure.** Programmers are famously bad at predicting which part of their code is slow.

```js
function time(label, fn) {
  const start = performance.now();
  const result = fn();
  console.log(label, `${(performance.now() - start).toFixed(1)} ms`);
  return result;
}
const ids = Array.from({ length: 20000 }, (_, i) => i * 7);
const lookups = Array.from({ length: 20000 }, (_, i) => i * 3);
time("array includes", () => lookups.filter((x) => ids.includes(x)).length);
const idSet = new Set(ids);
time("Set has       ", () => lookups.filter((x) => idSet.has(x)).length);
```

`performance.now()` gives high-resolution milliseconds; `console.time(label)` / `console.timeEnd(label)` is a shortcut. In the browser, the developer tools' **Performance** panel records exactly where time goes, and **Lighthouse** audits a whole page's loading speed.

The example shows the most common real-world speed-up: the `includes` inside `filter` is a loop inside a loop (O(n²): 400 million comparisons); a `Set` makes each lookup instant (O(n) in total). **Choosing the right data structure** beats every micro-optimisation.

## Common performance wins

- **Avoid repeated work**: compute once outside the loop, cache (memoize) pure functions, build lookup Maps instead of searching arrays repeatedly.
- **Batch DOM changes**: build elements first and insert them in one `append(...)` or `replaceChildren(...)`; avoid reading layout (`offsetHeight`) and writing styles alternately in a loop ("layout thrashing").
- **Do less on rapid events**: debounce input, throttle scroll (Module 10).
- **Keep the main thread free**: move heavy computation to a **Web Worker** (DevQuest runs your code in one), split long tasks, and stream large data instead of loading it whole.
- **Load less**: lazy-load images (`<img loading="lazy">`) and rarely used code (`import()`), and keep an eye on bundle size.
- **Avoid memory leaks**: remove event listeners and clear intervals you no longer need; don't let caches grow forever (limit their size, or use `WeakMap` keyed by objects that may disappear).

And the counterweight: **premature optimisation** makes code harder to read for no measurable gain. Write clear code first, measure, then optimise the part that matters.

## The bugs JavaScript lets through

Many of the bugs in this course were **type** bugs: a string where a number was expected (`"5" + 3`), a misspelt property that quietly gave `undefined`, a function called with the wrong arguments, a possibly-`null` value used as if it were always there. JavaScript only discovers these when the code runs, and often silently.

**TypeScript** is JavaScript with **type annotations** checked by a compiler *before* the code runs. Every JavaScript program is valid TypeScript; you add types where they help. The compiler (`tsc`) checks them, then **removes them**, producing ordinary JavaScript. Most professional JavaScript today is written in TypeScript: it's the default in Angular, recommended for React, Vue and Node projects, and used by VS Code itself.

```ts
function totalPrice(items: { price: number; qty: number }[], taxRate: number): number {
  return items.reduce((sum, item) => sum + item.price * item.qty, 0) * (1 + taxRate);
}
console.log(totalPrice([{ price: 10, qty: 2 }], 0.2));
```

With this, `totalPrice([{ price: "10", qty: 2 }], 0.2)` or `totalPrice(items)` (missing argument) are **compile errors**, shown as red squiggles in your editor before you ever run anything, and `item.prcie` is an error instead of `undefined`. (DevQuest runs TypeScript by removing the types, so it doesn't report type errors itself; the TypeScript course adds a real type checker. Install TypeScript locally to see them: `npm install --save-dev typescript` and `npx tsc`.)

## Basic types and inference

```ts
let title: string = "DevQuest";
let level: number = 3;
let done: boolean = false;
let tags: string[] = ["js", "ts"];
let point: [number, number] = [3, 4];
let anything: unknown = JSON.parse('{"a": 1}');

let score = 10;
const name = "Ada";
console.log(title, level, done, tags, point, anything, score, name);
```

You rarely need to write types for variables: TypeScript **infers** them from the value (`score` is a `number`, so `score = "ten"` is an error). Annotate function **parameters** and public APIs; let inference do the rest.

Prefer `unknown` over `any` for values you don't know yet (like parsed JSON): `any` switches type checking off, while `unknown` forces you to check the value before using it.

## Describing objects: type and interface

```ts
type User = {
  id: number;
  name: string;
  email?: string;
  readonly createdAt: string;
};

interface Product {
  sku: string;
  price: number;
}

function describe(user: User): string {
  return `${user.name} <${user.email ?? "no email"}>`;
}
console.log(describe({ id: 1, name: "Ada", createdAt: "2026-10-14" }));
```

`?` marks an optional property; `readonly` one that can't be reassigned. `type` and `interface` are mostly interchangeable for objects (interfaces can be extended and merged; `type` can also name unions and other types). Teams pick one style.

## Unions and narrowing

A **union** type says a value is one of several types. TypeScript then makes you **narrow** it (check which one it is) before using type-specific features:

```ts
type Shape =
  | { kind: "circle"; r: number }
  | { kind: "rect"; w: number; h: number };

function area(shape: Shape): number {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.r ** 2;
    case "rect":
      return shape.w * shape.h;
  }
}

function label(id: string | number): string {
  return typeof id === "number" ? `#${id.toFixed(0)}` : id.toUpperCase();
}

console.log(area({ kind: "rect", w: 2, h: 3 }).toFixed(1), label(7), label("ab"));
```

The `kind` property makes `Shape` a **discriminated union**: inside `case "circle"`, TypeScript knows `shape.r` exists. Add a new shape kind and forget a case, and the compiler tells you. That's the "replace conditionals" lesson from Module 9, checked by the computer. Literal types like `"circle"` and unions like `"small" | "medium" | "large"` replace error-prone magic strings.

`strictNullChecks` (part of `"strict": true`, which every project should enable) makes `null` and `undefined` their own types, so "Cannot read properties of undefined" becomes a compile-time error unless you've checked first.

## Generics: types with parameters

Some functions work for **any** type, but should keep track of **which** one:

```ts
function first<T>(items: T[]): T | undefined {
  return items[0];
}
function groupBy<T, K extends string>(items: T[], key: (item: T) => K): Record<K, T[]> {
  const groups = {} as Record<K, T[]>;
  for (const item of items) (groups[key(item)] ??= []).push(item);
  return groups;
}
const n = first([3, 1, 2]);
const s = first(["a", "b"]);
console.log(n, s, groupBy([1, 2, 3, 4], (x) => (x % 2 ? "odd" : "even")));
```

`T` is a **type parameter**: `first([3, 1, 2])` returns a `number | undefined`, `first(["a"])` a `string | undefined`. `Array<T>`, `Promise<T>`, `Map<K, V>` are all generic types you've been using.

## Types and classes

```ts
class Account {
  private balance = 0;

  constructor(public readonly owner: string) {}

  deposit(amount: number): number {
    if (amount <= 0) throw new RangeError("Deposits must be positive");
    this.balance += amount;
    return this.balance;
  }
}
const acc = new Account("Ada");
console.log(acc.owner, acc.deposit(50));
```

`public readonly owner` in the constructor's parameters declares and assigns a property in one go. TypeScript's `private` is checked only at compile time; JavaScript's `#private` (Module 8) is enforced at runtime too. Classes can `implements` an interface, making the "interfaces by agreement" from Module 9 checked.

- Libraries ship type definitions (or have them in `@types/...` packages), giving you autocomplete and checks for code you didn't write.
- Types describe your code; they don't validate data at runtime. Data from outside (JSON, forms) still needs runtime checks (libraries like Zod do both at once).

## More than a language

Knowing JavaScript is half the job. The other half is the **toolchain** professionals use to write, check, test, build and ship it. You don't need to master every tool now, but you should recognise them, know what problem each solves, and be able to set up a modern project.

## Starting a project

```
npm create vite@latest my-app
cd my-app
npm install
npm run dev
```

**Vite** creates a ready-made project (plain JavaScript, TypeScript, React, Vue, Svelte...), and runs a **dev server** that reloads the page the instant you save a file. `npm run build` produces an optimised version for production: a **bundler** combines your modules, removes unused code ("tree shaking"), minifies it and adds content hashes to file names for caching. DevQuest itself is built with Vite.

## Formatting and linting

- **Prettier** formats code automatically (indentation, quotes, line breaks), so nobody argues about style and diffs only show real changes. Editors run it on save.
- **ESLint** finds likely bugs and bad patterns: unused variables, `==` instead of `===`, a missing `await`, unreachable code, a `React` hook used wrongly. Rules can be errors (block CI) or warnings.

```
npm install --save-dev prettier eslint @eslint/js
npx prettier --write .
npx eslint .
```

Together they turn whole categories of code review comments into automatic checks.

## Environment configuration

Configuration that differs between your laptop, the test server and production (API URLs, keys, feature flags) goes in **environment variables**, not in code:

```
# .env  (listed in .gitignore, never committed)
API_URL=https://api.example.com
API_KEY=sk_test_123
```

Node reads them as `process.env.API_KEY` (Node 20.6+ can load a `.env` file with `node --env-file=.env app.js`); Vite exposes `VITE_...` variables to the browser code as `import.meta.env.VITE_API_URL` (anything sent to the browser is public!). Commit a `.env.example` with the names but fake values, so others know what to set.

## Testing at every level

| Level | Tests | Typical tools |
|---|---|---|
| **Unit** | single functions and classes, in isolation | Vitest, Jest, `node:test` |
| **Integration** | several parts together: API + database, component + store | the same runners, plus test databases |
| **End-to-end (E2E)** | the real app in a real browser, like a user | Playwright, Cypress |

Many fast unit tests, fewer integration tests, a handful of slow E2E tests for critical journeys (sign-up, checkout): the **testing pyramid**.

## Continuous integration

**CI** runs your checks automatically on every push and pull request, so broken code never reaches the main branch. With GitHub Actions, it's a file in your repository, `.github/workflows/ci.yml`:

```
name: CI
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npx eslint .
      - run: npm test
      - run: npm run build
```

Teams add **pre-commit hooks** (Husky with lint-staged) to run formatting and linting before each commit, and **deployment** steps that publish the app when the main branch passes.

## Debugging and source maps

Bundled, minified code is unreadable, but **source maps** link it back to your original files, so the browser's debugger and error stack traces show your real code and line numbers. Error-monitoring services (Sentry, for example) use them to report production crashes with the exact line.

## The wider ecosystem

You'll meet these names constantly; here's what they are:

- **Front-end frameworks**: React (most used), Vue, Svelte, Angular, Solid. Full-stack frameworks built on them: Next.js, Nuxt, SvelteKit, Remix. They all apply the "render from state" idea of Module 11.
- **Back end on Node**: Express (minimal, classic), Fastify (fast), NestJS (structured, Angular-like); ORMs and query builders such as Prisma and Drizzle to talk to databases.
- **Other runtimes**: Deno and Bun run JavaScript and TypeScript like Node, with built-in tooling.

function parseEnv(text) {
  const env = {};
  text.split("\n").forEach((raw, i) => {
    const line = raw.trim();
    if (line === "" || line.startsWith("#")) return;
    const m = line.match(/^([A-Za-z_][A-Za-z0-9_]*)\s*=\s*(.*)$/);
    if (!m) throw new Error(`Invalid line ${i + 1}`);
    let value = m[2];
    if (value.startsWith('"') && value.endsWith('"') && value.length >= 2) {
      value = value.slice(1, -1).replaceAll("\\n", "\n");
    } else if (value.startsWith("'") && value.endsWith("'") && value.length >= 2) {
      value = value.slice(1, -1);
    } else {
      value = value.split(" #")[0].trim();
    }
    env[m[1]] = value;
  });
  return env;
}

::solution
const escapeHtml = (text) =>
  String(text).replaceAll("&", "&amp;").replaceAll("<", "&lt;").replaceAll(">", "&gt;").replaceAll('"', "&quot;").replaceAll("'", "&#39;");

function lookup(data, path) {
  let value = data;
  for (const key of path.split(".")) {
    if (value === null || typeof value !== "object" || !Object.hasOwn(value, key)) return "";
    value = value[key];
  }
  return value ?? "";
}

function templateRender(template, data) {
  return template
    .replace(/\{\{\{\s*([\w.]+)\s*\}\}\}/g, (_, path) => String(lookup(data, path)))
    .replace(/\{\{\s*([\w.]+)\s*\}\}/g, (_, path) => escapeHtml(lookup(data, path)));
}

::starter

}
::solution
const WEEK = 7 * 24 * 60 * 60 * 1000;
const weekday = new Intl.DateTimeFormat("en-US", { weekday: "long", timeZone: "UTC" });
const plural = (n, word) => `${n} ${word}${n === 1 ? "" : "s"}`;

function weeklyReport(events, now) {
  const end = now.getTime();
  const recent = events.filter((e) => {
    const t = new Date(e.at).getTime();
    return t >= end - WEEK && t < end;
  });
  if (recent.length === 0) return ["Total: 0 events"];
  const byUser = new Map();
  for (const e of recent) {
    const counts = byUser.get(e.user) ?? { commit: 0, review: 0, deploy: 0, total: 0 };
    counts[e.type]++;
    counts.total++;
    byUser.set(e.user, counts);
  }
  const lines = [...byUser]
    .sort((a, b) => b[1].total - a[1].total || a[0].localeCompare(b[0]))
    .map(([user, c]) => {
      const parts = ["commit", "review", "deploy"].filter((type) => c[type] > 0).map((type) => plural(c[type], type));
      return `${user}: ${parts.join(", ")}`;
    });
  const byDay = new Map();
  for (const e of [...recent].sort((a, b) => a.at.localeCompare(b.at))) {
    const day = weekday.format(new Date(e.at));
    byDay.set(day, (byDay.get(day) ?? 0) + 1);
  }
  let busiest = null;
  for (const [day, n] of byDay) if (busiest === null || n > byDay.get(busiest)) busiest = day;
  lines.push(`Total: ${recent.length} events, busiest day ${busiest}`);
  return lines;
}
