## When things go wrong

Some problems aren't bugs in your code but facts of life: the user types "abc" where you wanted a number, a file is missing, the network is down, a server sends broken JSON. A program that crashes on the first surprise isn't professional; it should **detect** the problem, **report** it clearly and, where possible, **recover**.

When JavaScript hits a problem it can't handle, it **throws** an *exception*: an error object that interrupts normal execution and travels **up the call stack**, from the function where it happened to its caller, and its caller's caller, until some code **catches** it. If nothing catches it, the program stops (in Node.js) or the error is reported in the console (in a browser).

## try and catch

```js
try {
  console.log("Parsing...");
  const settings = JSON.parse("{broken json");
  console.log("This line is skipped");
} catch (error) {
  console.log("Could not read the settings:", error.message);
}
console.log("The program carries on.");
```

- The code in `try` runs normally until something throws.
- At that moment, the rest of the `try` block is **skipped** and the `catch` block runs, with the error object in the variable you named (`error`, or `err`, or `e`).
- If nothing throws, the `catch` block is skipped entirely.
- Either way, the program continues after the whole `try`/`catch`.

If you don't need the error object, you can leave out the variable: `catch { ... }`.

## The error object

Errors are objects with useful properties:

```js
try {
  const user = null;
  console.log(user.name);
} catch (error) {
  console.log(error.name);
  console.log(error.message);
  console.log(error instanceof TypeError, error instanceof Error);
  console.log(String(error));
}
```

- `name`: the kind of error (`TypeError`, `RangeError`...).
- `message`: what went wrong, in words.
- `stack`: the call stack at the moment the error was created, as text (what you see printed under uncaught errors). Log it when you need to know where an error came from.

`instanceof` checks the error's type, which lets you handle different problems differently.

## finally: code that always runs

A `finally` block runs **whether or not** an error happened, and even if the `try` block `return`s. Use it for clean-up that must never be skipped: closing a file, hiding a "loading..." spinner, releasing a lock.

```js
function loadData(text) {
  console.log("Show spinner");
  try {
    return JSON.parse(text);
  } catch {
    return null;
  } finally {
    console.log("Hide spinner");
  }
}
console.log(loadData('{"ok": true}'));
console.log(loadData("nope"));
```

## Throwing your own errors

Your functions should throw when they're asked to do something impossible or invalid. Use `throw` with an `Error` object:

```js
function withdraw(balance, amount) {
  if (typeof amount !== "number" || Number.isNaN(amount)) {
    throw new TypeError(`Amount must be a number, got ${amount}`);
  }
  if (amount <= 0) {
    throw new RangeError(`Amount must be positive, got ${amount}`);
  }
  if (amount > balance) {
    throw new Error(`Insufficient funds: balance ${balance}, requested ${amount}`);
  }
  return balance - amount;
}

for (const amount of [30, -5, 500, "ten"]) {
  try {
    console.log("New balance:", withdraw(100, amount));
  } catch (error) {
    console.log(`${error.name}: ${error.message}`);
  }
}
```

Good habits:

- **Throw `Error` objects**, never plain strings: `throw "oops"` works, but has no `name`, no `stack`, and breaks code that reads `error.message`.
- **Pick a fitting type**: `TypeError` for a value of the wrong type, `RangeError` for a number outside the allowed range, `Error` for everything else (or your own error classes, below).
- **Write messages that help**: say what was expected and include the bad value. "Invalid input" helps nobody; `Amount must be positive, got -5` points straight at the problem.
- **Fail fast**: check inputs at the start of a function (guard clauses that throw) so bad data is stopped where it enters, not three functions later.

## Errors travel up the call stack

An error thrown deep inside nested calls skips all the code in between until it reaches a `catch`:

```js
function readAge(text) {
  const age = Number(text);
  if (!Number.isInteger(age) || age < 0) throw new RangeError(`Not a valid age: "${text}"`);
  return age;
}
function describeUser(name, ageText) {
  const age = readAge(ageText);
  return `${name} is ${age}`;
}
function main() {
  for (const [name, age] of [["Ada", "36"], ["Bob", "-1"], ["Cy", "twelve"]]) {
    try {
      console.log(describeUser(name, age));
    } catch (error) {
      console.log(`Skipped ${name}: ${error.message}`);
    }
  }
}
main();
```

`readAge` doesn't need to know how errors will be reported, and `describeUser` doesn't need any error handling at all. **Catch errors where you can do something useful about them**: usually near the top, where you can show a message, skip an item or try again. Catching everywhere just to log and rethrow clutters code.

## Catch only what you expect

A `catch` block catches **everything**, including bugs you didn't anticipate. Swallowing those hides problems. Check the type, and rethrow what you can't handle:

```js
function parseConfig(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    if (error instanceof SyntaxError) {
      return {};
    }
    throw error;
  }
}
console.log(parseConfig("{oops}"));
```

The worst pattern of all is an empty `catch {}` around a large block: the program fails silently and nobody ever knows why.

## Custom error classes

For your own application's errors, define error **classes**. You'll learn classes properly in Module 8; for now, this pattern is all you need: a new kind of error that extends JavaScript's `Error`, with its own name and any extra properties:

```js
class ValidationError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

function validateSignup({ email, age }) {
  if (!email.includes("@")) throw new ValidationError("Email needs an @", "email");
  if (age < 13) throw new ValidationError("You must be at least 13", "age");
  return true;
}

try {
  validateSignup({ email: "ada.example.com", age: 36 });
} catch (error) {
  if (error instanceof ValidationError) {
    console.log(`Please fix the ${error.field} field: ${error.message}`);
  } else {
    throw error;
  }
}
```

Now calling code can tell "the user typed something invalid" (show a friendly message next to the field) from "the program has a bug" (let it crash and get reported).

## Wrapping errors with a cause

When you catch a low-level error and throw a higher-level one, keep the original as its `cause`, so the details aren't lost:

```js
function loadSettings(text) {
  try {
    return JSON.parse(text);
  } catch (error) {
    throw new Error("Could not load the settings file", { cause: error });
  }
}
try {
  loadSettings("{bad");
} catch (error) {
  console.log(error.message);
  console.log("Because:", error.cause.message);
}
```

## Throw, or return a special value?

Not every failure deserves an exception. A rough guide:

- **Expected, common outcomes** are normal return values: `find` returns `undefined` when nothing matches; a `parseNumber` helper might return `null` for "not a number". The caller checks the result.
- **Invalid use or impossible situations** throw: a negative quantity, a missing required setting, a broken invariant. The caller shouldn't have to check for them on every call.

One warning for later: `try`/`catch` only catches errors thrown **while its block is running**. An error thrown later, inside a `setTimeout` callback or a promise, escapes it. Module 10 shows how to catch errors in asynchronous code.

function parseLine(line) {
  const parts = line.split(" x ");
  if (parts.length !== 2) throw new Error(`expected "quantity x price", got "${line}"`);
  const qty = Number(parts[0]);
  const price = Number(parts[1]);
  if (!Number.isInteger(qty) || qty < 1) throw new RangeError(`bad quantity "${parts[0]}"`);
  if (Number.isNaN(price) || price < 0) throw new RangeError(`bad price "${parts[1]}"`);
  return qty * price;
}

function safeTotal(lines) {
  let total = 0;
  const errors = [];
  for (const [i, line] of lines.entries()) {
    try {
      total += parseLine(line);
    } catch (error) {
      errors.push(`Line ${i + 1}: ${error.message}`);
    }
  }
  return { total: Math.round(total * 100) / 100, errors };
}

class InsufficientFundsError extends Error {
  constructor(message, shortfall) {
    super(message);
    this.name = "InsufficientFundsError";
    this.shortfall = shortfall;
  }
}

function transfer(accounts, from, to, amount) {
  if (typeof amount !== "number" || !(amount > 0)) throw new RangeError("Amount must be a positive number");
  for (const name of [from, to]) {
    if (!(name in accounts)) throw new Error(`Unknown account: ${name}`);
  }
  if (accounts[from] < amount) {
    const shortfall = amount - accounts[from];
    throw new InsufficientFundsError(`${from} is short by ${shortfall}`, shortfall);
  }
  accounts[from] -= amount;
  accounts[to] += amount;
  return accounts;
}

## Debugging is a skill

Every programmer spends a large share of their time finding out why code doesn't do what they expect. Good debuggers aren't lucky; they're **systematic**. They treat a bug like a scientist treats a puzzle:

1. **Reproduce it.** Find exact steps or inputs that make the bug happen every time. A bug you can't trigger, you can't confirm you've fixed.
2. **Read the evidence.** The error message, the line, the stack trace, the wrong output. What exactly happens, versus what should?
3. **Form a hypothesis.** "I think `total` is a string, so `+` joins instead of adding."
4. **Test it.** Print the value, or pause the program and look. Was the guess right?
5. **Fix, then verify.** Run the reproduction again, and the tests, to confirm it's fixed and nothing else broke.

The trap is skipping to step 5: changing things at random until the symptom disappears. That often hides the bug instead of fixing it.

## Logging like a professional

`console.log` is the simplest debugging tool, and pros use it all the time. A few tricks make it far more useful:

```js
const price = "19.99";
const qty = 3;
console.log({ price, qty });
console.log(typeof price, typeof qty);
console.log("total:", price * qty, "joined:", price + qty);
```

- `console.log({ price, qty })` uses shorthand properties to print each value **with its name**. No more guessing which number is which.
- Print `typeof` when you suspect a type problem.
- Label every log, so you can find it in a long output.

More of the console toolkit:

```js
const orders = [
  { id: 1, item: "Book", qty: 2 },
  { id: 2, item: "Pen", qty: 10 },
];
console.table(orders);
console.group("Processing order 1");
console.log("checking stock");
console.log("charging card");
console.groupEnd();
for (let i = 0; i < 3; i++) console.count("loop ran");
console.assert(orders.length === 3, "expected 3 orders, got", orders.length);
```

- `console.table` shows arrays of objects as a table.
- `console.group` / `groupEnd` indent related messages.
- `console.count(label)` counts how often a line is reached. Great for "is this loop running too often?"
- `console.assert(condition, message)` prints only when the condition is **false**.
- `console.time("label")` / `console.timeEnd("label")` measure how long code takes.
- `console.error` and `console.warn` stand out in red and yellow in browsers, and in Node they go to the separate error stream.
- `console.trace()` prints the current call stack: "how did I get here?"

Remove debugging logs before you commit your code (or use a proper logging library in larger apps, where log levels let you switch detail on and off).

## The debugger: pausing a running program

Logging shows you what you thought to print. A **debugger** lets you **pause** the program at any line and look at *everything*: every variable, the whole call stack, and then continue step by step. Every browser has one built in:

1. Open the developer tools (`F12`) and go to the **Sources** tab (Firefox: **Debugger**).
2. Open your script file and click a line number to set a **breakpoint** (a blue marker).
3. Do whatever triggers the code (reload, click the button...). Execution pauses on that line, *before* it runs.
4. Look at the **Scope** panel (all variables and their values) and the **Call Stack** panel (who called this function), and hover over variables in the code.
5. Step through:
   - **Step over** (F10): run this line, pause on the next.
   - **Step into** (F11): go inside the function called on this line.
   - **Step out** (Shift+F11): finish this function, pause back in its caller.
   - **Resume** (F8): run until the next breakpoint.

Useful extras: right-click a line number for a **conditional breakpoint** (pause only when, say, `i === 99`) or a **logpoint** (prints a message without editing your code); tick **Pause on exceptions** to stop right where an error is thrown; add **watch** expressions to track values as you step.

You can also write `debugger;` in your code: when developer tools are open, execution pauses there.

For Node.js, VS Code has the same debugger built in: open your file, click in the margin to set a breakpoint, and press `F5` (Run and Debug → Node.js). Or run `node --inspect-brk app.js` and open `chrome://inspect` in Chrome.

## Narrowing it down

When you don't know where a bug is, shrink the search space:

- **Divide and conquer**: check the value halfway through the process. Correct there? The bug is in the second half. Repeat. Ten checks can find one bad line among a thousand.
- **Make a minimal reproduction**: copy the failing case into a new file and delete everything that isn't needed for the bug to happen. Often the bug becomes obvious along the way, and if not, you have the perfect example to show a colleague or post online.
- **Check your assumptions**: the bug is usually in the part you were *sure* was fine. Print it anyway.
- **Explain it out loud** ("rubber duck debugging"): describing the code line by line to someone, or to a rubber duck, forces you to notice the step that doesn't do what you assumed.
- **Take a break**: fresh eyes solve in five minutes what tired ones couldn't in an hour. That's not a joke; it's common professional advice.

## A field guide to JavaScript bugs

Most bugs you'll meet belong to a few families. When stuck, run down this list:

| Symptom | Usual suspect |
|---|---|
| `"5" + 3` gives `"53"`, totals look like long numbers | a string where you expected a number (from input, JSON or the DOM) |
| a value is unexpectedly `undefined` | a typo in a property name (`user.nmae` gives undefined silently), a missing `return`, or a function's result not stored |
| `NaN` appears and spreads | maths on `undefined` or text that isn't a number |
| a loop does one iteration too many or too few | `<=` versus `<` (off by one) |
| data changes "by itself" | two names for one object (aliasing), or a function mutating its argument |
| the condition is always true | `=` instead of `===`, or `x === "a" \|\| "b"` |
| sorted numbers in the wrong order | `sort()` without a comparator |
| a value is missing right after you fetched it | asynchronous code not awaited (Module 10) |
| `this` is undefined in a callback | a method passed as a callback (Module 8) |

## A worked example

This function should return the average score, but prints a strange result:

```js
function average(scores) {
  let total = 0;
  for (let i = 0; i <= scores.length; i++) {
    total += scores[i];
  }
  return total / scores.length;
}
console.log(average([80, 90, 100]));
```

The result is `NaN`. Hypothesis: something in the sum isn't a number. Add a log inside the loop, `console.log({ i, score: scores[i], total })`, and run again: the last iteration shows `i: 3, score: undefined`. The loop runs one step too far, because `<=` should be `<`. Adding `undefined` to a number gives `NaN`, and `NaN` poisons the total. The fix is one character; finding it took one well-placed log. (Better still: `for (const score of scores)` can't go out of bounds at all.)

=== lesson js-testing | Automated testing | 90
## Why test automatically?

You've been testing all along: running your code and checking the output by eye. That works for ten lines. For a real application it fails, because every change can break something you checked last week, and nobody re-checks everything by hand every time.

**Automated tests** are small programs that run your code with known inputs and check the results, in seconds, every time you change anything. Professional teams run thousands of them before every release (DevQuest itself has a test suite you can see in its `tests/` folder). They give you:

- **Confidence to change code**: if the tests still pass after a refactoring, you didn't break anything they cover.
- **Regression protection**: a test written for a fixed bug makes sure it never comes back.
- **Documentation**: tests show exactly how a function is meant to be used and what it returns at the edges.
- **Better design**: code that's easy to test (pure functions, few hidden dependencies) is usually easier to understand too.

## assert: the building block

You've used `assert` since Module 5. In Node.js it's a built-in module you import: `import assert from "node:assert/strict";`. The essential checks:

| Check | Passes when |
|---|---|
| `assert.strictEqual(actual, expected)` | `actual === expected` |
| `assert.deepStrictEqual(actual, expected)` | arrays/objects have equal contents |
| `assert.ok(value)` | `value` is truthy |
| `assert.throws(fn, expected)` | calling `fn` throws a matching error |
| `assert.match(text, /regex/)` | the text matches the pattern |
| `assert.notStrictEqual(a, b)` | `a !== b` |

The `expected` argument of `assert.throws` can be an error class (`RangeError`), a regular expression matched against the message (`/positive/`), or an object of properties to compare (`{ name: "TypeError", message: "..." }`). Note that you pass a **function** that makes the call: `assert.throws(() => withdraw(-5))`. Writing `assert.throws(withdraw(-5))` would call `withdraw` immediately, outside the check, and crash.

## Test runners: test() and describe()

A **test runner** organises checks into named tests, runs them all, and reports which passed. Node.js has one built in, `node:test`; DevQuest provides the same `test` and `describe` functions:

```js
function slugify(title) {
  return title.trim().toLowerCase().replaceAll(" ", "-");
}

test("lowercases and joins words with dashes", () => {
  assert.strictEqual(slugify("Hello World"), "hello-world");
});

test("removes surrounding spaces", () => {
  assert.strictEqual(slugify("  Hi  "), "hi");
});

describe("edge cases", () => {
  test("empty title gives an empty slug", () => {
    assert.strictEqual(slugify(""), "");
  });
  test("double spaces", () => {
    assert.strictEqual(slugify("a  b"), "a-b");
  });
});
```

Each test runs separately, so one failure doesn't stop the others, and the report says exactly which behaviour broke. Run it: the last test fails, because `slugify` turns two spaces into two dashes. Is that a bug in the code, or a wrong expectation in the test? Deciding that is part of testing.

On your own computer, put tests in files named like `slugify.test.js`, start them with:

```
import { test, describe } from "node:test";
import assert from "node:assert/strict";
import { slugify } from "./slugify.js";
```

and run `node --test`. Node finds the test files and runs them all. Many projects use **Vitest** or **Jest** instead, which work the same way with a different style of checks: `expect(slugify("Hi")).toBe("hi")`. Learn one and the others take an afternoon.

## Writing good tests

**Arrange, Act, Assert.** Most tests have three steps: set up the inputs, call the code, check the result. Keep them visibly separate:

```js
function addItem(cart, item, qty) {
  return { ...cart, [item]: (cart[item] ?? 0) + qty };
}

test("adding an item that's already in the cart increases its quantity", () => {
  const cart = { apple: 2 };
  const updated = addItem(cart, "apple", 3);
  assert.deepStrictEqual(updated, { apple: 5 });
  assert.deepStrictEqual(cart, { apple: 2 }, "the original cart is unchanged");
});
```

More habits of good testers:

- **One behaviour per test**, named as a sentence about that behaviour. When `"rejects negative amounts"` fails, you know what broke without reading the code.
- **Test the edges, not just the middle.** Bugs live at boundaries. For any function, ask about:
  - empty input (`""`, `[]`, `{}`), zero, one item;
  - the boundaries of every rule (exactly 18, 17, 19);
  - negative numbers, very large numbers, decimals;
  - invalid input (wrong type, missing values) and the errors it should throw;
  - text with spaces, capitals, accents and emoji.
- **Keep tests independent**: no test should depend on another having run first. `beforeEach(() => { ... })` inside a `describe` can set up fresh data before every test.
- **Make them fast and deterministic**: same result every run, no real network, no waiting, no randomness (see test doubles below).

## Test-driven development

In **TDD**, you write the test *before* the code:

1. **Red**: write a test for the next small behaviour. Run it; watch it fail (proving the test can fail).
2. **Green**: write the simplest code that makes it pass.
3. **Refactor**: tidy the code, with the tests guarding you.

Then repeat with the next behaviour. TDD forces you to decide what the code should do before getting lost in how, and leaves you with a full test suite as a side effect. Even if you don't practise it strictly, the rhythm of small steps with tests is how many professionals work.

## Test doubles: replacing what you can't control

Some code depends on things that make tests slow or unpredictable: the current time, random numbers, the network, a database, sending emails. The trick is **dependency injection**: instead of the function reaching out for the dependency itself, it **receives** it as a parameter. In tests, you pass in a stand-in, called a **test double**.

```js
function greeting(now = new Date()) {
  const hour = now.getHours();
  if (hour < 12) return "Good morning";
  if (hour < 18) return "Good afternoon";
  return "Good evening";
}

test("before noon it's morning", () => {
  assert.strictEqual(greeting(new Date(2026, 0, 1, 9, 0)), "Good morning");
});
test("at 18:00 it's evening", () => {
  assert.strictEqual(greeting(new Date(2026, 0, 1, 18, 0)), "Good evening");
});
```

Real callers just call `greeting()`, and the default uses the real clock. Tests pass a fixed date, so they give the same answer at any time of day.

Kinds of doubles you'll hear about:

- a **stub** returns canned answers (`() => 0.5` instead of `Math.random`);
- a **fake** is a simple working replacement (an in-memory list instead of a database);
- a **spy** records how it was called, so the test can check that something *happened*:

```js
function makeSpy() {
  const calls = [];
  const spy = (...args) => {
    calls.push(args);
  };
  spy.calls = calls;
  return spy;
}

function placeOrder(order, sendEmail) {
  if (order.items.length === 0) throw new Error("Empty order");
  sendEmail(order.customer, `Thanks for your order of ${order.items.length} item(s)!`);
  return "placed";
}

test("placing an order emails the customer once", () => {
  const send = makeSpy();
  placeOrder({ customer: "ada@example.com", items: ["book"] }, send);
  assert.deepStrictEqual(send.calls, [["ada@example.com", "Thanks for your order of 1 item(s)!"]]);
});
```

Libraries such as Vitest and Jest have spies and module mocking built in (`vi.fn()`, `jest.fn()`), and `node:test` has `mock.fn()`; they're all this same idea.

## How do you know your tests are good?

**Code coverage** tools (`node --test --experimental-test-coverage`, `vitest --coverage`) show which lines your tests ran. Lines never run are certainly untested, but running a line isn't the same as checking its result.

A sharper idea is **mutation testing**: deliberately put a small bug (a *mutant*) in the code, such as `<` instead of `<=`, and see whether any test fails. If none does, your tests have a gap. Tools like Stryker do this automatically. The exercises below work exactly like that: your tests must pass on the correct code and catch every one of several buggy versions.

::solution
class ParseError extends Error {
  constructor(message, field) {
    super(message);
    this.name = "ParseError";
    this.field = field;
  }
}

function parseOrder(text) {
  const parts = text.split(";");
  if (parts.length !== 3) throw new ParseError(`Expected 3 fields, got ${parts.length}: "${text}"`, "line");
  const [id, email, qtyText] = parts.map((p) => p.trim());
  if (!id.startsWith("ORD-")) throw new ParseError(`Bad order id "${id}"`, "id");
  if (!email.includes("@")) throw new ParseError(`Bad email "${email}"`, "email");
  const qty = Number(qtyText);
  if (!Number.isInteger(qty) || qty < 1 || qty > 100) throw new ParseError(`Bad quantity "${qtyText}"`, "qty");
  return { id, email, qty };
}
