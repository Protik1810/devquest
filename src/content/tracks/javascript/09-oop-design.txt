## Building on an existing class

Often one kind of thing is a **special case** of another: a savings account *is a* bank account that also earns interest; a manager *is an* employee who also has a team. **Inheritance** lets a class take everything from another class and add or change only what's different:

```js
class Employee {
  constructor(name, salary) {
    this.name = name;
    this.salary = salary;
  }
  describe() {
    return `${this.name} earns ${this.salary}`;
  }
  raise(percent) {
    this.salary = Math.round(this.salary * (1 + percent / 100));
  }
}

class Manager extends Employee {
  constructor(name, salary, team = []) {
    super(name, salary);
    this.team = team;
  }
  describe() {
    return `${super.describe()} and manages ${this.team.length} people`;
  }
}

const boss = new Manager("Grace", 90000, ["Ada", "Linus"]);
boss.raise(10);
console.log(boss.describe());
console.log(boss instanceof Manager, boss instanceof Employee);
```

- `class Manager extends Employee` makes `Manager` a **subclass** (or *child class*) of `Employee`, its **superclass** (*parent* or *base* class).
- `Manager` **inherits** everything `Employee` has: `raise` works on a manager without being written again.
- It can **add** new things (`team`) and **override** methods by defining one with the same name (`describe`).
- A manager is also an employee: `instanceof Employee` is true.

## super: calling the parent

`super` gives access to the parent class:

- `super(...)` in the constructor runs the **parent's constructor**. In a subclass constructor, you **must** call it before using `this`, because the parent creates and sets up the object. Forget, and you get `ReferenceError: Must call super constructor in derived class before accessing 'this'`.
- `super.method(...)` calls the parent's version of a method, so an override can **extend** the parent's behaviour instead of rewriting it, as `describe` does above.

If a subclass doesn't need its own constructor, leave it out: it automatically passes all arguments to the parent's.

## How it works: the chain grows

`extends` simply adds a link in the prototype chain from the last lesson: `boss` → `Manager.prototype` → `Employee.prototype` → `Object.prototype`. When you call `boss.raise()`, JavaScript doesn't find `raise` on `Manager.prototype`, so it continues to `Employee.prototype` and finds it there. When you call `boss.describe()`, it finds `Manager`'s version first, so that one wins. Static methods are inherited too.

That last check shows the most powerful idea in this module: a method in the parent class can call a method that a **subclass** overrides, and the subclass's version runs. The parent defines the overall algorithm; children fill in details. This is called the **template method** pattern.

## Private fields aren't inherited for direct access

A subclass can't touch its parent's `#private` fields; to the subclass they're as hidden as to anyone else. It must use the parent's public (or getter) interface:

```js
class Account {
  #balance = 0;
  deposit(amount) {
    this.#balance += amount;
  }
  get balance() {
    return this.#balance;
  }
}
class SavingsAccount extends Account {
  constructor(rate) {
    super();
    this.rate = rate;
  }
  addInterest() {
    this.deposit(Math.round(this.balance * this.rate * 100) / 100);
  }
}
const s = new SavingsAccount(0.05);
s.deposit(200);
s.addInterest();
console.log(s.balance);
```

That's a good thing: the parent keeps control of its invariants, even against its own children. JavaScript has no "protected" keyword; when a subclass truly needs more access, the parent exposes a method for it.

## Extending built-in classes

You can extend JavaScript's own classes. You've already done it with `Error`; arrays and maps work too:

```js
class Stack extends Array {
  peek() {
    return this.at(-1);
  }
}
const s = Stack.from([1, 2, 3]);
s.push(4);
console.log(s.peek(), s.length, s instanceof Array);
```

Be careful with this: an `Array` subclass exposes *every* array method, so code could `splice` the middle of your "stack". Often it's better to wrap an array in a private field (composition, coming in two lessons).

## Abstract base classes

Sometimes a parent class only exists to be extended: there's no such thing as a plain "shape", only circles and squares. JavaScript has no `abstract` keyword, but you can enforce it:

```js
class Shape {
  constructor(name) {
    if (new.target === Shape) {
      throw new TypeError("Shape is abstract: create a Circle or a Square");
    }
    this.name = name;
  }
  area() {
    throw new Error(`${this.constructor.name} must implement area()`);
  }
  describe() {
    return `${this.name} with area ${this.area().toFixed(2)}`;
  }
}

class Circle extends Shape {
  constructor(r) {
    super("circle");
    this.r = r;
  }
  area() {
    return Math.PI * this.r ** 2;
  }
}

console.log(new Circle(1).describe());
try {
  new Shape("blob");
} catch (error) {
  console.log(error.message);
}
```

`new.target` is the class that `new` was actually called with, so the check only fires for `new Shape(...)`. The "abstract" `area` method throws a clear message if a subclass forgets to implement it.

## When to inherit

Inheritance is powerful and easy to overuse. Use it only when:

- the relationship is genuinely **"is a"**: a `Manager` *is an* `Employee`; a `Car` is *not* an `Engine` (it *has* one);
- the subclass can be used **anywhere** the parent is expected, without surprises. This is the **Liskov substitution principle**: code written for `Employee` must keep working when given a `Manager`. A `Square` subclass of `Rectangle` whose `setWidth` secretly changes the height breaks that promise;
- the hierarchy stays **shallow**: one or two levels. Deep chains (`Animal` → `Mammal` → `Pet` → `Dog` → `ServiceDog`) become hard to change, because every class depends on all the ones above it.

When in doubt, prefer **composition**, two lessons from now.

=== lesson js-polymorphism | Polymorphism and duck typing | 80
## One call, many behaviours

**Polymorphism** (Greek for "many forms") means code can work with objects of different types through the **same interface**, and each object responds in its own way:

```js
class Circle {
  constructor(r) {
    this.r = r;
  }
  area() {
    return Math.PI * this.r ** 2;
  }
}
class Square {
  constructor(side) {
    this.side = side;
  }
  area() {
    return this.side ** 2;
  }
}
class Triangle {
  constructor(base, height) {
    this.base = base;
    this.height = height;
  }
  area() {
    return (this.base * this.height) / 2;
  }
}

const shapes = [new Circle(1), new Square(2), new Triangle(3, 4)];
const total = shapes.reduce((sum, s) => sum + s.area(), 0);
console.log(total.toFixed(2));
```

The `reduce` doesn't know or care what kind of shape it has; it just calls `area()`. Add a `Hexagon` class tomorrow, and the total still works without changing a single line of it.

## Duck typing

Notice something: `Circle`, `Square` and `Triangle` don't share a parent class. In JavaScript, polymorphism doesn't need inheritance. Any object with an `area()` method works. This is **duck typing**: "if it walks like a duck and quacks like a duck, it's a duck." What matters is what an object **can do**, not what class it came from.

```js
const shapes = [
  { area: () => 10 },
  { name: "custom", area() { return 2.5; } },
];
console.log(shapes.map((s) => s.area()));
```

You've relied on duck typing all along: `for...of` works on anything iterable, `JSON.stringify` uses any object's `toJSON`, template literals use any object's `toString`. These informal agreements about which methods an object provides are called **protocols** or **interfaces**.

## Interfaces by agreement

Languages like Java and C# have an `interface` keyword the compiler checks. JavaScript doesn't, so you document the expected shape and, where it matters, check it at the boundary:

```js
/**
 * @typedef {object} Notifier
 * @property {(to: string, text: string) => string} send
 */

function notifyAll(notifiers, to, text) {
  for (const n of notifiers) {
    if (typeof n.send !== "function") throw new TypeError("Every notifier needs a send(to, text) method");
  }
  return notifiers.map((n) => n.send(to, text));
}

const email = { send: (to, text) => `email to ${to}: ${text}` };
const sms = { send: (to, text) => `SMS to ${to}: ${text.slice(0, 20)}` };
console.log(notifyAll([email, sms], "Ada", "Your order has shipped!"));
```

The JSDoc `@typedef` documents the interface for readers and editors. TypeScript (Module 12) turns exactly this kind of agreement into something the computer checks for you.

## Replacing conditionals with polymorphism

A tell-tale sign that polymorphism would help is a `switch` on an object's "type" that appears in several places:

```js
function area(shape) {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.r ** 2;
    case "square":
      return shape.side ** 2;
    default:
      throw new Error(`Unknown shape ${shape.kind}`);
  }
}
console.log(area({ kind: "square", side: 3 }));
```

Every new shape means finding and editing every such `switch` (area, perimeter, drawing, saving...), and forgetting one is a bug. With polymorphism, each class carries its own behaviour, and adding a shape means adding **one class** and touching nothing else. This is the **open/closed principle**: code should be *open* for extension (new kinds of things) but *closed* for modification (no editing of working code).

That said, a single small `switch` is often perfectly fine. Reach for polymorphism when the same type-check keeps reappearing.

## Polymorphism with functions

Functions are objects with one behaviour, so passing different functions is polymorphism too:

```js
const strategies = {
  standard: (total) => total,
  member: (total) => total * 0.9,
  blackFriday: (total) => Math.max(total - 20, 0),
};
function checkout(total, pricing) {
  return pricing(total).toFixed(2);
}
for (const [name, pricing] of Object.entries(strategies)) {
  console.log(name, checkout(100, pricing));
}
```

Choosing between interchangeable algorithms at runtime is the **strategy pattern**. In JavaScript it's often just a function or an object of functions; no class needed.

## Checking types: when, and how

Sometimes you do need to know what you have. Options, from best to worst:

1. **Check for the capability**: `typeof x.render === "function"`, `Symbol.iterator in x`. Works for every object that fits.
2. **`instanceof`** when there's a real class family: `if (error instanceof ValidationError)`.
3. **Comparing `x.constructor.name`** strings: fragile (minifiers rename classes); avoid.

    this.rate = rate;
    this.hours = hours;

    return "Hourly";

## "Has a" instead of "is a"

**Composition** builds an object out of other objects that each do one job. A car **has** an engine, wheels and a radio; it isn't a subclass of any of them:

```js
class Engine {
  constructor(horsepower) {
    this.horsepower = horsepower;
    this.running = false;
  }
  start() {
    this.running = true;
    return "Vroom";
  }
}

class Radio {
  #station = "off";
  tune(station) {
    this.#station = station;
  }
  get station() {
    return this.#station;
  }
}

class Car {
  constructor(model, engine, radio = new Radio()) {
    this.model = model;
    this.engine = engine;
    this.radio = radio;
  }
  start() {
    return `${this.model}: ${this.engine.start()}`;
  }
}

const car = new Car("Roadster", new Engine(300));
console.log(car.start());
car.radio.tune("Jazz FM");
console.log(car.radio.station, car.engine.running);
```

`Car` **delegates** work to its parts: `car.start()` asks the engine to start. Each part is small, focused and reusable: the same `Radio` class could go in a boat.

## Why "composition over inheritance"?

This advice, from the classic *Design Patterns* book (1994), is one of the most repeated in software design. Inheritance has costs that appear as programs grow:

- **Tight coupling**: a subclass depends on its parent's internals. Changing the parent can break children in surprising ways (the *fragile base class* problem).
- **Rigid hierarchies**: real things don't fit one tree. Is a `FlyingCar` a `Car` or a `Plane`? With single inheritance you must pick one and duplicate the other.
- **You get everything**: inheriting gives a child *all* of the parent's methods, wanted or not (remember `Stack extends Array` exposing `splice`). As Joe Armstrong put it: "you wanted a banana, but you got a gorilla holding the banana and the entire jungle."

Composition avoids these: parts are swapped freely, each class exposes only what it chooses, and new combinations need no new hierarchy.

## Swappable parts and dependency injection

Because the car *receives* its engine in the constructor, you can give it any engine with a `start()` method, including an electric one, or a fake one in tests. This is **dependency injection** again, now with objects:

```js
class ElectricMotor {
  start() {
    return "Hmmm (silently)";
  }
}
class Car {
  constructor(model, engine) {
    this.model = model;
    this.engine = engine;
  }
  start() {
    return `${this.model}: ${this.engine.start()}`;
  }
}
console.log(new Car("Model E", new ElectricMotor()).start());
const fakeEngine = { start: () => "test engine started" };
console.log(new Car("Test car", fakeEngine).start());
```

Composition plus duck typing gives you polymorphism without any inheritance at all.

## Wrapping instead of extending

Remember the `Stack extends Array` that exposed every array method? Composition fixes it: wrap a private array and expose only what a stack should do:

```js
class Stack {
  #items = [];
  push(x) {
    this.#items.push(x);
    return this;
  }
  pop() {
    return this.#items.pop();
  }
  get size() {
    return this.#items.length;
  }
}
const s = new Stack().push(1).push(2);
console.log(s.pop(), s.size, typeof s.splice);
```

## Mixins: sharing behaviour across unrelated classes

Sometimes several unrelated classes need the same small ability: serialising to JSON, emitting events, logging. A **mixin** is a reusable bundle of methods mixed into a class. The simplest form copies methods onto a prototype:

```js
const Describable = {
  describe() {
    return `${this.constructor.name}: ${JSON.stringify(this)}`;
  },
};
class Book {
  constructor(title) {
    this.title = title;
  }
}
class Song {
  constructor(name) {
    this.name = name;
  }
}
Object.assign(Book.prototype, Describable);
Object.assign(Song.prototype, Describable);
console.log(new Book("Dune").describe());
console.log(new Song("Loops").describe());
```

A more powerful form is the **class-factory mixin**: a function that takes a base class and returns a new class extending it. Mixins can then be stacked:

```js
const Timestamped = (Base) =>
  class extends Base {
    touch() {
      this.updatedAt = "2026-10-14";
      return this;
    }
  };
const Validated = (Base) =>
  class extends Base {
    validate() {
      for (const [key, value] of Object.entries(this)) {
        if (value === "") throw new Error(`${key} is empty`);
      }
      return true;
    }
  };

class Note {
  constructor(text) {
    this.text = text;
  }
}
class SmartNote extends Validated(Timestamped(Note)) {}

const note = new SmartNote("Buy milk").touch();
console.log(note, note.validate());
```

Use mixins sparingly: when several mixins define the same method name, the last one wins silently, and it gets hard to see where a method came from. Plain composition (an object *has* an `EventEmitter`) is usually clearer.

## Choosing between them

| Use | When |
|---|---|
| **Composition** (has a) | the default: combining independent parts, swappable behaviour, testability |
| **Inheritance** (is a) | a true specialisation, used anywhere the parent is, in a shallow hierarchy |
| **Mixin** | one small ability shared by unrelated classes |
| **Plain functions** | behaviour that needs no state at all |

=== lesson js-design-patterns | Design principles and patterns | 85
## Why principles?

Code that works is the beginning, not the end. Real programs live for years and change constantly: new features, new rules, new people. **Design principles** are hard-won lessons about what makes code easy (or painful) to change. **Design patterns** are named, proven solutions to problems that keep coming up. Knowing their names also lets you talk with other developers: "let's put an adapter around that API" says a paragraph in four words.

## Three everyday principles

- **DRY, Don't Repeat Yourself**: every piece of knowledge (a tax rate, a validation rule, a formula) should live in one place. Copy-pasted logic means fixing every bug several times, and missing one.
- **KISS, Keep It Simple**: the simplest design that works is usually best. Clever code is hard to read and harder to debug.
- **YAGNI, You Aren't Gonna Need It**: don't build flexibility for imagined future needs. Add it when a real need arrives; you'll know far more by then.

DRY and YAGNI pull in opposite directions sometimes. A useful rule: tolerate a duplication twice; on the third time, extract it.

## SOLID

Five principles for object-oriented design, collected by Robert C. Martin:

| | Principle | In one sentence |
|---|---|---|
| **S** | Single responsibility | A class (or function) should have one reason to change. |
| **O** | Open/closed | Add behaviour by adding code (new classes), not by editing working code. |
| **L** | Liskov substitution | Subclasses must work wherever their parent is expected. |
| **I** | Interface segregation | Don't force objects to provide methods they don't need: prefer small interfaces. |
| **D** | Dependency inversion | High-level code should depend on abstractions (interfaces), not on concrete details. |

You met O and L in the last lessons. Here's **S** in action. This function does three jobs, so it has three reasons to change (new validation rules, new prices, a new output format):

```js
function processOrder(order) {
  if (!order.items.length) throw new Error("Empty order");
  let total = 0;
  for (const item of order.items) total += item.price * item.qty;
  if (order.coupon === "SAVE10") total *= 0.9;
  return `Order for ${order.customer}: ${total.toFixed(2)}`;
}
console.log(processOrder({ customer: "Ada", coupon: "SAVE10", items: [{ price: 20, qty: 2 }] }));
```

Split by responsibility, each piece is small, named, reusable and testable on its own:

```js
const validateOrder = (order) => {
  if (!order.items.length) throw new Error("Empty order");
};
const subtotal = (items) => items.reduce((sum, i) => sum + i.price * i.qty, 0);
const applyCoupon = (total, coupon) => (coupon === "SAVE10" ? total * 0.9 : total);
const formatOrder = (customer, total) => `Order for ${customer}: ${total.toFixed(2)}`;

function processOrder(order) {
  validateOrder(order);
  const total = applyCoupon(subtotal(order.items), order.coupon);
  return formatOrder(order.customer, total);
}
console.log(processOrder({ customer: "Ada", coupon: "SAVE10", items: [{ price: 20, qty: 2 }] }));
```

And **D**: a high-level `ReportService` shouldn't create a specific database connection inside itself. It should receive "something that can load data" (an abstraction), so it can be given a real database, a file or a fake for tests. That's dependency injection, which you've now seen three times; it's the most practical idea in this lesson.

## Patterns you'll meet constantly

### Factory

A function (or static method) that decides **which** object to create, so callers don't need to know the concrete classes:

```js
class EmailNotifier {
  send(to, msg) {
    return `Email to ${to}: ${msg}`;
  }
}
class SmsNotifier {
  send(to, msg) {
    return `SMS to ${to}: ${msg}`;
  }
}
function createNotifier(channel) {
  switch (channel) {
    case "email":
      return new EmailNotifier();
    case "sms":
      return new SmsNotifier();
    default:
      throw new Error(`Unknown channel: ${channel}`);
  }
}
console.log(createNotifier("sms").send("Ada", "Your code is ready"));
```

### Observer

An object (the *subject*) keeps a list of listeners and notifies them when something happens, without knowing who they are. You built one in the mixins exercise; the browser's `addEventListener` and Node's `EventEmitter` are this pattern, and it's the heart of every UI framework.

### Adapter

Wraps an object whose interface doesn't fit, so it looks like the interface your code expects. Typical when integrating an old system or a third-party library:

```js
const legacyWeather = {
  getTempF(city) {
    return city === "Paris" ? 68 : 50;
  },
};
const weatherAdapter = {
  temperature(city) {
    const celsius = ((legacyWeather.getTempF(city) - 32) * 5) / 9;
    return { city, celsius: Math.round(celsius) };
  },
};
console.log(weatherAdapter.temperature("Paris"));
```

### Decorator

Wraps an object to **add behaviour while keeping the same interface**, so the wrapped object can be used anywhere the original was. (You wrapped *functions* this way in Module 5.)

```js
function withLogging(repo, log) {
  return {
    get(id) {
      log.push(`get ${id}`);
      return repo.get(id);
    },
  };
}
const users = { get: (id) => ({ id, name: id === 1 ? "Ada" : "Unknown" }) };
const log = [];
const logged = withLogging(users, log);
console.log(logged.get(1).name, log);
```

Decorators stack: `withCache(withLogging(withRetry(api)))`, each layer adding one concern.

### Facade

A simple interface in front of a complicated subsystem: `checkout(cart)` hides the payment, stock and email steps behind one call.

### Singleton (and why to be careful)

"Exactly one instance" (one configuration, one database pool). In JavaScript, a module that exports one object already is a singleton; there's no need for special class tricks. But singletons are **global state** in disguise: any code can change them, and tests interfere with each other. Prefer passing the one instance in where it's needed.

## Patterns are tools, not goals

The biggest pattern mistake is using them where they aren't needed: a factory for one class, an abstract base for one subclass, five layers of indirection for a ten-line script. Patterns should **remove** pain you actually feel. Start simple (KISS, YAGNI), notice repetition and rigid spots as the program grows, and refactor towards a pattern when it clearly helps.

Two famous anti-patterns to avoid: the **god object** (one class that knows and does everything) and **spaghetti code** (logic tangled across functions and globals so that every change breaks something elsewhere).

## What makes for...of work?

`for...of` works on arrays, strings, Maps, Sets... but not on plain objects. What do the working ones have in common? They follow the **iteration protocol**:

- An **iterable** is an object with a method stored under the special key `Symbol.iterator`. Calling it returns an **iterator**.
- An **iterator** is an object with a `next()` method. Each call returns `{ value, done }`: the next value, and `done: true` once there are no more.

```js
const letters = ["a", "b"];
const it = letters[Symbol.iterator]();
console.log(it.next());
console.log(it.next());
console.log(it.next());
```

`for...of` does exactly this behind the scenes: get an iterator, call `next()` until `done` is true. So do spread (`[...x]`), destructuring (`const [a, b] = x`), `Array.from(x)`, `new Set(x)`, `new Map(x)` and `Promise.all(x)`. Make your own objects iterable, and all of these work with them.

## Making a class iterable

```js
class Countdown {
  constructor(from) {
    this.from = from;
  }
  [Symbol.iterator]() {
    let current = this.from;
    return {
      next: () => (current > 0 ? { value: current--, done: false } : { value: undefined, done: true }),
    };
  }
}
const c = new Countdown(3);
for (const n of c) console.log(n);
console.log([...c], Math.max(...c));
```

Each call to `[Symbol.iterator]()` creates a fresh iterator with its own `current`, so the same countdown can be looped over again and again.

## Generators: iterators made easy

Writing `next()` by hand is fiddly. A **generator function**, written `function*`, builds the iterator for you. Inside it, `yield value` hands out the next value and **pauses** the function right there until the next value is requested:

```js
function* countdown(from) {
  for (let i = from; i > 0; i--) {
    yield i;
  }
  return "liftoff";
}
const gen = countdown(2);
console.log(gen.next());
console.log(gen.next());
console.log(gen.next());
console.log([...countdown(5)]);
```

Calling `countdown(2)` doesn't run any of its code yet; it returns a generator object. Each `next()` runs the function until the next `yield`, then freezes it, local variables and all, until the next `next()`. (A `return` value shows up once with `done: true`, but `for...of` and spread ignore it.)

With a generator, the iterable class becomes much simpler: make `[Symbol.iterator]` a generator method with `*`:

```js
class Range {
  constructor(start, end, step = 1) {
    this.start = start;
    this.end = end;
    this.step = step;
  }
  *[Symbol.iterator]() {
    for (let i = this.start; i <= this.end; i += this.step) yield i;
  }
}
console.log([...new Range(1, 10, 3)]);
const [first, second] = new Range(5, 100);
console.log(first, second);
```

## Laziness and infinite sequences

Because generators produce values **only when asked**, they can describe sequences that never end, as long as you only take what you need:

```js
function* naturals() {
  let n = 1;
  while (true) yield n++;
}
function* take(iterable, count) {
  if (count <= 0) return;
  for (const value of iterable) {
    yield value;
    if (--count === 0) return;
  }
}
function* filter(iterable, predicate) {
  for (const value of iterable) if (predicate(value)) yield value;
}
const squaresOfOdds = filter(naturals(), (n) => n % 2 === 1);
console.log([...take(squaresOfOdds, 5)]);
```

Nothing here builds a big array: each number flows through the pipeline one at a time. That's **lazy evaluation**, useful for huge data (reading a large file line by line), endless streams (IDs, events) and work you might stop early.

Modern JavaScript (2025: current browsers and Node.js 22+) adds these helpers directly to iterators: `naturals().filter((n) => n % 2).map((n) => n * n).take(5).toArray()`. On older platforms, small generator functions like `take` and `filter` above do the same job.

## yield*: delegating to another iterable

`yield* other` yields every value of another iterable in turn. It makes recursive generators natural, such as walking a tree of folders:

```js
const folder = {
  name: "project",
  children: [
    { name: "README.md" },
    { name: "src", children: [{ name: "app.js" }, { name: "utils", children: [{ name: "math.js" }] }] },
  ],
};
function* walk(node, path = "") {
  const here = path ? `${path}/${node.name}` : node.name;
  if (!node.children) {
    yield here;
    return;
  }
  for (const child of node.children) yield* walk(child, here);
}
console.log([...walk(folder)]);
```

## Where you'll see this

- Libraries for data processing and streams use iterators everywhere.
- **Async generators** (`async function*` with `for await...of`, Module 10) handle data that arrives over time, such as pages from an API.
- Many algorithms (tree traversals, permutations, pagination) are cleanest as generators.

=== lesson js-oop-case-study | Case study: designing a task manager | 90
## From requirements to design

Knowing the features of classes isn't the same as knowing how to design with them. In this lesson we'll design a small but realistic program step by step, the way a professional would, using the ideas from Modules 7 to 9.

**The requirements** (from an imaginary product manager):

1. Tasks have a title, an optional due date and a priority (low, normal, high).
2. A task moves through the states *todo* → *doing* → *done*. It can go back from *doing* to *todo*, but a *done* task is finished.
3. Tasks belong to projects. We list a project's tasks, filter them (by state, overdue), and see its progress.
4. Other parts of the app (a sidebar counter, a notification) need to react when tasks change.
5. Projects must be saved and loaded (in the browser this will be `localStorage`).

## Step 1: find the nouns and verbs

Nouns suggest classes and data: **task**, **project**, **state**, **priority**, **due date**. Verbs suggest methods: *create, start, finish, reopen, list, filter, save, load*. Rules suggest invariants: "a done task is finished", "titles aren't empty".

A first sketch:

- `Task`: title, due date, priority, state; methods `start()`, `finish()`, `reopen()`, `isOverdue(today)`.
- `Project`: a name and its tasks; methods `add()`, `find()`, filters, `progress`.
- Saving: `toJSON()` and `fromJSON()`, with the actual storage injected (so tests don't need a browser).
- Change notifications: an observer, composed into `Project`.

## Step 2: a Task that protects its rules

State transitions are a classic source of bugs, so the task enforces them itself, with a small table of allowed moves:

```js
class Task {
  static #moves = { todo: ["doing"], doing: ["todo", "done"], done: [] };
  #state = "todo";

  constructor(title, { due = null, priority = "normal" } = {}) {
    if (!title || !title.trim()) throw new Error("A task needs a title");
    if (!["low", "normal", "high"].includes(priority)) throw new RangeError(`Unknown priority: ${priority}`);
    this.title = title.trim();
    this.due = due;
    this.priority = priority;
  }

  get state() {
    return this.#state;
  }

  #moveTo(next) {
    if (!Task.#moves[this.#state].includes(next)) {
      throw new Error(`Can't move "${this.title}" from ${this.#state} to ${next}`);
    }
    this.#state = next;
  }

  start() {
    this.#moveTo("doing");
  }
  finish() {
    this.#moveTo("done");
  }
  reopen() {
    this.#moveTo("todo");
  }

  isOverdue(today) {
    return this.due !== null && this.#state !== "done" && this.due < today;
  }
}

const t = new Task("Write tests", { due: "2026-10-10", priority: "high" });
t.start();
console.log(t.state, t.isOverdue("2026-10-14"));
t.finish();
try {
  t.start();
} catch (error) {
  console.log(error.message);
}
```

Design notes:

- The **options object** keeps the constructor readable: `new Task("Write tests", { priority: "high" })`.
- The state is **private**, changed only through intention-revealing methods (`start`, `finish`), so the rules can't be bypassed.
- The transition table is **data**, not a tangle of `if`s: adding a "blocked" state later means editing one line.
- Dates are passed in as `"YYYY-MM-DD"` strings, which compare correctly as text, and `isOverdue` receives `today` instead of reading the clock: **dependency injection** of time, so tests are deterministic.

## Step 3: a Project that composes tasks and events

```js
class Emitter {
  #handlers = new Map();
  on(event, fn) {
    if (!this.#handlers.has(event)) this.#handlers.set(event, []);
    this.#handlers.get(event).push(fn);
  }
  emit(event, data) {
    for (const fn of this.#handlers.get(event) ?? []) fn(data);
  }
}

class Project {
  #tasks = [];
  events = new Emitter();

  constructor(name) {
    this.name = name;
  }

  add(task) {
    this.#tasks.push(task);
    this.events.emit("changed", { type: "added", title: task.title });
    return task;
  }

  update(title, action) {
    const task = this.#tasks.find((t) => t.title === title);
    if (!task) throw new Error(`No task called "${title}"`);
    task[action]();
    this.events.emit("changed", { type: action, title });
  }

  inState(state) {
    return this.#tasks.filter((t) => t.state === state);
  }

  get progress() {
    if (this.#tasks.length === 0) return 0;
    return Math.round((this.inState("done").length / this.#tasks.length) * 100);
  }

  *[Symbol.iterator]() {
    yield* this.#tasks;
  }
}

class Task {
  #state = "todo";
  constructor(title) {
    this.title = title;
  }
  get state() {
    return this.#state;
  }
  start() {
    this.#state = "doing";
  }
  finish() {
    this.#state = "done";
  }
}

const home = new Project("Home");
home.events.on("changed", (e) => console.log(`[event] ${e.type}: ${e.title}`));
home.add(new Task("Water plants"));
home.add(new Task("Fix the tap"));
home.update("Water plants", "start");
home.update("Water plants", "finish");
console.log(`${home.name}: ${home.progress}% done`);
console.log([...home].map((t) => `${t.title} (${t.state})`));
```

(This example repeats a simplified `Task` so it can run on its own.) Design notes:

- `Project` **has** an emitter (composition), rather than extending one: other parts of the app subscribe with `project.events.on(...)` without the project knowing who they are (observer).
- The task list is private; outside code gets **filtered copies** and **iteration** (a generator method), never the array itself.
- `update` tells the task what to do (tell, don't ask), and is the one place where changes are announced.

## Step 4: saving and loading

Persistence is a separate responsibility, so it lives in a separate place. The domain classes only know how to turn themselves into plain data and back; **where** data is stored is injected:

```js
class Task {
  constructor(title, state = "todo") {
    this.title = title;
    this.state = state;
  }
  toJSON() {
    return { title: this.title, state: this.state };
  }
  static fromJSON(data) {
    return new Task(data.title, data.state);
  }
}

class MemoryStorage {
  #data = new Map();
  save(key, text) {
    this.#data.set(key, text);
  }
  load(key) {
    return this.#data.get(key) ?? null;
  }
}

function saveTasks(storage, key, tasks) {
  storage.save(key, JSON.stringify(tasks));
}
function loadTasks(storage, key) {
  const text = storage.load(key);
  return text === null ? [] : JSON.parse(text).map(Task.fromJSON);
}

const storage = new MemoryStorage();
```

In the browser, a `LocalStorageAdapter` with the same `save`/`load` methods would wrap `localStorage.setItem`/`getItem`; in Node, a file-based one would use `fs`. The rest of the program never changes: **dependency inversion** in practice.

## Step 5: tests pin it all down

Every rule from the requirements becomes a test: transitions, invalid input, filters, progress, a save/load round trip. Because time and storage are injected, every test is fast and deterministic. You've written tests like these in Module 7; the exercises below are checked the same way.

## What we didn't do

No inheritance hierarchy (no `HighPriorityTask extends Task`): priority is just data. No singleton "TaskManager" that owns everything. No abstraction for things that don't vary yet (YAGNI). The design is small, and each part has one job, which is what makes it easy to grow.

📚 **Go deeper:** Sandi Metz, *Practical Object-Oriented Design* (examples in Ruby, ideas universal); Martin Fowler, "Tell Don't Ask" and "Anemic Domain Model" (martinfowler.com); *Eloquent JavaScript* (4th ed.), chapter 7, "Project: A Robot".

class Task {
  static #moves = { todo: ["doing"], doing: ["todo", "done"], done: [] };
  #state = "todo";

  constructor(title, { due = null, priority = "normal" } = {}) {
    if (!title || !title.trim()) throw new Error("A task needs a title");
    if (!["low", "normal", "high"].includes(priority)) throw new RangeError(`Unknown priority: ${priority}`);
    this.title = title.trim();
    this.due = due;
    this.priority = priority;
  }

  get state() {
    return this.#state;
  }

  #moveTo(next) {
    if (!Task.#moves[this.#state].includes(next)) throw new Error(`Can't move from ${this.#state} to ${next}`);
    this.#state = next;
  }

  start() {
    this.#moveTo("doing");
  }

  finish() {
    this.#moveTo("done");
  }

  reopen() {
    this.#moveTo("todo");
  }

  isOverdue(today) {
    return this.due !== null && this.#state !== "done" && this.due < today;
  }

  toJSON() {
    return { title: this.title, due: this.due, priority: this.priority, state: this.#state };
  }

  static fromJSON({ title, due, priority, state }) {
    const task = new Task(title, { due, priority });
    task.#state = state;
    return task;
  }
}

class Emitter {
  #handlers = new Map();
  on(event, fn) {
    if (!this.#handlers.has(event)) this.#handlers.set(event, []);
    this.#handlers.get(event).push(fn);
  }
  emit(event, data) {
    for (const fn of this.#handlers.get(event) ?? []) fn(data);
  }
}

class Task {
  constructor(title, { due = null, state = "todo" } = {}) {
    this.title = title;
    this.due = due;
    this.state = state;
  }
  start() { if (this.state !== "todo") throw new Error("not todo"); this.state = "doing"; }
  finish() { if (this.state !== "doing") throw new Error("not doing"); this.state = "done"; }
  reopen() { if (this.state !== "doing") throw new Error("not doing"); this.state = "todo"; }
  isOverdue(today) { return this.due !== null && this.state !== "done" && this.due < today; }
  toJSON() { return { title: this.title, due: this.due, state: this.state }; }
}

class Project {
  #tasks = new Map();
  events = new Emitter();

  constructor(name) {
    this.name = name;
  }

  add(title, options) {
    if (this.#tasks.has(title)) throw new Error(`Duplicate task: ${title}`);
    const task = new Task(title, options);
    this.#tasks.set(title, task);
    this.events.emit("changed", { type: "added", title });
    return task;
  }

  update(title, action) {
    const task = this.#tasks.get(title);
    if (!task) throw new Error(`No task called "${title}"`);
    task[action]();
    this.events.emit("changed", { type: action, title });
  }

  overdue(today) {
    return [...this].filter((t) => t.isOverdue(today)).map((t) => t.title);
  }

  get progress() {
    const all = [...this];
    if (all.length === 0) return 0;
    return Math.round((all.filter((t) => t.state === "done").length / all.length) * 100);
  }

  *[Symbol.iterator]() {
    yield* this.#tasks.values();
  }

  toJSON() {
    return { name: this.name, tasks: [...this] };
  }

  static fromJSON({ name, tasks }) {
    const project = new Project(name);
    for (const t of tasks) project.#tasks.set(t.title, new Task(t.title, t));
    return project;
  }
}

class Pipeline {
  constructor(source) {
    this.source = source;
  }

  *[Symbol.iterator]() {
    yield* this.source;
  }

  map(fn) {
    const source = this.source;
    return new Pipeline((function* () {
      for (const x of source) yield fn(x);
    })());
  }

  filter(fn) {
    const source = this.source;
    return new Pipeline((function* () {
      for (const x of source) if (fn(x)) yield x;
    })());
  }

  take(n) {
    const source = this.source;
    return new Pipeline((function* () {
      if (n <= 0) return;
      let count = 0;
      for (const x of source) {
        yield x;
        if (++count >= n) return;
      }
    })());
  }

  toArray() {
    return [...this];
  }
}

function from(iterable) {
  return new Pipeline(iterable);
}

class Channel {
  constructor() {
    if (new.target === Channel) throw new TypeError("Channel is abstract");
  }

  send(user, message) {
    if (!message) throw new Error("Empty message");
    return this.deliver(user, message);
  }

  deliver() {
    throw new Error(`${this.constructor.name} must implement deliver()`);
  }
}

class EmailChannel extends Channel {
  deliver(user, message) {
    if (!user.email) throw new Error("No email address");
    return `email:${user.email}:${message}`;
  }
}

class SmsChannel extends Channel {
  deliver(user, message) {
    if (!user.phone) throw new Error("No phone number");
    return `sms:${user.phone}:${message.slice(0, 20)}`;
  }
}

function createChannel(type) {
  if (type === "email") return new EmailChannel();
  if (type === "sms") return new SmsChannel();
  throw new Error(`Unknown channel: ${type}`);
}

class Notifier {
  constructor(channels) {
    this.channels = channels;
  }

  notify(user, message) {
    return this.channels.map((channel) => {
      try {
        return channel.send(user, message);
      } catch (error) {
        return `failed:${channel.constructor.name}:${error.message}`;
      }
    });
  }
}
