## Data plus behaviour

So far, objects have mostly held data, and separate functions did things *to* that data. **Object-oriented programming** (OOP) puts the two together: an object holds its data **and** the functions that work on it. Those functions are its **methods**.

```js
const counter = {
  count: 0,
  increment() {
    this.count++;
    return this.count;
  },
  reset() {
    this.count = 0;
  },
};
counter.increment();
counter.increment();
console.log(counter.count);
counter.reset();
console.log(counter.count);
```

Inside a method, `this` refers to **the object the method was called on**. `counter.increment()` runs `increment` with `this` set to `counter`, so `this.count++` changes `counter.count`. You've been using methods all along: `"hi".toUpperCase()`, `[1, 2].push(3)`, `console.log(...)`.

## this is decided by the call

The key rule: **`this` is whatever is in front of the dot when the function is called**, not where the function was written. The same function can serve many objects:

```js
function describe() {
  return `${this.name} costs ${this.price}`;
}
const book = { name: "Dune", price: 9.99, describe };
const pen = { name: "Pen", price: 1.5, describe };
console.log(book.describe());
console.log(pen.describe());
```

## Losing this: the classic bug

If a method is called **without** an object in front of the dot, `this` is `undefined` (in strict mode, which modules, classes and DevQuest always use):

```js
const counter = {
  count: 0,
  increment() {
    this.count++;
    return this.count;
  },
};
const inc = counter.increment;
inc();
```

`inc` is the same function, but called on its own, so `this` is `undefined` and `this.count` throws. This happens most often when you **pass a method as a callback**: `setTimeout(counter.increment, 1000)` or `button.addEventListener("click", counter.increment)` hand over the function alone, without its object. Two fixes:

```js
const counter = {
  count: 0,
  increment() {
    this.count++;
    return this.count;
  },
};
const viaArrow = () => counter.increment();
const viaBind = counter.increment.bind(counter);
viaArrow();
viaBind();
console.log(counter.count);
```

- Wrap the call in an arrow function, which calls the method *on its object*.
- Or `bind`: `fn.bind(obj)` returns a new function whose `this` is permanently `obj`.

## Arrow functions don't have their own this

An arrow function **doesn't get its own `this`**; it uses the `this` of the code around it. That makes arrows perfect for callbacks *inside* methods:

```js
const team = {
  name: "Blue",
  members: ["Ada", "Grace"],
  introduce() {
    return this.members.map((m) => `${m} plays for ${this.name}`);
  },
};
console.log(team.introduce());
```

The arrow inside `map` sees the `this` of `introduce`, which is `team`. With a regular `function () { ... }` callback there, `this` would be `undefined` and the code would crash.

But it also means arrows are **wrong as methods** in object literals:

```js
const broken = {
  name: "Broken",
  hello: () => `Hi from ${this?.name}`,
};
console.log(broken.hello());
```

The arrow takes `this` from the surrounding code (here, the top level, where it's `undefined`), not from `broken`. Rule of thumb: **method shorthand for methods, arrows for callbacks inside them.**

## call and apply

Every function has `call` and `apply` methods that run it with a chosen `this`: `describe.call(book)` or `describe.call(book, arg1, arg2)`; `apply` takes the arguments as an array. You'll rarely need them in your own code, but you'll see them in libraries and older code.

## Getters and setters

A **getter** is a method that looks like a property when you read it; a **setter** runs when you assign to it. They let an object compute values on demand or check values before storing them:

```js
const person = {
  first: "Ada",
  last: "Lovelace",
  get fullName() {
    return `${this.first} ${this.last}`;
  },
  set fullName(value) {
    const [first, last] = value.split(" ");
    this.first = first;
    this.last = last;
  },
};
console.log(person.fullName);
person.fullName = "Grace Hopper";
console.log(person.first, person.last);
```

No parentheses: `person.fullName`, not `person.fullName()`. Getters are great for values derived from other data, which then can never get out of sync.

## Method chaining

A method that returns `this` lets callers chain calls, a style you'll see in many libraries:

```js
const query = {
  parts: [],
  where(condition) {
    this.parts.push(`WHERE ${condition}`);
    return this;
  },
  orderBy(field) {
    this.parts.push(`ORDER BY ${field}`);
    return this;
  },
  build() {
    return this.parts.join(" ");
  },
};
console.log(query.where("age > 18").orderBy("name").build());
```

## Factory functions

To make many similar objects, a function can build and return them. Each call creates a fresh object with its own data:

```js
function createCounter(start = 0) {
  return {
    count: start,
    increment() {
      this.count++;
      return this.count;
    },
  };
}
const a = createCounter();
const b = createCounter(10);
a.increment();
console.log(a.count, b.increment());
```

This works, but every object gets its own copy of every method, and nothing says "these objects are all counters". **Classes**, the next lesson, are JavaScript's dedicated tool for making many objects of the same kind.

## Blueprints for objects

A shop has thousands of products, a bank millions of accounts. Each account has the same *kind* of data (owner, balance) and the same *behaviour* (deposit, withdraw). A **class** is the blueprint; each account made from it is an **object**, also called an **instance** of the class.

```js
class BankAccount {
  constructor(owner, balance = 0) {
    this.owner = owner;
    this.balance = balance;
  }

  deposit(amount) {
    this.balance += amount;
    return this.balance;
  }

  withdraw(amount) {
    if (amount > this.balance) {
      throw new Error(`Insufficient funds: ${this.owner} has ${this.balance}`);
    }
    this.balance -= amount;
    return this.balance;
  }
}

const ada = new BankAccount("Ada", 100);
const grace = new BankAccount("Grace");
ada.deposit(50);
grace.deposit(20);
console.log(ada.balance, grace.balance);
console.log(ada);
console.log(ada instanceof BankAccount);
```

- `class BankAccount { ... }` defines the class. Class names use **PascalCase** (each word capitalised).
- The **constructor** runs when you create an object with `new`. Its job is to set up the new object's starting state, stored on `this`.
- `new BankAccount("Ada", 100)` creates a fresh object, runs the constructor with `this` pointing at it, and gives you the object.
- Methods are written without the `function` keyword, and every instance can use them.
- Each instance has **its own state**: depositing into `ada` doesn't touch `grace`.

The vocabulary, worth knowing for interviews and documentation: the object's data is its **state**, stored in **properties** (also called fields or attributes); its methods are its **behaviour**; and the set of public methods and properties that other code uses is its **interface**.

## Class fields

Properties that every instance starts with can be declared at the top of the class, as **fields**:

```js
class TodoList {
  items = [];
  completed = 0;

  constructor(title) {
    this.title = title;
  }

  add(text) {
    this.items.push({ text, done: false });
    return this;
  }
}
const home = new TodoList("Home");
const work = new TodoList("Work");
home.add("Water plants").add("Call mum");
console.log(home.items.length, work.items.length);
```

Fields are created fresh for **each** instance, so every list gets its own `items` array. Declaring fields at the top also documents, in one place, what data the class holds.

## Validate in the constructor

The constructor is the gatekeeper: reject impossible values there, and no invalid object can ever exist:

```js
class Rectangle {
  constructor(width, height) {
    if (!(width > 0) || !(height > 0)) {
      throw new RangeError(`Width and height must be positive, got ${width} x ${height}`);
    }
    this.width = width;
    this.height = height;
  }

  get area() {
    return this.width * this.height;
  }

  scale(factor) {
    return new Rectangle(this.width * factor, this.height * factor);
  }

  toString() {
    return `Rectangle ${this.width}x${this.height}`;
  }
}
const r = new Rectangle(3, 4);
console.log(r.area, String(r.scale(2)), `${r}`);
try {
  new Rectangle(-1, 5);
} catch (error) {
  console.log(error.message);
}
```

Notice `toString()`: JavaScript calls it whenever the object is turned into text, as in template literals or `String(r)`. Without it, you'd get `[object Object]`.

## Objects have identity

Two objects created from the same class with the same data are still **two different objects**:

```js
class Point {
  constructor(x, y) {
    this.x = x;
    this.y = y;
  }
  equals(other) {
    return this.x === other.x && this.y === other.y;
  }
}
const p = new Point(1, 2);
const q = new Point(1, 2);
console.log(p === q, p.equals(q));
const alias = p;
alias.x = 99;
console.log(p.x);
```

`===` asks "same object?". When "equal" should mean "same data", write an `equals` method. And everything from the references lesson applies: two variables can name one object, and changing it through one is visible through the other.

## Static members: belonging to the class itself

Some things belong to the class as a whole rather than to one object. Mark them `static`; you use them through the class name:

```js
class Temperature {
  static ABSOLUTE_ZERO = -273.15;
  static created = 0;

  constructor(celsius) {
    if (celsius < Temperature.ABSOLUTE_ZERO) throw new RangeError("Below absolute zero");
    this.celsius = celsius;
    Temperature.created++;
  }

  static fromFahrenheit(f) {
    return new Temperature(((f - 32) * 5) / 9);
  }

  get fahrenheit() {
    return (this.celsius * 9) / 5 + 32;
  }
}
const boiling = Temperature.fromFahrenheit(212);
console.log(boiling.celsius, new Temperature(20).fahrenheit, Temperature.created);
```

Common uses:

- **Alternative constructors** (*factory methods*) with clear names: `Temperature.fromFahrenheit(212)`, `User.fromJSON(data)`, `Color.fromHex("#ff0000")`.
- **Constants** shared by all instances: `Temperature.ABSOLUTE_ZERO`.
- **Helpers** that relate to the class but don't need an instance: `Array.isArray(x)`, `Number.isInteger(x)` and `Object.keys(obj)` are all static methods of built-in classes.

## Classes in practice

- A class is declared before it's used: unlike function declarations, `new BankAccount()` above the `class` line throws a ReferenceError.
- Class bodies always run in strict mode.
- Under the hood, `typeof BankAccount` is `"function"`: a class is a special kind of function, and its methods live on a shared *prototype* (Module 8, lesson 4).

What makes a good class? It represents **one** clear concept (a noun: `Invoice`, `Player`, `ShoppingCart`), keeps the data it needs together with the operations on that data, has short methods with verb names, and makes invalid states impossible. If you can't describe a class in one sentence without "and", it's probably two classes.

  lines = [];

  addItem(name, price, qty = 1) {
    if (!(price >= 0)) throw new RangeError("Price must be 0 or more");
    if (!Number.isInteger(qty) || qty < 1) throw new RangeError("Quantity must be a positive whole number");

    return this;

## Protecting an object's state

Here's a bank account class with a problem:

```js
class Account {
  constructor(owner) {
    this.owner = owner;
    this.balance = 0;
  }
  deposit(amount) {
    if (amount <= 0) throw new RangeError("Deposits must be positive");
    this.balance += amount;
  }
}
const acc = new Account("Ada");
acc.deposit(100);
acc.balance = -1000000;
console.log(acc.balance);
```

`deposit` carefully validates its input, but any code anywhere can simply write `acc.balance = -1000000` and skip all the rules. A rule that must always hold for an object ("the balance is never negative") is called an **invariant**, and **encapsulation** means hiding an object's internal state so that only its own methods can change it, which lets the object guarantee its invariants.

## Private fields: #

Prefix a field's name with `#` to make it **private**: it can only be used inside the class body.

```js
class Account {
  #balance = 0;

  constructor(owner) {
    this.owner = owner;
  }

  deposit(amount) {
    if (!(amount > 0)) throw new RangeError("Deposits must be positive");
    this.#balance += amount;
  }

  withdraw(amount) {
    if (!(amount > 0)) throw new RangeError("Withdrawals must be positive");
    if (amount > this.#balance) throw new Error("Insufficient funds");
    this.#balance -= amount;
  }

  get balance() {
    return this.#balance;
  }
}
const acc = new Account("Ada");
acc.deposit(100);
acc.withdraw(30);
console.log(acc.balance);
acc.balance = 5;
```

- `#balance` is declared at the top of the class (private fields must be declared).
- Inside the class, it's read and written as `this.#balance`.
- Outside, it simply doesn't exist: writing `acc.#balance` anywhere outside the class is a **SyntaxError** before the program even runs.
- The **getter** `balance` lets other code *read* the balance, but since there's no setter, assigning to it fails (`Cannot set property balance of #<Account> which has only a getter`).

Now the only way to change the balance is through `deposit` and `withdraw`, which enforce the rules. Private fields don't appear in `console.log` output or `JSON.stringify` either.

Methods can be private too: `#validate(amount) { ... }`, called as `this.#validate(amount)`. Use them for helper steps that aren't part of the object's public interface.

## Public interface, private implementation

Encapsulation splits a class into two parts:

- the **interface**: the public methods and properties that other code may use, which you promise to keep working;
- the **implementation**: the private details of how it works, which you can change at any time.

Because nobody outside can depend on private fields, you can later store the balance in cents, keep a transaction log, or cache values, without breaking a single caller. That freedom to change is the real payoff of encapsulation in large programs.

## Setters that validate

A setter runs code on assignment, so it can check the new value, keeping assignment syntax for the caller:

```js
class Thermostat {
  #target = 20;

  get target() {
    return this.#target;
  }

  set target(value) {
    if (typeof value !== "number" || value < 5 || value > 30) {
      throw new RangeError(`Target must be 5 to 30 degrees, got ${value}`);
    }
    this.#target = value;
  }
}
const t = new Thermostat();
t.target = 22;
console.log(t.target);
try {
  t.target = 90;
} catch (error) {
  console.log(error.message);
}
console.log(t.target);
```

Use getters and setters when reading or assigning should look like a property. Use ordinary methods (`setTarget(value)`, `raiseBy(2)`) when the action has a meaningful name of its own, or might be slow; callers don't expect assignments to do heavy work.

## Don't leak your internals

A getter that returns a private **array or object** hands out a reference to it, and then callers can change it behind the object's back. Return a **copy**:

```js
class Course {
  #students = [];

  enrol(name) {
    if (this.#students.includes(name)) throw new Error(`${name} is already enrolled`);
    this.#students.push(name);
  }

  get students() {
    return [...this.#students];
  }
}
const js = new Course();
js.enrol("Ada");
js.students.push("Mallory");
console.log(js.students);
```

The copy can be modified freely, but the course's real list is safe. This is called a **defensive copy**.

## Tell, don't ask

Encapsulated objects work best when you **tell** them what to do rather than **asking** for their data and doing the work yourself:

- Asking: `if (account.balance >= price) { account.balance -= price; }` spreads the account's rules across the program.
- Telling: `account.withdraw(price);` keeps the rule in one place, inside the class.

If you find code outside a class repeatedly reading its properties to make decisions, that logic probably belongs in a method of the class.

## Other ways to hide things

- Before `#private` existed (2021), developers marked fields with an underscore, `this._balance`, as a *convention* meaning "please don't touch". It isn't enforced, but you'll see it in lots of existing code.
- **Closures** (Module 5) also give true privacy: a factory function's local variables can only be reached by the functions it returns.
- `Object.freeze(this)` at the end of a constructor makes all public properties read-only, which suits **immutable value objects** (a `Point`, a `Money`, a `Date` range) whose "changes" return new objects.

=== lesson js-prototypes | Prototypes and special methods | 85
## Where do methods live?

You've seen that methods work on every instance of a class. But each instance only stores its own **fields**; the methods aren't copied into it:

```js
class Dog {
  constructor(name) {
    this.name = name;
  }
  bark() {
    return `${this.name} says woof`;
  }
}
const rex = new Dog("Rex");
console.log(Object.keys(rex));
console.log(Object.hasOwn(rex, "bark"), "bark" in rex);
console.log(Object.getPrototypeOf(rex) === Dog.prototype);
console.log(Object.getOwnPropertyNames(Dog.prototype));
```

Every object has a hidden link to another object, its **prototype**. When you read a property that the object doesn't have itself, JavaScript looks in its prototype, then in the prototype's prototype, and so on: the **prototype chain**. A class puts its methods on one shared object, `Dog.prototype`, and every `Dog` instance links to it. A million dogs share one `bark` function.

## The prototype chain

```js
class Dog {
  constructor(name) {
    this.name = name;
  }
  bark() {
    return "woof";
  }
}
const rex = new Dog("Rex");
const level1 = Object.getPrototypeOf(rex);
const level2 = Object.getPrototypeOf(level1);
const level3 = Object.getPrototypeOf(level2);
console.log(level1 === Dog.prototype, level2 === Object.prototype, level3);
console.log(rex.toString(), rex.hasOwnProperty("name"));
```

`rex` → `Dog.prototype` → `Object.prototype` → `null`. That's why every object has `toString` and `hasOwnProperty`: they live on `Object.prototype`, at the end of almost every chain.

Built-in values work the same way: `[1, 2].map(...)` finds `map` on `Array.prototype`, and `"hi".toUpperCase()` finds it on `String.prototype`. When MDN documents `Array.prototype.map()`, that's what the name means.

`instanceof` checks the chain too: `rex instanceof Dog` asks "is `Dog.prototype` somewhere in `rex`'s prototype chain?".

## Before classes: constructor functions

Classes arrived in 2015. Before that, the same thing was written with a **constructor function** and its `prototype` property, and you'll still meet this style in older code and libraries:

```js
function Cat(name) {
  this.name = name;
}
Cat.prototype.meow = function () {
  return `${this.name} says meow`;
};
const tom = new Cat("Tom");
console.log(tom.meow(), tom instanceof Cat);
```

`class` does exactly this behind the scenes, with nicer syntax and a few safety features (classes must be called with `new`, their bodies are always strict). That's why people describe classes as "syntactic sugar over prototypes".

## Object.create: linking objects directly

`Object.create(proto)` makes a new object whose prototype is `proto`. It shows the core idea without any class at all: objects **delegating** to other objects.

```js
const robotMethods = {
  introduce() {
    return `I am ${this.name}, model ${this.model}`;
  },
};
const r2 = Object.create(robotMethods);
r2.name = "R2";
r2.model = "astromech";
console.log(r2.introduce(), Object.getPrototypeOf(r2) === robotMethods);
```

## Don't modify built-in prototypes

Because `Array.prototype` is shared by every array in the program, you *could* add your own methods to it: `Array.prototype.last = function () { ... }`. Don't. This is called **monkey patching**, and it causes clashes when a library does the same thing, or when JavaScript later adds a built-in method with the same name. (This really happened: a library's `Array.prototype.flatten` is why the built-in had to be named `flat`.) Write a normal function instead.

## Symbols: keys that can't clash

Property keys are usually strings, but there's a second kind: **symbols**. `Symbol("description")` creates a brand-new value that is **unique**: no other symbol, and no string, is ever equal to it. That makes symbols safe keys for adding properties that can't accidentally collide with anyone else's:

```js
const id = Symbol("id");
const user = { name: "Ada", [id]: 42 };
console.log(user[id], user.id);
console.log(Object.keys(user), JSON.stringify(user));
console.log(Symbol("id") === Symbol("id"));
```

Symbol-keyed properties are skipped by `Object.keys`, `for...in` and `JSON.stringify`, so they stay out of the way of ordinary data. JavaScript itself uses a set of built-in, **well-known symbols** (`Symbol.iterator`, `Symbol.toPrimitive`, `Symbol.toStringTag`...) as the names of special methods. That's how the language could add new protocols over the years without breaking any existing object that happened to have a method called `iterator`.

## Special methods: how objects plug into the language

Python has its "dunder" methods; JavaScript has a smaller set of special methods that the language calls for you:

| Method | Called when |
|---|---|
| `toString()` | the object is turned into a string (templates, `String(obj)`, `+ ""`) |
| `valueOf()` | the object is used as a number (`+obj`, `obj > 5`) |
| `[Symbol.toPrimitive](hint)` | either; `hint` is `"number"`, `"string"` or `"default"` |
| `toJSON()` | `JSON.stringify` serialises the object |
| `[Symbol.iterator]()` | the object is used in `for...of` or spread (Module 9) |

```js
class Money {
  constructor(cents) {
    this.cents = cents;
  }
  toString() {
    return `$${(this.cents / 100).toFixed(2)}`;
  }
  valueOf() {
    return this.cents;
  }
  toJSON() {
    return { amount: this.cents / 100, currency: "USD" };
  }
}
const price = new Money(1250);
const shipping = new Money(499);
```

class Money {

    if (!Number.isInteger(cents)) throw new TypeError(`Cents must be a whole number, got ${cents}`);
    this.cents = cents;
    Object.freeze(this);
  }

  static fromDollars(dollars) {
    return new Money(Math.round(dollars * 100));
  }

  plus(other) {
    return new Money(this.cents + other.cents);
  }

  times(factor) {
    return new Money(Math.round(this.cents * factor));
  }

  equals(other) {
    return other instanceof Money && other.cents === this.cents;
  }

  toString() {
    const sign = this.cents < 0 ? "-" : "";
    return `${sign}$${(Math.abs(this.cents) / 100).toFixed(2)}`;
  }

  toJSON() {
    return { dollars: this.cents / 100 };
  }

  valueOf() {
    return this.cents;
  }
}

::solution
class Book {
  #available;

  constructor(isbn, title, copies = 1) {
    if (!Number.isInteger(copies) || copies < 1) throw new RangeError("Copies must be a positive whole number");
    this.isbn = isbn;
    this.title = title;
    this.copies = copies;
    this.#available = copies;
  }

  get available() {
    return this.#available;
  }

  get isAvailable() {
    return this.#available > 0;
  }

  checkOut() {
    if (this.#available === 0) throw new Error("No copies left");
    this.#available--;
  }

  checkIn() {
    if (this.#available === this.copies) throw new Error("All copies are already in");
    this.#available++;
  }
}

class Library {
  #books = new Map();

  addBook(book) {
    if (this.#books.has(book.isbn)) throw new Error("Duplicate ISBN");
    this.#books.set(book.isbn, book);
    return this;
  }

  find(isbn) {
    return this.#books.get(isbn);
  }

  lend(isbn) {
    const book = this.find(isbn);
    if (!book) throw new Error("Unknown book");
    book.checkOut();
  }

  get availableTitles() {
    return [...this.#books.values()]
      .filter((b) => b.isAvailable)
      .map((b) => b.title)
      .sort((a, b) => a.localeCompare(b));
  }
}
