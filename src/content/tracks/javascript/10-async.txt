## Waiting without freezing

Many things a program does involve **waiting**: for a server to reply, a file to be read, a timer to finish, a user to click. Waiting can take a long time in computer terms: a typical web request takes 50 to 500 milliseconds, in which a computer could run hundreds of millions of instructions.

JavaScript runs your code on **one thread**: it does one thing at a time. If it simply stopped and waited for each network reply, a web page would freeze completely (no scrolling, no clicking) every time it loaded data. Instead, JavaScript is **asynchronous**: you *start* a slow operation, say what should happen when it finishes, and carry on with other work. When the result is ready, your code is called back.

```js
console.log("1. Ordering a coffee");
setTimeout(() => {
  console.log("3. Coffee is ready!");
}, 1000);
console.log("2. Reading a book while I wait");
```

`setTimeout(callback, ms)` asks for `callback` to be run after (at least) `ms` milliseconds. It doesn't pause anything: line 3 runs immediately, and the callback runs a second later. Reading async code means getting used to the fact that **the order in the file is not the order things happen**.

## The event loop

How can one thread juggle all this? The JavaScript engine works with a few structures:

- the **call stack**: the function calls currently running (Module 5);
- the **task queue** (or macrotask queue): callbacks that are ready to run: a timer that has expired, a click that happened, a network response that arrived;
- the **microtask queue**: a higher-priority queue for promise reactions (next lesson).

The **event loop** is a simple rule that runs forever:

1. Run the current code until the call stack is empty.
2. Run **all** waiting microtasks (including any new ones they add).
3. Take the **next** task from the task queue, run it, and go back to step 2.

The slow work itself (the timer counting down, the network transfer) happens *outside* JavaScript, in the browser or in Node.js. Only when it's done does its callback join the queue.

```js
console.log("A: script starts");
setTimeout(() => console.log("E: timer callback (a task)"), 0);
Promise.resolve().then(() => console.log("C: promise reaction (a microtask)"));
queueMicrotask(() => console.log("D: another microtask"));
console.log("B: script ends");
```

Even with a delay of **0**, the timer callback runs **last**: it must wait until the current script has finished *and* all microtasks have run. `setTimeout(fn, 0)` means "as soon as possible after the current work", not "now".

## Don't block the event loop

Since there's only one thread, a long-running piece of synchronous code blocks **everything**: no timers fire, no clicks are handled, the page freezes.

```js
const start = Date.now();
setTimeout(() => console.log(`Timer fired after ${Math.round((Date.now() - start) / 100) * 100} ms, not 10`), 10);
let total = 0;
while (Date.now() - start < 300) {
  total++;
}
console.log("Busy loop finished");
```

The timer was due after 10 ms, but it couldn't run until the busy loop let go of the thread. In a browser, a task that takes more than about 50 ms already makes a page feel sluggish. Heavy computation belongs in a **Web Worker** (a background thread, which is how DevQuest itself runs your code without freezing the app) or must be split into small chunks.

## Callbacks: the original async style

The first way to handle async results was to pass a **callback** function, called with the result when it's ready. Node.js's classic APIs use **error-first callbacks**: the first argument is an error (or `null`), the second the result:

```js
function readUser(id, callback) {
  setTimeout(() => {
    if (id <= 0) callback(new Error(`Invalid id ${id}`), null);
    else callback(null, { id, name: "Ada" });
  }, 50);
}

readUser(1, (error, user) => {
  if (error) {
    console.log("Failed:", error.message);
    return;
  }
  console.log("Loaded", user.name);
});
readUser(-1, (error) => console.log("Failed:", error.message));
```

Callbacks work, but chaining several steps (load the user, *then* their orders, *then* the products in the last order) nests them deeper and deeper, with error checks at every level. This shape is famous enough to have a name, **callback hell** or the *pyramid of doom*:

```
getUser(id, (err, user) => {
  if (err) return handle(err);
  getOrders(user, (err, orders) => {
    if (err) return handle(err);
    getProducts(orders[0], (err, products) => {
      if (err) return handle(err);
      show(products);
    });
  });
});
```

**Promises**, the next lesson, and **async/await**, the one after, were invented to fix exactly this. You'll still meet callbacks in event handlers (`button.addEventListener("click", ...)`) and older Node.js code.

## Timers in more detail

- `setTimeout(fn, ms, ...args)` runs `fn` once; it returns an id you can pass to `clearTimeout(id)` to cancel it.
- `setInterval(fn, ms)` runs `fn` repeatedly; stop it with `clearInterval(id)`. Forgetting to clear an interval keeps a program running forever.
- The delay is a **minimum**, never a guarantee: a busy thread delays it, and browsers slow timers down in background tabs.

```js
let ticks = 0;
const id = setInterval(() => {
  ticks++;
  console.log("tick", ticks);
  if (ticks === 3) {
    clearInterval(id);
    console.log("stopped");
  }
}, 100);
```

## A promise of a future value

A **promise** is an object that stands for a value that isn't available **yet**: the reply from a server, the contents of a file, the end of a timer. Instead of passing a callback *into* a function, the function **returns** a promise, and you attach what should happen next.

A promise is always in one of three states:

- **pending**: still waiting;
- **fulfilled**: finished successfully, with a **value**;
- **rejected**: failed, with a **reason** (usually an `Error`).

Once fulfilled or rejected, a promise is **settled** and never changes again.

```js
function sleep(ms) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

const p = sleep(500);
console.log(p);
p.then(() => console.log("Half a second later"));
console.log("This prints first");
```

## Creating promises

`new Promise(executor)` creates a promise. The **executor** function runs immediately and receives two functions: call `resolve(value)` to fulfil the promise, or `reject(error)` to reject it:

```js
function rollDie() {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      const value = 4;
      if (value === 6) reject(new Error("Lost the die under the sofa"));
      else resolve(value);
    }, 100);
  });
}
rollDie().then((n) => console.log("Rolled", n));
```

Only the first `resolve` or `reject` counts; later calls are ignored. Wrapping a callback-style API like this is called **promisifying** it, and you'll rarely need `new Promise` otherwise: most modern APIs (`fetch`, Node's `fs/promises`) already return promises.

## then, catch and finally

- `promise.then(onFulfilled)` runs when the promise is fulfilled, with its value.
- `promise.catch(onRejected)` runs when it's rejected, with the reason.
- `promise.finally(onSettled)` runs either way (clean-up, like `finally` in Module 7).

```js
function parseLater(text) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      try {
        resolve(JSON.parse(text));
      } catch (error) {
        reject(error);
      }
    }, 50);
  });
}

parseLater('{"ok": true}')
  .then((data) => console.log("Parsed:", data))
  .catch((error) => console.log("Failed:", error.message))
  .finally(() => console.log("Done with the first one"));

parseLater("{broken")
  .then((data) => console.log("Parsed:", data))
  .catch((error) => console.log("Failed:", error.name))
  .finally(() => console.log("Done with the second one"));
```

## Chaining: the cure for callback hell

`then` **returns a new promise**, which settles with whatever your callback returns. If the callback returns a value, the next `then` receives it; if it returns a **promise**, the chain waits for that promise first. So sequential async steps become a flat chain:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const getUser = (id) => sleep(50).then(() => ({ id, name: "Ada" }));
const getOrders = (user) => sleep(50).then(() => [{ id: 7, items: ["book", "pen"] }]);
const getItemCount = (order) => sleep(50).then(() => order.items.length);

getUser(1)
  .then((user) => {
    console.log("Got user", user.name);
    return getOrders(user);
  })
  .then((orders) => getItemCount(orders[0]))
  .then((count) => console.log("Items in the latest order:", count))
  .catch((error) => console.log("Something failed:", error.message));
```

Compare it with the callback pyramid from the last lesson: each step is one level, and **a single `catch` at the end handles a failure in any step**. When a promise in the chain rejects, every following `then` is skipped until a `catch` is reached, just like an exception skipping code until a `catch` block.

⚠️ The most common promise bug: **forgetting to `return`** inside a `then` callback. Without it, the next step doesn't wait, and receives `undefined`.

## Running promises together

Promises really shine when several async operations can run **at the same time**. The static methods of `Promise` combine them:

| Method | Settles when | Result |
|---|---|---|
| `Promise.all(ps)` | all fulfil, or the **first** rejects | array of all values (in the original order) |
| `Promise.allSettled(ps)` | all have settled, either way | array of `{ status, value }` / `{ status, reason }` |
| `Promise.race(ps)` | the **first** settles, either way | that value or reason |
| `Promise.any(ps)` | the first **fulfils** (rejects only if all reject) | that value |

```js
const sleep = (ms, value) => new Promise((r) => setTimeout(() => r(value), ms));

const start = Date.now();
Promise.all([sleep(200, "a"), sleep(100, "b"), sleep(150, "c")]).then((values) => {
  const took = Math.round((Date.now() - start) / 100) * 100;
  console.log(values, `in about ${took} ms`);
});
Promise.race([sleep(300, "slow"), sleep(50, "fast")]).then((winner) => console.log("race:", winner));
```

The three sleeps run **in parallel**, so `Promise.all` takes about as long as the slowest one (200 ms), not the sum (450 ms). And the values come back in the order you passed the promises, not the order they finished.

Use `Promise.all` when you need every result and one failure means the whole job failed. Use `allSettled` when partial success is fine and you want to report each outcome:

```js
const ok = (v) => Promise.resolve(v);
const fail = (msg) => Promise.reject(new Error(msg));
Promise.allSettled([ok("profile"), fail("orders service down"), ok("settings")]).then((results) => {
  for (const r of results) {
    console.log(r.status === "fulfilled" ? `✓ ${r.value}` : `✗ ${r.reason.message}`);
  }
});
```

## Always handle rejections

A rejected promise that nobody handles is an **unhandled rejection**. Browsers log it as an error; Node.js (and DevQuest) end the program:

```js
function risky() {
  return Promise.reject(new Error("Nobody handled me"));
}
risky();
console.log("Program continues... for now");
```

Every promise chain needs a `catch` somewhere (or a `try`/`catch` around an `await`, next lesson).

function readConfig(name, callback) {

## Async code that reads like sync code

Promise chains are much better than callback pyramids, but still not quite as easy to read as ordinary step-by-step code. **async/await** (2017) lets you write asynchronous code that looks almost exactly like synchronous code:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const getUser = (id) => sleep(50).then(() => ({ id, name: "Ada" }));
const getOrders = (user) => sleep(50).then(() => [{ id: 7, total: 59.9 }]);

async function showLatestOrder(userId) {
  const user = await getUser(userId);
  const orders = await getOrders(user);
  console.log(`${user.name}'s latest order: ${orders[0].total}`);
}

showLatestOrder(1);
console.log("showLatestOrder has started");
```

- `async function` declares an **async function**. It can use `await`, and it **always returns a promise**.
- `await promise` **pauses this function** until the promise settles, then gives you its value (or throws its rejection reason).
- While the function is paused, the rest of the program keeps running: notice "showLatestOrder has started" is printed **first**. `await` never freezes the thread; it hands control back to the event loop.

Arrow functions and methods can be async too: `const load = async (id) => { ... }`, `async save() { ... }`.

## Async functions return promises

Whatever an async function returns becomes the value of its promise; whatever it throws becomes the rejection. So the caller either `await`s it (inside another async function) or uses `then`:

```js
async function double(n) {
  return n * 2;
}
async function fails() {
  throw new Error("Something broke");
}
double(21).then((v) => console.log("then got", v));
fails().catch((e) => console.log("catch got", e.message));
```

DevQuest (like JavaScript **modules**, in browsers and Node.js) also allows **top-level `await`**, outside any function. That's why lessons can simply write `const data = await something();` at the top level.

## Errors: plain try/catch

With `await`, a rejected promise **throws** at that line, so the error handling you learned in Module 7 just works:

```js
async function loadSettings(text) {
  await new Promise((r) => setTimeout(r, 20));
  return JSON.parse(text);
}

async function main() {
  try {
    const good = await loadSettings('{"theme": "dark"}');
    console.log("Theme:", good.theme);
    const bad = await loadSettings("{oops}");
    console.log("Never printed", bad);
  } catch (error) {
    console.log("Could not load settings:", error.name);
  } finally {
    console.log("Finished loading");
  }
}
main();
```

## Sequential versus parallel

`await` makes it easy to accidentally do things **one after another** that could run **at the same time**:

```js
const sleep = (ms, v) => new Promise((r) => setTimeout(() => r(v), ms));
const fetchPrice = (item) => sleep(100, item.length * 10);

async function sequential(items) {
  const prices = [];
  for (const item of items) prices.push(await fetchPrice(item));
  return prices;
}
async function parallel(items) {
  return Promise.all(items.map((item) => fetchPrice(item)));
}

const items = ["pen", "book", "lamp"];
let start = Date.now();
console.log(await sequential(items), `${Math.round((Date.now() - start) / 100) * 100} ms`);
start = Date.now();
console.log(await parallel(items), `${Math.round((Date.now() - start) / 100) * 100} ms`);
```

Same results, three times faster. The rule:

- Steps that **depend** on each other (you need the user before you can load *their* orders): `await` them one after another.
- Steps that are **independent**: start them all, then `await Promise.all([...])`.

Sometimes sequential is deliberate: to avoid overloading a server with hundreds of requests at once (the next-but-one lesson shows how to limit concurrency).

## The forEach trap

`forEach` doesn't wait for async callbacks; it fires them all and returns immediately:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const saved = [];

async function saveAll(items) {
  items.forEach(async (item) => {
    await sleep(20);
    saved.push(item);
  });
  console.log("saveAll thinks it's done; saved so far:", saved.length);
}

await saveAll(["a", "b", "c"]);
await sleep(50);
console.log("Actually saved:", saved.length);
```

Use `for...of` with `await` for one-by-one processing, or `await Promise.all(items.map(async (item) => ...))` for parallel processing. Never `forEach` with async callbacks.

## Async iteration: for await...of

When values arrive over time, such as pages of results from an API or lines from a large file, an **async generator** (`async function*`) yields them one by one, and `for await...of` consumes them:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function* pages() {
  for (let page = 1; page <= 3; page++) {
    await sleep(30);
    yield [`item ${page * 2 - 1}`, `item ${page * 2}`];
  }
}

for await (const items of pages()) {
  console.log("got", items);
}
console.log("all pages loaded");
```

You'll use this pattern for paginated APIs in the fetch lesson.

|---|---|
| Wait for one result | `const x = await f();` |
| Several independent results | `const [a, b] = await Promise.all([f(), g()]);` |

| Process items one by one | `for (const x of items) await handle(x);` |
| Process items in parallel | `await Promise.all(items.map(handle));` |
| Values that arrive over time | `for await (const x of stream) { ... }` |

=== lesson js-fetch | Fetching data from web APIs | 90
## Talking to servers

Most apps get their data from **web APIs**: servers that answer requests over HTTP with data, usually JSON. A weather app asks a weather API; a shop's page asks the shop's own API for products; a payment form talks to a payment provider. In JavaScript, browsers and Node.js 18+ have the same built-in function for this: **`fetch`**.

## HTTP in a nutshell

A **request** has:

- a **method**: `GET` (read), `POST` (create), `PUT` / `PATCH` (replace / update), `DELETE` (remove);
- a **URL**: `https://api.example.com/users/1?fields=name`: the server, the path to a **resource**, and optional query parameters after `?`;
- **headers**: extra information, such as `Content-Type: application/json` or an `Authorization` token;
- an optional **body**: the data sent, for `POST`, `PUT` and `PATCH`.

A **response** has a **status code**, headers and a body. The status codes to know:

| Code | Meaning |
|---|---|
| `200 OK` | success |
| `201 Created` | a new resource was created |
| `204 No Content` | success, nothing to send back |
| `400 Bad Request` | the request was invalid (e.g. missing fields) |
| `401 Unauthorized` / `403 Forbidden` | not logged in / not allowed |
| `404 Not Found` | no such resource |
| `429 Too Many Requests` | slow down (rate limit) |
| `500 Internal Server Error` / `503 Service Unavailable` | the server failed / is overloaded |

2xx means success, 4xx means *your* request was wrong, 5xx means the *server* had a problem.

## The demo API

DevQuest includes a small demo API at **`https://api.example.com`**. (`example.com` is a domain reserved for documentation, so it can never be a real service.) It answers instantly-ish (about 100 ms) and works offline, so the examples are predictable:

| Endpoint | Returns |
|---|---|
| `GET /users`, `GET /users/:id` | users `{ id, name, email, city }` |
| `GET /users/:id/posts`, `GET /posts?userId=1` | posts `{ id, userId, title }` |
| `POST /posts`, `PATCH`/`PUT`/`DELETE /posts/:id` | create, update, delete posts (JSON body) |
| `GET /todos?completed=true` | todos `{ id, title, completed }` |
| `GET /products?page=1` | `{ page, items, nextPage }`, 5 products per page |
| `GET /weather?city=Paris` | `{ city, tempC }` |
| `GET /slow?ms=2000`, `GET /flaky`, `GET /error` | a slow reply, a reply that fails twice before succeeding, a server error |

On your own computer these URLs won't work; free public practice APIs such as JSONPlaceholder (`https://jsonplaceholder.typicode.com/users`) behave very similarly.

## GET: reading data

```js
const response = await fetch("https://api.example.com/users/1");
console.log(response.status, response.ok);
const user = await response.json();
console.log(user.name, "lives in", user.city);
```

Two awaits, because two things take time: `fetch` resolves as soon as the response **headers** arrive; `response.json()` waits for the **body** to download and parses it as JSON. Use `response.text()` for plain text instead.

## Check response.ok!

Here's the surprise that catches everyone: **`fetch` does not reject for HTTP errors**. A 404 or 500 is still a successfully *received* response. `fetch` only rejects when there's no response at all (no network, the server is unreachable, the request was cancelled).

```js
const response = await fetch("https://api.example.com/users/99");
console.log(response.ok, response.status);
console.log(await response.json());
```

So always check `response.ok` (true for statuses 200 to 299) and turn failures into errors yourself. Professionals wrap this in a small helper:

```js
async function getJson(url, options) {
  const response = await fetch(url, options);
  if (!response.ok) {
    let detail = response.statusText;
    try {
      detail = (await response.json()).error ?? detail;
    } catch {
      // the error body wasn't JSON
    }
    throw new Error(`HTTP ${response.status}: ${detail}`);
  }
  return response.json();
}

try {
  const users = await getJson("https://api.example.com/users");
  console.log(users.map((u) => u.name));
  await getJson("https://api.example.com/users/42");
} catch (error) {
  console.log("Request failed:", error.message);
}
```

## Query parameters

Build query strings with `URLSearchParams` (or a `URL` object) rather than gluing strings: it escapes spaces and special characters correctly.

```js
const url = new URL("https://api.example.com/todos");
url.searchParams.set("completed", "false");
console.log(url.toString());
const todos = await (await fetch(url)).json();
console.log(todos.map((t) => t.title));

const params = new URLSearchParams({ city: "Paris" });
const weather = await (await fetch(`https://api.example.com/weather?${params}`)).json();
console.log(weather);
```

## Sending data: POST, PATCH, DELETE

To send JSON, set the method, a `Content-Type` header, and the body as a JSON **string**:

```js
const response = await fetch("https://api.example.com/posts", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ userId: 1, title: "Hello from fetch" }),
});
console.log(response.status);
const created = await response.json();
console.log(created);

const updated = await fetch(`https://api.example.com/posts/${created.id}`, {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title: "Hello again" }),
});
console.log((await updated.json()).title);
```

Forgetting `JSON.stringify` (sending `body: { ... }`) is a classic bug: the object gets turned into the text `[object Object]`.

## Loading related data in parallel

Requests that don't depend on each other should run together:

```js
const ids = [1, 2, 3];
const users = await Promise.all(
  ids.map(async (id) => {
    const response = await fetch(`https://api.example.com/users/${id}`);
    return response.json();
  }),
);
console.log(users.map((u) => `${u.name} (${u.city})`));
```

## Things to know before real projects

- **Network errors** (offline, DNS failure) make `fetch` reject with a `TypeError` ("Failed to fetch" / "fetch failed"). Combine a `try`/`catch` around the call with the `response.ok` check, and you've covered both kinds of failure.
- **CORS**: in browsers, a page may only read responses from *another* domain if that server allows it with CORS headers. If you see a "blocked by CORS policy" error, the fix is on the server (or a proxy), not in your fetch code.
- **Secrets**: never put private API keys in browser JavaScript: anyone can read them in the developer tools. Calls that need secret keys go through your own server.
- **Validate** what comes back: a JSON body is just data from outside your program. Check that the fields you need are there before trusting them.

=== lesson js-async-patterns | Async patterns: timeouts, retries and concurrency | 85
## The real world is unreliable

Networks are slow, servers go down for a moment, users click twice. Professional async code is defined less by the happy path than by how it handles these cases. This lesson collects the patterns you'll use again and again.

## Cancelling with AbortController

An `AbortController` lets you cancel an operation that's in progress. Pass its `signal` to `fetch` (and many other APIs); calling `abort()` makes the `fetch` reject with an `AbortError`:

```js
const controller = new AbortController();
setTimeout(() => controller.abort(), 100);
try {
  await fetch("https://api.example.com/slow?ms=2000", { signal: controller.signal });
} catch (error) {
  console.log(error.name, "-", error.message);
}
```

Typical uses: the user navigates away or closes a dialog, or types a new search before the old one returned.

## Timeouts

Never let a request hang forever. `AbortSignal.timeout(ms)` gives you a signal that aborts by itself:

```js
try {
  await fetch("https://api.example.com/slow?ms=2000", { signal: AbortSignal.timeout(300) });
} catch (error) {
  console.log(error.name);
}
```

For any promise (not just `fetch`), race it against a timer:

```js
function withTimeout(promise, ms) {
  let timer;
  const timeout = new Promise((_, reject) => {
    timer = setTimeout(() => reject(new Error(`Timed out after ${ms} ms`)), ms);
  });
  return Promise.race([promise, timeout]).finally(() => clearTimeout(timer));
}
const slow = new Promise((r) => setTimeout(() => r("finally!"), 500));
try {
  console.log(await withTimeout(slow, 100));
} catch (error) {
  console.log(error.message);
}
```

Clearing the timer in `finally` matters: a forgotten timer keeps running (and keeps a Node.js program alive) after the race is over.

## Retrying with backoff

Many failures are **temporary**: a `503 Service Unavailable`, a dropped connection. Retrying often succeeds. But retrying instantly, in a tight loop, hammers a struggling server. The standard approach is **exponential backoff**: wait a little, then double the wait each time (100 ms, 200 ms, 400 ms...), and give up after a few attempts:

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));

async function fetchWithRetry(url, attempts = 4, baseDelay = 50) {
  for (let i = 1; i <= attempts; i++) {
    const response = await fetch(url);
    if (response.ok) return response.json();
    const retryable = response.status === 503 || response.status === 429 || response.status >= 500;
    if (!retryable || i === attempts) throw new Error(`HTTP ${response.status} after ${i} attempt(s)`);
    console.log(`Attempt ${i} got ${response.status}; retrying in ${baseDelay * 2 ** (i - 1)} ms`);
    await sleep(baseDelay * 2 ** (i - 1));
  }
}

console.log(await fetchWithRetry("https://api.example.com/flaky"));
```

Only retry what can succeed later: a `404` or `400` will fail the same way every time. Real systems also add a little randomness ("jitter") to the delays so thousands of clients don't retry at the same instant.

- 401 Unauthorized

## Limiting concurrency

`Promise.all(urls.map(fetch))` starts **everything** at once. For 5 requests that's great; for 5,000 it overwhelms the server (and gets you rate-limited). The fix is a **pool**: at most N tasks running at any moment.

```js
async function mapWithLimit(items, limit, task) {
  const results = new Array(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await task(items[i], i);
    }
  }
  const workers = Array.from({ length: Math.min(limit, items.length) }, worker);
  await Promise.all(workers);
  return results;
}

let running = 0;
let peak = 0;
const slowDouble = async (n) => {
  running++;
  peak = Math.max(peak, running);
  await new Promise((r) => setTimeout(r, 30));
  running--;
  return n * 2;
};
console.log(await mapWithLimit([1, 2, 3, 4, 5, 6, 7], 3, slowDouble), "peak:", peak);
```

Each "worker" takes the next item until none are left; three workers means never more than three tasks at once. (Because JavaScript is single-threaded, `const i = next++` can't be interrupted halfway, so two workers never take the same item.) Libraries like `p-limit` package this pattern.

## Debounce and throttle

User events can fire very fast: every keystroke in a search box, every pixel of scrolling.

- **Debounce**: wait until the events **stop** for a moment, then act once. Search-as-you-type: query the server 300 ms after the user stops typing, not on every key.
- **Throttle**: act at most once per time window. Scroll handlers: update at most every 100 ms.

```js
function debounce(fn, ms) {
  let timer;
  return (...args) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(...args), ms);
  };
}
const search = debounce((text) => console.log("Searching for", text), 50);
search("j");
search("ja");
search("jav");
search("java");
```

Only the last call survives. Notice the closure (Module 5) keeping `timer` between calls.

## Race conditions: stale responses

Async code has its own class of bugs. Say a user types "a", then "ab". Two searches start. If the "a" search happens to return **after** the "ab" one, the page ends up showing results for "a": stale data. Two common fixes:

- **Abort the previous request** when a new one starts (keep its `AbortController`).
- **Ignore outdated responses**: give each request an increasing id and only accept the response if it's still the latest.

```js
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const fakeSearch = async (text) => {
  await sleep(text.length === 1 ? 100 : 30);
  return `results for "${text}"`;
};

let latest = 0;
let shown = "";
async function onInput(text) {
  const id = ++latest;
  const results = await fakeSearch(text);
  if (id !== latest) return;
  shown = results;
}
onInput("a");
onInput("ab");
await sleep(150);
console.log(shown);
```

Without the `id !== latest` check, the slow "a" response would overwrite the newer one.

class ApiClient {

  constructor(baseUrl, { timeoutMs = 1000, retries = 2 } = {}) {

    this.timeoutMs = timeoutMs;
    this.retries = retries;
  }

  get requests() {
    return this.#requests;
  }

  async get(path) {
    for (let attempt = 0; ; attempt++) {
      this.#requests++;
      const response = await fetch(this.baseUrl + path, { signal: AbortSignal.timeout(this.timeoutMs) });
      const body = await response.json();
      if (response.ok) return body;
      const retryable = response.status >= 500;
      if (!retryable || attempt >= this.retries) throw new Error(`HTTP ${response.status}: ${body.error}`);
      await new Promise((r) => setTimeout(r, 10 * 2 ** attempt));
    }
  }

  async getMany(paths) {
    return Promise.all(paths.map((p) => this.get(p)));
  }
