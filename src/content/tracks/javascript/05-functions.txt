## Why functions?

You've already *used* many functions: `console.log`, `Math.max`, `prompt`, `Number`. A **function** is a named, reusable piece of code. Writing your own is the single most important step from "scripts" to "programs":

- **Don't repeat yourself.** Write a calculation once, use it fifty times. Fix a bug once, and it's fixed everywhere.
- **Give ideas names.** `isLeapYear(year)` says what it means; `(year % 4 === 0 && year % 100 !== 0) || year % 400 === 0` makes every reader work it out.
- **Break big problems into small ones** that you can understand, test and trust one at a time.

## Declaring and calling a function

```js
function greet(name) {
  console.log(`Hello, ${name}!`);
}

greet("Ada");
greet("Grace");
```

- `function` starts a **function declaration**, followed by the function's name (`greet`, in camelCase like variables).
- `name` in the parentheses is a **parameter**: a variable that receives a value each time the function is called.
- The body in `{ }` runs **only when the function is called**. Declaring it does nothing visible.
- `greet("Ada")` **calls** the function; `"Ada"` is the **argument**, the value the parameter gets for this call.

Parameters versus arguments: the *parameter* is the name in the definition; the *argument* is the actual value in a call. Several parameters are separated by commas, and arguments are matched to them **by position**:

```js
function introduce(name, language) {
  console.log(`${name} codes in ${language}.`);
}
introduce("Ada", "JavaScript");
introduce("JavaScript", "Ada");
```

## return: giving a value back

Most useful functions **compute** something and hand it back with `return`. The call then *is* that value, and you can use it anywhere a value fits:

```js
function area(width, height) {
  return width * height;
}

const kitchen = area(3, 4);
console.log(kitchen);
console.log(area(2, 5) + area(1, 1));
console.log(`A 10 by 10 room is ${area(10, 10)} square metres`);
```

`return` also **ends the function immediately**: any code after it in that call doesn't run. A function with no `return` (or a bare `return;`) gives back `undefined`:

```js
function shout(text) {
  console.log(text.toUpperCase());
}
const result = shout("hi");
console.log(result);
```

### Printing is not returning

This confuses every beginner at least once. `console.log` *shows* a value to a human; `return` *gives* a value to the code that called the function. A function that prints its answer can't be used in a calculation:

```js
function addAndPrint(a, b) {
  console.log(a + b);
}
function add(a, b) {
  return a + b;
}
console.log(add(2, 3) * 10);
console.log(addAndPrint(2, 3) * 10);
```

The last line prints 5 (from inside the function) and then `NaN`, because `addAndPrint` returns `undefined` and `undefined * 10` is `NaN`. **Prefer functions that return values**, and do the printing in one place, outside them.

## Early returns

Because `return` ends the function, you can handle special cases first and return straight away, the guard clauses from Module 3, now with a natural home:

```js
function ticketPrice(age) {
  if (age < 4) return 0;
  if (age <= 12) return 6;
  if (age >= 65) return 8;
  return 12;
}
console.log(ticketPrice(2), ticketPrice(10), ticketPrice(30), ticketPrice(70));
```

No `else` needed: once a `return` runs, the rest of the function is skipped.

## Functions calling functions

Functions can use other functions, so you build big things out of small, trusted pieces:

```js
function isLeapYear(year) {
  return (year % 4 === 0 && year % 100 !== 0) || year % 400 === 0;
}
function daysInYear(year) {
  return isLeapYear(year) ? 366 : 365;
}
console.log(daysInYear(2024), daysInYear(2025));
```

`isLeapYear` returns a boolean directly; there's no need for `if (...) return true; else return false;`.

Function **declarations** are *hoisted*: JavaScript makes them available before the line where they're written, so you can call a function that's declared further down the file. Many programmers put the main code at the top and the helper functions below.

## Pure functions and side effects

A **pure** function depends only on its parameters and only produces its return value: same arguments, same result, every time, with nothing else changed. `area` and `isLeapYear` are pure. Anything else a function does (printing, changing a variable outside itself, asking for input, writing a file) is a **side effect**.

Programs need side effects, or they couldn't show anything. But pure functions are far easier to understand, reuse and **test**, so professionals keep most of their logic in pure functions and the side effects at the edges.

## Checking a function with assert

How do you know a function works? Call it with known inputs and compare the results with what you expect. `assert` does exactly that: it stays silent when a check passes and raises an error when it fails.

```js
function area(width, height) {
  return width * height;
}
assert.strictEqual(area(3, 4), 12);
assert.strictEqual(area(0, 9), 0);
assert.strictEqual(area(2.5, 2), 5);
console.log("All checks passed!");
```

Change `width * height` to `width + height` and run it again to see a failing check. From now on, many exercises are checked this way: hidden checks **call your function** with different arguments and compare what it **returns**. (DevQuest provides `assert` for you. In Node.js you'd write `import assert from "node:assert/strict";` first; Module 7 covers testing properly.)

## Documenting a function

A comment block starting with `/**` just above a function is a **JSDoc** comment. Editors such as VS Code show it when you hover over a call, and tools can check the types it describes:

```js
/**
 * Converts a temperature from Celsius to Fahrenheit.
 * @param {number} celsius - the temperature in degrees Celsius
 * @returns {number} the temperature in degrees Fahrenheit
 */
function toFahrenheit(celsius) {
  return celsius * 9 / 5 + 32;
}
console.log(toFahrenheit(100));
```

=== lesson js-function-forms | Function expressions, arrows and parameters | 80
## Functions are values

In JavaScript, a function is a value, just like a number or a string. You can store it in a variable:

```js
const square = function (n) {
  return n * n;
};
console.log(square(5));
console.log(typeof square);
```

This is a **function expression**: a function written where a value is expected, here assigned to `square`. Unlike a declaration, it's **not hoisted**: it exists only from its line onwards, like any `const`.

## Arrow functions

Modern JavaScript has a shorter way to write function expressions, the **arrow function**:

```js
const square = (n) => {
  return n * n;
};
const cube = (n) => n * n * n;
const add = (a, b) => a + b;
const sayHi = () => console.log("Hi!");
console.log(square(3), cube(3), add(3, 4));
sayHi();
```

- Parameters go in parentheses, then `=>` ("fat arrow"), then the body.
- If the body is a **single expression**, leave out the braces and `return`: the expression's value is returned automatically. This is called a *concise body*.
- With braces, it's a normal body and you need `return` as usual.
- With no parameters, write empty parentheses `()`. With exactly one, the parentheses are optional (`n => n * 2`), but formatters such as Prettier add them, so you'll usually see `(n) => n * 2`.

⚠️ To return an object from a concise arrow, wrap it in parentheses. Otherwise the braces are read as a function body:

```js
const broken = () => { name: "Ada" };
const works = () => ({ name: "Ada" });
console.log(broken(), works());
```

## Which form should I use?

| Form | Typical use |
|---|---|
| `function name() { }` (declaration) | named, top-level functions; hoisted, so order doesn't matter |
| `const name = () => ...` (arrow) | short functions, and functions passed to other functions (next lessons) |
| `const name = function () { }` (expression) | rarely needed now; you'll see it in older code |

Arrow functions also differ in how they treat `this`, which matters for methods (Module 8). Until then, the choice is mostly style. Many teams use declarations for named functions and arrows for small callbacks.

## Missing and extra arguments

JavaScript doesn't check how many arguments you pass:

```js
function describe(name, age) {
  return `${name} is ${age}`;
}
console.log(describe("Ada", 36));
console.log(describe("Ada"));
console.log(describe("Ada", 36, "London"));
```

A missing argument makes its parameter `undefined`; extra arguments are simply ignored. That's flexible, but it hides bugs, which is one reason TypeScript exists (Module 12).

## Default parameters

Give a parameter a **default value** with `=`. It's used when the argument is missing (or is `undefined`):

```js
function greet(name = "friend", greeting = "Hello") {
  return `${greeting}, ${name}!`;
}
console.log(greet());
console.log(greet("Ada"));
console.log(greet("Ada", "Welcome"));
console.log(greet(undefined, "Hi"));
```

Defaults are evaluated at each call, and can even use earlier parameters: `function box(width, height = width) { ... }` makes a square when no height is given.

## Rest parameters: any number of arguments

A parameter written with three dots, `...name`, collects **all remaining arguments** into an array (an ordered list; arrays get their own module next, but `for...of` already works on them):

```js
function sum(...numbers) {
  let total = 0;
  for (const n of numbers) {
    total += n;
  }
  return total;
}
console.log(sum());
console.log(sum(4));
console.log(sum(1, 2, 3, 4, 5));
```

`Math.max(3, 9, 2)` works the same way: it accepts any number of arguments. The rest parameter must be the **last** parameter: `function log(level, ...messages)`.

You may see the old `arguments` object in legacy code, which also holds all the arguments. It doesn't work in arrow functions and isn't a real array; use rest parameters instead.

## Choosing good parameters

- **Few parameters.** Three is plenty. A call like `createUser("Ada", 36, true, false, "UK")` is impossible to read; Module 6 shows how to pass one *object* with named properties instead.
- **Required first, optional last**, so callers can leave the optional ones out.
- **Don't change parameters** to pass results back. Return a value instead.

=== lesson js-scope-closures | Scope, closures and the call stack | 85
## Where can a variable be seen?

A variable's **scope** is the part of the program where its name can be used. JavaScript has three levels:

- **Global scope**: declared outside any function or block; visible everywhere in the file.
- **Function scope**: declared inside a function (including its parameters); visible only inside that function.
- **Block scope**: declared with `let` or `const` inside `{ }` (an `if`, a loop...); visible only inside that block.

```js
const appName = "DevQuest";
function welcome(user) {
  const message = `Welcome to ${appName}, ${user}!`;
  return message;
}
console.log(welcome("Ada"));
console.log(message);
```

The function can see the global `appName`, but `message` belongs to the function and doesn't exist outside it. Every call gets **fresh** local variables, which disappear when the call ends.

**Keep variables in the smallest scope that works.** Global variables can be changed from anywhere, so when one has a wrong value, any line in the program could be to blame.

## Shadowing

An inner scope may declare a name that also exists outside. Inside, the inner one wins; it **shadows** the outer one:

```js
const level = "global";
function test() {
  const level = "function";
  if (true) {
    const level = "block";
    console.log(level);
  }
  console.log(level);
}
test();
console.log(level);
```

It's legal, but it makes code confusing to read; linters (Module 12) can warn you about it.

## Lexical scope: where the code is written

JavaScript looks a name up **from the inside out**: the current block, then the enclosing blocks, then the function, then the scope *where the function was written*, out to the global scope. This is called **lexical scope**: what matters is where the code sits in the source, not where it's called from.

```js
const x = "outer";
function show() {
  return x;
}
function caller() {
  const x = "caller's own";
  return show();
}
console.log(caller());
```

`show` was written next to the outer `x`, so that's the one it sees, even though it's called from inside `caller`.

## The call stack

When a function calls another function, JavaScript has to remember where to come back to. It keeps a **call stack**: each call pushes a *frame* (that call's local variables and its position) on top; when a call returns, its frame is popped off and execution continues in the frame below.

```js
function c() {
  throw new Error("Something went wrong in c");
}
function b() {
  c();
}
function a() {
  b();
}
a();
```

The error shows the stack at the moment it happened, innermost call first: `c` was called by `b`, called by `a`, called from the top level. Node.js prints the same chain as `at c (file.js:2:9)`, `at b (file.js:5:3)` and so on. When an error is raised deep inside your program, this trace tells you the path that led there; the bug is often in a caller that passed a bad value, not in the function that crashed.

## Closures

Here's where JavaScript gets powerful. A function remembers the scope it was **created** in, even after that outer function has finished:

```js
function makeCounter() {
  let count = 0;
  return () => {
    count++;
    return count;
  };
}

const counter = makeCounter();
console.log(counter());
console.log(counter());
console.log(counter());
```

`makeCounter` has finished running, so you might expect `count` to be gone. But the arrow function it returned still refers to `count`, so JavaScript keeps it alive. A function together with the variables it remembers is called a **closure**.

Each call to `makeCounter` creates a **new** `count`, so counters are independent:

```js
function makeCounter() {
  let count = 0;
  return () => ++count;
}
const visits = makeCounter();
const clicks = makeCounter();
visits();
visits();
clicks();
console.log("visits:", visits(), "clicks:", clicks());
```

Closures give you **private state**: nothing outside can read or change `count` except through the function. That's the foundation of many patterns you'll meet: event handlers that remember things, functions configured once and used many times, and the module pattern.

## Function factories

A function that builds and returns configured functions is a **factory**:

```js

    done = true;

  };

```

## Closures in loops: let saves the day

Each iteration of a `for (let ...)` loop gets its **own** copy of the loop variable, so functions created in the loop remember the value of their own iteration. `setTimeout(fn, ms)` runs `fn` later, after the loop has finished:

```js

  setTimeout(() => console.log("let:", i), 0);
}
for (var j = 1; j <= 3; j++) {
  setTimeout(() => console.log("var:", j), 0);
}
```

With old-style `var`, there's only **one** `j` for the whole loop, and by the time the functions run it has reached 4. This exact bug filled the internet with questions for years; `let` fixed it. One more reason to never use `var`.

## A function that calls itself

A **recursive** function solves a problem by calling **itself** on a smaller version of the same problem. It sounds circular, but it's how many problems are most naturally described. A countdown from `n` is: "say `n`, then do a countdown from `n - 1`", and a countdown from 0 is "say Liftoff!".

```js
function countdown(n) {
  if (n === 0) {
    console.log("Liftoff!");
    return;
  }
  console.log(n);
  countdown(n - 1);
}
countdown(3);
```

Every recursive function needs two parts:

1. **A base case**: a version so small it's answered directly, without recursion (`n === 0`).
2. **A recursive case**: the function calls itself on a **smaller** problem that gets closer to the base case (`n - 1`).

## Recursion that returns values

The factorial of n (written n!) is 1 × 2 × 3 × ... × n. Notice that 5! = 5 × 4!. That's a recursive definition:

```js
function factorial(n) {
  if (n <= 1) return 1;
  return n * factorial(n - 1);
}
console.log(factorial(5));
```

Here's what happens, using the call stack from the last lesson:

```
factorial(5) = 5 * factorial(4)
                   factorial(4) = 4 * factorial(3)
                                      factorial(3) = 3 * factorial(2)
                                                         factorial(2) = 2 * factorial(1)
                                                                            factorial(1) = 1
                                                         factorial(2) = 2 * 1 = 2
                                      factorial(3) = 3 * 2 = 6
                   factorial(4) = 4 * 6 = 24
factorial(5) = 5 * 24 = 120
```

The calls pile up on the stack until the base case returns; then each waiting call finishes its multiplication on the way back down.

## Forgetting the base case

Without a base case that's actually reached, the function calls itself forever, or rather, until the call stack runs out of space:

```js
function forever(n) {
  return forever(n + 1);
}
forever(1);
```

`RangeError: Maximum call stack size exceeded` is JavaScript's name for a **stack overflow**. When you see it, check that your base case exists and that every recursive call really moves towards it. The same error appears if the input is simply too big: JavaScript allows roughly ten thousand nested calls, so recursion isn't suitable for going 100,000 levels deep.

## Recursion on strings

Strings shrink nicely: work on the first character, recurse on the rest with `slice(1)`, and stop at the empty string.

```js
function reverse(text) {
  if (text === "") return "";
  return reverse(text.slice(1)) + text[0];
}
function countChar(text, ch) {
  if (text.length === 0) return 0;
  const here = text[0] === ch ? 1 : 0;
  return here + countChar(text.slice(1), ch);
}
console.log(reverse("recursion"));
console.log(countChar("banana", "a"));
```

## Recursion versus loops

Anything a loop can do, recursion can do, and vice versa. For simple counting, a loop is usually clearer and faster in JavaScript. Recursion shines when the data itself is **nested** or branches: folders inside folders, comments with replies to replies, the structure of a web page, game trees, or the "divide and conquer" algorithms of the DSA track. You'll write recursion over nested arrays and objects in Module 6.

## Branching recursion and its cost

Some recursive functions call themselves **more than once**. The Fibonacci numbers (0, 1, 1, 2, 3, 5, 8, 13...) are each the sum of the two before:

```js
let calls = 0;
function fib(n) {
  calls++;
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);
}
console.log(fib(25), "after", calls, "calls");
```

A quarter of a million calls for `fib(25)`! The same values are recomputed over and over: `fib(23)` is computed twice, `fib(22)` three times, and so on, so the work roughly doubles with every step up. Two fixes:

- Rewrite it as a **loop** that keeps the last two values.
- **Memoize** it: remember results you've already computed, so each is calculated once. You'll do this with a closure and a `Map` in Module 6.

## A classic: the Towers of Hanoi

Move a tower of discs from peg A to peg C, one disc at a time, never putting a bigger disc on a smaller one. The recursive insight: to move `n` discs, move the top `n - 1` out of the way to the spare peg, move the biggest disc, then move the `n - 1` back on top of it.

```js
function hanoi(n, from, to, spare) {
  if (n === 0) return;
  hanoi(n - 1, from, spare, to);
  console.log(`Move disc ${n} from ${from} to ${to}`);
  hanoi(n - 1, spare, to, from);
}
hanoi(3, "A", "C", "B");
```

Seven moves for three discs; `n` discs always need 2ⁿ − 1 moves. Trying to plan this with loops is surprisingly hard; the recursive version is five lines.

## How to think recursively

1. **What's the smallest input?** Answer it directly: that's the base case.
2. **Assume the function already works for a smaller input.** Don't trace every call in your head; trust it.
3. **How do you build the answer for this input from the answer for the smaller one?** That's the recursive case.

Step 2 is the "leap of faith" that makes recursion click. You check it once, with the base case and one step, rather than following every call.

## Passing functions around

Since functions are values, you can pass them **to** other functions and get them **back** from functions. A function that takes or returns another function is a **higher-order function**. This is one of JavaScript's most important ideas: the whole browser, Node.js and every modern framework are built on it.

```js
function repeat(times, action) {
  for (let i = 1; i <= times; i++) {
    action(i);
  }
}
repeat(3, (n) => console.log(`Hello number ${n}`));
repeat(2, (n) => console.log("*".repeat(n)));
```

`repeat` knows *how often* to do something; the caller decides *what*. The function you pass in (`action`) is called a **callback**: you hand it over, and the other function calls it back when it's time.

Note the difference between passing a function and calling it: `repeat(3, sayHi)` passes the function; `repeat(3, sayHi())` would call `sayHi` right away and pass its *result* (probably `undefined`).

## Callbacks customise behaviour

Higher-order functions let you write the general part once and plug in the specific part:

```js
function countWhere(text, test) {
  let count = 0;
  for (const ch of text) {
    if (test(ch)) count++;
  }
  return count;
}
const sentence = "Hello World, 2026!";
console.log(countWhere(sentence, (ch) => "aeiouAEIOU".includes(ch)));
console.log(countWhere(sentence, (ch) => ch === ch.toUpperCase() && ch !== ch.toLowerCase()));
console.log(countWhere(sentence, (ch) => "0123456789".includes(ch)));
```

One loop, three different questions. A callback that returns `true` or `false` like `test` is called a **predicate**.

## Returning functions

The other direction: functions that **build** functions. You did this with closures in the scope lesson:

```js
const multiplyBy = (factor) => (n) => n * factor;

```

`(factor) => (n) => n * factor` reads as "given a factor, return a function that, given n, returns n times factor". Arrows chained like this are common in modern code.

## Composing functions

Small functions can be glued together. `compose(f, g)` returns a new function that applies `g`, then `f`:

```js
const compose = (f, g) => (x) => f(g(x));
const trim = (s) => s.trim();
const upper = (s) => s.toUpperCase();
const exclaim = (s) => s + "!";
const shout = compose(exclaim, compose(upper, trim));
console.log(shout("   hello  "));
```

This style, building programs from small, pure, combinable functions, is called **functional programming**. You'll do more of it in Module 12.

## Wrapping a function to add behaviour

A higher-order function can return a new version of a function with something extra, without touching the original's code. This is called a **decorator** or **wrapper**:

```js
function logged(fn, name) {
  return (...args) => {
    const result = fn(...args);
    console.log(`${name}(${args.join(", ")}) -> ${result}`);
    return result;
  };
}
const add = (a, b) => a + b;
const loggedAdd = logged(add, "add");
loggedAdd(2, 3);
loggedAdd(10, -4);
```

`(...args)` collects whatever arguments the wrapper gets, and `fn(...args)` **spreads** them back out into the original function. Professional code uses wrappers like this for logging, timing, caching results and checking permissions.

::prompt
Write `caesar(text, shift)` that encrypts text with a **Caesar cipher**: each letter is moved `shift` places along the alphabet, wrapping around from z to a. Keep the case of each letter, and leave everything else (spaces, digits, punctuation) unchanged. Negative shifts move backwards, so `caesar(caesar(t, 3), -3)` gives back `t`.

Two helpers: `"a".charCodeAt(0)` is 97 (the code of a character), and `String.fromCharCode(98)` is `"b"`. Lowercase letters are codes 97 to 122, uppercase 65 to 90. To wrap a position `p` from 0 to 25 safely, even for negative shifts, use `((p % 26) + 26) % 26`.
::starter
function caesar(text, shift) {
}
::solution
function shiftLetter(ch, shift, base) {
  const p = ch.charCodeAt(0) - base + shift;
  return String.fromCharCode(base + (((p % 26) + 26) % 26));
}

function caesar(text, shift) {
  let result = "";
  for (const ch of text) {
    if (ch >= "a" && ch <= "z") result += shiftLetter(ch, shift, 97);
    else if (ch >= "A" && ch <= "Z") result += shiftLetter(ch, shift, 65);
    else result += ch;
  }
  return result;
}
::tests
assert.strictEqual(caesar("abc", 1), "bcd");
assert.strictEqual(caesar("xyz", 3), "abc");
assert.strictEqual(caesar("Hello, World!", 3), "Khoor, Zruog!");
assert.strictEqual(caesar("Khoor, Zruog!", -3), "Hello, World!");
assert.strictEqual(caesar("abc", 26), "abc");
assert.strictEqual(caesar("Attack at 10pm", 13), "Nggnpx ng 10cz");
assert.strictEqual(caesar("", 5), "");
assert.strictEqual(caesar("a", -1), "z");
::hints
- Loop over the characters; letters are shifted, everything else is copied as it is.
- A helper function `shiftLetter(ch, shift, base)` avoids writing the maths twice (base 97 for lowercase, 65 for uppercase).
- Position in the alphabet: `ch.charCodeAt(0) - base`. Add the shift, wrap it, and add `base` back.

Write `memoize(fn)` that returns a version of the one-argument function `fn` that **remembers** results: the first call with a given argument calls `fn`; later calls with the **same** argument return the remembered result without calling `fn` again. Store results in an object used as a lookup table: `const cache = {};`, then `cache[arg]` reads or writes the result for `arg`, and `arg in cache` tells you whether it's there. (Objects get a full module next; this is all you need.)
::starter

}
::solution
function memoize(fn) {
  const cache = {};
  return (arg) => {
    if (!(arg in cache)) {
      cache[arg] = fn(arg);
    }
    return cache[arg];
  };
}
::tests

assert.strictEqual(__calls, 2);

::hints
