## One file is not enough

Real programs have thousands of lines. Keeping them in one file makes every name global to everything, every change risky, and nothing reusable. **Modules** split a program into files, each with its own scope, that explicitly **export** what others may use and **import** what they need.

Modern JavaScript has a built-in module system, **ES modules** (ESM), used by browsers, Node.js and every modern tool. In DevQuest, write several files in one editor by starting each with a marker line `// file: name.js`; the program starts from `main.js`. On your computer, these would simply be separate files in one folder.

```js
// file: math.js
export const PI = 3.14159;

export function circleArea(r) {
  return PI * r ** 2;
}

function secretHelper() {
  return "not exported, so nobody else can use me";
}

// file: main.js
import { PI, circleArea } from "./math.js";

console.log(PI, circleArea(2).toFixed(2));
```

- `export` in front of a declaration makes it available to other modules. Everything else (`secretHelper`) stays **private** to its file.
- `import { ... } from "./math.js"` brings in exported names. The path is relative to the importing file; `./` means "the same folder", `../` "the folder above". Include the `.js` extension (browsers and Node require it for your own files).
- Each module has its **own scope**: a `const` at the top of `math.js` isn't a global, and two modules can both have a variable called `total` without clashing.
- Modules are always in **strict mode**, and may use **top-level `await`**.

## Named and default exports

A module can have many **named** exports and at most one **default** export, the module's "main thing":

```js
// file: shapes.js
export default class Circle {
  constructor(r) {
    this.r = r;
  }
  get area() {
    return Math.PI * this.r ** 2;
  }
}
export const unitCircle = new Circle(1);

// file: main.js
import Circle, { unitCircle } from "./shapes.js";
import * as shapes from "./shapes.js";
import { unitCircle as unit } from "./shapes.js";

console.log(new Circle(2).area.toFixed(1), unitCircle.area.toFixed(2));
console.log(Object.keys(shapes), unit === unitCircle);
```

| Syntax | Imports |
|---|---|
| `import Circle from "./shapes.js"` | the default export, under any name you choose |
| `import { unitCircle } from "./shapes.js"` | a named export, by its exact name |
| `import { unitCircle as unit } from ...` | a named export, renamed |
| `import * as shapes from ...` | everything, as one object (a *namespace*) |

On the exporting side you can also export a list at the end of a file, `export { area, PI as pi };`, or re-export from another module, `export { slugify } from "./strings.js";`. That's how libraries offer one tidy entry file (`index.js`) that gathers everything.

Many teams prefer **named exports only**: the name is the same everywhere it's used, editors can auto-import it, and typos are errors. Importing a name that doesn't exist fails immediately:

```js
// file: math.js
export const add = (a, b) => a + b;
// file: main.js
import { ad } from "./math.js";
console.log(ad(1, 2));
```

## A module runs once

The first `import` of a module runs its code; every later import, from anywhere, gets the **same** module instance. That makes a module a natural place for shared state and one-time setup:

```js
// file: counter.js
console.log("counter.js runs (only once)");
let count = 0;
export function increment() {
  count++;
  return count;
}
// file: a.js
import { increment } from "./counter.js";
export const fromA = increment();
// file: main.js
import { fromA } from "./a.js";
import { increment } from "./counter.js";
console.log(fromA, increment(), increment());
```

Imports are also **live, read-only views**: you can't assign to an imported name (`count = 5` is an error in the importing module), but if the exporting module changes its variable, importers see the new value.

## Loading on demand: dynamic import()

`import(path)` is a function-like expression that loads a module **when it's called** and returns a promise of its namespace object. Use it for code that isn't always needed, such as a big charting library only loaded when the user opens the charts page:

```js
// file: main.js
const wantsReport = true;
if (wantsReport) {
  const { default: makeReport } = await import("./report.js");
  console.log(makeReport([3, 5, 8]));
}
// file: report.js
export default function makeReport(values) {
  return `Total: ${values.reduce((a, b) => a + b, 0)}`;
}
```

Bundlers split dynamically imported modules into separate files ("code splitting"), so web pages start faster.

## Modules in the browser

A page loads a module with `type="module"`:

```
<script type="module" src="main.js"></script>
```

Module scripts are deferred (they run after the page has been parsed) and follow the import graph themselves. Without `type="module"`, `import` statements are a SyntaxError: the classic beginner trap. (Opening an HTML file straight from your disk, with a `file://` address, also blocks module loading for security reasons; use a small local server such as `npx serve` or VS Code's Live Server.)

## CommonJS: Node's older module system

Before ES modules existed (2015), Node.js invented its own system, **CommonJS**, and a huge amount of code and many tutorials still use it:

```
// math.cjs
function add(a, b) { return a + b; }
module.exports = { add };

// main.cjs
const { add } = require("./math.cjs");
```

Differences: `require()` is an ordinary function call that loads modules synchronously, can be called anywhere (even inside an `if`), and returns whatever `module.exports` is. In Node, a `.js` file is treated as an ES module when the nearest `package.json` says `"type": "module"` (or the file ends in `.mjs`), and as CommonJS otherwise (or with `.cjs`). New projects should use ES modules; be able to read `require` when you meet it.

## Designing modules

- **One clear responsibility per module**, like classes: `money.js`, `cart.js`, `api-client.js`.
- **Export a small surface**: the fewer exported names, the more you can change inside freely.
- **Avoid circular imports** (A imports B and B imports A): they work in simple cases but lead to confusing "used before initialised" errors. A cycle usually means some code belongs in a third module.
- **Keep side effects out of module top level** when you can: a module that does work just by being imported (connecting to a database, changing globals) is surprising. Export functions that do the work when called.

=== lesson js-npm | Packages and npm | 80
## Standing on other people's shoulders

Nobody writes everything from scratch. Need to parse dates, talk to a database, run tests or build a website? Someone has published a **package** for it. **npm** (the Node Package Manager) is both the tool that installs packages and the registry (npmjs.com) that hosts more than two million of them: the largest software library in the world. It's installed together with Node.js.

## Starting a project: package.json

Every JavaScript project has a `package.json` at its root, describing it. Create one with:

```
npm init -y
```

A typical one, a bit later in the project's life:

```json
{
  "name": "budget-tracker",
  "version": "1.2.0",
  "type": "module",
  "scripts": {
    "start": "node src/main.js",
    "test": "node --test",
    "lint": "eslint ."
  },
  "dependencies": {
    "date-fns": "^4.1.0"
  },
  "devDependencies": {
    "eslint": "^9.12.0"
  }
}
```

- `"type": "module"` makes `.js` files ES modules (otherwise Node treats them as CommonJS).
- `scripts` are named commands: `npm run lint`, and the special shortcuts `npm start` and `npm test`. Scripts can use any installed tool by name.
- `dependencies` are packages your code needs to **run**; `devDependencies` are only needed while **developing** (test runners, linters, bundlers).

## Installing packages

```
npm install date-fns
npm install --save-dev eslint
npm install
```

The first command downloads `date-fns` into a folder called `node_modules` and records it in `package.json`; the second adds a dev dependency; the third, with no name, installs everything listed in `package.json` (what you run after cloning a project). Then you import a package by its **name**, without `./`:

```
import { format, addDays } from "date-fns";
console.log(format(addDays(new Date(2026, 0, 31), 1), "yyyy-MM-dd"));
```

Rules every team follows:

- **Never commit `node_modules`** (it can contain tens of thousands of files); put it in `.gitignore`. Anyone can recreate it with `npm install`.
- **Do commit `package-lock.json`**. It records the exact version of every package (including the packages your packages depend on), so every developer and every server installs exactly the same code. `npm ci` installs strictly from the lock file, which is what CI pipelines use.
- `npx some-tool` runs a package's command without installing it permanently: `npx serve` starts a quick web server.

(DevQuest can't install packages: its sandbox has no internet access to the registry. It includes a few of Node's built-in modules, covered next lesson.)

## Semantic versioning

Package versions follow **semver**: `MAJOR.MINOR.PATCH`, such as `4.1.0`.

| Part | Increases when... | Safe to upgrade? |
|---|---|---|
| PATCH (4.1.**1**) | bugs are fixed | yes |
| MINOR (4.**2**.0) | features are added, nothing breaks | yes |
| MAJOR (**5**.0.0) | something **breaking** changes | read the changelog first |

In `package.json`, `"^4.1.0"` (the caret, npm's default) means "4.1.0 or any newer 4.x.y", so you get fixes and features but never a breaking major version. `"~4.1.0"` allows only patches (4.1.x); `"4.1.0"` pins one exact version. Versions starting with `0.` are special: `0.x` packages may break things in any minor release.

## Choosing packages wisely

Every dependency is code you didn't write but are responsible for. Before adding one, check:

- **Do you need it?** Modern JavaScript has `fetch`, `structuredClone`, `Intl`, array methods... A five-line function is often better than a package.
- **Is it maintained?** Recent releases, open issues being answered, a real repository.
- **Is it popular and trusted?** Weekly downloads, who maintains it.
- **What does it pull in?** Some small packages bring dozens of dependencies with them.
- **Licence**: MIT, Apache-2.0 and BSD are permissive; check before using anything else in a commercial product.

Supply-chain attacks (malicious code slipped into a package, or a lookalike package name such as `lodahs`) are real. `npm audit` lists known vulnerabilities in your dependencies, and `npm outdated` shows what's behind. Keep dependencies few and up to date.

## The tools behind a modern project

Most front-end projects use npm packages for their whole toolchain, which you'll meet in Module 12: a **bundler/dev server** (Vite) that serves and optimises the code, **TypeScript** for types, **ESLint** to catch mistakes, **Prettier** to format code, and a **test runner** (Vitest or Node's own). They're all `devDependencies`, all started through `scripts`. DevQuest itself is built exactly this way.

::solution
function parse(v) {
  return v.split(".").map(Number);
}

function satisfiesCaret(version, range) {
  const [ma, mi, pa] = parse(version);
  const [rma, rmi, rpa] = parse(range.slice(1));
  if (ma !== rma) return false;
  if (mi !== rmi) return mi > rmi;
  return pa >= rpa;
}

function outdated(pkg, latest) {
  const all = { ...(pkg.dependencies ?? {}), ...(pkg.devDependencies ?? {}) };
  return Object.entries(all)
    .filter(([name, range]) => name in latest && !satisfiesCaret(latest[name], range))
    .map(([name]) => name)
    .sort();
}

assert.strictEqual(satisfiesCaret("2.2.9", "^2.3.1"), false);
assert.strictEqual(satisfiesCaret("3.0.0", "^2.3.1"), false);

=== lesson js-node | Node.js: files, processes and the command line | 90
## JavaScript outside the browser

**Node.js** (2009) took Chrome's V8 engine out of the browser and gave it access to the computer: files, network, processes. It made JavaScript a general-purpose language: web servers (Express, Fastify, NestJS), command-line tools (npm itself, ESLint, Vite), desktop apps (Electron, which DevQuest uses) and scripts.

Node has no `document` or `window`, but it has a large **standard library** of built-in modules, imported with the `node:` prefix. DevQuest includes a small, sandboxed version of the most common ones (`node:fs` works on an in-memory disk, so nothing on your computer is touched), so the examples here run as they would in Node.

## A program's surroundings: process

The global `process` object describes the running program:

```js
console.log(process.argv);
console.log(process.cwd(), process.platform);
console.log(process.env.HOME ?? "no HOME variable here");
process.stdout.write("write without a new line... ");
process.stdout.write("then finish the line\n");
```

- `process.argv` holds the **command-line arguments**: `node app.js report --verbose` gives `["/path/to/node", "/path/to/app.js", "report", "--verbose"]`, so your own arguments start at index 2: `process.argv.slice(2)`.
- `process.env` holds **environment variables**: configuration such as `process.env.PORT` or API keys, kept outside the code.
- `process.exit(code)` ends the program at once; by convention `0` means success and anything else failure, which scripts and CI systems check.

## Reading and writing files: node:fs

```js
// file: notes.txt
buy milk
call the plumber
learn Node.js
// file: main.js
import { readFileSync, writeFileSync, existsSync } from "node:fs";

const text = readFileSync("notes.txt", "utf8");
const lines = text.split("\n");
console.log(`${lines.length} notes, the first is "${lines[0]}"`);

const numbered = lines.map((line, i) => `${i + 1}. ${line}`).join("\n");
writeFileSync("numbered.txt", numbered);
console.log(existsSync("numbered.txt"));
console.log(readFileSync("numbered.txt", "utf8"));
```

(The `// file: notes.txt` section is how DevQuest creates a file for the program to read.) Pass `"utf8"` to get text; without an encoding, Node gives you raw bytes (a `Buffer`). A missing file throws an error with `code: "ENOENT"` ("error, no entry"), the most common file error:

```js
import { readFileSync } from "node:fs";
try {
  readFileSync("missing.json", "utf8");
} catch (error) {
  console.log(error.code, "-", error.message);
}
```

## Sync or async?

Every `fs` function comes in two styles:

- `readFileSync` (synchronous) **blocks** until the file is read. Fine in scripts and command-line tools that do one thing at a time.
- `readFile` from `node:fs/promises` (asynchronous) returns a promise, so the program can do other work meanwhile. **Use this in servers**: a server that blocks on a file read stops answering every other user for that moment.

```js

```

## Paths: node:path

Never glue paths together with `+ "/" +`: Windows uses `\`, other systems `/`. `node:path` handles it:

```js
import path from "node:path";

console.log(path.join("reports", "2026", "..", "summary.txt"));
console.log(path.basename("/home/ada/photos/cat.jpg"), path.extname("cat.jpg"));
console.log(path.dirname("/home/ada/photos/cat.jpg"));
console.log(path.parse("/home/ada/notes.txt"));
```

(On Windows, `path.join` produces backslashes; DevQuest behaves like Linux and macOS.)

## Events: node:events

Many Node objects (servers, streams, processes) are **event emitters**, the observer pattern from Module 9. You can make your own:

```js
import { EventEmitter } from "node:events";

class Downloader extends EventEmitter {
  async download(files) {
    for (const [i, file] of files.entries()) {
      await new Promise((r) => setTimeout(r, 20));
      this.emit("progress", file, Math.round(((i + 1) / files.length) * 100));
    }
    this.emit("done", files.length);
  }
}

const d = new Downloader();
d.on("progress", (file, percent) => console.log(`${file}: ${percent}%`));
d.once("done", (count) => console.log(`Finished ${count} files`));
await d.download(["a.zip", "b.zip", "c.zip"]);
```

## Servers, briefly

Node's best-known job is serving web requests. With the built-in `node:http` module, a complete server is a few lines (this one can't run inside DevQuest, which has no network ports; try it on your computer and open http://localhost:3000):

```
import http from "node:http";

const server = http.createServer((request, response) => {
  response.writeHead(200, { "Content-Type": "application/json" });
  response.end(JSON.stringify({ message: "Hello from Node!", path: request.url }));
});
server.listen(3000, () => console.log("Listening on http://localhost:3000"));
```

Real applications use a framework such as **Express** or **Fastify** on top of this for routing, parsing request bodies and middleware. The Web Development and backend career paths build on exactly this.

## Streams, briefly

`readFileSync` loads a whole file into memory, which fails for a 20 GB log file. **Streams** process data piece by piece: `fs.createReadStream(path)` gives chunks as they're read, and `for await (const line of readline.createInterface({ input: stream }))` reads a huge file line by line with almost no memory. Network sockets, HTTP bodies and compression all use streams.

## The page as a tree of objects

When a browser loads HTML, it builds the **DOM** (Document Object Model): a tree of objects, one for every element, piece of text and comment. JavaScript changes a page by changing this tree; the browser redraws the screen to match.

```
<body>
  <h1>Shopping</h1>
  <ul id="list">
    <li>Milk</li>
    <li class="done">Bread</li>
  </ul>
</body>
```

becomes a tree: `body` has two children, `h1` and `ul`; the `ul` has two `li` children, each containing a text node. Every element object has properties (`id`, `className`, `textContent`...) and methods, and links to its relatives: `parentElement`, `children`, `firstElementChild`, `nextElementSibling`.

The global `document` object is the entry point. The examples in this module are whole web pages: press **▶ Show page** to see them, with anything they log shown underneath.

## Finding elements

```html
<!doctype html>
<html>
  <body>
    <h1 id="title">Shopping</h1>
    <ul id="list">
      <li>Milk</li>
      <li class="done">Bread</li>
      <li>Eggs</li>
    </ul>
    <script>
      const title = document.querySelector("#title");
      const firstItem = document.querySelector("#list li");
      const allItems = document.querySelectorAll("#list li");
      const done = document.querySelector(".done");
      console.log(title.textContent, "|", firstItem.textContent, "|", allItems.length, "|", done.textContent);
      for (const li of allItems) console.log("item:", li.textContent);
    </script>
  </body>
</html>
```

`querySelector(css)` returns the **first** element matching a CSS selector (or `null`); `querySelectorAll(css)` returns **all** of them, as a list you can loop over with `for...of` (spread it, `[...list]`, to use array methods like `map`). Any CSS selector works: `#id`, `.class`, `tag`, `ul > li`, `input[type=email]`, `li:nth-child(2)`. You'll also see the older `getElementById("title")`.

A script must run **after** the elements it uses exist. Put `<script>` at the end of `<body>` (as here), or add `defer` to a script in `<head>`, which waits until the page is parsed. A script that runs too early gets `null` from `querySelector`, and then `Cannot read properties of null` errors.

## Changing content and attributes

```html
<!doctype html>
<html>
  <body>
    <h1 id="title">Old title</h1>
    <p id="intro">Plain text</p>
    <a id="link" href="https://example.com">a link</a>
    <img id="pic" alt="placeholder" width="40" height="40">
    <script>
      document.querySelector("#title").textContent = "New title";
      const intro = document.querySelector("#intro");
      intro.innerHTML = "Text with <strong>bold</strong> in it";
      const link = document.querySelector("#link");
      link.href = "https://developer.mozilla.org";
      link.textContent = "MDN";
      link.setAttribute("target", "_blank");
      document.querySelector("#pic").alt = "A picture";
      console.log(link.getAttribute("href"), link.dataset.kind ?? "no data-kind");
    </script>
  </body>
</html>
```

- `textContent` gets or sets the **text** inside an element.
- `innerHTML` gets or sets the **HTML** inside it, parsing tags.
- Standard attributes are properties: `link.href`, `img.src`, `input.value`, `button.disabled`. For any attribute, use `getAttribute` / `setAttribute`; custom `data-*` attributes appear in `element.dataset` (`data-user-id` becomes `dataset.userId`).

⚠️ **Security rule: never put user-supplied text into `innerHTML`.** If a user's "name" is `<img src=x onerror="steal()">`, `innerHTML` would run their code in your page: a **cross-site scripting (XSS)** attack, one of the most common web vulnerabilities. Use `textContent` for text; it never interprets tags.

## Creating and removing elements

```html
<!doctype html>
<html>
  <body>
    <ul id="list"></ul>
    <script>
      const list = document.querySelector("#list");
      const fruits = ["Apple", "Banana", "Cherry"];
      for (const fruit of fruits) {
        const li = document.createElement("li");
        li.textContent = fruit;
        list.append(li);
      }
      const first = document.createElement("li");
      first.textContent = "Avocado (added first)";
      list.prepend(first);
      list.children[2].remove();
      console.log([...list.children].map((li) => li.textContent));
    </script>
  </body>
</html>
```

`document.createElement(tag)` makes a new element that's not yet on the page; `parent.append(child)` (or `prepend`, `before`, `after`) inserts it; `element.remove()` takes it out. When you build many elements, a common pattern is a function that turns one data item into one element, called in a loop: you'll write those in the exercises.

## Classes and styles

Change how things look by toggling **CSS classes**, rather than setting styles one by one: the CSS stays in the stylesheet, and JavaScript only says *which state* an element is in.

```html
<!doctype html>
<html>
  <head>
    <style>
      .done { text-decoration: line-through; color: gray; }
      .highlight { background: gold; }
    </style>
  </head>
  <body>
    <ul>
      <li id="a">Buy milk</li>
      <li id="b">Learn the DOM</li>
    </ul>
    <script>
      const a = document.querySelector("#a");
      a.classList.add("done");
      const b = document.querySelector("#b");
      b.classList.toggle("highlight");
      b.style.padding = "4px";
      console.log(a.classList.contains("done"), b.className, b.style.padding);
    </script>
  </body>
</html>
```

`classList.add`, `remove`, `toggle` and `contains` manage classes. `element.style.property` sets an inline style (CSS names in camelCase: `backgroundColor`); `getComputedStyle(element)` reads the final style after all CSS rules apply.

## Layout and animation

Elements also report their size and position: `element.getBoundingClientRect()` gives `{ x, y, width, height }` on screen, and `offsetWidth`/`offsetHeight` the size. For smooth animation, change things once per screen refresh with `requestAnimationFrame(callback)`, which calls back just before the browser draws the next frame (about 60 times per second):

```html
<!doctype html>
<html>
  <body>
    <div id="ball" style="width:30px;height:30px;border-radius:50%;background:tomato;position:relative"></div>
    <script>
      const ball = document.querySelector("#ball");
      const start = performance.now();
      function frame(now) {
        const t = (now - start) / 1000;
        ball.style.left = `${100 + Math.sin(t * 2) * 100}px`;
        if (t < 10) requestAnimationFrame(frame);
      }
      requestAnimationFrame(frame);
    </script>
  </body>
</html>
```

Basing the position on the **elapsed time** (not on "move 2 pixels per frame") keeps the speed the same on fast and slow screens. For simple effects, CSS transitions and animations are even better: the browser runs them without any JavaScript.

## Rendering data: the core of every front end

Most front-end code follows one pattern: keep the **data** in JavaScript, and write a function that **renders** the page from it. When the data changes, render again:

```html
<!doctype html>
<html>
  <body>
    <ul id="todos"></ul>
    <p id="count"></p>
    <script>
      const todos = [
        { text: "Learn the DOM", done: true },
        { text: "Learn events", done: false },
      ];
      function render() {
        const list = document.querySelector("#todos");
        list.replaceChildren(
          ...todos.map((t) => {
            const li = document.createElement("li");
            li.textContent = (t.done ? "✓ " : "○ ") + t.text;
            return li;
          }),
        );
        document.querySelector("#count").textContent = `${todos.filter((t) => !t.done).length} left`;
      }
      render();
      todos.push({ text: "Build an app", done: false });
      render();
    </script>
  </body>
</html>
```

`replaceChildren(...)` swaps out all the old children at once. Frameworks such as React, Vue and Svelte are, at heart, very clever versions of this `render()` function: you describe the page for the current data, and they work out the smallest set of DOM changes.

=== lesson js-events | Events | 85
## Reacting to the user

Pages come alive by **reacting**: to clicks, key presses, typing, scrolling, the page finishing loading. The browser fires an **event** for each of these, and you register a function, an **event listener** (or handler), to run when it happens:

```html
<!doctype html>
<html>
  <body>
    <button id="like">👍 Like</button>
    <span id="count">0</span>
    <script>
      let likes = 0;
      const button = document.querySelector("#like");
      button.addEventListener("click", () => {
        likes++;
        document.querySelector("#count").textContent = likes;
        console.log("clicked", likes);
      });
    </script>
  </body>
</html>
```

Click the button in the preview. `element.addEventListener(type, listener)` can be called several times for the same event; all listeners run, in order. `removeEventListener(type, sameFunction)` removes one (keep a reference to the function to do that). You'll see `onclick="..."` attributes in old HTML: avoid them, they mix behaviour into markup and allow only one handler.

## The event object

Every listener receives an **event object** with details about what happened:

```html
<!doctype html>
<html>
  <body>
    <button id="a">Click me</button>
    <input id="name" placeholder="Type here">
    <p id="out"></p>
    <script>
      document.querySelector("#a").addEventListener("click", (event) => {
        console.log(event.type, event.target.id, event.clientX >= 0, event.shiftKey);
      });
      document.querySelector("#name").addEventListener("input", (event) => {
        document.querySelector("#out").textContent = `Hello, ${event.target.value}!`;
      });
    </script>
  </body>
</html>
```

- `event.type`: which event (`"click"`).
- `event.target`: the element the event happened on.
- Mouse/pointer events: `clientX`/`clientY` (position), `button`; keyboard events: `key` (`"Enter"`, `"a"`, `"ArrowLeft"`), plus `shiftKey`, `ctrlKey`, `altKey`, `metaKey` on both.

## Common events

| Event | Fires when |
|---|---|
| `click`, `dblclick` | an element is clicked (also by keyboard on buttons) |
| `pointerdown`, `pointermove`, `pointerup` | mouse, pen or touch is pressed, moves, is released |
| `keydown`, `keyup` | a key is pressed / released (`event.key`) |
| `input` | a field's value changes, on every keystroke |
| `change` | a field's value is committed (select picked, checkbox ticked, input left) |
| `submit` | a form is submitted (next lesson) |
| `focus`, `blur` | an element gains / loses keyboard focus |
| `scroll`, `resize` | the page or an element scrolls / the window is resized |
| `DOMContentLoaded`, `load` | the HTML is parsed / everything, including images, has loaded |

## Default actions

Many events have a built-in **default action**: clicking a link navigates, submitting a form reloads the page, pressing space scrolls. `event.preventDefault()` cancels it, so your code can handle the event instead:

```html
<!doctype html>
<html>
  <body>
    <a id="link" href="https://example.com">Go somewhere</a>
    <p id="msg"></p>
    <script>
      document.querySelector("#link").addEventListener("click", (event) => {
        event.preventDefault();
        document.querySelector("#msg").textContent = "Navigation cancelled: handled in JavaScript instead.";
      });
    </script>
  </body>
</html>
```

## Propagation and event delegation

An event doesn't only fire on its target: it **bubbles up** through every ancestor, from the button to its list, to `body`, to `document`. A listener on a parent hears events from all its children:

```html
<!doctype html>
<html>
  <body>
    <ul id="list">
      <li><button data-id="1">Delete 1</button></li>
      <li><button data-id="2">Delete 2</button></li>
      <li><button data-id="3">Delete 3</button></li>
    </ul>
    <script>
      const list = document.querySelector("#list");
      list.addEventListener("click", (event) => {
        const button = event.target.closest("button");
        if (!button) return;
        console.log("delete item", button.dataset.id);
        button.closest("li").remove();
      });
    </script>
  </body>
</html>
```

This is **event delegation**: one listener on the container instead of one per item. It also works for items added **later**, which per-item listeners would miss. `event.target.closest("button")` finds the button even when the click landed on an icon inside it. (`event.stopPropagation()` stops the bubbling, but is rarely the right fix; prefer checking `event.target`.)

## Keyboard input

```html
<!doctype html>
<html>
  <body>
    <p>Click here, then use the arrow keys.</p>
    <div id="box" style="width:30px;height:30px;background:steelblue;position:relative;left:0;top:0"></div>
    <script>
      const pos = { x: 0, y: 0 };
      const box = document.querySelector("#box");
      document.addEventListener("keydown", (event) => {
        const moves = { ArrowLeft: [-10, 0], ArrowRight: [10, 0], ArrowUp: [0, -10], ArrowDown: [0, 10] };
        const move = moves[event.key];
        if (!move) return;
        event.preventDefault();
        pos.x += move[0];
        pos.y += move[1];
        box.style.left = pos.x + "px";
        box.style.top = pos.y + "px";
      });
    </script>
  </body>
</html>
```

`event.key` gives the character or key name, regardless of the keyboard layout. A lookup table (`moves`) beats a long `if` chain.

## Events and the event loop

Event handlers are **tasks** in the event loop from Module 10: they run one at a time, when the current code has finished. A slow handler freezes the page until it returns; keep handlers short, and start async work (`fetch`) from them rather than computing everything there. Rapid events like `input`, `scroll` and `pointermove` are where **debouncing** and **throttling** (Module 10) earn their keep.

## Accessibility

Use real `<button>` elements for things that are clicked: they can be focused with Tab and pressed with Enter or Space for free, and screen readers announce them as buttons. A `<div>` with a click listener works for mouse users only. Good event handling and good HTML go together.

## Forms: how users give you data

Sign-ups, searches, checkouts, settings: forms are how users give data to an application. HTML provides the controls; JavaScript reads them, validates them, and decides what to do on submit.

```html
<!doctype html>
<html>
  <body>
    <form id="signup">
      <label>Name <input name="name" required></label>
      <label>Email <input name="email" type="email" required></label>
      <label>Plan
        <select name="plan">
          <option value="free">Free</option>
          <option value="pro">Pro</option>
        </select>
      </label>
      <label><input name="news" type="checkbox"> Send me news</label>
      <button>Sign up</button>
    </form>
    <p id="result"></p>
    <script>
      const form = document.querySelector("#signup");
      form.addEventListener("submit", (event) => {
        event.preventDefault();
        const data = new FormData(form);
        const values = Object.fromEntries(data);
        document.querySelector("#result").textContent = JSON.stringify(values);
        console.log(values);
      });
    </script>
  </body>
</html>
```

Fill it in and press Sign up. Important pieces:

- Listen for the form's **`submit`** event, not the button's click: it also fires when the user presses Enter in a field.
- `event.preventDefault()` stops the browser's default action (sending the form and reloading the page), so JavaScript can handle it, for example by sending the data with `fetch`.
- `new FormData(form)` collects every named field; `Object.fromEntries(formData)` turns it into a plain object. Each field needs a `name` attribute to be included.
- Field values are **always strings** (`"3"`, not 3); an unchecked checkbox is simply missing. Convert as needed.

## Reading individual controls

| Control | Read with |
|---|---|
| text, email, password, textarea | `input.value` (a string) |
| number, range | `input.value` (a string) or `input.valueAsNumber` |
| checkbox | `checkbox.checked` (true/false) |
| radio buttons | `form.elements.size.value` (the checked one in the group named `size`) |
| select | `select.value` (the selected option's value) |
| file | `input.files` (a list of `File` objects) |

`form.elements.name` reaches any named field of a form.

## Built-in validation

HTML can validate many things without any JavaScript, using attributes: `required`, `type="email"`, `type="url"`, `min`/`max` (numbers and dates), `minlength`/`maxlength`, and `pattern` (a regular expression). The browser refuses to submit an invalid form and shows a message next to the first problem.

From JavaScript you can use the same machinery, the **Constraint Validation API**:

- `input.checkValidity()` / `form.checkValidity()` return true or false;
- `input.validity` tells you why (`valueMissing`, `typeMismatch`, `tooShort`, `patternMismatch`...);
- `input.setCustomValidity("message")` marks a field invalid with your own message (and `""` makes it valid again), for rules HTML can't express:

```html
<!doctype html>
<html>
  <body>
    <form id="f" novalidate>
      <label>Password <input id="pw" type="password" minlength="8" required></label>
      <label>Repeat <input id="pw2" type="password" required></label>
      <button>Save</button>
    </form>
    <p id="msg"></p>
    <script>
      const form = document.querySelector("#f");
      const pw = document.querySelector("#pw");
      const pw2 = document.querySelector("#pw2");
      form.addEventListener("submit", (event) => {
        event.preventDefault();
        pw2.setCustomValidity(pw.value === pw2.value ? "" : "The passwords don't match");
        const problems = [pw, pw2].filter((input) => !input.checkValidity()).map((input) => input.validationMessage);
        document.querySelector("#msg").textContent = problems.length ? problems.join(" / ") : "Saved!";
      });
    </script>
  </body>
</html>
```

(`novalidate` turns off the browser's own pop-up messages so the page shows its messages itself; the rules still apply.)

⚠️ **Client-side validation is for the user's convenience, not for security.** Anyone can bypass your JavaScript (open the developer tools, or send requests directly). The server must validate everything again.

## Storing data in the browser

Web pages forget everything when they're reloaded, unless they store data. **Web Storage** keeps small amounts of data in the browser, per website:

- `localStorage` keeps data **until it's deleted**, even after the browser is closed;
- `sessionStorage` keeps it only **for the current tab**, until the tab is closed.

Both store **strings only**, so objects go through JSON (Module 6):

```html
<!doctype html>
<html>
  <body>
    <label><input id="dark" type="checkbox"> Dark mode</label>
    <p id="visits"></p>
    <script>
      const settings = JSON.parse(localStorage.getItem("settings") ?? '{"dark": false, "visits": 0}');
      settings.visits++;
      localStorage.setItem("settings", JSON.stringify(settings));
      const box = document.querySelector("#dark");
      box.checked = settings.dark;
      box.addEventListener("change", () => {
        settings.dark = box.checked;
        localStorage.setItem("settings", JSON.stringify(settings));
        document.body.style.background = settings.dark ? "#222" : "";
        document.body.style.color = settings.dark ? "#eee" : "";
      });
      document.querySelector("#visits").textContent = `Visits on this device: ${settings.visits}`;
      console.log(localStorage.getItem("settings"));
    </script>
  </body>
</html>
```

The methods are `setItem(key, text)`, `getItem(key)` (or `null` if missing, hence the `??` default), `removeItem(key)` and `clear()`. (DevQuest's previews run in a sealed sandbox, so their storage resets every run; on a real website it persists.) Remember:

- Storage holds about 5 MB per site and is synchronous, so keep it small: preferences, drafts, a cart.
- **Never store secrets** (passwords, tokens if avoidable): any script on the page, including an injected one, can read it.
- For larger or structured data (thousands of records, offline apps), browsers have **IndexedDB**, an asynchronous database; most people use it through a small library such as `idb`.
- **Cookies** are the other classic storage, mainly for the server's benefit (sessions): they're sent with every request.

DevQuest itself saves your progress with `localStorage` (plus a file on disk in the desktop app).

## Two ways to draw

Web pages can draw graphics in two ways:

- **SVG** (Scalable Vector Graphics): shapes described as elements in the page, like HTML. Each circle or path is a DOM element you can style with CSS, attach events to, and change later. Great for icons, diagrams and charts with a modest number of shapes. It stays sharp at any size.
- **Canvas**: a rectangle of pixels you paint with JavaScript commands. Once painted, a shape is just pixels: there are no elements to update, you redraw the picture. Great for games, animations, image editing and charts with thousands of points.

## SVG basics

```html
<!doctype html>
<html>
  <body>
    <svg width="220" height="120" viewBox="0 0 220 120">
      <rect x="10" y="10" width="80" height="50" rx="8" fill="steelblue" />
      <circle cx="150" cy="40" r="30" fill="tomato" />
      <line x1="10" y1="100" x2="200" y2="100" stroke="black" stroke-width="2" />
      <text x="110" y="90" text-anchor="middle" font-family="sans-serif">Hello SVG</text>
    </svg>
    <script>
      const circle = document.querySelector("circle");
      circle.addEventListener("click", () => circle.setAttribute("fill", "gold"));
      console.log(circle.getAttribute("r"));
    </script>
  </body>
</html>
```

The coordinate system starts at the **top-left** corner, with y growing **downwards** (true for canvas too). SVG shapes are DOM elements: select them, change attributes, listen for clicks. To create SVG elements from JavaScript, use `document.createElementNS("http://www.w3.org/2000/svg", "circle")` (they belong to a different namespace than HTML).

## Canvas basics

```html
<!doctype html>
<html>
  <body>
    <canvas id="c" width="300" height="150" style="border:1px solid #ccc"></canvas>
    <script>
      const canvas = document.querySelector("#c");
      const ctx = canvas.getContext("2d");

      ctx.fillStyle = "steelblue";
      ctx.fillRect(10, 10, 100, 60);

      ctx.strokeStyle = "tomato";
      ctx.lineWidth = 4;
      ctx.beginPath();
      ctx.moveTo(130, 20);
      ctx.lineTo(200, 120);
      ctx.lineTo(260, 30);
      ctx.stroke();

      ctx.beginPath();
      ctx.arc(60, 115, 25, 0, Math.PI * 2);
      ctx.fillStyle = "gold";
      ctx.fill();

      ctx.fillStyle = "black";
      ctx.font = "16px sans-serif";
      ctx.fillText("Canvas!", 180, 140);
    </script>
  </body>
</html>
```

- `canvas.getContext("2d")` gives the **drawing context**, the object with all the drawing methods.
- `fillRect` and `strokeRect` draw rectangles directly.
- Other shapes are **paths**: `beginPath()`, then `moveTo`, `lineTo`, `arc` (angles in radians: a full circle is `2 * Math.PI`), `quadraticCurveTo`..., then `fill()` or `stroke()`.
- Styles are **state** on the context (`fillStyle`, `strokeStyle`, `lineWidth`, `font`) that apply to everything drawn afterwards. `ctx.save()` and `ctx.restore()` remember and bring back the state, which is handy around transformations (`translate`, `rotate`, `scale`).
- `ctx.drawImage(image, x, y)` draws an image; `ctx.getImageData` reads pixels back.

## A bar chart

Data plus a loop gives a chart. Scaling the values to fit the canvas is the main idea:

```html
<!doctype html>
<html>
  <body>
    <canvas id="chart" width="320" height="160"></canvas>
    <script>
      const sales = [["Mon", 12], ["Tue", 19], ["Wed", 7], ["Thu", 15], ["Fri", 23]];
      const ctx = document.querySelector("#chart").getContext("2d");
      const max = Math.max(...sales.map(([, v]) => v));
      const barWidth = 40, gap = 20, bottom = 140, height = 120;
      sales.forEach(([day, value], i) => {
        const x = 20 + i * (barWidth + gap);
        const h = (value / max) * height;
        ctx.fillStyle = value === max ? "tomato" : "steelblue";
        ctx.fillRect(x, bottom - h, barWidth, h);
        ctx.fillStyle = "black";
        ctx.font = "12px sans-serif";
        ctx.fillText(day, x + 8, bottom + 14);
        ctx.fillText(String(value), x + 12, bottom - h - 4);
      });
    </script>
  </body>
</html>
```

Because the y axis points down, a bar of height `h` starts at `bottom - h`.

## Animation: clear, update, draw

Canvas animation is a loop: each frame, clear the canvas, update the positions, and draw everything again, scheduled with `requestAnimationFrame`:

```html
<!doctype html>
<html>
  <body>
    <canvas id="game" width="300" height="150" style="background:#111"></canvas>
    <script>
      const ctx = document.querySelector("#game").getContext("2d");
      const ball = { x: 50, y: 50, vx: 120, vy: 90, r: 10 };
      let last = performance.now();
      function frame(now) {
        const dt = (now - last) / 1000;
        last = now;
        ball.x += ball.vx * dt;
        ball.y += ball.vy * dt;
        if (ball.x < ball.r || ball.x > 300 - ball.r) ball.vx *= -1;
        if (ball.y < ball.r || ball.y > 150 - ball.r) ball.vy *= -1;
        ctx.clearRect(0, 0, 300, 150);
        ctx.beginPath();
        ctx.arc(ball.x, ball.y, ball.r, 0, Math.PI * 2);
        ctx.fillStyle = "lime";
        ctx.fill();
        requestAnimationFrame(frame);
      }
      requestAnimationFrame(frame);
    </script>
  </body>
</html>
```

Velocities in pixels **per second**, multiplied by the time since the last frame (`dt`), keep the speed independent of the screen's refresh rate. This loop (input, update, draw) is the heart of every game, from Pong to 3D engines (which use canvas's 3D sibling, **WebGL** / **WebGPU**).

A Node.js **CSV report** tool, in modules. `report.js` exports a function `summarize(csvText)` that takes CSV text with a header row `category,amount` and returns an array of `{ category, total }`, totals rounded to 2 decimals, sorted by total (highest first). `main.js` reads the file named in `process.argv[2]` with `node:fs`, calls `summarize`, and prints one line per category like `food: 42.50`. Lines that are blank are skipped; a line with a non-numeric amount makes `summarize` throw an `Error` whose message includes the line number (counting the header as line 1), e.g. `Bad amount on line 4`. For the sample file, the program prints `food: 42.50`, `travel: 30.00` and `fun: 15.25`.

// file: spending.csv
category,amount
food,12.50
travel,30
food,30

fun,15.25
// file: report.js
export function summarize(csvText) {
  const totals = new Map();
  const lines = csvText.split("\n");
  lines.forEach((line, i) => {
    if (i === 0 || line.trim() === "") return;
    const [category, amountText] = line.split(",");
    const amount = Number(amountText);
    if (amountText === undefined || amountText.trim() === "" || Number.isNaN(amount)) throw new Error(`Bad amount on line ${i + 1}`);
    totals.set(category, (totals.get(category) ?? 0) + amount);
  });
  return [...totals]
    .map(([category, total]) => ({ category, total: Math.round(total * 100) / 100 }))
    .sort((a, b) => b.total - a.total);
}
// file: main.js
process.argv = ["node", "main.js", "spending.csv"];
import { readFileSync } from "node:fs";
import { summarize } from "./report.js";

const text = readFileSync(process.argv[2], "utf8");
for (const { category, total } of summarize(text)) {
  console.log(`${category}: ${total.toFixed(2)}`);
}
