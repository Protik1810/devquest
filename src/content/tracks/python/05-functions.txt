=== module Module 5 · Functions

=== lesson py-functions | Defining functions | 90
You've been **calling** functions since your first lesson: `print`, `len`, `input`, `int`, `round`. Now you'll write your own. A **function** is a named, reusable block of code. Functions are how programmers tame complexity:

- **Don't repeat yourself.** Write the logic once, use it everywhere. Fix a bug once, and it's fixed everywhere.
- **Names explain code.** `total = add_tax(price)` says what happens without showing how.
- **Decomposition.** Big problems become small functions you can understand one at a time.
- **Testing.** A small function can be checked on its own, with many inputs.

## Defining and calling

```python
def greet(name):
    """Print a friendly greeting."""
    print(f"Hello, {name}!")

greet("Ada")      # Hello, Ada!
greet("Alan")     # Hello, Alan!
```

- `def` starts a **function definition**, followed by the function's name (snake_case, usually a verb), its **parameters** in parentheses, and a colon.
- The indented **body** runs each time the function is called.
- The string on the first line is a **docstring**: documentation that `help(greet)` shows.

**Defining a function doesn't run it.** It only creates it, like writing down a recipe without cooking. The body runs when you **call** it: `greet("Ada")`. Python reads top to bottom, so define a function *before* the line that calls it, or you get a `NameError`.

## Parameters and arguments

A **parameter** is the variable named in the definition (`name`). An **argument** is the value you pass in the call (`"Ada"`). When the function is called, each parameter is set to its argument. Pass the wrong number and Python complains:

```
TypeError: greet() missing 1 required positional argument: 'name'
```

## return: handing a value back

Most useful functions **compute** something and give it back with `return`:

```python
def square(n):
    return n * n

area = square(4) + square(3)    # 16 + 9
print(area)                     # 25
```

`return` ends the function **immediately** and sends the value back to where it was called. The call `square(4)` then *becomes* that value, so it can be used in any expression.

## print versus return

This is the most common confusion for new programmers, so slow down here:

- `print` **shows** a value to a human on the screen.
- `return` **gives** a value back to the program.

A function that prints its result instead of returning it can't be used in further calculations:

```python
def bad_square(n):
    print(n * n)

x = bad_square(4)    # prints 16 on the screen...
print(x)             # None
print(x + 1)         # TypeError: unsupported operand type(s) for +: 'NoneType' and 'int'
```

A function without a `return` (or with a bare `return`) returns **`None`**. The rule of thumb: functions that **compute** should **return**; let the code that calls them decide what to print.

## Several exits

`return` can appear in several places, and the first one reached wins. Returning early often makes code simpler:

```python
def sign(n):
    if n > 0:
        return "positive"
    if n < 0:
        return "negative"
    return "zero"
```

No `elif` is needed: once a `return` runs, the rest of the function is skipped.

## Returning several values

Separate them with commas. Python packs them into a **tuple** (an unchangeable list, covered in Module 6), which you can unpack:

```python
def min_max(numbers):
    return min(numbers), max(numbers)

low, high = min_max([4, 9, 1, 7])
print(low, high)    # 1 9
```

## How a call runs

When Python reaches a call, it **jumps** into the function, sets up the parameters, runs the body until a `return` (or the end), and then **jumps back** to exactly where it was, carrying the returned value. Functions can call other functions, and each call remembers where to come back to.

Building big functions out of small ones is called **composition**:

```python
def average(numbers):
    return sum(numbers) / len(numbers)

def describe(numbers):
    return f"{len(numbers)} numbers with an average of {average(numbers):.1f}"

print(describe([3, 4, 8]))    # 3 numbers with an average of 5.0
```

## Checking a function with assert

`assert` checks that something is true, and stops the program with an `AssertionError` if it isn't:

```python
assert square(3) == 9       # passes silently
assert square(-2) == 4      # passes
assert square(2) == 5       # AssertionError
```

From now on, many DevQuest exercises ask for a **function** and check it with hidden `assert` lines like these, calling it with many different inputs. When one fails, you'll see the check, what was expected and what your function returned. You'll write full test suites yourself in Module 7.

## What makes a good function

- It does **one thing**, and its name says what (`calculate_tax`, `is_valid_email`).
- It's short enough to read at a glance.
- It gets its inputs from **parameters** and gives its result with **return**, rather than reading `input()` or printing in the middle of a calculation.

=== lesson py-params | Parameters in depth | 90
Functions become far more flexible once you know all the ways to pass information into them.

## Positional and keyword arguments

```python
def describe_pet(animal, name):
    return f"{name} is a {animal}"

describe_pet("dog", "Rex")                 # positional: matched by order
describe_pet(name="Rex", animal="dog")     # keyword: matched by name, any order
describe_pet("dog", name="Rex")            # mixed: positional ones first
```

Keyword arguments make calls easier to read, especially when there are several numbers or booleans: `resize(img, width=800, keep_ratio=True)` is clearer than `resize(img, 800, True)`. A positional argument can't come after a keyword one: `describe_pet(name="Rex", "dog")` is a `SyntaxError`.

## Default values

A parameter can have a **default**, used when the caller leaves it out:

```python
def greet(name, greeting="Hello"):
    return f"{greeting}, {name}!"

greet("Ada")                  # 'Hello, Ada!'
greet("Ada", "Welcome back")  # 'Welcome back, Ada!'
greet("Ada", greeting="Hi")   # 'Hi, Ada!'
```

You've been using defaults all along: `print` has `sep=" "` and `end="\n"`, and `round(x)` has `ndigits=None`. Parameters with defaults must come after the ones without.

## The mutable default trap

Default values are created **once**, when the `def` line runs, not on every call. With a list as a default, that one list is shared by every call:

```python
def add_item(item, items=[]):
    items.append(item)
    return items

print(add_item("a"))    # ['a']
print(add_item("b"))    # ['a', 'b']   ← surprise! the same list again
```

The standard fix is to use `None` as the default and create a fresh list inside:

```python
def add_item(item, items=None):
    if items is None:
        items = []
    items.append(item)
    return items
```

This is one of Python's most famous gotchas, and a favourite interview question.

## *args: any number of positional arguments

A parameter with one star collects all the extra positional arguments into a **tuple**:

```python
def total(*numbers):
    result = 0
    for n in numbers:
        result += n
    return result

total(1, 2, 3)     # 6
total()            # 0
```

`print` works this way, which is why it takes any number of values.

## **kwargs: any number of keyword arguments

Two stars collect extra keyword arguments into a **dictionary** of name/value pairs (Module 6 covers dictionaries; for now, `.items()` loops over the pairs):

```python
def make_profile(name, **details):
    lines = [name]
    for key, value in details.items():
        lines.append(f"  {key}: {value}")
    return "\n".join(lines)

print(make_profile("Ada", born=1815, field="mathematics"))
```

The names `args` and `kwargs` are only conventions; the stars are what matter.

## Keyword-only and positional-only parameters

A bare `*` in the parameter list means "everything after this must be passed by name":

```python
def connect(host, *, timeout=10, retries=3):
    ...

connect("example.com", timeout=5)     # fine
connect("example.com", 5)             # TypeError: takes 1 positional argument but 2 were given
```

This forces readable calls for options. The opposite, a `/`, makes the parameters before it **positional-only**; you'll see it in the documentation of built-ins such as `len(obj, /)`.

The full order is: normal parameters, `*args`, keyword-only parameters, `**kwargs`.

## Unpacking arguments in a call

Stars also work in the other direction, spreading a sequence or dictionary into separate arguments:

```python
point = [3, 4]
print(*point)                  # same as print(3, 4)
options = {"sep": " | ", "end": "!\n"}
print("a", "b", **options)     # a | b!
```

## A peek at type hints

You can note the expected types of parameters and the return value:

```python
def area(width: float, height: float) -> float:
    return width * height
```

Python doesn't enforce them, but editors and tools use them to catch mistakes. Module 12 covers them.

=== lesson py-scope | Scope and the call stack | 90
## Local variables

Variables created inside a function, including its parameters, are **local**: they exist only while that call is running, and only that function can see them.

```python
def make_total(prices):
    total = 0                # a local variable
    for p in prices:
        total += p
    return total

make_total([3, 4])
print(total)                 # NameError: name 'total' is not defined
```

Every call gets a **fresh** set of local variables, so calls can't interfere with each other. This is what makes functions safe to reuse.

## Global variables

A variable assigned at the top level of the file (outside any function) is **global**. Functions can **read** globals:

```python
TAX_RATE = 0.2

def with_tax(price):
    return price * (1 + TAX_RATE)    # reading a global is fine
```

But **assigning** to a name inside a function makes it local to that function, even if a global has the same name:

```python
count = 0

def increment():
    count += 1        # UnboundLocalError: cannot access local variable 'count' where it is not associated with a value
```

Python sees the assignment, decides `count` is local, and then finds it has no value yet. The `global count` statement would make it refer to the global, but **avoid this**: when any function can change a global, bugs can come from anywhere, and the function is hard to test. Instead, pass values in as parameters and send results back with `return`:

```python
def increment(count):
    return count + 1

count = increment(count)
```

Global *constants* (in CAPITALS, never reassigned) like `TAX_RATE` are fine.

## The LEGB rule

When Python meets a name, it looks for it in four places, in order:

1. **L**ocal: the current function;
2. **E**nclosing: any function this one is nested inside (Module 12 uses this for closures);
3. **G**lobal: the top level of the file;
4. **B**uilt-in: Python's own names like `print`, `len` and `sum`.

The first match wins.

## Don't shadow built-ins

Because your names are found before the built-ins, reusing a built-in's name **hides** it:

```python
sum = 0                  # now "sum" means this number...
for n in [1, 2, 3]:
    sum += n
print(sum([4, 5]))       # TypeError: 'int' object is not callable
```

Avoid naming variables `list`, `dict`, `str`, `sum`, `max`, `min`, `input`, `id` or `type`. Use `total`, `items`, `largest` and so on.

## The call stack

Each function call gets a **frame** holding its local variables. Frames pile up on the **call stack**: when `main` calls `report` and `report` calls `average`, there are three frames. When `average` returns, its frame is removed and `report` continues.

That's exactly what a **traceback** shows when something goes wrong deep inside:

```
Traceback (most recent call last):
  File "<exec>", line 9, in <module>
  File "<exec>", line 6, in report
  File "<exec>", line 2, in average
ZeroDivisionError: division by zero
```

Read it as a story from top to bottom: the main program called `report`, which called `average`, where the division failed. The **bottom** frame is where the error happened; the frames above tell you how the program got there. Often the real bug is in a caller that passed bad data (here, perhaps an empty list).

## Pure functions and side effects

A **pure** function only uses its parameters and only communicates through its return value: the same input always gives the same output, and nothing else changes. `square(n)` is pure. Anything else a function does (printing, reading input, changing a global or a list it was given, writing a file) is a **side effect**.

Pure functions are easy to test and reason about. A good design keeps the calculations pure and does input/output in a few places at the edges of the program.

## Functions are values

A function's name without parentheses refers to the function itself, which you can store or pass to another function:

```python
def shout(text):
    return text.upper() + "!"

def whisper(text):
    return text.lower() + "..."

def speak(style, text):
    return style(text)       # call whichever function was passed in

speak(shout, "Hello")      # 'HELLO!'
speak(whisper, "Hello")    # 'hello...'
```

`shout` is the function; `shout("hi")` *calls* it. Passing functions around is a powerful idea that you'll use with `sorted(key=...)` and more in Module 12.

## A tidy program layout

Larger programs usually put everything in functions and start with a `main` function:

```python
def main():
    name = input("Name: ")
    print(make_greeting(name))

main()
```

=== lesson py-recursion | Recursion | 90
A function can call **itself**. That's called **recursion**, and it's a beautifully simple way to solve problems that contain smaller copies of themselves.

```python
def countdown(n):
    if n == 0:
        print("Liftoff!")
    else:
        print(n)
        countdown(n - 1)

countdown(3)    # 3, 2, 1, Liftoff!
```

Every recursive function has two parts:

1. a **base case**: a situation simple enough to answer directly, without recursion (`n == 0`);
2. a **recursive case**: the function calls itself on a **smaller** version of the problem (`n - 1`), so it moves towards the base case.

## Thinking recursively: factorial

The factorial of n (written n!) is 1 × 2 × ... × n. Notice that 5! = 5 × 4!, and 4! = 4 × 3!, and so on, down to 1! = 1. That self-similar definition turns straight into code:

```python
def factorial(n):
    if n <= 1:                       # base case
        return 1
    return n * factorial(n - 1)      # recursive case
```

How does `factorial(4)` run? Each call waits for the one it made, building up the call stack, and then the answers come back down:

```
factorial(4) = 4 * factorial(3)
                   factorial(3) = 3 * factorial(2)
                                      factorial(2) = 2 * factorial(1)
                                                         factorial(1) = 1
                                      factorial(2) = 2 * 1 = 2
                   factorial(3) = 3 * 2 = 6
factorial(4) = 4 * 6 = 24
```

## The leap of faith

Tracing every call quickly gets confusing. Instead, experienced programmers take a **leap of faith**: assume the recursive call already works for the smaller problem, and only ask "how do I use that answer to solve the bigger one?" If `total(rest)` correctly adds up the rest of a list, then the total of the whole list is the first item plus `total(rest)`:

```python
def total(numbers):
    if not numbers:                          # an empty list adds up to 0
        return 0
    return numbers[0] + total(numbers[1:])
```

Check the base case, check that each call gets closer to it, and trust the rest.

## More examples

```python
def reverse(text):
    if len(text) <= 1:
        return text
    return reverse(text[1:]) + text[0]

def power(base, exp):
    if exp == 0:
        return 1
    return base * power(base, exp - 1)
```

## When the base case is missing

Without a base case (or if the problem never gets smaller), the function calls itself until Python gives up:

```
RecursionError: maximum recursion depth exceeded
```

Python allows about 1,000 nested calls by default, so very deep recursion fails even when it's correct.

## Recursion or loops?

Anything written recursively can also be written with a loop, and in Python a loop is usually faster and has no depth limit. Recursion shines when the **data itself is nested**: folders inside folders, comments with replies to replies, family trees, the structure of a web page. It's also the natural way to express "divide and conquer" algorithms such as merge sort and quicksort (see the algorithms track).

Nested lists are a good example. A loop handles the top level, and recursion handles each inner list:

```python
def deep_sum(items):
    total = 0
    for x in items:
        if isinstance(x, list):      # isinstance checks a value's type
            total += deep_sum(x)     # a list inside: add up its contents recursively
        else:
            total += x
    return total

deep_sum([1, [2, 3], [4, [5, 6]]])   # 21
```

## A warning about repeated work

The Fibonacci numbers (0, 1, 1, 2, 3, 5, 8, ...) are each the sum of the two before. The direct recursive version is elegant but **very slow**:

```python
def fib(n):
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)
```

`fib(35)` makes about 30 million calls, because it recomputes the same values again and again. Remembering results you've already computed (**memoization**) makes it instant; you'll do that with `functools.lru_cache` in Module 12.

📚 **Go deeper:** *Think Python* (3rd ed.), chapters 5–6 (recursion and "leap of faith"); CS50P / CS50x lectures on recursion; Python for Everybody has a good visual of the stack.
