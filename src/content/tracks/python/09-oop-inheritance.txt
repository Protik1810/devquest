## Building on an existing class

Often one kind of thing is a **special case** of another: a dog *is an* animal, a savings account *is a* bank account, a manager *is an* employee. **Inheritance** lets a new class start with everything an existing class has and then add or change only what's different.

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return "..."

    def describe(self):
        return f"{self.name} says {self.speak()}"


class Dog(Animal):          # Dog inherits from Animal
    def speak(self):        # override: replace the inherited version
        return "Woof!"


class Cat(Animal):
    def speak(self):
        return "Meow"


print(Dog("Rex").describe())     # Rex says Woof!
print(Cat("Tom").describe())     # Tom says Meow
print(Animal("Generic").describe())  # Generic says ...
```

- `Animal` is the **base class** (also called parent or superclass); `Dog` is a **derived class** (child, subclass).
- `Dog` **inherits** `__init__` and `describe` without writing them again.
- `Dog` **overrides** `speak`. Notice that the inherited `describe` calls `self.speak()`, and gets the **dog's** version, because `self` is a `Dog`. That's the heart of OOP: general code in the base class, specific behaviour in the subclasses.

## How Python finds a method

For `rex.describe()`, Python looks in the object, then in its class `Dog`, then in `Dog`'s base class `Animal`, and so on up the chain. The first match wins. At the top of every chain is the class `object`, which provides defaults like `__repr__` and `__eq__`; that's why even an empty class can be printed and compared.

## Extending a method with super()

Often you want to **add to** the parent's behaviour rather than replace it. `super()` gives access to the parent's version:

```python
class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)      # let Animal set up what it knows about
        self.breed = breed          # then add what's specific to dogs
        self.tricks = []

    def describe(self):
        return super().describe() + f" (a {self.breed})"


rex = Dog("Rex", "beagle")
print(rex.describe())    # Rex says ... (a beagle)
```

If a subclass defines its own `__init__`, the parent's `__init__` does **not** run automatically. Forgetting `super().__init__(...)` is a classic bug: attributes the parent sets up (like `name`) never get created.

## isinstance and issubclass

```python
isinstance(rex, Dog)        # True
isinstance(rex, Animal)     # True: a Dog is an Animal
isinstance(rex, Cat)        # False
issubclass(Dog, Animal)     # True
```

Use `isinstance` rather than `type(x) == Dog`, because it respects inheritance.

## Inheritance you already use

Python's exceptions are a class hierarchy, which is why `except LookupError` catches a `KeyError`. When you wrote `class InsufficientFundsError(Exception)` in Module 7, you were using inheritance: your exception got all of `Exception`'s behaviour for free.

## When is inheritance right?

Use it for a genuine **"is a"** relationship, where a subclass object can be used **anywhere** a base class object is expected without surprises. (That rule has a name, the **Liskov substitution principle**, which Module 10 returns to.) A savings account is a bank account: any code that deposits into an account works with it. Inheritance is the wrong tool when you just want to reuse some code; the composition lesson shows the alternative.

Keep hierarchies **shallow**: one or two levels are easy to follow; five levels of subclasses make it hard to know where any method comes from.

=== lesson py-polymorphism | Polymorphism, duck typing and abstract classes | 100
**Polymorphism** ("many forms") means code can work with objects of **different classes** through the **same interface**:

```python
shapes = [Circle(1), Rectangle(2, 3), Square(4)]
for shape in shapes:
    print(shape.describe())          # each object answers in its own way
total = sum(shape.area() for shape in shapes)
```

The loop doesn't care which kind of shape it has. Add a `Triangle` class tomorrow, and this code works with it unchanged. That's the real power of OOP: code that is **open to new kinds of objects without being edited**.

## Duck typing

In Python, polymorphism doesn't even need a shared base class. "If it walks like a duck and quacks like a duck, it's a duck": any object that has the methods you call will do.

```python
class Duck:
    def speak(self):
        return "Quack"

class Robot:
    def speak(self):
        return "Beep"

for thing in [Duck(), Robot()]:
    print(thing.speak())     # works: both have speak()
```

The built-ins work this way. `len()` works on anything with `__len__`; a `for` loop works on anything iterable; `print` works on anything with `__str__`. Files, network connections and in-memory buffers all have `read()` and `write()`, so code written for one often works with the others.

Duck typing fits with EAFP from Module 7: just call the method, and handle `AttributeError` if something might not have it. When you really need to check, `hasattr(obj, "speak")` asks about the **behaviour**, which is better than checking the exact type.

## Abstract base classes: enforcing an interface

Duck typing is flexible but relies on everyone remembering which methods to write. When you design a family of classes, an **abstract base class** (ABC) makes the required interface explicit and enforced:

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        """Return the shape's area."""

    @abstractmethod
    def perimeter(self):
        """Return the distance around the shape."""

    def describe(self):                              # a normal, shared method
        return f"area {self.area():.2f}, perimeter {self.perimeter():.2f}"


class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        return 3.14159 * self.r ** 2

    def perimeter(self):
        return 2 * 3.14159 * self.r
```

- You **can't create** an instance of an abstract class: `Shape()` raises `TypeError: Can't instantiate abstract class Shape...`.
- A subclass that forgets to implement an abstract method can't be instantiated either, so the mistake shows up immediately, not later in production.
- An ABC can still provide ordinary shared methods, like `describe`.

Compared with the `raise NotImplementedError` approach from the last lesson, an ABC catches the missing method when the object is **created**, not when the method is finally called.

## Structural typing with Protocol (a peek)

`typing.Protocol` describes an interface for **type checkers** without requiring inheritance: "anything with a `speak()` method returning `str`". It's duck typing that tools can verify. Module 12 introduces type hints.

## Avoid type-checking chains

If you see code like this, polymorphism can probably replace it:

```python
if isinstance(shape, Circle):
    area = 3.14159 * shape.r ** 2
elif isinstance(shape, Rectangle):
    area = shape.w * shape.h
```

Every new shape means editing this chain (and all the others like it). Moving `area()` into each class puts the knowledge where it belongs.

## Inheriting from several classes

A Python class can have more than one base class:

```python
class Flyer:
    def fly(self):
        return f"{self.name} flies"

class Swimmer:
    def swim(self):
        return f"{self.name} swims"

class Duck(Flyer, Swimmer):
    def __init__(self, name):
        self.name = name

d = Duck("Donald")
d.fly(), d.swim()     # both work
```

## The diamond problem

Trouble starts when two parents share a grandparent and define the same method:

```
      A
     / \
    B   C
     \ /
      D
```

```python
class A:
    def who(self):
        return "A"

class B(A):
    def who(self):
        return "B"

class C(A):
    def who(self):
        return "C"

class D(B, C):
    pass

print(D().who())    # ?
```

Which `who` does `D` get? Python answers with the **method resolution order** (MRO): a single, well-defined list of classes to search, computed by an algorithm called **C3 linearisation**. You can see it:

```python
print([cls.__name__ for cls in D.__mro__])     # ['D', 'B', 'C', 'A', 'object']
```

So `D().who()` returns `"B"`. The MRO always keeps a class **before its parents**, keeps the **left-to-right order** of the bases you listed, and visits each class **once**: `A` comes after both `B` and `C`.

## super() follows the MRO

Here's the subtle part: `super()` doesn't mean "my parent". It means "**the next class in the MRO** of the object". That makes **cooperative** multiple inheritance work, where every class in the diamond runs exactly once:

```python
class A:
    def hello(self):
        return ["A"]

class B(A):
    def hello(self):
        return ["B"] + super().hello()

class C(A):
    def hello(self):
        return ["C"] + super().hello()

class D(B, C):
    def hello(self):
        return ["D"] + super().hello()

print(D().hello())      # ['D', 'B', 'C', 'A']
```

Inside `B.hello`, for a `D` object, `super()` is `C` (the next class in D's MRO), not `A`. If `B` and `C` had called `A.hello(self)` directly instead, `A` would run twice. The rule: in a hierarchy that might be combined, **always use `super()`**, and keep method signatures compatible.

## Mixins: small reusable abilities

The most practical use of multiple inheritance is the **mixin**: a small class that adds **one ability** to any class that includes it, and isn't meant to be used on its own:

```python
import json

class JsonMixin:
    def to_json(self):
        return json.dumps(vars(self), sort_keys=True)

class ReprMixin:
    def __repr__(self):
        fields = ", ".join(f"{k}={v!r}" for k, v in vars(self).items())
        return f"{type(self).__name__}({fields})"

class User(ReprMixin, JsonMixin):
    def __init__(self, name, email):
        self.name = name
        self.email = email

u = User("Ada", "ada@x.io")
print(u)              # User(name='Ada', email='ada@x.io')
print(u.to_json())    # {"email": "ada@x.io", "name": "Ada"}
```

Web frameworks like Django use mixins heavily (`LoginRequiredMixin`, and so on). Conventions: name them `...Mixin`, keep them small, give them no `__init__` of their own (or a cooperative one), and list them **before** the main base class.

## Looking inside classes: introspection

Python lets a program examine its own objects:

```python
type(u)                     # <class 'User'>
type(u).__name__            # 'User'
User.__bases__              # (ReprMixin, JsonMixin)
User.__mro__                # the full lookup order
isinstance(u, JsonMixin)    # True
dir(u)                      # every attribute and method name, inherited ones included
```

## Use with care

Multiple inheritance is powerful but can make code hard to follow. Mixins that add independent abilities are a good use. Deep diamonds of "real" classes are usually a sign that **composition** (next lesson) would be simpler.

=== lesson py-composition | Composition over inheritance | 100
Inheritance models **"is a"**. Most relationships between objects are **"has a"**: a car *has an* engine, an order *has* line items, a game *has* players. Modelling that is called **composition**: an object holds other objects in its attributes and uses them.

```python
class Engine:
    def __init__(self, horsepower):
        self.horsepower = horsepower
        self.running = False

    def start(self):
        self.running = True


class Car:
    def __init__(self, model, engine):
        self.model = model
        self.engine = engine          # the car HAS an engine

    def start(self):
        self.engine.start()           # delegate the work to the part
        return f"{self.model} is running"


car = Car("Mini", Engine(130))
print(car.start())
```

When `Car.start` passes the work on to `self.engine.start()`, that's called **delegation**.

## Why "composition over inheritance"?

This advice, from the famous *Design Patterns* book, exists because inheritance is often used just to **reuse code**, and that goes wrong in two classic ways.

**1. Inheriting more than you wanted.** Make a stack by inheriting from `list`:

```python
class Stack(list):
    def push(self, item):
        self.append(item)
```

It works, but a `Stack` now also has `insert`, `sort`, `remove`, indexing, and every other list method. Anyone can put items in the middle, and the "last in, first out" promise is broken. With composition, the stack *has* a list, and exposes only what a stack should:

```python
class Stack:
    def __init__(self):
        self._items = []

    def push(self, item):
        self._items.append(item)

    def pop(self):
        return self._items.pop()
```

**2. A subclass that can't keep the parent's promises.** In maths a square is a rectangle, so `Square(Rectangle)` seems natural. But if `Rectangle` lets you set `width` and `height` independently, a `Square` either breaks that behaviour or stops being square. Code written for rectangles ("set width to 5, height stays 2, area is 10") gives wrong answers for squares. That's a violation of the **Liskov substitution principle**: a subclass must work anywhere its parent does.

## Composition makes swapping parts easy

Because parts are just attributes, you can give an object **different** parts, even at run time:

```python
car = Car("Mini", ElectricMotor(180))     # any object with start() will do: duck typing
```

## Dependency injection

When an object **receives** its collaborators instead of creating them itself, that's **dependency injection**. It sounds grand, but it's just passing objects in:

```python
class Greeter:
    def __init__(self, clock):
        self.clock = clock               # injected: anything with an hour() method

    def greet(self, name):
        h = self.clock.hour()
        part = "morning" if h < 12 else "afternoon" if h < 18 else "evening"
        return f"Good {part}, {name}"
```

In the real program you pass a clock that reads the system time. In a **test** you pass a fake clock that always says 9 o'clock, so the test is fast and predictable. If `Greeter` created its own clock inside, you couldn't test the evening greeting without waiting for the evening. Dependency injection is one of the main reasons well-designed code is easy to test.

## How to decide

- Ask "is a" or "has a"? Only a true "is a" relationship, where the child can be used anywhere the parent can, calls for inheritance.
- Prefer composition when you want to **reuse** behaviour, **combine** several behaviours, or **swap** parts.
- Inheritance is great for frameworks' extension points and families of closely related types (exceptions, shapes behind an ABC).

=== lesson py-dataclasses-enums | Dataclasses and enums | 100
Two standard-library tools remove most of the boilerplate from everyday classes.

## Dataclasses: classes that mainly hold data

Many classes are mostly fields, plus an `__init__` that copies them, a `__repr__` and an `__eq__`. Writing those by hand is tedious and error-prone. The `@dataclass` decorator generates them from **type-annotated** fields:

```python
from dataclasses import dataclass, field

@dataclass
class Product:
    name: str
    price_cents: int
    tags: list[str] = field(default_factory=list)     # a fresh list for each product

    def price(self):
        return self.price_cents / 100


p = Product("Mug", 899)
print(p)                          # Product(name='Mug', price_cents=899, tags=[])
print(p == Product("Mug", 899))   # True: __eq__ compares the fields
```

The `name: str` syntax is a **type annotation**: it declares a field (Module 12 covers annotations in general). Python doesn't check the types at runtime; `@dataclass` uses the annotations to know which fields exist.

## Defaults and the mutable default trap again

Fields with defaults come after fields without. For a mutable default (a list or dict), you must use `field(default_factory=list)`, so each instance gets its own; `tags: list = []` is refused with a `ValueError`. It's the mutable-default trap from Module 5, and dataclasses protect you from it.

## Validation with __post_init__

The generated `__init__` calls `__post_init__` (if you define it) after setting the fields. It's the place to validate or compute derived values:

```python
@dataclass
class Product:
    name: str
    price_cents: int

    def __post_init__(self):
        if self.price_cents < 0:
            raise ValueError("price can't be negative")
```

## frozen=True and order=True

```python
@dataclass(frozen=True, order=True)
class Version:
    major: int
    minor: int
    patch: int = 0

v = Version(1, 4)
v.minor = 5                 # FrozenInstanceError: cannot assign to field 'minor'
sorted([Version(2, 0), Version(1, 9)])   # order=True compares field by field
{Version(1, 4), Version(1, 4)}           # frozen dataclasses are hashable: one item
```

- `frozen=True` makes instances **immutable** (and hashable), perfect for values like versions, coordinates and money.
- `order=True` generates `<`, `<=`, `>`, `>=` comparing the fields as a tuple, in order.
- `dataclasses.replace(v, minor=5)` returns a **copy** with some fields changed: the way to "modify" frozen objects.

## Enums: named constants

"Magic strings" are fragile: `status = "shiped"` (typo) silently never matches `"shipped"`. An **enumeration** defines a fixed set of named values:

```python
from enum import Enum

class Status(Enum):
    PENDING = "pending"
    PAID = "paid"
    SHIPPED = "shipped"

s = Status.PAID
print(s)                    # Status.PAID
print(s.name, s.value)      # PAID paid
Status("shipped")           # Status.SHIPPED: look up a member by its value
Status["PAID"]              # Status.PAID: look up by name
Status("lost")              # ValueError: 'lost' is not a valid Status
list(Status)                # all members, in definition order
s is Status.PAID            # True: each member is a single object
```

A typo like `Status.SHIPED` is an `AttributeError` immediately, instead of a silent bug. Editors can also autocomplete the members.

Enum classes can have **methods** too:

```python
class Light(Enum):
    RED = 1
    GREEN = 2
    YELLOW = 3

    def next(self):
        order = [Light.RED, Light.GREEN, Light.YELLOW]
        return order[(order.index(self) + 1) % 3]
```

`enum.auto()` assigns values automatically, and `IntEnum` / `StrEnum` create members that also behave like ints or strings, handy when talking to databases or JSON.

## When to use what

| Need | Tool |
|---|---|
| a record of named fields, with sensible `repr` and `==` | `@dataclass` |
| an immutable, hashable value object | `@dataclass(frozen=True)` (or a `namedtuple`) |
| a fixed set of options or states | `Enum` |
| behaviour-heavy objects with invariants | a regular class (properties, methods) |

::solution
from dataclasses import dataclass, replace


@dataclass(frozen=True, order=True)
class Version:
    major: int
    minor: int
    patch: int = 0

    def __str__(self):
        return f"{self.major}.{self.minor}.{self.patch}"

    @classmethod
    def parse(cls, text):
        parts = [int(p) for p in text.split(".")]
        return cls(*parts)

    def bump_minor(self):
        return replace(self, minor=self.minor + 1, patch=0)

Build a tiny battle system with inheritance and polymorphism:

- `Character(name, hp)` with `take_damage(amount)` (hp never goes below 0), an `is_alive` property, and `attack(target)` that deals **10** damage and returns the damage dealt;

- `Mage(name, hp, mana)`: its `attack` deals **25** damage and costs 10 mana if it has at least 10 mana, otherwise it falls back to the basic `Character` attack (use `super()`);
- `battle_round(attackers, target)` makes every **living** attacker attack the target in order and returns the total damage the attacks returned.
::starter
class Character:
    def __init__(self, name, hp):
        self.name = name
        self.hp = hp
::solution
class Character:
    def __init__(self, name, hp):
        self.name = name
        self.hp = hp

    def take_damage(self, amount):
        self.hp = max(0, self.hp - amount)

    @property
    def is_alive(self):
        return self.hp > 0

    def attack(self, target):
        target.take_damage(10)
        return 10


class Warrior(Character):
    def __init__(self, name, hp, armor):
        super().__init__(name, hp)
        self.armor = armor

    def take_damage(self, amount):
        super().take_damage(max(0, amount - self.armor))

    def attack(self, target):
        target.take_damage(15)
        return 15


class Mage(Character):
    def __init__(self, name, hp, mana):
        super().__init__(name, hp)
        self.mana = mana

    def attack(self, target):
        if self.mana >= 10:
            self.mana -= 10
            target.take_damage(25)
            return 25
        return super().attack(target)


def battle_round(attackers, target):
    total = 0
    for a in attackers:
        if a.is_alive:
            total += a.attack(target)
    return total

::solution
from dataclasses import dataclass, field
from enum import Enum


class Status(Enum):
    PENDING = 1
    PAID = 2
    SHIPPED = 3
    DELIVERED = 4


@dataclass
class Order:
    order_id: str
    items: dict = field(default_factory=dict)
    status: Status = Status.PENDING

    def add_item(self, name, price_cents):
        if self.status is not Status.PENDING:
            raise ValueError("can only add items to a pending order")
        self.items[name] = price_cents

    @property
    def total(self):
        return sum(self.items.values())

    def advance(self):
        order = list(Status)
        i = order.index(self.status)
        if i == len(order) - 1:
            raise ValueError("the order is already delivered")
        if self.status is Status.PENDING and not self.items:
            raise ValueError("can't pay for an empty order")
        self.status = order[i + 1]
        return self.status
