=== lesson py-solid | Design principles: SOLID and friends | 105
Knowing the syntax of classes is one thing; designing code that stays easy to change as it grows is another. Over decades, developers distilled their experience into principles. The best known are the five **SOLID** principles, popularised by Robert C. Martin. They're guidelines, not laws, but they explain *why* some designs age well and others turn into a tangle.

## S: Single responsibility principle

*A class should have one reason to change.*

```python
class SalesReport:                       # does three jobs
    def __init__(self, sales):
        self.sales = sales
    def total(self): ...                 # 1. calculations
    def as_text(self): ...               # 2. presentation
    def save(self, path): ...            # 3. storage
```

If the finance team changes how totals work, the marketing team wants a new layout, and IT moves files to the cloud, all three edits land in the same class, and each risks breaking the others. Split it: a `SalesStats` class for the numbers, a `ReportFormatter` for the text, and a separate function or class for saving. Each is small, focused and easy to test.

A practical test: try describing the class in one sentence **without** the word "and".

## O: Open/closed principle

*Code should be open for extension but closed for modification.* You should be able to add new behaviour **without editing** code that already works.

```python
# Closed to extension: every new discount type means editing this function
def apply_discount(price, kind):
    if kind == "percent": ...
    elif kind == "fixed": ...
    elif kind == "bogo": ...

# Open to extension: new rules are new classes; this function never changes
def apply_rules(price, rules):
    for rule in rules:
        price = rule.apply(price)
    return price
```

Polymorphism is the usual tool: define an interface (each rule has `apply(price)`), and extend the system by adding new classes.

## L: Liskov substitution principle

*Objects of a subclass must be usable wherever the base class is expected, without surprises.* You met this with `Square(Rectangle)` in Module 9. A subclass shouldn't demand more (refuse inputs the parent accepts), promise less (return something the parent never would), or raise new kinds of errors that callers can't expect.

## I: Interface segregation principle

*Don't force classes to depend on methods they don't use.* A `Printer` interface with `print`, `scan` and `fax` forces a simple printer to fake `scan` and `fax`. Several small interfaces (`Printable`, `Scannable`) are better than one big one. In Python, with duck typing and ABCs, this means keeping abstract base classes and protocols **small**.

## D: Dependency inversion principle

*Depend on abstractions, not on concrete details.* High-level code (the business rules) shouldn't create or know about low-level details (which database, which email service). It should talk to an **interface**, and the details are plugged in from outside, which is the dependency injection you met in Module 9:

```python
class OrderService:
    def __init__(self, repository, notifier):     # any objects with save()/send()
        self.repository = repository
        self.notifier = notifier

    def place(self, order):
        self.repository.save(order)
        self.notifier.send(f"Order {order['id']} placed")
```

The same `OrderService` works with a real database in production and an in-memory fake in tests.

## Cohesion and coupling

Two words you'll hear in every design discussion:

- **Cohesion**: how closely the parts *inside* a module or class belong together. Aim **high**: everything in `SalesStats` is about statistics.
- **Coupling**: how much separate modules or classes depend on each other's details. Aim **low**: `OrderService` knows only that the notifier has `send()`.

High cohesion and low coupling are what SOLID is ultimately trying to achieve.

## Three more rules of thumb

- **DRY** (don't repeat yourself): every piece of knowledge should live in one place. But don't merge code that merely *looks* similar and changes for different reasons.
- **KISS** (keep it simple): the simplest design that works is usually best.
- **YAGNI** (you aren't gonna need it): don't build flexibility for imagined future needs. Make code easy to change instead; the tests and the principles above do that.

Principles conflict sometimes, and over-applying them produces needless layers of tiny classes. Use them to **explain and improve** a design, not as a checklist to satisfy.

=== lesson py-patterns | Design patterns the Python way | 105
A **design pattern** is a named, reusable solution to a common design problem. The 1994 book *Design Patterns* (by the "Gang of Four") catalogued 23 of them for languages like C++ and Java. Knowing the names gives developers a shared vocabulary: "use a strategy here" says a lot in three words.

Python changes the picture. Because **functions are objects**, classes can be created on the fly, and duck typing needs no interfaces, many patterns shrink to a few lines, or disappear into the language. Here are the ones you'll meet most.

## Strategy: interchangeable algorithms

Pick an algorithm at runtime. In Java this means a `Strategy` interface and a class per algorithm. In Python, a strategy is often just a **function**:

```python
def regular(total):
    return total

def black_friday(total):
    return total * 0.7

def bulk(total):
    return total * 0.9 if total > 100 else total

class Checkout:
    def __init__(self, pricing=regular):
        self.pricing = pricing                 # any function: total -> total

    def pay(self, total):
        return round(self.pricing(total), 2)

Checkout(black_friday).pay(50)    # 35.0
```

`sorted(items, key=...)` is the strategy pattern you've already used: you pass the comparison strategy in.

## Factory: creating the right object

When the kind of object to create depends on data (a config file, user input, a JSON message), a **factory** decides. A dictionary from names to classes is the Pythonic version:

```python
SHAPES = {"circle": Circle, "rect": Rect}

def make_shape(spec):
    kind = spec.pop("type")
    try:
        cls = SHAPES[kind]
    except KeyError:
        raise ValueError(f"unknown shape: {kind}") from None
    return cls(**spec)                 # make_shape({"type": "circle", "radius": 2})
```

Class methods like `Date.from_string` are factories too.

## Observer: "tell me when something happens"

Objects **subscribe** to events, and a **subject** notifies all subscribers when the event happens. Buttons in user interfaces, "webhooks" and message queues all work this way. With callbacks, it's tiny:

```python
class EventBus:
    def __init__(self):
        self._subscribers = {}

    def subscribe(self, event, callback):
        self._subscribers.setdefault(event, []).append(callback)

    def publish(self, event, data):
        for callback in self._subscribers.get(event, []):
            callback(data)

bus = EventBus()
bus.subscribe("order_placed", lambda order: print("email receipt for", order))
bus.subscribe("order_placed", lambda order: print("update stock for", order))
bus.publish("order_placed", "A-17")
```

(`lambda` makes a small unnamed function; Module 12 explains it.) The publisher doesn't know who's listening: very low coupling.

## Iterator: one item at a time

The **iterator protocol** is how `for` loops work. An **iterable** has `__iter__`, which returns an **iterator**; an iterator has `__next__`, which returns the next item or raises `StopIteration` when there are no more:

```python
class Countdown:
    def __init__(self, start):
        self.current = start

    def __iter__(self):
        return self                      # this object is its own iterator

    def __next__(self):
        if self.current <= 0:
            raise StopIteration
        self.current -= 1
        return self.current + 1

for n in Countdown(3):
    print(n)                             # 3, 2, 1
```

`for x in obj` calls `iter(obj)` once, then `next(...)` repeatedly until `StopIteration`. Note the subtlety: an object that is **its own iterator** can only be looped over **once**. To be re-iterable (like a list), `__iter__` must return a **fresh** iterator each time. Module 12's **generators** make writing iterators much easier.

## Adapter: making interfaces fit

An **adapter** wraps an object to give it the interface other code expects, like a travel plug adapter:

```python
class FahrenheitSensor:                 # a third-party class we can't change
    def read_f(self):
        return 98.6

class CelsiusAdapter:
    def __init__(self, sensor):
        self.sensor = sensor

    def read(self):                      # the interface our code expects
        return round((self.sensor.read_f() - 32) * 5 / 9, 1)
```

## Patterns Python mostly doesn't need

- **Singleton** (exactly one instance): in Python, a module is already a single shared object. Put the shared instance at module level.
- **Command** (an object representing an action): a function, or a function plus arguments, already is one.
- **Decorator** (wrapping an object to add behaviour): Python has a whole language feature, `@decorator`, for wrapping functions (Module 12). It's related but not identical to the book's pattern.

## A word of caution

Patterns are tools, not goals. Introduce one when the problem it solves actually shows up (the second or third time you'd otherwise edit an `if` chain), not "just in case".

class EventBus:

=== lesson py-exceptions-oop | Exception hierarchies and context managers | 105
Libraries and applications define their own families of exceptions. Designed well, they make errors easy to handle precisely, and the `with` statement makes cleanup automatic even when errors happen.

## A base exception for your code

Give your application (or library) one base exception, and derive specific ones from it:

```python
class BankError(Exception):
    """Base class for every error raised by the bank module."""

class InsufficientFunds(BankError):
    def __init__(self, balance, amount):
        super().__init__(f"balance {balance} is less than {amount}")
        self.balance = balance                 # extra data for whoever handles it
        self.amount = amount

class AccountLocked(BankError):
    pass
```

Callers can now choose how precise to be:

```python
try:
    account.withdraw(500)
except InsufficientFunds as e:
    print(f"You need {e.amount - e.balance} more")      # handle one case specially
except BankError as e:
    print("Bank problem:", e)                           # anything else from the bank module
```

Code that catches `BankError` will automatically handle new bank errors added later: the hierarchy is **open for extension**. Real libraries do exactly this: `requests.RequestException`, `sqlite3.Error`, `json.JSONDecodeError` (a subclass of `ValueError`).

## Exceptions carry data

An exception is an object, so it can have attributes, like `balance` and `amount` above. Pass a readable message to `super().__init__(...)` (that's what `str(e)` shows) and keep the details as attributes for code that wants to react to them.

## Translate exceptions at boundaries

Low-level errors shouldn't leak out of a module that's supposed to hide its details. A user store backed by a dictionary raises `KeyError` for a missing user; callers shouldn't need to know it's a dictionary. **Translate** it at the boundary, keeping the cause with `from`:

```python
class UserNotFound(LookupError):
    def __init__(self, user_id):
        super().__init__(f"no user with id {user_id}")
        self.user_id = user_id

def load_user(db, user_id):
    try:
        return db[user_id]
    except KeyError as e:
        raise UserNotFound(user_id) from e
```

If the store later moves to a real database, callers still catch `UserNotFound`, and nothing else changes.

## More about exception objects

A few more details complete the picture of exceptions as objects:

- **`e.args`** holds the arguments given to the exception: `ValueError("bad", 42).args` is `("bad", 42)`.
- **Implicit chaining:** if an exception happens *while handling* another one, Python keeps the first in `__context__` and the traceback says "During handling of the above exception, another exception occurred". Explicit `raise ... from e` sets `__cause__` instead, which says "was the direct cause of".
- **Notes** (Python 3.11+): `e.add_note("while importing row 17")` attaches extra context that's shown in the traceback, without changing the exception type or message.
- **Exception groups** (Python 3.11+): when several independent things can fail at once (validating many records, running many tasks), raise them together as an `ExceptionGroup`, and handle each kind with `except*`:

```python
def validate(rows):
    errors = []
    for i, row in enumerate(rows):
        if row < 0:
            errors.append(ValueError(f"row {i}: negative"))
        elif row > 100:
            errors.append(OverflowError(f"row {i}: too big"))
    if errors:
        raise ExceptionGroup("invalid rows", errors)

try:
    validate([5, -1, 300, -7])
except* ValueError as group:
    print(len(group.exceptions), "negative rows")       # 2 negative rows
except* OverflowError as group:
    print(len(group.exceptions), "rows too big")        # 1 rows too big
```

Unlike `except`, **every** matching `except*` clause runs, each receiving a group with just its kind of exception. `asyncio.TaskGroup` raises exception groups when several tasks fail.

## Context managers: setup and cleanup, guaranteed

Many resources must be **released** after use: files closed, locks released, database transactions committed or rolled back. Forgetting, or skipping it because an exception happened, causes leaks and corrupted data. The `with` statement guarantees it:

```python
with open("notes.txt") as f:        # the file is opened...
    data = f.read()
# ...and closed here, even if read() raised an exception
```

Any object with `__enter__` and `__exit__` methods works with `with`. That's the **context manager protocol**:

```python
class Transaction:
    def __init__(self, account):
        self.account = account

    def __enter__(self):
        self.saved = self.account.balance       # setup: remember the state
        return self.account                     # bound to the "as" name

    def __exit__(self, exc_type, exc, tb):
        if exc_type is not None:                # an exception happened inside the with block
            self.account.balance = self.saved   # roll back
        return False                            # False: let the exception continue upwards

with Transaction(account) as acc:
    acc.withdraw(30)
    acc.deposit(-1)          # raises ValueError → the withdrawal is rolled back too
```

- `__enter__` runs at the start; what it returns is bound by `as`.
- `__exit__` **always** runs at the end, and receives the exception's type, value and traceback (all `None` if the block finished normally).
- Returning `True` from `__exit__` would **swallow** the exception; do that only deliberately.

=== lesson py-oop-internals | Under the hood: descriptors, slots and metaclasses | 105
This lesson opens the hood of Python's object system. You won't use these tools every day, but frameworks such as Django, SQLAlchemy and pydantic are built on them, and understanding them explains how features you've already used really work.

## Classes are objects too

Everything in Python is an object, including classes. Their type is `type`:

```python
class Point:
    pass

type(Point())        # <class '__main__.Point'>
type(Point)          # <class 'type'>
Dynamic = type("Dynamic", (), {"greeting": "hi"})     # create a class at runtime
Dynamic().greeting   # 'hi'
```

The `class` statement is essentially a call to `type(name, bases, namespace)`.

## How attribute lookup really works

For `obj.name`, Python checks **data descriptors** on the class, then the instance's `__dict__`, then the class and its MRO. Two hooks let a class take part:

- `__getattr__(self, name)` is called **only when normal lookup fails**: a safe place for fallbacks and delegation (a wrapper that forwards unknown attributes to the object it wraps).
- `__setattr__(self, name, value)` is called for **every** assignment, so it can validate or forbid changes. Inside it, store values with `super().__setattr__(name, value)` to avoid calling yourself forever.

## Descriptors: the machinery behind @property

A **descriptor** is an object, stored on a class, with `__get__` and/or `__set__` methods. When an attribute lookup finds one, Python calls those methods instead of returning the object itself. Properties, methods, `classmethod` and `staticmethod` are all descriptors.

Writing your own lets you reuse validation across many attributes and classes:

```python
class Positive:
    def __set_name__(self, owner, name):      # called when the class is created
        self.name = "_" + name

    def __get__(self, obj, objtype=None):
        return getattr(obj, self.name)

    def __set__(self, obj, value):
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be positive")
        setattr(obj, self.name, value)


class Product:
    price = Positive()
    weight = Positive()

    def __init__(self, price, weight):
        self.price = price          # goes through Positive.__set__
        self.weight = weight
```

One small class replaces a pair of property methods for every validated attribute. This is how ORM fields (`name = models.CharField(...)`) work.

## __slots__: fixed attributes

Normally each object has a `__dict__`, so you can add any attribute. Declaring `__slots__` gives instances a fixed set of attributes instead:

```python
class Pixel:
    __slots__ = ("x", "y")
    def __init__(self, x, y):
        self.x, self.y = x, y

p = Pixel(1, 2)
p.colour = "red"     # AttributeError: 'Pixel' object has no attribute 'colour'
```

Slotted objects use noticeably less memory (useful for millions of small objects) and catch attribute typos. Dataclasses support it with `@dataclass(slots=True)`.

## Subclassing built-in types

Subclassing `dict` or `list` directly has a surprise: the built-in methods are written in C and don't call your overrides, so a `dict` subclass that overrides `__setitem__` is bypassed by `update()` and the constructor. To customise behaviour, subclass `collections.UserDict` or `UserList`, which route every operation through the methods you override:

```python
from collections import UserDict

class LowerKeyDict(UserDict):
    def __setitem__(self, key, value):
        super().__setitem__(key.lower(), value)

    def __getitem__(self, key):
        return super().__getitem__(key.lower())

d = LowerKeyDict({"Name": "Ada"})
d["NAME"]           # 'Ada'
```

## Hooks for subclasses: __init_subclass__

`__init_subclass__` runs whenever a class is subclassed, a neat way to build **plugin registries** without any extra registration code:

```python
class Exporter:
    formats = {}

    def __init_subclass__(cls, fmt, **kwargs):
        super().__init_subclass__(**kwargs)
        Exporter.formats[fmt] = cls

class CsvExporter(Exporter, fmt="csv"):
    ...

Exporter.formats        # {'csv': <class '__main__.CsvExporter'>}
```

## Metaclasses (in one paragraph)

A **metaclass** is the class of a class (`type` is the default one). A custom metaclass, `class Meta(type)`, can change how classes are created: rename attributes, register them, add methods. Frameworks use them, but they're rarely the right tool in application code: class decorators and `__init_subclass__` solve the same problems more simply. As Tim Peters put it, if you wonder whether you need metaclasses, you don't.

=== lesson py-oop-case-study | Case study: building a gradebook step by step | 150
This lesson is a **guided project**: you'll build a small but real program the way professionals do, in steps, with tests at every stage. The goal isn't just the code; it's the **process**.

## Step 0: understand the problem

A teacher wants a gradebook:

> *Students are enrolled in a course. The teacher records scores (0–100) for each student. They want each student's average, a class report using either letter grades or pass/fail, and a way to save the gradebook and load it again.*

Before writing code, extract the pieces:

- **Nouns** → candidate classes and attributes: *student*, *course*, *score*, *report*, *grading policy*.
- **Verbs** → methods: *enrol*, *record a score*, *compute an average*, *grade*, *save*, *load*.
- **Rules** → invariants and errors: scores must be 0–100; you can't record a score for someone who isn't enrolled; enrolling twice is a mistake.

A useful old technique is the **CRC card** (Class, Responsibilities, Collaborators): one index card per class listing what it **knows**, what it **does**, and which classes it **works with**.

| Class | Responsibilities | Collaborators |
|---|---|---|
| `Student` | knows its id and name | none |
| `Course` | knows its students and their scores; enrols, records, averages | `Student` |
| grading policies | turn an average into a grade | none |
| `GradebookError` | reports domain mistakes | none |

## Step 1: the core model

Start with the smallest useful piece and **test it**. Students are plain data, so a frozen dataclass fits. The course enforces the rules and raises one domain exception, `GradebookError`, for every mistake. Store scores per student id; averages are computed, not stored, so they can never get out of date.

## Step 2: pluggable grading (strategy + open/closed)

The teacher wants letter grades for one class and pass/fail for another, and next term maybe something else. Rather than an `if policy == ...` chain inside `Course`, make grading a **strategy**: any object with a `grade(average)` method. `Course.report(policy)` uses whatever policy it's given. New policies need no changes to `Course`.

## Step 3: saving and loading (serialisation)

To save, convert the course to plain dictionaries and lists (which the `json` module can write, Module 11) with `to_dict()`, and rebuild it with a `from_dict()` **class method**, an alternative constructor. A good test for this is the **round trip**: `Course.from_dict(c.to_dict())` must behave exactly like `c`.

## Working style, in every step

1. Write or read the tests for the step first, so you know when you're done.
2. Make the simplest change that passes.
3. **Refactor** with the tests as a safety net.
4. Keep each class focused: if a method needs another class's data, consider whether it belongs there.

Each exercise below is one step. Each starter contains a working solution of the previous steps, so you can always continue even if you used a hint.

from dataclasses import dataclass


class GradebookError(Exception):
    pass


@dataclass(frozen=True)
class Student:
    student_id: int
    name: str


def student_name(student):
    return student.name


class LetterGrades:
    def grade(self, average):
        for limit, letter in [(90, "A"), (80, "B"), (70, "C"), (60, "D")]:
            if average >= limit:
                return letter
        return "F"


class PassFail:
    def __init__(self, pass_mark=50):
        self.pass_mark = pass_mark

    def grade(self, average):
        return "pass" if average >= self.pass_mark else "fail"


class Course:
    def __init__(self, title):
        self.title = title
        self._students = {}
        self._scores = {}

    def enrol(self, student):
        if student.student_id in self._students:
            raise GradebookError(f"student {student.student_id} is already enrolled")
        self._students[student.student_id] = student
        self._scores[student.student_id] = []

    def _check(self, student_id):
        if student_id not in self._students:
            raise GradebookError(f"no student {student_id} in {self.title}")

    def record(self, student_id, score):
        self._check(student_id)
        if not 0 <= score <= 100:
            raise GradebookError(f"score must be 0-100, got {score}")
        self._scores[student_id].append(score)

    def average(self, student_id):
        self._check(student_id)
        scores = self._scores[student_id]
        return round(sum(scores) / len(scores), 1) if scores else None

    def students(self):
        return sorted(self._students.values(), key=student_name)

    def report(self, policy):
        lines = []
        for s in self.students():
            avg = self.average(s.student_id)
            if avg is None:
                lines.append(f"{s.name}: no scores")
            else:
                lines.append(f"{s.name}: {avg} ({policy.grade(avg)})")
        return lines

class Course:
    def __init__(self, title):
        self.title = title
        self._students = {}
        self._scores = {}

    def enrol(self, student):
        if student.student_id in self._students:
            raise GradebookError(f"student {student.student_id} is already enrolled")
        self._students[student.student_id] = student
        self._scores[student.student_id] = []

    def _check(self, student_id):
        if student_id not in self._students:
            raise GradebookError(f"no student {student_id} in {self.title}")

    def record(self, student_id, score):
        self._check(student_id)
        if not 0 <= score <= 100:
            raise GradebookError(f"score must be 0-100, got {score}")
        self._scores[student_id].append(score)

    def average(self, student_id):
        self._check(student_id)
        scores = self._scores[student_id]
        return round(sum(scores) / len(scores), 1) if scores else None

    def students(self):
        return sorted(self._students.values(), key=student_name)

    def to_dict(self):
        return {
            "title": self.title,
            "students": [
                {"id": sid, "name": self._students[sid].name, "scores": list(self._scores[sid])}
                for sid in sorted(self._students)
            ],
        }

    @classmethod
    def from_dict(cls, data):
        course = cls(data["title"])
        for s in data["students"]:
            course.enrol(Student(s["id"], s["name"]))
            for score in s["scores"]:
                course.record(s["id"], score)
        return course

::solution
from abc import ABC, abstractmethod

FORMATTERS = {}


class Formatter(ABC):
    @abstractmethod
    def apply(self, text):
        pass


class Upper(Formatter):
    def apply(self, text):
        return text.upper()


class Title(Formatter):
    def apply(self, text):
        return text.title()


class Snake(Formatter):
    def apply(self, text):
        return "_".join(text.lower().split())


def register(name, cls):
    FORMATTERS[name] = cls


register("upper", Upper)
register("title", Title)
register("snake", Snake)


def format_text(text, names):
    for name in names:
        if name not in FORMATTERS:
            raise ValueError(f"unknown formatter: {name}")
        text = FORMATTERS[name]().apply(text)
    return text

class InventoryError(Exception):
    pass


class OutOfStock(InventoryError):
    def __init__(self, item, wanted, available):
        super().__init__(f"only {available} x {item} left, wanted {wanted}")
        self.item = item
        self.wanted = wanted
        self.available = available


class Inventory:
    def __init__(self, low_stock_level=3):
        self.low_stock_level = low_stock_level
        self._stock = {}
        self._listeners = []

    def add(self, item, qty):
        self._stock[item] = self._stock.get(item, 0) + qty

    def quantity(self, item):
        return self._stock.get(item, 0)

    def on_low_stock(self, callback):
        self._listeners.append(callback)

    def remove(self, item, qty):
        available = self.quantity(item)
        if qty > available:
            raise OutOfStock(item, qty, available)
        self._stock[item] = available - qty
        if self._stock[item] <= self.low_stock_level:
            for callback in self._listeners:
                callback(item, self._stock[item])
