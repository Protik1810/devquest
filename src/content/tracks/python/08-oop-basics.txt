## Why objects?

So far, **data** (variables, lists, dictionaries) and **behaviour** (functions) have lived separately. In a small program that's fine. In a big one, you end up with a dictionary for a bank account here, functions like `deposit(account, amount)` there, and nothing stopping some other code from setting the balance to `-1000` directly.

**Object-oriented programming** (OOP) bundles data **and** the functions that work on it into a single unit: an **object**. A car object has **state** (its fuel level, its speed) and **behaviour** (accelerate, brake), and the behaviour keeps the state sensible: you can't brake below zero speed.

You've been using objects all along. Every value in Python is an object: `"hi".upper()` calls a method of a string object, `scores.append(9)` calls a method of a list object. `type(42)` says `<class 'int'>`: even numbers are objects of a class. Now you'll create your own classes.

## Classes and instances

A **class** is a blueprint; an **instance** (or object) is a thing built from it. One `Dog` class can produce any number of dogs, each with its own name and age, like one cookie cutter making many cookies.

```python
class Dog:
    def __init__(self, name, age):
        self.name = name
        self.age = age

    def bark(self):
        return f"{self.name} says woof!"

    def birthday(self):
        self.age += 1


rex = Dog("Rex", 3)
fido = Dog("Fido", 7)
print(rex.bark())          # Rex says woof!
rex.birthday()
print(rex.age, fido.age)   # 4 7
```

Let's take it apart:

- `class Dog:` defines a class. Class names use **CapWords** (`BankAccount`, `HttpRequest`).
- Functions defined inside a class are called **methods**.
- `__init__` (say "dunder init", for the double underscores) is the **initialiser**. Python calls it automatically when you create an object with `Dog("Rex", 3)`. Its job is to give the new object its starting state.
- `self` is **the object the method is working on**. When you write `rex.bark()`, Python actually calls `Dog.bark(rex)`, passing `rex` in as `self`. That's why every method's first parameter is `self`.
- `self.name = name` creates an **attribute**: a variable that belongs to that particular object. `rex.name` and `fido.name` are separate.
- Outside the class, you reach attributes and methods with a dot: `rex.age`, `rex.bark()`.

## What happens when you write Dog("Rex", 3)

1. Python creates a new, empty `Dog` object.
2. It calls `__init__(that_object, "Rex", 3)`, which fills in its attributes.
3. It gives you back the object, which you name `rex`.

`__init__` doesn't `return` anything; it just sets up `self`.

## Methods read and change the object's state

`bark` reads `self.name`; `birthday` changes `self.age`. Because each object has its own attributes, `rex.birthday()` doesn't affect `fido`. Methods can also call other methods of the same object with `self.method()`.

## The classic mistakes

- Forgetting `self` in the method definition: `def bark():` gives `TypeError: Dog.bark() takes 0 positional arguments but 1 was given` when called, because Python always passes the object.
- Writing `name = name` instead of `self.name = name`: that just creates a local variable inside `__init__`, which vanishes. Later, `rex.name` fails with `AttributeError: 'Dog' object has no attribute 'name'`.
- Calling a method without its object: `bark()` instead of `rex.bark()` (or `self.bark()` inside the class).

## Designing a class: nouns and verbs

Describe the problem in a sentence or two. The **nouns** suggest classes and attributes; the **verbs** suggest methods. *"A bank account has an owner and a balance. You can deposit money and withdraw it, but you can't withdraw more than the balance."*

```python
class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("a deposit must be positive")
        self.balance += amount

    def withdraw(self, amount):
        if amount > self.balance:
            raise ValueError("insufficient funds")
        self.balance -= amount


account = BankAccount("Ada", 100)
account.deposit(50)
account.withdraw(30)
print(account.balance)    # 120
```

Notice how the class **protects its own rules**: code using the account calls `withdraw`, and `withdraw` refuses to let the balance go negative. A rule that must always hold is called an **invariant**; keeping invariants safe is one of the main jobs of a class.

## Printing an object

`print(rex)` shows something like `<__main__.Dog object at 0x7f3a...>`: the class name and a memory address. Two lessons from now you'll teach your classes to print nicely.

## When is a class worth it?

Use a class when some data and the operations on it belong together, especially when you need several objects of the same shape. Not everything needs one: if a "class" has only `__init__` and one other method, a plain function is usually simpler.

        if task not in self.tasks:

## Objects are reached through references

Everything you learned about lists and references applies to all objects. A variable holds a **reference** to an object; assigning it to another name doesn't copy the object:

```python
a = BankAccount("Ada", 100)
b = a              # the same account, two names
b.deposit(50)
print(a.balance)   # 150
```

Passing an object to a function passes a reference too, so the function can call its methods and change it. That's often exactly what you want ("give this account to the payroll function"), but be aware of it.

## Identity and equality

By default, `==` between two of your objects compares **identity**: it's `True` only for the very same object.

```python
x = Dog("Rex", 3)
y = Dog("Rex", 3)
print(x == y)     # False: two different dogs that happen to look alike
print(x == x)     # True
```

If two objects with the same data should count as equal (two points at the same coordinates, two amounts of money), you define `__eq__`, as you'll see in the special methods lesson.

## Where attributes live

Each object keeps its attributes in its own dictionary, which `vars()` shows:

```python
rex = Dog("Rex", 3)
print(vars(rex))          # {'name': 'Rex', 'age': 3}
```

Methods aren't stored in each object; they live once, on the **class**. When you write `rex.bark`, Python looks in the object first, then in its class. That's why all dogs share one `bark` method but each has its own `name`.

## Define every attribute in __init__

Python lets you add attributes to an object at any time (`rex.colour = "brown"`), but then different dogs have different attributes, and code that reads `colour` crashes on some of them. Give **every** attribute a starting value in `__init__`, even if it's `None` or an empty list. A typo like `rex.nmae` then fails loudly with `AttributeError` instead of silently creating a new attribute when assigned.

## Attributes by name: getattr and friends

When the attribute's name is in a variable, use the built-ins:

```python
field = "age"
getattr(rex, field)              # 3, same as rex.age
getattr(rex, "colour", "unknown")  # a default instead of AttributeError
setattr(rex, field, 4)           # rex.age = 4
hasattr(rex, "bark")             # True
```

## Objects working together

Objects often hold other objects: a `Library` holds `Book`s, an `Order` holds `LineItem`s, a `Game` holds `Player`s.

```python
class Book:
    def __init__(self, title, author):
        self.title = title
        self.author = author
        self.available = True


class Library:
    def __init__(self):
        self.books = []

    def add(self, book):
        self.books.append(book)

    def by_author(self, author):
        return [b.title for b in self.books if b.author == author]
```

Lists of objects are everywhere. To sort them, give `sorted` a key function that pulls out the attribute:

```python
def by_age(dog):
    return dog.age

for dog in sorted(dogs, key=by_age):
    print(dog.name)
```

(`operator.attrgetter("age")` does the same, and Module 12's `lambda` makes it shorter.)

## Changing state versus returning new objects

There are two styles of method:

- **Mutating** methods change the object: `account.deposit(50)`, `list.append(x)`. They usually return `None`.
- **Non-mutating** methods leave the object alone and return a **new** one: `"hi".upper()`, or a `Point.moved(dx, dy)` that returns a new point.

Objects that never change after creation are **immutable**. They're easier to reason about: no other code can change them behind your back, so they're safe to share and to use as dictionary keys. Many value-like objects (points, dates, money) are designed this way.

## Method chaining

A method that changes the object can `return self`, so calls can be chained into a readable sentence. Query builders and many libraries work like this:

```python
query = Query("users").where("age > 18").order_by("name").limit(10)
```

class Query:
    def __init__(self, table):
        self.table = table
        self.conditions = []
        self.order = None
        self.max_rows = None

    def where(self, condition):
        self.conditions.append(condition)
        return self

    def order_by(self, column):
        self.order = column
        return self

    def limit(self, n):
        self.max_rows = n
        return self

    def build(self):
        sql = f"SELECT * FROM {self.table}"
        if self.conditions:
            sql += " WHERE " + " AND ".join(self.conditions)
        if self.order:
            sql += f" ORDER BY {self.order}"
        if self.max_rows is not None:
            sql += f" LIMIT {self.max_rows}"
        return sql

=== lesson py-class-attrs | Class attributes, classmethods and staticmethods | 95
## Class attributes: shared by every instance

Attributes set on `self` belong to one object. Variables defined directly in the class body belong to the **class**, and every instance shares them:

```python
class Dog:
    species = "Canis familiaris"     # class attribute: one value for all dogs
    count = 0                        # how many dogs have been created

    def __init__(self, name):
        self.name = name             # instance attribute: one per dog
        Dog.count += 1


a = Dog("Rex")
b = Dog("Fido")
print(a.species, b.species)   # both read the class attribute
print(Dog.count)              # 2
```

Class attributes are good for **constants** that belong to the class (`MAX_SPEED = 120`, `species`) and for data about the class as a whole (a count of instances).

## Reading versus assigning

**Reading** `a.species` finds the class attribute, because Python looks on the object first and then on the class. **Assigning** through an object is different: `a.species = "wolf"` creates a new **instance** attribute on `a` that hides the class one. Other dogs still see the class value.

That causes a classic bug when counting:

```python
def __init__(self, name):
    self.count += 1      # BUG: reads Dog.count, then creates self.count on this one dog!
```

To change a class attribute, assign it through the class: `Dog.count += 1` (or `type(self).count += 1`).

## The shared mutable trap

A **mutable** class attribute is shared by every instance, which is almost never what you want for per-object data:

```python
class Player:
    inventory = []            # BUG: one list for ALL players

    def pick_up(self, item):
        self.inventory.append(item)

a, b = Player(), Player()
a.pick_up("sword")
print(b.inventory)            # ['sword']  ← b has a's sword!
```

`self.inventory.append` doesn't assign, it mutates the shared list. The fix: create the list in `__init__` (`self.inventory = []`), so each player gets their own. It's the same idea as the mutable default argument trap.

## Class methods: methods of the class itself

Decorating a method with `@classmethod` makes Python pass the **class** (named `cls` by convention) instead of an instance. The most common use is **alternative constructors**: other ways to create objects.

```python
class Date:
    def __init__(self, year, month, day):
        self.year = year
        self.month = month
        self.day = day

    @classmethod
    def from_string(cls, text):
        """Create a Date from text like '2026-10-14'."""
        year, month, day = text.split("-")
        return cls(int(year), int(month), int(day))


d = Date.from_string("2026-10-14")
print(d.month)     # 10
```

Python's own classes do this: `dict.fromkeys(...)`, `int.from_bytes(...)`, `datetime.fromisoformat(...)`. Using `cls(...)` rather than `Date(...)` means the method also works properly for subclasses (Module 9).

## Static methods: plain functions kept in the class

`@staticmethod` receives neither the instance nor the class. It's an ordinary function placed inside the class because it belongs there conceptually:

```python
class Date:
    ...
    @staticmethod
    def is_leap(year):
        return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

Date.is_leap(2024)    # True
```

## Which kind of method?

| Kind | First parameter | Use it when the method needs... |
|---|---|---|
| instance method | `self` | the object's data (most methods) |
| `@classmethod` | `cls` | the class: alternative constructors, class-wide data |
| `@staticmethod` | none | neither, but it belongs with the class |

The `@` lines are **decorators**: they modify the function defined below them. Module 12 shows how they work and how to write your own.

=== lesson py-encapsulation | Encapsulation and properties | 100
## Hiding the engine

A car gives you a steering wheel and pedals (its **interface**) and hides the engine (its **implementation**). You can drive any car without knowing how its engine works, and the manufacturer can redesign the engine without retraining every driver.

**Encapsulation** applies the same idea to classes: code that uses a class should go through its **methods** and documented attributes, not reach into its internals. Two big benefits:

1. The class can **protect its invariants**: if only `withdraw` can lower the balance, the balance can never go negative.
2. You can **change the internals** later (store cents instead of dollars, cache a value, read from a database) without breaking any code that uses the class.

## Python's conventions

Python doesn't have keywords like `private` in Java or C++. It relies on naming conventions; the community motto is "we're all consenting adults here":

- `self.balance`: **public**, part of the interface.
- `self._balance`: one leading underscore means **internal**. Python doesn't stop anyone using it, but the underscore says "not part of the interface; may change without warning". Tools and other developers respect it.
- `self.__balance`: two leading underscores trigger **name mangling**: Python renames it to `_BankAccount__balance`. It exists to avoid accidental name clashes with subclasses, not for security. Most code just uses one underscore.

## Properties: attribute syntax, method power

Suppose `Temperature` objects must never go below absolute zero. A plain attribute can't enforce that, because anyone can write `t.celsius = -500`. A **property** looks like an attribute from the outside but runs methods behind the scenes:

```python
class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius            # goes through the setter below!

    @property
    def celsius(self):                    # the "getter": runs on  t.celsius
        return self._celsius

    @celsius.setter
    def celsius(self, value):             # the "setter": runs on  t.celsius = value
        if value < -273.15:
            raise ValueError("below absolute zero")
        self._celsius = value

    @property
    def fahrenheit(self):                 # computed, read-only
        return self._celsius * 9 / 5 + 32


t = Temperature(20)
t.celsius = 25          # validated by the setter
print(t.fahrenheit)     # 77.0, computed on demand
t.celsius = -500        # ValueError: below absolute zero
t.fahrenheit = 100      # AttributeError: property 'fahrenheit' of 'Temperature' object has no setter
```

The real value is stored in `self._celsius` (with the underscore); `celsius` is the public face. Callers write natural code (`t.celsius = 25`), and the class keeps control.

## Why not get_x() and set_x() methods?

In some languages, every attribute gets getter and setter methods "just in case". In Python, **start with plain public attributes**. If you later need validation or a computed value, turn the attribute into a property, and every caller's code keeps working unchanged. That's exactly why properties exist.

## Read-only and computed attributes

A property without a setter is **read-only**. That's useful for:

- values computed from others (`area` from `width` and `height`, `full_name` from first and last names), which can then never get out of sync;
- values that must only change through methods (an account's `balance`, changed only by `deposit` and `withdraw`).

## Tell, don't ask

Encapsulated designs **tell** objects what to do instead of **asking** for their data and doing it themselves:

```python
# asking: the rule lives outside the class, and is repeated wherever it's needed
if account.balance >= 50:
    account.balance -= 50

# telling: the rule lives in one place, inside the class
account.withdraw(50)
```

=== lesson py-dunder | Special methods (dunder methods) | 105
How does `len("hello")` know the length of a string, and `len([1, 2])` of a list? How does `+` add numbers but join strings? Python's **data model** answers: built-in functions and operators call **special methods** on the object, whose names start and end with double underscores ("dunder" methods).

| You write | Python calls |
|---|---|
| `len(x)` | `x.__len__()` |
| `str(x)`, `print(x)`, `f"{x}"` | `x.__str__()` |
| `repr(x)`, and inside lists | `x.__repr__()` |
| `x == y` | `x.__eq__(y)` |
| `x < y` | `x.__lt__(y)` |
| `x + y` | `x.__add__(y)` |
| `x[i]` | `x.__getitem__(i)` |
| `item in x` | `x.__contains__(item)` |
| `bool(x)`, `if x:` | `x.__bool__()` (or `__len__`) |

Define these methods, and your objects work with Python's syntax as naturally as the built-in types.

## __repr__ and __str__

```python
class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __repr__(self):
        return f"Point({self.x!r}, {self.y!r})"

    def __str__(self):
        return f"({self.x}, {self.y})"


p = Point(1, 2)
print(p)           # (1, 2)          uses __str__
print(repr(p))     # Point(1, 2)     uses __repr__
print([p, p])      # [Point(1, 2), Point(1, 2)]   containers show repr
```

- `__repr__` is for **developers**: unambiguous, ideally looking like the code that would recreate the object. It appears in the shell, in lists, in debuggers and in error messages.
- `__str__` is for **users**: readable. If you only define `__repr__`, `str()` uses it too.

Always write at least a `__repr__`; it makes debugging far easier.

## __eq__ and hashing

```python
    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented          # let Python try the other side, then fall back to False
        return (self.x, self.y) == (other.x, other.y)
```

Now `Point(1, 2) == Point(1, 2)` is `True`. Returning `NotImplemented` (not raising) for unknown types is the polite convention.

There's a catch: defining `__eq__` makes objects **unhashable** (you can no longer put them in sets or use them as dictionary keys) unless you also define `__hash__`. Equal objects must have equal hashes, so hash the same fields you compare, and only for objects that don't change after creation:

```python
    def __hash__(self):
        return hash((self.x, self.y))
```

## Ordering: __lt__ and friends

Define `__lt__` (less than), and `sorted()`, `min()` and `max()` work on your objects. The `functools.total_ordering` decorator fills in `<=`, `>` and `>=` from `__eq__` and `__lt__`:

```python
from functools import total_ordering

@total_ordering
class Version:
    def __init__(self, major, minor):
        self.major, self.minor = major, minor

    def __eq__(self, other):
        return (self.major, self.minor) == (other.major, other.minor)

    def __lt__(self, other):
        return (self.major, self.minor) < (other.major, other.minor)
```

Comparing tuples of fields is a neat trick: tuples compare item by item.

## Containers: __len__, __getitem__, __contains__, __iter__

```python
class Playlist:
    def __init__(self, songs):
        self._songs = list(songs)

    def __len__(self):
        return len(self._songs)

    def __getitem__(self, index):         # pl[0], pl[-1], pl[1:3]
        return self._songs[index]

    def __contains__(self, song):         # "Yesterday" in pl
        return song in self._songs

    def __iter__(self):                   # for song in pl
        return iter(self._songs)
```

By **delegating** to the list inside, a few lines make `Playlist` behave like a real sequence. (Module 12 shows how to write `__iter__` with generators.)

## Arithmetic: __add__, __mul__ and the reflected versions

```python
class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)

    def __mul__(self, k):                 # v * 3
        return Vector(self.x * k, self.y * k)

    def __rmul__(self, k):                # 3 * v: int doesn't know Vector, so Python tries v.__rmul__(3)
        return self * k
```

Operators should return **new** objects and leave the operands unchanged, like numbers do.

## Truthiness and calling

- `__bool__` decides truthiness: an empty playlist or a zero vector might be falsy. Without it, Python uses `__len__` (0 is falsy), and otherwise every object is truthy.
- `__call__` makes an instance callable like a function: `obj(args)`.

## Use operators only when the meaning is obvious

`vector + vector` and `money + money` read naturally. `user + user` doesn't: what would it mean? Overloading operators with surprising meanings makes code harder to read, so prefer a well-named method in that case.

@total_ordering
class Money:
    def __init__(self, cents, currency):
        self.cents = cents
        self.currency = currency

    def __repr__(self):
        return f"Money({self.cents!r}, {self.currency!r})"

    def __str__(self):
        return f"{self.cents / 100:.2f} {self.currency}"

    def __eq__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return (self.cents, self.currency) == (other.cents, other.currency)

    def __hash__(self):
        return hash((self.cents, self.currency))

    def _check(self, other):
        if self.currency != other.currency:
            raise ValueError(f"can't mix {self.currency} and {other.currency}")

    def __add__(self, other):
        self._check(other)
        return Money(self.cents + other.cents, self.currency)

    def __lt__(self, other):
        self._check(other)
        return self.cents < other.cents

class ShoppingCart:
    def __init__(self):
        self._items = {}

    def add(self, name, price_cents, qty=1):
        if qty <= 0:
            raise ValueError("quantity must be positive")
        if name in self._items:
            self._items[name][1] += qty
        else:
            self._items[name] = [price_cents, qty]

    def remove(self, name):
        del self._items[name]

    @property
    def total(self):
        return sum(price * qty for price, qty in self._items.values())

    def __len__(self):
        return sum(qty for _, qty in self._items.values())

    def __contains__(self, name):
        return name in self._items

    def __str__(self):
        lines = [f"{qty} x {name} @ {price / 100:.2f} = {price * qty / 100:.2f}" for name, (price, qty) in self._items.items()]
        lines.append(f"Total: {self.total / 100:.2f}")
        return "\n".join(lines)

import math


class Ratio:
    def __init__(self, n, d):
        if d == 0:
            raise ZeroDivisionError("denominator is zero")
        if d < 0:
            n, d = -n, -d
        g = math.gcd(n, d)
        self.numerator = n // g
        self.denominator = d // g

    def __repr__(self):
        return f"Ratio({self.numerator}, {self.denominator})"

    def __str__(self):
        if self.denominator == 1:
            return str(self.numerator)
        return f"{self.numerator}/{self.denominator}"

    def __add__(self, other):
        return Ratio(self.numerator * other.denominator + other.numerator * self.denominator, self.denominator * other.denominator)

    def __mul__(self, other):
        return Ratio(self.numerator * other.numerator, self.denominator * other.denominator)

    def __eq__(self, other):
        if not isinstance(other, Ratio):
            return NotImplemented
        return (self.numerator, self.denominator) == (other.numerator, other.denominator)

    def __hash__(self):
        return hash((self.numerator, self.denominator))

    def __float__(self):
        return self.numerator / self.denominator
