=== lesson py-errors | Handling exceptions | 95
Programs meet a messy world: users type `ten` where you expected a number, files go missing, networks drop. When something goes wrong at runtime, Python **raises an exception**. If nothing handles it, the program crashes with a traceback. **Handling** exceptions lets a program recover gracefully.

## try and except

```python
try:
    age = int(input("Age: "))
    print("Next year you'll be", age + 1)
except ValueError:
    print("That's not a whole number.")
```

Python runs the `try` block. If a `ValueError` happens anywhere in it, Python **jumps** straight to the `except ValueError` block; the rest of the `try` block is skipped. If no error happens, the `except` block is skipped. Either way, the program carries on after the whole statement instead of crashing.

## Catch specific exceptions

Always name the exception you expect. A bare `except:` (or `except Exception:`) catches **everything**, including your own bugs:

```python
try:
    total = sum(prices) / len(pirces)     # typo!
except Exception:
    print("No prices yet")                 # hides the NameError: very confusing
```

The rule: **catch only what you know how to handle**, and let everything else crash loudly so you notice it.

## Several kinds of error

```python
try:
    result = values[index] / divisor
except IndexError:
    print("No value at that position")
except ZeroDivisionError:
    print("Can't divide by zero")
except (TypeError, ValueError):          # a tuple catches any of these
    print("Bad data")
```

Python checks the `except` clauses top to bottom and runs the **first** one that matches.

## Looking at the exception

`as` gives you the exception object, whose text is the error message:

```python
try:
    int("ten")
except ValueError as e:
    print("Problem:", e)      # Problem: invalid literal for int() with base 10: 'ten'
```

## else and finally

```python
try:
    value = int(text)
except ValueError:
    print("Not a number")
else:
    print("Converted:", value)    # runs only if the try block raised nothing
finally:
    print("Done")                 # ALWAYS runs: error or not, even after return
```

`else` keeps the `try` block small: only the risky line goes in `try`, and the code that depends on its success goes in `else`. `finally` is for **cleanup** that must happen no matter what, such as closing a connection. (For files, Module 11's `with` statement does this for you.)

## The exception family tree

Exceptions are organised in families. Catching a parent catches all its children:

```
BaseException
 ├── KeyboardInterrupt        (Ctrl+C)
 ├── SystemExit               (sys.exit())
 └── Exception                (everything a program normally handles)
      ├── ArithmeticError
      │    └── ZeroDivisionError
      ├── LookupError
      │    ├── IndexError
      │    └── KeyError
      ├── ValueError
      ├── TypeError
      ├── NameError
      ├── AttributeError
      └── OSError
           ├── FileNotFoundError
           └── PermissionError
```

So `except LookupError:` handles both a bad list index and a missing dictionary key. Put specific exceptions **before** general ones, or the general one catches everything first. Never catch `BaseException`: you'd stop Ctrl+C from working.

## A robust input loop

```python
while True:
    try:
        n = int(input("Number: "))
        break                         # only reached if int() succeeded
    except ValueError:
        print("Please type a whole number.")
```

## Two styles: look before you leap, or ask forgiveness

- **LBYL** (look before you leap): check first, `if text.isdigit(): n = int(text)`.
- **EAFP** (easier to ask forgiveness than permission): just try it, and handle the failure.

Python code often prefers EAFP, and for conversions it's more correct: `"-5".isdigit()` is `False`, yet `int("-5")` works fine. Let `int()` and `float()` decide what a valid number is.

## Exceptions travel up the call stack

If a function doesn't handle an exception, it passes up to the function that called it, then to *its* caller, and so on. Handle an exception at the level where you can **do something sensible** about it: ask the user again, use a default, skip a record. Often that's not where it happened.

=== lesson py-raise | Raising exceptions | 95
Handling errors is half the story. The other half: making **your own code** report problems clearly, by **raising** exceptions.

## raise

```python
def set_age(age):
    if age < 0:
        raise ValueError(f"age can't be negative, got {age}")
    return age
```

`raise` stops the function immediately and sends the exception up to the caller, exactly like Python's own errors. If nobody handles it, the program shows a traceback with your message.

## Why raise instead of returning something?

Imagine `set_age(-5)` returned `None` or `-1` instead. Every caller would have to remember to check, and the ones that forget would carry on with a bad value, causing a confusing failure much later, far from the real problem. An exception **can't be silently ignored**. This principle is called **fail fast**: detect bad data as early as possible and refuse it loudly.

## Choosing the exception type

Use the built-in type whose meaning fits:

| Situation | Raise |
|---|---|
| right type, but an unacceptable value (negative age, empty name) | `ValueError` |
| the wrong type entirely (a list where a number belongs) | `TypeError` |
| a missing key / position | `KeyError` / `IndexError` |
| something you haven't written yet | `NotImplementedError` |

And write a **helpful message**: what was wrong, and what was expected. `ValueError("percent must be between 0 and 100, got 150")` beats `ValueError("bad input")`.

## Re-raising

Sometimes you want to note an error and still let it continue upwards. A bare `raise` inside an `except` block re-raises the same exception:

```python
try:
    process(order)
except ValueError:
    print("Could not process", order)
    raise
```

## Chaining: raise ... from

When you catch a low-level error and raise a more meaningful one, link them with `from`, so the traceback shows both:

```python
def get_port(settings):
    try:
        return int(settings["port"])
    except (KeyError, ValueError) as e:
        raise RuntimeError("the configuration needs a numeric 'port'") from e
```

The traceback then says "The above exception was the direct cause of the following exception", and the original error is kept on the new one as `__cause__`. Writing `from None` hides the original when it would only confuse.

## Your own exception types

You can define a new kind of exception in one line:

```python
class InsufficientFundsError(Exception):
    """Raised when a withdrawal is larger than the balance."""

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError(f"balance {balance} is less than {amount}")
    return balance - amount

try:
    withdraw(50, 80)
except InsufficientFundsError as e:
    print("Declined:", e)
```

`class ... (Exception)` creates a new member of the `Exception` family. Classes are explained properly in Module 8, and Module 10 designs whole exception hierarchies; for now this one-line pattern is all you need. Custom exceptions let callers catch **exactly** your error and nothing else.

## assert is for bugs, not for input

`assert condition, "message"` checks something that should **always** be true if your code is correct, a sanity check for programmers:

```python
def apply_discount(price, percent):
    if not 0 <= percent <= 100:
        raise ValueError("percent must be between 0 and 100")     # bad INPUT: raise
    result = price * (1 - percent / 100)
    assert 0 <= result <= price, "discount maths is broken"      # a BUG would trigger this
    return result
```

Don't use `assert` to validate user input: Python can be run with assertions switched off (`python -O`), and then the check would silently disappear.

## Testing that something raises

To check that code raises an exception, expect it with `try`/`except`/`else`:

```python
try:
    set_age(-1)
except ValueError:
    pass                                       # good: it raised
else:
    raise AssertionError("set_age(-1) should raise ValueError")
```

Testing frameworks have shortcuts for this (`self.assertRaises` in unittest, `pytest.raises` in pytest), which you'll meet in the testing lesson.

=== lesson py-debugging | Debugging and logging | 95
**Debugging** is finding out why a program does what it does, rather than what you meant. Beginners often debug by randomly changing things until the error goes away. Professionals use a method, because it's faster and it actually finds the cause.

## A debugging method

It's the scientific method applied to code:

1. **Reproduce** the bug reliably, ideally with the smallest input that triggers it.
2. **Observe.** Read the traceback, or compare the expected output with the actual output line by line.
3. **Locate.** Find the first point where reality differs from what you expected, by looking at intermediate values.
4. **Hypothesise** one specific cause ("`total` is reset inside the loop"), and **test** it by changing one thing.
5. **Fix the cause**, not the symptom, and add a test so the bug can never silently return.

## Looking inside: print debugging done well

```python
print(f"{total=} {i=} {item=}")      # labels and values: total=12 i=3 item='5'
print(repr(name))                     # 'Ada ' shows the stray space
print(type(value))                    # <class 'str'>, not the int you expected?
```

Print **at the boundaries**: what goes into a function, and what comes out. Then narrow down. Remove the prints when you're done (or turn them into logging, below).

## Divide and conquer

If a long piece of code produces a wrong result, check the value **halfway** through. Correct there? The bug is in the second half. Wrong? The first half. Keep halving. This "binary search" finds a bug among 1,000 lines in about 10 checks. The same trick works on data: if a file of 10,000 records crashes your program, try the first half.

## Explain it to a duck

Explaining your code line by line, out loud, to someone (or a rubber duck) forces you to say what each line *actually* does. The mismatch with what you *meant* often jumps out. And when you're stuck for a long time, take a break: tired brains see what they expect, not what's there.

## A field guide to common bugs

| Symptom | Likely cause |
|---|---|
| `IndexError` at the end of a loop | off by one: `range(len(x) + 1)` or `<=` instead of `<` |
| a value is unexpectedly `None` | a function forgot to `return`; `x = x.sort()` |
| a list changes "by itself" | aliasing (`b = a`), or a mutable default argument |
| `'int' object is not callable` | a variable named after a built-in (`sum`, `max`, `list`) |
| `"5" + "3"` gives `"53"` | `input()` text never converted with `int()` |
| the program hangs | a loop whose condition never becomes false |
| `UnboundLocalError` | assigning to a global's name inside a function |
| wrong only at the edges | `<` vs `<=`, empty input, a single item |
| two floats "should" be equal | binary floats: use `math.isclose` |

## Logging: print statements for grown-up programs

`print` mixes debugging output with the program's real output. The `logging` module separates them and lets you choose how much detail to see:

```python
import logging

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

logging.debug("cart contents: %s", cart)          # hidden at INFO level
logging.info("order %s processed", order_id)      # normal events
logging.warning("stock low for %s", product)      # something unexpected
logging.error("payment failed for %s", order_id)  # something went wrong
```

There are five levels, from least to most serious: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL`. The configured level hides everything below it, so you can leave the logging calls in your code and turn detail up or down without editing it. Logs can go to the screen, to files, or to monitoring services in production.

In larger programs, each module gets its own named logger:

```python
logger = logging.getLogger(__name__)
logger.info("starting import of %d rows", len(rows))
```

Notice the `%s`/`%d` placeholders with separate arguments: the message is only formatted if that level is actually shown.

## Debuggers

A **debugger** pauses a running program so you can step through it line by line and inspect every variable. === lesson py-testing | Writing automated tests | 100
Every DevQuest exercise so far was checked by tests someone else wrote. Professional developers write their own, constantly. **Automated tests** are small programs that check your program, and they're one of the most valuable habits you can build.

## Why bother?

- **Catch mistakes early**, while the code is fresh in your mind.
- **Change code without fear.** When you improve or **refactor** code, the tests tell you instantly if you broke something that used to work (a **regression**).
- **Document behaviour.** A test like `test_rejects_negative_age` explains what the code should do better than a comment.

## The shape of a test

A good test has three parts, often called **Arrange, Act, Assert**:

```python
def test_discount_reduces_price():
    price = 100              # arrange: set up the inputs
    result = discount(price, 20)  # act: call the code
    assert result == 80      # assert: check the outcome
```

Each test checks **one behaviour** and its name says which. When it fails, the name alone tells you what broke.

## pytest: the popular way

**pytest** is the most widely used test tool in Python (`pip install pytest`, Module 12). You write test files named `test_something.py` containing functions named `test_...` that use plain `assert`. Running `pytest` finds and runs them all and shows exactly which values differed:

```python
# test_pricing.py
from pricing import discount

def test_discount_reduces_price():
    assert discount(100, 20) == 80

def test_zero_percent_changes_nothing():
    assert discount(59.99, 0) == 59.99

def test_rejects_percent_over_100():
    try:
        discount(10, 150)
    except ValueError:
        pass
    else:
        assert False, "expected a ValueError"
```

With pytest, the last test is usually written `with pytest.raises(ValueError): discount(10, 150)`.

## unittest: the one in the standard library

Python ships with **unittest**. Tests are methods of a class (classes arrive in Module 8; just recognise the shape):

```python
import unittest
from pricing import discount

class TestDiscount(unittest.TestCase):
    def test_reduces_price(self):
        self.assertEqual(discount(100, 20), 80)

    def test_rejects_percent_over_100(self):
        with self.assertRaises(ValueError):
            discount(10, 150)

if __name__ == "__main__":
    unittest.main()
```

Run it with `python -m unittest`. pytest can run unittest tests too.

? Which test name tells you most when it fails?
- `test_1`
- `test_function`
+ `test_rejects_empty_password`
- `check`
> A good name states the behaviour being checked.
~~~

## What to test

For each function, think in three groups:

1. **Typical cases**: normal inputs, with an answer you've worked out by hand.
2. **Edge cases**: empty input, zero, one item, negative numbers, very large values, exactly-on-the-boundary values, text with spaces or capitals.
3. **Error cases**: inputs that should raise an exception.

Bugs cluster at the edges, so that's where good testers spend their effort.

## Test-driven development (TDD)

Some developers write the test **before** the code:

1. **Red:** write a test for the next small piece of behaviour; it fails, because the code doesn't exist.
2. **Green:** write the simplest code that makes it pass.
3. **Refactor:** tidy the code, with the tests guarding you.

Even if you don't always work this way, writing a test first forces you to decide exactly what the function should do.

## Do your tests actually catch bugs?

A test suite that never fails is useless. One way to check it: deliberately put a bug in the code (a **mutant**). If no test fails, your tests have a gap. Tools like `mutmut` do this automatically. The exercises below work exactly like that: your tests are run against the correct code (they must pass) and against several buggy versions (each must make at least one test fail).

📚 **Go deeper:** pytest documentation, "Get started"; Python Library Reference, `unittest`; *Python Testing with pytest* (2nd ed.) by Brian Okken; Kent Beck, *Test-Driven Development by Example*.

def _no_sort(numbers):

        raise ValueError("empty")
