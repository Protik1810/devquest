=== lesson mongo-intro | Documents, collections & your first inserts | 50
**MongoDB** is a *document database*. Instead of rows in tables, it stores **documents**: JSON-like objects grouped into **collections**.

| Relational (SQL) | MongoDB |
|---|---|
| database | database |
| table | collection |
| row | document |
| column | field |
| JOIN | embedding, or `$lookup` |

A document can hold nested objects and arrays, so data that belongs together is stored together:

```js
{
  _id: ObjectId('65f1…'),
  name: 'Ada',
  skills: ['math', 'engines'],
  address: { city: 'London', country: 'UK' }
}
```

- Every document has a unique **`_id`**. If you don't give one, MongoDB creates an **ObjectId** (12 bytes: timestamp + random + counter).
- Documents in one collection *can* have different shapes (a **flexible schema**). In practice you keep them consistent and can enforce it with schema validation.
- On disk MongoDB uses **BSON** (binary JSON), which adds types such as dates, 64-bit integers and decimals.

**The shell.** You talk to MongoDB with `mongosh`. Collections are created the first time you insert into them:

```js
db.heroes.insertOne({ name: 'Ada', level: 7 })
db.heroes.insertMany([{ name: 'Linus' }, { name: 'Grace' }])
db.heroes.countDocuments()            // 3
db.heroes.findOne({ name: 'Ada' })    // the first match, or null
```

In DevQuest's MongoDB shell, `print(...)` and `printjson(...)` show values the way `mongosh` does.

**When to choose MongoDB:** data that is naturally hierarchical (product catalogues, user profiles, content), schemas that change often, and horizontal scaling. **When to prefer SQL:** many relationships, complex joins and reporting, and multi-table transactions everywhere.

=== lesson mongo-query | Querying with filters & operators | 55
`find(filter, projection)` returns a **cursor** over every matching document. The filter is itself a document:

```js
db.books.find({ author: 'Andy Weir' })              // equality
db.books.find({ year: { $gte: 2000, $lt: 2010 } })   // range
db.books.find({ genres: 'sci-fi' })                  // matches if the ARRAY contains 'sci-fi'
db.books.find({ title: /^the/i })                    // regular expression
```

**Comparison operators:** `$eq $ne $gt $gte $lt $lte $in $nin`. **Logical:** fields listed together are ANDed; use `$or`, `$and`, `$nor` and `$not` for more:

```js
db.books.find({ $or: [{ stock: 0 }, { price: { $gt: 20 } }] })
db.books.find({ subtitle: { $exists: false } })
```

**Projection** picks the fields to return: `1` includes, `0` excludes. `_id` is included unless you exclude it:

```js
db.books.find({ genres: 'fantasy' }, { _id: 0, title: 1, price: 1 })
```

**Counting:** `countDocuments(filter)`. **Iterating:** `cursor.forEach(printjson)` or `cursor.toArray()`.

Today's collection, **`books`**, has fields `title`, `author`, `year`, `genres` (array), `price`, `stock` and `ratings` (array).

=== lesson mongo-sort | Sorting, paging & distinct values | 50
Cursors can be shaped before you read them:

```js
db.books.find().sort({ price: 1 })            // 1 = ascending, -1 = descending
db.books.find().sort({ year: -1, title: 1 })  // tie-breaker on the second key
db.books.find().limit(5)                       // at most 5
db.books.find().skip(10).limit(5)              // page 3 when a page holds 5
db.books.distinct('genres')                    // unique values (arrays are flattened)
```

**Pagination.** Page *p* (counting from 1) with page size *n* is `skip((p - 1) * n).limit(n)`. Always sort when paging, otherwise the order (and so the pages) isn't guaranteed. For very deep pages, `skip` gets slow because the server still walks the skipped documents. Large apps use **range pagination** instead: "items with `_id` greater than the last one I showed".

The order in which you call `sort`, `skip` and `limit` on a cursor doesn't matter: MongoDB always sorts first, then skips, then limits.

=== lesson mongo-update | Updating & deleting documents | 60
Updates take a **filter** and an **update document** made of operators:

```js
db.books.updateOne({ title: 'Dune' }, { $set: { price: 8.99 } })
db.books.updateMany({ stock: 0 }, { $set: { status: 'sold out' } })
db.books.updateOne({ _id: 1 }, { $inc: { stock: -1 } })   // atomic counter
```

| Operator | Effect |
|---|---|
| `$set` / `$unset` | set or remove fields |
| `$inc` / `$mul` | add to / multiply a number |
| `$push` / `$addToSet` | append to an array (`$addToSet` skips duplicates) |
| `$pull` | remove matching array elements |
| `$rename` | rename a field |

**Upsert** updates a match, or inserts a new document when nothing matches:

```js
db.books.updateOne({ title: 'Leviathan Wakes' }, { $set: { year: 2011 } }, { upsert: true })
```

**Deleting:** `deleteOne(filter)` and `deleteMany(filter)`. Beware `deleteMany({})`: an empty filter matches *everything*.

Every write to a **single document** is atomic, even when it changes many fields or nested arrays. That's one reason MongoDB encourages keeping data that changes together in one document. For multi-document atomicity MongoDB also has transactions, at a performance cost.

=== lesson mongo-nested | Nested documents & arrays | 60
Real documents nest. Query inside them with **dot notation** (always quoted):

```js
db.orders.find({ 'customer.city': 'London' })
db.orders.find({ 'items.sku': 'MS-2' })          // any element of the items array
db.orders.find({ items: { $size: 2 } })           // exactly two items
```

**The array trap.** Conditions on an array of sub-documents are checked *independently*:

```js
// "some item has sku MN-4" AND "some (maybe other) item has qty >= 2"
db.orders.find({ 'items.sku': 'MN-4', 'items.qty': { $gte: 2 } })
```

To require **one element** to satisfy every condition, use **`$elemMatch`**:

```js
db.orders.find({ items: { $elemMatch: { sku: 'MN-4', qty: { $gte: 2 } } } })
```

**Modelling: embed or reference?**
- **Embed** when the data is read together, owned by the parent and bounded in size (order lines, addresses).
- **Reference** (store an id) when the data is shared, large, unbounded or changes independently (authors of posts, products in orders when the catalogue changes). You'll join references with `$lookup` later.

A document can be at most **16 MB**, so never let an array grow forever (think "comments on a viral post").

=== lesson mongo-aggregate | The aggregation pipeline | 70
For reports and transformations, MongoDB runs documents through a **pipeline** of stages. Each stage's output feeds the next:

```js
db.orders.aggregate([
  { $match: { status: 'shipped' } },                          // filter (like WHERE)
  { $unwind: '$items' },                                      // one document per array element
  { $group: { _id: '$items.sku', units: { $sum: '$items.qty' } } },   // like GROUP BY
  { $sort: { units: -1 } },
  { $limit: 3 },
])
```

| Stage | SQL cousin |
|---|---|
| `$match` | WHERE |
| `$group` with `$sum $avg $min $max $push $count` | GROUP BY + aggregates |
| `$project`, `$addFields` | SELECT expressions |
| `$sort`, `$limit`, `$skip` | ORDER BY, LIMIT, OFFSET |
| `$unwind` | turning an array into rows |
| `$lookup` | LEFT OUTER JOIN |

**Field paths** start with `$` (`'$items.qty'`). **Expressions** compute values: `{ $multiply: ['$items.qty', '$items.price'] }`, `{ $concat: ['$first', ' ', '$last'] }`.

Put `$match` (and `$sort` on indexed fields) **as early as possible**, so later stages handle fewer documents and indexes can be used.

=== lesson mongo-indexes | Indexes, uniqueness & $lookup | 70
Without an index, a query has to read **every document** (a **COLLSCAN**). An **index** is a sorted structure (a B-tree) over one or more fields, so MongoDB can jump straight to matches (an **IXSCAN**):

```js
db.posts.createIndex({ author: 1 })                      // single field
db.posts.createIndex({ author: 1, likes: -1 })           // compound: filter by author, sort by likes
db.users.createIndex({ email: 1 }, { unique: true })     // also enforces uniqueness
db.posts.find({ author: 'u1' }).explain().queryPlanner.winningPlan
```

Indexes speed up reads but cost **memory and slower writes** (each insert updates every index). Index the fields you filter and sort by most, and check with `explain()`.

**Joining references with `$lookup`.** When documents refer to each other by id, join at read time:

```js
db.posts.aggregate([
  { $lookup: { from: 'users', localField: 'author', foreignField: '_id', as: 'user' } },
  { $unwind: '$user' },
  { $project: { _id: 0, title: 1, name: '$user.name' } },
])
```

`$lookup` is a left outer join: `user` is an *array* of matches, which is why it's usually followed by `$unwind`.

=== lesson mongo-design | Schema design & production MongoDB | 60
Designing for MongoDB starts from **how the app reads and writes**, not from normalisation rules.

**Patterns you'll meet:**
- **Embedded one-to-few:** a user's 2-3 addresses live inside the user.
- **One-to-many with references:** a product stores `categoryId`; the category list is its own collection.
- **Subset pattern:** keep the 10 newest reviews embedded for the product page, and all reviews in a separate collection.
- **Computed pattern:** store `ratingAvg` and `ratingCount`, updated with `$inc` on each review, instead of recomputing every read.
- **Bucket pattern:** group time-series readings per sensor per hour into one document.

**Consistency & scale:**
- **Replica sets:** one primary takes writes; secondaries copy its oplog and take over automatically on failure.
- **Write concern** (`w: 'majority'`) decides how many replicas must confirm a write. **Read concern** decides what you may read.
- **Sharding** splits a collection across servers by a **shard key**. Choose one with high cardinality that spreads writes (not an ever-increasing timestamp alone).
- **Transactions** across documents exist, but a design that needs them everywhere may fit SQL better.

**Security basics:** enable authentication, never expose port 27017 to the internet, use least-privilege roles, and validate input. Operators like `$where` or a raw user-supplied `{ "$gt": "" }` in a filter enable **NoSQL injection**.

--- cards
Subset pattern :: Embed a small, frequently-read part of a large related set (e.g. newest reviews); keep the rest in its own collection.
Shard key :: The field(s) that decide which shard stores a document; should have high cardinality and spread writes.
NoSQL injection :: Passing user-controlled objects (like { "$ne": "" }) into query filters. Prevent it by validating types.
