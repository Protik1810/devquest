## Doing several things at once

A **goroutine** is a function running concurrently with the rest of the program. You start one by putting **`go`** before a call. Goroutines are extremely cheap (a few kilobytes of stack that grows as needed), so a program can run hundreds of thousands of them; the Go runtime schedules them onto the CPU's cores.

```go
package main

import (
	"fmt"
	"time"
)

func say(word string, times int) {
	for i := 1; i <= times; i++ {
		fmt.Println(word, i)
		time.Sleep(10 * time.Millisecond)
	}
}

func main() {
	go say("goroutine", 3) // runs concurrently
	say("main", 3)         // runs in the main goroutine
	// when main returns, the program ends, even if other goroutines are still running
}
```

The lines interleave differently from run to run: the order of concurrent work is **not deterministic**. And the program ends when `main` returns, killing any goroutines still running, so we need a way to **wait**.

## sync.WaitGroup

A `WaitGroup` counts running goroutines: `Add` before starting, `Done` when one finishes, `Wait` blocks until the count is back to zero. Since Go 1.25, **`wg.Go(f)`** does the `Add` and `Done` for you:

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func fetch(url string) string {
	time.Sleep(50 * time.Millisecond) // pretend to download
	return "content of " + url
}

func main() {
	urls := []string{"a.example", "b.example", "c.example", "d.example"}
	results := make([]string, len(urls)) // one slot per goroutine: no sharing

	start := time.Now()
	var wg sync.WaitGroup
	for i, url := range urls {
		wg.Go(func() { // Go 1.22+: i and url are fresh variables in each iteration
			results[i] = fetch(url)
		})
	}
	wg.Wait()

	for _, r := range results {
		fmt.Println(r)
	}
	fmt.Println("all done in about", time.Since(start).Round(50*time.Millisecond))
}
```

Four 50 ms downloads finish in about 50 ms instead of 200, because they wait **at the same time**. Each goroutine writes only its own slot of `results`, so they never touch the same memory.

The classic form, which you'll see in most existing code:

```
var wg sync.WaitGroup
for _, job := range jobs {
	wg.Add(1)
	go func() {
		defer wg.Done()
		process(job)
	}()
}
wg.Wait()
```

## Concurrency is not parallelism

**Concurrency** is about *structure*: several tasks in progress at once (waiting for the network while handling another request). **Parallelism** is about *execution*: tasks literally running at the same instant on different cores. Go's runtime runs goroutines in parallel on all cores (`runtime.GOMAXPROCS`), but goroutines help even on one core, because most programs spend their time waiting.

## The golden rule

When two goroutines access the same variable and at least one writes, you have a **data race**: the result is unpredictable and can be silently wrong. Either give each goroutine its own data (as above), **communicate through channels** (next lesson), or protect shared data with a **mutex** (lesson 4). Go's motto: *"Don't communicate by sharing memory; share memory by communicating."*

=== lesson go-channels | Channels | 80
## Typed pipes between goroutines

A **channel** sends values from one goroutine to another, safely. `make(chan int)` creates one; `ch <- v` sends, `v := <-ch` receives. On an **unbuffered** channel a send waits until another goroutine receives, so the two meet: the channel both passes the data and **synchronises** them.

```go
package main

import "fmt"

func sum(nums []int, out chan<- int) { // chan<- : this function may only send
	total := 0
	for _, n := range nums {
		total += n
	}
	out <- total
}

func main() {
	nums := []int{7, 2, 8, -9, 4, 0}
	results := make(chan int)
	go sum(nums[:len(nums)/2], results)
	go sum(nums[len(nums)/2:], results)
	a, b := <-results, <-results // wait for both
	fmt.Println(a, b, a+b)
}
```

Direction types document intent and are checked by the compiler: `chan<- int` can only send, `<-chan int` can only receive.

## Buffered channels, close and range

A **buffered** channel (`make(chan T, n)`) holds up to `n` values: sends block only when it's full, receives only when it's empty. The sender **closes** the channel when there's nothing more to send; the receiver's `for v := range ch` loop then ends:

```go
package main

import "fmt"

func generate(n int) <-chan int {
	out := make(chan int, 3)
	go func() {
		defer close(out) // tell receivers there's nothing more
		for i := 1; i <= n; i++ {
			out <- i
		}
	}()
	return out
}

func main() {
	for v := range generate(5) {
		fmt.Print(v, " ")
	}
	fmt.Println()

	ch := make(chan string, 2)
	ch <- "a"
	ch <- "b"
	close(ch)
	fmt.Println(len(ch), cap(ch))
	v, ok := <-ch
	fmt.Println(v, ok)
	<-ch
	v, ok = <-ch // closed and empty: zero value and false
	fmt.Printf("%q %v\n", v, ok)
}
```

Rules worth memorising: only the **sender** closes; sending on a closed channel **panics**; receiving from a closed channel returns the zero value immediately (with `ok == false`); a `nil` channel blocks forever.

## Pipelines

Channels connect stages, each in its own goroutine, like an assembly line. Each stage receives from the previous one and sends to the next:

```go
package main

import (
	"fmt"
	"strings"
)

func words(text string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for _, w := range strings.Fields(text) {
			out <- w
		}
	}()
	return out
}

func upper(in <-chan string) <-chan string {
	out := make(chan string)
	go func() {
		defer close(out)
		for w := range in {
			out <- strings.ToUpper(w)
		}
	}()
	return out
}

func main() {
	for w := range upper(words("share memory by communicating")) {
		fmt.Println(w)
	}
}
```

## Worker pools: fan-out, fan-in

To process many jobs with a fixed number of goroutines, start **N workers** that all receive from one jobs channel (*fan-out*), and send their results to one results channel (*fan-in*). Closing the results channel after all workers finish (WaitGroup) ends the final loop:

```go
package main

import (
	"fmt"
	"slices"
	"sync"
)

type result struct{ n, square int }

func main() {
	jobs := make(chan int)
	results := make(chan result)

	var wg sync.WaitGroup
	for range 3 { // 3 workers
		wg.Go(func() {
			for n := range jobs {
				results <- result{n, n * n}
			}
		})
	}

	go func() { // feed the jobs, then close
		for n := 1; n <= 6; n++ {
			jobs <- n
		}
		close(jobs)
	}()

	go func() { // close results once every worker is done
		wg.Wait()
		close(results)
	}()

	var got []result
	for r := range results {
		got = append(got, r)
	}
	slices.SortFunc(got, func(a, b result) int { return a.n - b.n }) // workers finish in any order
	fmt.Println(got)
}
```

~~~check
? Who should close a channel?
+ The sender, when it has nothing more to send
- The receiver, when it has read enough
- Nobody: channels close themselves
- Any goroutine, at any time
> Sending on a closed channel panics.
~~~

=== lesson go-select | select, timeouts and tickers | 70
## Waiting on several channels

**`select`** waits until one of several channel operations can proceed, then runs that case (if several are ready, it picks one at random). It's how Go programs handle timeouts, cancellation and multiple event sources:

```go
package main

import (
	"fmt"
	"time"
)

func fetch(name string, delay time.Duration) <-chan string {
	ch := make(chan string, 1) // buffered: the goroutine can finish even if nobody receives
	go func() {
		time.Sleep(delay)
		ch <- name + " answered"
	}()
	return ch
}

func main() {
	// take the fastest of two replicas
	select {
	case r := <-fetch("server A", 80*time.Millisecond):
		fmt.Println(r)
	case r := <-fetch("server B", 30*time.Millisecond):
		fmt.Println(r)
	}

	// a timeout
	select {
	case r := <-fetch("slow server", 300*time.Millisecond):
		fmt.Println(r)
	case <-time.After(100 * time.Millisecond):
		fmt.Println("timed out after 100ms")
	}
}
```

Note the **buffer of 1** in `fetch`: when the timeout wins, nobody ever receives from that channel. With an unbuffered channel the goroutine would block forever on its send: a **goroutine leak**, a slow memory leak in long-running servers.

## Non-blocking operations with default

A `select` with a **`default`** case never waits: if no channel is ready, `default` runs. It's useful to try a send or receive, or to drop events when a buffer is full:

```go
package main

import "fmt"

func main() {
	events := make(chan string, 2)
	for _, e := range []string{"click", "scroll", "resize", "key"} {
		select {
		case events <- e:
			fmt.Println("queued", e)
		default:
			fmt.Println("dropped", e, "(queue full)")
		}
	}
	close(events)
	for e := range events {
		fmt.Println("handled", e)
	}
}
```

## Tickers and loops with select

A **`time.Ticker`** sends the time at regular intervals. A `for`-`select` loop that handles ticks, work and a quit signal is the skeleton of many background services:

```go
package main

import (
	"fmt"
	"time"
)

func main() {
	ticker := time.NewTicker(40 * time.Millisecond)
	defer ticker.Stop()
	done := make(chan struct{}) // struct{} carries no data: a pure signal
	go func() {
		time.Sleep(150 * time.Millisecond)
		close(done) // closing wakes every receiver at once
	}()

	ticks := 0
	for {
		select {
		case <-ticker.C:
			ticks++
			fmt.Println("tick", ticks)
		case <-done:
			fmt.Println("stopping after", ticks, "ticks")
			return
		}
	}
}
```

Closing a channel is a **broadcast**: every goroutine waiting on `<-done` wakes up. That's why `done` channels (and contexts, next-but-one lesson) are closed rather than sent to.

	"fmt"
	"sync/atomic"
	"time"

	Name  string
	Delay time.Duration
}

	time.Sleep(s.Delay)
	completed.Add(1)
	return s.Name
}

func firstResponse(servers []Server, timeout time.Duration) (string, error) {
	answers := make(chan string, len(servers))
	for _, s := range servers {
		go func() { answers <- s.Query() }()
	}
	select {
	case name := <-answers:
		return name, nil
	case <-time.After(timeout):

=== lesson go-sync | Mutexes, atomics and the race detector | 75
## Protecting shared state

Channels are great for passing data along, but sometimes goroutines must share one piece of state: a cache, a counter, a bank balance. A **`sync.Mutex`** (mutual exclusion lock) lets only one goroutine at a time run the code between `Lock` and `Unlock`:

```go
package main

import (
	"fmt"
	"sync"
)

type Counter struct {
	mu     sync.Mutex
	counts map[string]int
}

func (c *Counter) Inc(key string) {
	c.mu.Lock()
	defer c.mu.Unlock() // unlocks even if the code below panics
	c.counts[key]++
}

func (c *Counter) Get(key string) int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.counts[key]
}

func main() {
	c := Counter{counts: map[string]int{}}
	var wg sync.WaitGroup
	for i := range 1000 {
		wg.Go(func() {
			if i%2 == 0 {
				c.Inc("even")
			} else {
				c.Inc("odd")
			}
		})
	}
	wg.Wait()
	fmt.Println(c.Get("even"), c.Get("odd"))
}
```

Without the mutex, this program would crash with **`fatal error: concurrent map writes`**, or silently lose updates for plain variables. Conventions: put the mutex next to the fields it protects, use **pointer receivers** (a copied mutex protects nothing; `go vet` reports copies), keep critical sections short, and never call slow or blocking code while holding a lock.

## RWMutex and Once

- **`sync.RWMutex`** allows many readers at once (`RLock`/`RUnlock`) or one writer (`Lock`): good for caches that are read far more often than written.
- **`sync.Once`** runs a function exactly once, however many goroutines call it: lazy initialisation of a configuration or connection. `sync.OnceValue(f)` returns a function that computes and caches the value.

```go
package main

import (
	"fmt"
	"sync"
)

type Cache struct {
	mu   sync.RWMutex
	data map[string]string
}

func (c *Cache) Get(k string) (string, bool) {
	c.mu.RLock()
	defer c.mu.RUnlock()
	v, ok := c.data[k]
	return v, ok
}

func (c *Cache) Set(k, v string) {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.data[k] = v
}

var loadConfig = sync.OnceValue(func() map[string]string {
	fmt.Println("loading config (once)")
	return map[string]string{"env": "prod"}
})

func main() {
	c := &Cache{data: map[string]string{}}
	c.Set("lang", "go")
	var wg sync.WaitGroup
	for range 5 {
		wg.Go(func() {
			if v, ok := c.Get("lang"); ok && loadConfig()["env"] == "prod" {
				_ = v
			}
		})
	}
	wg.Wait()
	fmt.Println(loadConfig()["env"])
}
```

## Atomics

For a single number or pointer, **`sync/atomic`** types (`atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`) update it without a lock, using special CPU instructions:

```go
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	var requests atomic.Int64
	var plain int64
	var wg sync.WaitGroup
	for range 100 {
		wg.Go(func() {
			for range 1000 {
				requests.Add(1)
				plain++ // a data race: updates get lost
			}
		})
	}
	wg.Wait()
	fmt.Println("atomic:", requests.Load())
	fmt.Println("plain (usually less than 100000):", plain)
}
```

## The race detector

Go ships a **race detector**: run or test with **`-race`** (`go test -race ./...`, `go run -race .`) and it reports every data race it observes, with the stack traces of both accesses. It needs cgo (on Windows, a C compiler such as MinGW), slows the program down, and only finds races that actually happen during the run, so run your tests with it regularly in CI. The plain counter above would be reported immediately.

## Choosing a tool

| Situation | Tool |
|---|---|
| passing data or ownership between goroutines, pipelines | channels |
| several goroutines updating one structure (map, cache, account) | `sync.Mutex` / `RWMutex` |
| a counter or flag | `sync/atomic` |
| one-time initialisation | `sync.Once`, `sync.OnceValue` |
| waiting for a group of goroutines | `sync.WaitGroup` |

## Stopping work nobody needs any more

A web request is cancelled when the user closes the page; a job must stop when its deadline passes; a server shutting down must stop all its goroutines. Go's standard way to carry **cancellation signals, deadlines and request-scoped values** across function calls and goroutines is **`context.Context`**:

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

// slowSum checks ctx between steps and stops early when it's cancelled
func slowSum(ctx context.Context, n int) (int, error) {
	total := 0
	for i := 1; i <= n; i++ {
		select {
		case <-ctx.Done(): // closed when the context is cancelled or times out
			return total, ctx.Err()
		case <-time.After(20 * time.Millisecond): // one step of work
			total += i
		}
	}
	return total, nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 110*time.Millisecond)
	defer cancel() // always release the context's resources

	total, err := slowSum(ctx, 10)
	fmt.Println(total, err, errors.Is(err, context.DeadlineExceeded))

	total, err = slowSum(context.Background(), 3) // a context that's never cancelled
	fmt.Println(total, err)
}
```

## The rules

- A function that does I/O or may run for long takes **`ctx context.Context` as its first parameter**, and passes it on to everything it calls (`http.NewRequestWithContext`, database queries, other services).
- Contexts form a **tree**: `WithCancel`, `WithTimeout`, `WithDeadline` and `WithValue` derive a child from a parent. Cancelling a parent cancels all its children.
- Every `With...` returns a **`cancel` function**: call it (usually `defer cancel()`) when the work is done, or resources leak.
- **`ctx.Done()`** is a channel that's closed on cancellation; **`ctx.Err()`** then says why: `context.Canceled` or `context.DeadlineExceeded`.
- Use `context.Background()` at the top (in `main`, in tests); `context.TODO()` marks a place where a real context should be passed later.
- **`WithValue`** carries request-scoped data such as a request ID or the authenticated user, never optional function parameters.

## Cancelling a group of goroutines

When one worker fails, the others should stop. A shared context makes that easy:

```go
package main

import (
	"context"
	"errors"
	"fmt"
	"sync"
	"time"
)

func worker(ctx context.Context, id int, results chan<- string) error {
	for step := 1; ; step++ {
		select {
		case <-ctx.Done():
			results <- fmt.Sprintf("worker %d stopped at step %d", id, step)
			return ctx.Err()
		case <-time.After(30 * time.Millisecond):
			if id == 2 && step == 3 {
				return errors.New("worker 2: disk full")
			}
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()
	results := make(chan string, 3)
	var once sync.Once
	var firstErr error
	var wg sync.WaitGroup
	for id := 1; id <= 3; id++ {
		wg.Go(func() {
			if err := worker(ctx, id, results); err != nil && !errors.Is(err, context.Canceled) {
				once.Do(func() { firstErr = err })
				cancel() // stop everyone else
			}
		})
	}
	wg.Wait()
	close(results)
	fmt.Println("first error:", firstErr)
	stopped := 0
	for range results { // workers 1 and 3 report where they stopped
		stopped++
	}
	fmt.Println("workers stopped early:", stopped)
}
```

This "run a group, stop at the first error" pattern is so common that the `golang.org/x/sync/errgroup` package implements it: `g, ctx := errgroup.WithContext(ctx)`, `g.Go(func() error {...})`, `err := g.Wait()`.

	return Output{base + "_small." + ext, 320, j.Height * 320 / j.Width}, nil
}

func process(ctx context.Context, jobs []Job, workers int) ([]Output, error) {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	type indexed struct {
		i   int
		job Job
	}
	queue := make(chan indexed)
	go func() {
		defer close(queue)
		for i, j := range jobs {
			select {
			case queue <- indexed{i, j}:
			case <-ctx.Done():
				return
			}
		}
	}()

	outputs := make([]Output, len(jobs))
	completed := make([]bool, len(jobs))
	var mu sync.Mutex
	var firstErr error
	var wg sync.WaitGroup
	for range workers {
		wg.Go(func() {
			for item := range queue {
				out, err := resize(ctx, item.job)
				mu.Lock()
				if err != nil {
					if firstErr == nil && !errors.Is(err, context.Canceled) {
						firstErr = err
						cancel()
					}
				} else {
					outputs[item.i] = out
					completed[item.i] = true
				}
				mu.Unlock()
			}
		})
	}
	wg.Wait()

	var done []Output
	for i, ok := range completed {
		if ok {
			done = append(done, outputs[i])
		}
	}
	return done, firstErr
}

func main() {
	batch := []Job{{"1.jpg", 1920, 1280}, {"2.jpg", 1920, 1080}, {"3.png", 800, 800}, {"4.jpg", 1600, 1200}, {"5.png", 900, 1200}, {"6.jpg", 1280, 800}}
	out, err := process(context.Background(), batch, 3)
	fmt.Printf("batch 1: %d resized, err: %v\n", len(out), err)
	for i, o := range out {
		fmt.Printf("  %s -> %s (%dx%d)\n", batch[i].Name, o.Name, o.Width, o.Height)
	}

	var bad []Job
	for i := range 30 {
		bad = append(bad, Job{fmt.Sprintf("%d.jpg", i), 100, 100})
	}
	bad[2] = Job{"bad.jpg", 100, 100}
	out, err = process(context.Background(), bad, 2)
	fmt.Println("batch 2 error:", err)
	fmt.Println("batch 2 stopped early:", len(out) < 10)
}

::hints
- Send `(index, job)` pairs through the channel so each worker knows where its output goes.
- The feeder's `select` between `queue <- item` and `<-ctx.Done()` lets it stop when work is cancelled.
- Record the first non-cancellation error under the mutex, then call `cancel()`: the other `resize` calls return `context.Canceled`, which you ignore.
