=== lesson pg-intro | PostgreSQL, tables & types | 55
**PostgreSQL** ("Postgres") is a free, open-source relational database known for correctness, rich SQL and extensibility. It powers everything from startups to banks. The database you type into here is **real PostgreSQL**, compiled to WebAssembly and running inside DevQuest.

You usually talk to Postgres with the **`psql`** terminal client (or a GUI). Handy `psql` commands: `\l` (databases), `\dt` (tables), `\d tablename` (columns and indexes), `\x` (expanded output), `\q` (quit).

**Creating a table** with sensible types:

```sql
CREATE TABLE members (
  id     integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,  -- auto-numbered
  name   text NOT NULL,
  email  text NOT NULL UNIQUE,
  level  integer NOT NULL DEFAULT 1,
  joined timestamptz NOT NULL DEFAULT now()
);
```

| Need | Postgres type |
|---|---|
| whole numbers | `integer`, `bigint` |
| money, exact decimals | `numeric(10,2)` (never `float` for money) |
| text | `text` (no length limit needed) |
| true/false | `boolean` |
| dates and times | `date`, `timestamptz` (time zone aware) |
| ids from other systems | `uuid` |
| flexible documents | `jsonb` |

**`RETURNING`** gives you back the rows you just wrote, which is perfect for getting generated ids:

```sql
INSERT INTO members (name, email) VALUES ('Ada', 'ada@x.dev') RETURNING id, joined;
```

=== lesson pg-select | Filtering, sorting & CASE | 50
A `SELECT` reads in this logical order: **FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT**. That's why you can't use a SELECT alias inside WHERE, but you can in ORDER BY.

```sql
SELECT name, price
FROM products
WHERE category = 'tech' AND price BETWEEN 20 AND 300
ORDER BY price DESC
LIMIT 3;
```

**Postgres goodies:**
- `ILIKE` is case-insensitive `LIKE`: `name ILIKE 'key%'`.
- `IS NULL` / `IS NOT NULL` (never `= NULL`), and `COALESCE(email, '(none)')` to replace NULLs.
- `CASE` builds a value from conditions:

```sql
SELECT name,
       CASE WHEN price < 50  THEN 'budget'
            WHEN price < 500 THEN 'mid'
            ELSE 'premium' END AS band
FROM products;
```

- `DISTINCT ON (category)` keeps the first row per group (with ORDER BY), which is great for "the cheapest product per category".

Tables today: `products(id, name, category, price)`, `customers(id, name, city, email)`, `orders(id, customer_id, ordered_on, status)`, `order_items(order_id, product_id, qty)`.

=== lesson pg-joins | Joins & aggregation | 60
Joins combine rows from tables that share a key:

| Join | Keeps |
|---|---|
| `INNER JOIN` | only rows with a match on both sides |
| `LEFT JOIN` | every row of the left table; NULLs where the right has no match |
| `FULL JOIN` | everything from both sides |
| `CROSS JOIN` | every combination (rarely what you want) |

```sql
SELECT c.name, o.id AS order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;   -- customers without orders still appear
```

**Aggregating** collapses rows into groups: `count`, `sum`, `avg`, `min`, `max`, `string_agg`, `array_agg`. Every selected column must be grouped or aggregated. Filter groups with **`HAVING`** (WHERE filters rows *before* grouping).

**Classic traps:**
- A condition on the right table in `WHERE` turns a LEFT JOIN back into an INNER JOIN. Put it in the `ON` clause instead.
- Joining two one-to-many tables multiplies rows, so counts and sums inflate. Use `count(DISTINCT …)` or aggregate in a subquery first.
- `sum()` of no rows is NULL: wrap it in `COALESCE(sum(...), 0)`.

=== lesson pg-cte | CTEs, subqueries & recursion | 65
A **CTE** (Common Table Expression) names a subquery with `WITH`, so complex queries read top-to-bottom:

```sql
WITH big_orders AS (
  SELECT order_id, sum(qty) AS units FROM order_items GROUP BY order_id HAVING sum(qty) > 2
)
SELECT o.id, o.status, b.units
FROM orders o JOIN big_orders b ON b.order_id = o.id;
```

Subqueries work too: in `WHERE x IN (SELECT …)`, `WHERE EXISTS (SELECT …)` or as a column.

**Recursive CTEs** walk hierarchies such as org charts, category trees and dependency graphs. They have an *anchor* (where to start) and a *recursive part* (how to take one step), joined by `UNION ALL`:

```sql
WITH RECURSIVE chain AS (
  SELECT id, name, 0 AS depth FROM employees WHERE manager_id IS NULL      -- anchor
  UNION ALL
  SELECT e.id, e.name, c.depth + 1 FROM employees e JOIN chain c ON e.manager_id = c.id   -- step
)
SELECT * FROM chain;
```

The recursion stops when a step returns no new rows. A cycle in the data (A manages B manages A) would loop forever, so add a depth limit or track visited ids when data can contain cycles.

=== lesson pg-window | Window functions | 70
**Window functions** compute across related rows *without* collapsing them like GROUP BY does. The `OVER (...)` clause defines the window:

```sql
SELECT name, category, price,
       rank()      OVER (PARTITION BY category ORDER BY price DESC) AS rank_in_category,
       avg(price)  OVER (PARTITION BY category)                      AS category_avg,
       price - lag(price) OVER (ORDER BY price)                      AS gap_to_cheaper
FROM products;
```

| Function | Gives |
|---|---|
| `row_number()`, `rank()`, `dense_rank()` | position in the window (ties differ) |
| `lag(x)`, `lead(x)` | the value from the previous / next row |
| `sum(x) OVER (ORDER BY …)` | a **running total** |
| `first_value`, `last_value`, `ntile(n)` | edges and buckets |

`PARTITION BY` restarts the window per group, and `ORDER BY` inside `OVER` defines the order (and turns aggregates into running ones). Window functions run after WHERE and GROUP BY, so to filter by them ("top 3 per category"), wrap the query in a CTE and filter outside.

=== lesson pg-jsonb | JSONB: documents inside Postgres | 60
Postgres can store **JSON documents** in a `jsonb` column (binary, indexable), so you get relational tables *and* flexible documents in one database.

```sql
CREATE TABLE events (id serial PRIMARY KEY, user_id int, kind text, payload jsonb);
INSERT INTO events (user_id, kind, payload)
VALUES (1, 'purchase', '{"device": "mobile", "amount": 30, "items": ["book"]}');
```

| Operator | Meaning | Example |
|---|---|---|
| `->` | get a field as jsonb | `payload -> 'items'` |
| `->>` | get a field as **text** | `payload ->> 'device'` |
| `#>>` | path as text | `payload #>> '{address,city}'` |
| `@>` | **contains** | `payload @> '{"device": "mobile"}'` |
| `?` | has key | `payload ? 'coupon'` |

Text needs a cast for maths: `(payload ->> 'amount')::numeric`. Useful functions: `jsonb_array_length`, `jsonb_array_elements`, `jsonb_build_object`, `jsonb_agg` (rows → JSON array) and `jsonb_set`.

A **GIN index** makes `@>` and `?` fast: `CREATE INDEX ON events USING gin (payload);`

**Rule of thumb:** put fields you filter, join or constrain often in real columns, and keep truly variable attributes in `jsonb`.

=== lesson pg-integrity | Constraints, upserts & transactions | 65
Let the database protect your data: rules in the schema hold for **every** app and script that writes to it.

```sql
CREATE TABLE accounts (
  id      int PRIMARY KEY,
  owner   int NOT NULL REFERENCES users(id) ON DELETE CASCADE,   -- foreign key
  balance numeric(12,2) NOT NULL CHECK (balance >= 0),            -- business rule
  iban    text UNIQUE
);
```

**Upsert:** insert, or update if the key already exists, in one atomic statement:

```sql
INSERT INTO inventory (sku, qty) VALUES ('KB-1', 2)
ON CONFLICT (sku) DO UPDATE SET qty = inventory.qty + EXCLUDED.qty;   -- EXCLUDED = the row you tried to insert
```

**Transactions** make several statements all-or-nothing (**ACID**: Atomicity, Consistency, Isolation, Durability):

```sql
BEGIN;
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
UPDATE accounts SET balance = balance + 50 WHERE id = 2;
COMMIT;      -- or ROLLBACK; to undo both
```

If any statement fails (for example the CHECK rejects a negative balance), the transaction is aborted and nothing is applied. **Isolation levels** (`READ COMMITTED` by default, `REPEATABLE READ`, `SERIALIZABLE`) decide what concurrent transactions can see of each other.

=== lesson pg-indexes | Indexes & EXPLAIN | 65
An **index** lets Postgres find rows without reading the whole table. The default is a **B-tree**, which is good for `=`, ranges, `ORDER BY` and prefix `LIKE 'abc%'`.

```sql
CREATE INDEX orders_customer_idx ON orders (customer_id);                 -- foreign keys are NOT indexed automatically
CREATE INDEX users_email_lower_idx ON users (lower(email));               -- expression index for WHERE lower(email) = …
CREATE INDEX orders_pending_idx ON orders (ordered_on) WHERE status = 'pending';   -- partial index: small and fast
CREATE UNIQUE INDEX ON users (lower(email));                              -- case-insensitive uniqueness
```

Other index types: **GIN** (jsonb, arrays, full-text search), **GiST** (geometry, ranges), **BRIN** (huge, naturally ordered tables such as logs).

**Reading plans.** `EXPLAIN` shows the plan; `EXPLAIN ANALYZE` also runs the query and reports real timings:

```
Index Scan using orders_customer_idx on orders  (cost=0.15..8.17 rows=1 width=44)
  Index Cond: (customer_id = 42)
```

Look for **Seq Scan** on big tables in hot queries, row estimates far from reality (run `ANALYZE`), and nested loops over many rows.

Indexes cost disk space and slow down writes, so add them for real query patterns, and drop unused ones (`pg_stat_user_indexes` shows usage).

=== lesson pg-internals | How PostgreSQL works inside | 55
Knowing the engine helps you design and debug.

**MVCC (multi-version concurrency control).** An UPDATE doesn't overwrite a row: it writes a *new version* and marks the old one dead. Each transaction sees a consistent **snapshot**, so readers never block writers and writers never block readers.

**VACUUM** later reclaims dead row versions. **Autovacuum** does it in the background. A table updated very heavily without vacuuming **bloats**, and very long-running transactions keep old versions alive.

**WAL (write-ahead log).** Every change is first appended to the WAL and flushed to disk at COMMIT, so after a crash Postgres replays the WAL. The same log drives **replication** (streaming WAL to standby servers) and **point-in-time recovery**.

**Connections are processes.** Each connection is a separate OS process using real memory, so apps use a **connection pool** (in the app, or PgBouncer) instead of opening hundreds of connections.

**Isolation levels:**
- `READ COMMITTED` (default): each statement sees data committed before it started.
- `REPEATABLE READ`: the whole transaction sees one snapshot.
- `SERIALIZABLE`: transactions behave as if run one at a time, and conflicts make one of them retry.

**Production checklist:** backups you have *test-restored*, monitoring of slow queries (`pg_stat_statements`), migrations in version control, least-privilege roles, and connection pooling.
