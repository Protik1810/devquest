## Naming the steps of a query

Long queries with nested subqueries are hard to read from the inside out. A **common table expression** (CTE) names a subquery up front with **`WITH`**, so the query reads top to bottom, like a program:

```sql shop
WITH customer_totals AS (
  SELECT o.customer_id, sum(oi.quantity * oi.unit_price) AS spent
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status <> 'cancelled'
  GROUP BY o.customer_id
),
average AS (
  SELECT avg(spent) AS avg_spent FROM customer_totals
)
SELECT c.name, round(t.spent, 2) AS spent
FROM customer_totals t
JOIN customers c ON c.id = t.customer_id
CROSS JOIN average a
WHERE t.spent > a.avg_spent
ORDER BY t.spent DESC;
```

Each CTE is like a temporary, named view that exists only for this statement. Later CTEs can use earlier ones (`average` uses `customer_totals`), and the main query can use any of them, as often as it likes.

CTEs don't make queries faster or slower by themselves: since PostgreSQL 12, the planner usually folds them into the main query like subqueries. Use them for **readability**: a complex report written as a sequence of named steps is far easier to check, change and review.

## CTEs with data changes

A CTE can contain `INSERT`, `UPDATE` or `DELETE ... RETURNING`, which lets one statement move data:

```sql shop
WITH removed AS (
  DELETE FROM reviews WHERE rating <= 2 RETURNING *
)
SELECT count(*) AS removed_reviews, string_agg(comment, '; ') AS comments FROM removed;
```

## Recursive CTEs: walking hierarchies

Some questions need an unknown number of steps: "everyone who reports to the CTO, directly or indirectly", "all subcategories of Electronics", "every stop on a route". **`WITH RECURSIVE`** handles them. A recursive CTE has two parts joined by `UNION ALL`:

1. the **anchor**: the starting rows;
2. the **recursive part**: a query that refers to the CTE itself, producing the next level from the previous one.

PostgreSQL runs the anchor, then repeats the recursive part on the rows found in the previous round, until a round finds nothing.

```sql company
WITH RECURSIVE reports AS (
  SELECT id, name, title, manager_id, 1 AS depth
  FROM employees
  WHERE name = 'Omar Haddad'                     -- anchor: the CTO

  UNION ALL

  SELECT e.id, e.name, e.title, e.manager_id, r.depth + 1
  FROM employees e
  JOIN reports r ON e.manager_id = r.id          -- recursive step: their direct reports
)
SELECT repeat('  ', depth - 1) || name AS person, title, depth
FROM reports
ORDER BY depth, name;
```

The same pattern walks up a tree (from a category to its ancestors), builds paths, or explores graphs:

```sql shop
WITH RECURSIVE tree AS (
  SELECT id, name, parent_id, name AS path
  FROM categories
  WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, c.name, c.parent_id, t.path || ' > ' || c.name
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
)
SELECT path FROM tree ORDER BY path;
```

Recursive CTEs can also **generate** data (here, the numbers 1 to 10, though `generate_series` is simpler for that):

```sql empty
WITH RECURSIVE n AS (
  SELECT 1 AS i
  UNION ALL
  SELECT i + 1 FROM n WHERE i < 10
)
SELECT string_agg(i::text, ' ') FROM n;
```

The `WHERE i < 10` stops the recursion. Without a stopping condition (or with a cycle in the data, like an employee who is their own manager's manager), a recursive query runs forever; DevQuest stops it after a while. PostgreSQL 14 added a `CYCLE` clause that detects cycles for you, and you can always add a depth limit (`WHERE depth < 20`).

=== lesson sql-window | Window functions | 90
## Aggregates without collapsing rows

`GROUP BY` collapses each group into one row. Often you want to keep every row **and** see a group-level value next to it: each order with its customer's total, each product with its rank in its category, each day with a running total. That's what **window functions** do:

```sql shop
SELECT name, category_id, price,
       round(avg(price) OVER (PARTITION BY category_id), 2) AS category_average,
       count(*) OVER (PARTITION BY category_id) AS products_in_category
FROM products
ORDER BY category_id, price;
```

`OVER (...)` turns an aggregate into a window function. **`PARTITION BY`** divides the rows into groups (here, categories), and the function is computed over each row's group, but every row stays in the result. `OVER ()` with nothing inside uses all rows:

```sql shop
SELECT name, price,
       round(100 * price / sum(price) OVER (), 1) AS percent_of_catalogue_value
FROM products
ORDER BY price DESC
LIMIT 5;
```

Window functions run **after** `WHERE`, `GROUP BY` and `HAVING`, at the `SELECT` step, so they see the filtered (and grouped) rows, and you can't use them in `WHERE`. To filter on one, use a subquery or CTE.

## Ranking

Ranking functions number rows in an order given by `ORDER BY` inside `OVER`:

```sql shop
SELECT name, category_id, price,
       row_number() OVER (PARTITION BY category_id ORDER BY price DESC) AS row_num,
       rank()       OVER (PARTITION BY category_id ORDER BY price DESC) AS rank,
       dense_rank() OVER (ORDER BY price DESC) AS price_rank_overall
FROM products
ORDER BY category_id, price DESC;
```

| Function | Ties | Example for prices 50, 40, 40, 30 |
|---|---|---|
| `row_number()` | numbered arbitrarily | 1, 2, 3, 4 |
| `rank()` | share a rank, then skip | 1, 2, 2, 4 |
| `dense_rank()` | share a rank, no gaps | 1, 2, 2, 3 |
| `ntile(n)` | split into n buckets | quartiles, percentiles |

The classic use is **top N per group**: the most expensive product in each category.

```sql shop
WITH ranked AS (
  SELECT name, category_id, price,
         row_number() OVER (PARTITION BY category_id ORDER BY price DESC, id) AS rn
  FROM products
)
SELECT category_id, name, price
FROM ranked
WHERE rn = 1
ORDER BY category_id;
```

## Running totals and moving windows

With `ORDER BY` inside `OVER`, an aggregate becomes **cumulative**: each row sees the rows from the start of its partition up to itself.

```sql shop
SELECT id, ordered_at::date AS day, shipping,
       sum(shipping) OVER (ORDER BY ordered_at) AS shipping_to_date,
       count(*) OVER (PARTITION BY customer_id ORDER BY ordered_at) AS customer_order_number
FROM orders
ORDER BY ordered_at;
```

The rows a window function sees are its **frame**, which you can set explicitly: `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` gives a three-row **moving average**:

```sql shop
WITH daily AS (
  SELECT date_trunc('month', o.ordered_at)::date AS month, sum(oi.quantity * oi.unit_price) AS revenue
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  GROUP BY 1
)
SELECT month, revenue,
       round(avg(revenue) OVER (ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_avg_3_months
FROM daily
ORDER BY month;
```

## Looking at neighbouring rows: LAG and LEAD

`lag(x)` returns the value of `x` in the **previous** row of the window, `lead(x)` in the next one: perfect for changes over time.

```sql shop
SELECT customer_id, id AS order_id, ordered_at::date AS day,
       ordered_at::date - lag(ordered_at::date) OVER (PARTITION BY customer_id ORDER BY ordered_at) AS days_since_previous
FROM orders
WHERE customer_id IN (1, 2, 3)
ORDER BY customer_id, ordered_at;
```

`first_value(x)`, `last_value(x)` and `nth_value(x, n)` read other positions of the frame.

## Named windows

When several functions share a window, name it once with `WINDOW`:

```sql shop
SELECT name, price,
       rank() OVER w AS rank,
       round(price - avg(price) OVER w, 2) AS diff_from_average
FROM products
WINDOW w AS (PARTITION BY category_id ORDER BY price DESC)
ORDER BY category_id, rank;
```

(Careful: with `ORDER BY` in the window, `avg` is cumulative, so `diff_from_average` here compares with the average **so far** in the ranking. Use a window without `ORDER BY` for the whole category's average.)

## Saving a query as a view

A **view** is a stored query with a name. You query it like a table, but it holds no data of its own: every time you use it, its query runs.

```sql shop
CREATE VIEW order_summaries AS
SELECT o.id, c.name AS customer, o.status, o.ordered_at,
       sum(oi.quantity * oi.unit_price) AS goods,
       o.shipping
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, c.name;

SELECT customer, count(*) AS orders, sum(goods + shipping) AS total
FROM order_summaries
WHERE status <> 'cancelled'
GROUP BY customer
ORDER BY total DESC
LIMIT 5;
```

Views are useful for:

- **simplifying**: complex joins written once, reused everywhere (a reporting team's favourite);
- **stable interfaces**: applications query the view, and you can change the tables underneath (renaming, splitting) while keeping the view the same;
- **security**: give a user access to a view showing only some columns or rows, but not to the table (Module 7).

`CREATE OR REPLACE VIEW` updates a view's query (it may add columns at the end, not remove them); `DROP VIEW` removes it.

## Updatable views

A **simple** view (one table, no aggregates, no `DISTINCT`) can be updated: `INSERT`, `UPDATE` and `DELETE` on it change the underlying table. `WITH CHECK OPTION` stops changes that would make a row fall outside the view:

```sql shop
CREATE VIEW uk_customers AS
SELECT id, name, email, city, country, joined_on FROM customers WHERE country = 'UK'
WITH CHECK OPTION;

UPDATE uk_customers SET city = 'Cambridge' WHERE name = 'Alan Turing';
SELECT name, city FROM customers WHERE id = 3;
```

```sql shop
-- error: WITH CHECK OPTION rejects a row that would leave the view
CREATE VIEW uk_customers AS SELECT * FROM customers WHERE country = 'UK' WITH CHECK OPTION;
UPDATE uk_customers SET country = 'FR' WHERE id = 3;
```

More complex views can be made writable with `INSTEAD OF` triggers (Module 7).

## Materialized views: stored results

A **materialized view** runs its query once and **stores the result**, like a table. Reading it is instant, but the data is a snapshot: it only changes when you refresh it.

```sql shop
CREATE MATERIALIZED VIEW product_stats AS
SELECT p.id, p.name, count(r.id) AS reviews, round(avg(r.rating), 2) AS rating
FROM products p
LEFT JOIN reviews r ON r.product_id = p.id
GROUP BY p.id, p.name;

INSERT INTO reviews (id, product_id, customer_id, rating, created_on) VALUES (13, 6, 2, 1, '2026-03-01');
SELECT * FROM product_stats WHERE id = 6;     -- still the old numbers

REFRESH MATERIALIZED VIEW product_stats;
SELECT * FROM product_stats WHERE id = 6;     -- updated
```

They suit expensive reports and dashboards that can be a few minutes (or a day) out of date, refreshed on a schedule. `REFRESH MATERIALIZED VIEW CONCURRENTLY` (which needs a unique index on the view) refreshes without blocking readers. A materialized view is the database's built-in way to **denormalize** for speed (Module 5). MySQL has no materialized views; SQL Server has "indexed views"; Oracle has them with automatic refresh options.

## Semi-structured data

Some data doesn't fit fixed columns well: product specifications that differ per category (a laptop has a CPU, a book has an author), settings, event payloads from other systems, API responses you want to keep. PostgreSQL's **`jsonb`** type stores JSON documents in a column, in a binary form that's fast to query and can be indexed:

```sql shop
ALTER TABLE products ADD COLUMN specs jsonb NOT NULL DEFAULT '{}';

UPDATE products SET specs = '{"cpu": "M-class 10-core", "ram_gb": 16, "ports": ["usb-c", "hdmi"]}' WHERE id = 1;
UPDATE products SET specs = '{"author": "Thomas and Hunt", "pages": 352, "edition": 2}' WHERE id = 14;
UPDATE products SET specs = '{"wireless": true, "battery_hours": 30}' WHERE id = 5;

SELECT id, name, specs FROM products WHERE specs <> '{}';
```

(`json` also exists: it stores the exact text, including whitespace and duplicate keys. Use `jsonb` unless you need that.)

## Reading values

| Operator | Returns | Example |
|---|---|---|
| `->` | the value as `jsonb` | `specs -> 'ports'` |
| `->>` | the value as `text` | `specs ->> 'cpu'` |
| `#>` / `#>>` | the value at a path | `specs #>> '{ports,0}'` |
| `@>` | does the left document **contain** the right one? | `specs @> '{"wireless": true}'` |
| `?` | does the key exist? | `specs ? 'author'` |

```sql shop
ALTER TABLE products ADD COLUMN specs jsonb NOT NULL DEFAULT '{}';
UPDATE products SET specs = '{"cpu": "M-class 10-core", "ram_gb": 16, "ports": ["usb-c", "hdmi"]}' WHERE id = 1;
UPDATE products SET specs = '{"wireless": true, "battery_hours": 30}' WHERE id = 5;

SELECT name,
       specs ->> 'cpu' AS cpu,
       (specs ->> 'ram_gb')::integer AS ram_gb,
       specs -> 'ports' -> 0 AS first_port,
       specs @> '{"wireless": true}' AS wireless
FROM products
WHERE id IN (1, 5);
```

`->>` returns text: cast it (`::integer`, `::numeric`) to compare numbers properly. A missing key gives `NULL`.

## Building JSON

Queries can **produce** JSON, which is how many APIs get their responses straight from the database:

```sql shop
SELECT json_build_object(
         'customer', c.name,
         'orders', json_agg(json_build_object('id', o.id, 'status', o.status) ORDER BY o.id)
       ) AS document
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.id = 1
GROUP BY c.name;
```

`jsonb_build_object`, `jsonb_agg`, `to_jsonb(row)` and `row_to_json` turn rows into documents; `jsonb_set` and the `||` operator change documents; `jsonb_array_elements` and `jsonb_each` turn a JSON array or object back into rows, and `jsonb_to_recordset` turns an array of objects into a table:

```sql empty
SELECT *
FROM jsonb_to_recordset('[{"sku": "A1", "qty": 2}, {"sku": "B7", "qty": 5}]') AS item(sku text, qty integer);
```

PostgreSQL 16 and 17 also support the standard SQL/JSON functions (`JSON_VALUE`, `JSON_QUERY`, `JSON_TABLE`) and JSON path expressions (`jsonb_path_query(specs, '$.ports[*]')`).

## When to use JSON columns

JSON columns are great for data that is **genuinely variable** or **opaque** to your application (stored and returned as a whole). But don't use them to avoid designing tables: values inside JSON can't have foreign keys, types aren't enforced, and queries get more complicated. A good rule: if you filter, join or aggregate on a value regularly, or it must obey rules, make it a column. Many designs mix both: real columns for the core facts, a `jsonb` column for the extras. A **GIN index** (Module 7) makes `@>` and `?` queries fast on large tables.

## Object-relational features

PostgreSQL describes itself as an **object-relational** database: besides tables of simple values, it lets you define your own types and store structured values. Other databases offer some of these (Oracle has object types, MySQL has `ENUM` and `SET`), but PostgreSQL's set is the richest. They're useful in moderation.

## Arrays

Any type can be an array: `text[]`, `integer[]`.

```sql empty
CREATE TABLE articles (id integer PRIMARY KEY, title text NOT NULL, tags text[] NOT NULL DEFAULT '{}');
INSERT INTO articles VALUES
  (1, 'Window functions explained', '{sql,postgres,analytics}'),
  (2, 'Indexing basics', ARRAY['sql', 'performance']),
  (3, 'Hello, JSON', '{postgres,json}');

SELECT title, tags[1] AS first_tag, cardinality(tags) AS tag_count
FROM articles
WHERE 'postgres' = ANY (tags);
```

- Arrays are written `'{a,b,c}'` or `ARRAY['a', 'b', 'c']`; indexes start at **1**.
- `x = ANY (array)` tests membership; `tags @> '{sql}'` tests containment; `unnest(tags)` turns an array into rows:

```sql empty
CREATE TABLE articles (id integer PRIMARY KEY, tags text[]);
INSERT INTO articles VALUES (1, '{sql,postgres}'), (2, '{sql,performance}'), (3, '{postgres,json}');

SELECT tag, count(*) AS articles
FROM articles, unnest(tags) AS tag
GROUP BY tag
ORDER BY articles DESC, tag;
```

Arrays break first normal form (several values in one cell), so the trade-off is the same as with JSON: fine for simple lists you read as a whole (tags, a few phone numbers), but if the elements need their own data, constraints or foreign keys, use a related table.

## Enums

An **enumerated type** is a fixed, ordered list of values:

```sql empty
CREATE TYPE order_status AS ENUM ('pending', 'paid', 'shipped', 'delivered', 'cancelled');
CREATE TABLE parcels (id integer PRIMARY KEY, status order_status NOT NULL DEFAULT 'pending');
INSERT INTO parcels VALUES (1, 'paid'), (2, 'delivered'), (3, 'pending');

SELECT id, status FROM parcels WHERE status < 'delivered' ORDER BY status;
```

Enums sort in their declared order (so `status < 'delivered'` means "earlier in the workflow"), and reject other values. Adding a value later is easy (`ALTER TYPE order_status ADD VALUE 'returned'`), but removing one isn't, so a `CHECK (status IN (...))` constraint (as the shop uses) or a lookup table is often more flexible.

## Domains

A **domain** is a type with rules attached, defined once and reused in many tables:

```sql empty
CREATE DOMAIN email AS text CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');
CREATE DOMAIN positive_money AS numeric(10, 2) CHECK (VALUE > 0);

CREATE TABLE invoices (id integer PRIMARY KEY, billing_email email NOT NULL, amount positive_money NOT NULL);
INSERT INTO invoices VALUES (1, 'ap@acme.example', 120.00);
SELECT * FROM invoices;
```

```sql empty
-- error: the domain's CHECK rejects an invalid email
CREATE DOMAIN email AS text CHECK (VALUE ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$');
SELECT 'not-an-email'::email;
```

## Composite types and ranges

A **composite type** groups several fields, like a struct:

```sql empty
CREATE TYPE address AS (street text, city text, postcode text);
CREATE TABLE warehouses (id integer PRIMARY KEY, name text, location address);
INSERT INTO warehouses VALUES (1, 'North', ROW('1 Dock Road', 'Leeds', 'LS1 1AA'));
SELECT name, (location).city FROM warehouses;
```

**Range types** (`int4range`, `numrange`, `daterange`, `tstzrange`) represent intervals with operators for overlap (`&&`) and containment (`@>`), which makes bookings and validity periods easy to query, and powers the exclusion constraints mentioned in the constraints lesson:

```sql empty
SELECT daterange('2026-05-01', '2026-05-08') && daterange('2026-05-07', '2026-05-10') AS overlaps,
       daterange('2026-05-01', '2026-05-08') @> date '2026-05-08' AS contains_last_day;
```

(Ranges are half-open by default, `[start, end)`: the 8th isn't included.)

**Customer value report.** Using CTEs and window functions, return one row per customer who has non-cancelled orders: `name`, `spent` (total goods value of their non-cancelled orders), `rank` (rank by `spent`, highest first, ties sharing a rank), `share_percent` (their share of all such spending, rounded to 1 decimal) and `cumulative_percent` (the running total of `share_percent` in rank order, computed from the unrounded shares and then rounded to 1 decimal; ties broken by name). ::dataset shop
::starter
SELECT c.name
FROM customers c;
::solution
WITH spending AS (
  SELECT c.name, sum(oi.quantity * oi.unit_price) AS spent
  FROM customers c
  JOIN orders o ON o.customer_id = c.id
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status <> 'cancelled'
  GROUP BY c.id, c.name
)
SELECT name,
       spent,
       rank() OVER (ORDER BY spent DESC) AS rank,
       round(100 * spent / sum(spent) OVER (), 1) AS share_percent,
       round(100 * sum(spent) OVER (ORDER BY spent DESC, name) / sum(spent) OVER (), 1) AS cumulative_percent
FROM spending
ORDER BY rank, name;
::reference
WITH s AS (SELECT o.customer_id, sum(oi.quantity * oi.unit_price) AS spent FROM orders o JOIN order_items oi ON oi.order_id = o.id WHERE o.status <> 'cancelled' GROUP BY o.customer_id), t AS (SELECT sum(spent) AS total FROM s) SELECT c.name, s.spent, rank() OVER (ORDER BY s.spent DESC) AS rank, round(100 * s.spent / t.total, 1) AS share_percent, round(100 * sum(s.spent) OVER (ORDER BY s.spent DESC, c.name ROWS UNBOUNDED PRECEDING) / t.total, 1) AS cumulative_percent FROM s JOIN customers c ON c.id = s.customer_id CROSS JOIN t ORDER BY 3, 1;
::ordered true

::prompt
For each **project**, return `project` (its name), `team` (a JSON array of the names of the people assigned, most hours first) and `top_contributor` (the name of the person with the most hours on it). Include projects with nobody assigned (with `team` as an empty JSON array `[]` and `top_contributor` NULL). Order by project name.
::dataset company
::starter
SELECT p.name AS project
FROM projects p;
::solution
WITH ranked AS (
  SELECT a.project_id, e.name, a.hours,
         row_number() OVER (PARTITION BY a.project_id ORDER BY a.hours DESC, e.name) AS rn
  FROM assignments a
  JOIN employees e ON e.id = a.employee_id
)
SELECT p.name AS project,
       COALESCE(jsonb_agg(r.name ORDER BY r.hours DESC, r.name) FILTER (WHERE r.name IS NOT NULL), '[]'::jsonb) AS team,
       max(r.name) FILTER (WHERE r.rn = 1) AS top_contributor
FROM projects p
LEFT JOIN ranked r ON r.project_id = p.id
GROUP BY p.id, p.name
ORDER BY project;
::reference
SELECT p.name AS project, COALESCE((SELECT jsonb_agg(e.name ORDER BY a.hours DESC, e.name) FROM assignments a JOIN employees e ON e.id = a.employee_id WHERE a.project_id = p.id), '[]') AS team, (SELECT e.name FROM assignments a JOIN employees e ON e.id = a.employee_id WHERE a.project_id = p.id ORDER BY a.hours DESC, e.name LIMIT 1) AS top_contributor FROM projects p ORDER BY 1;
::ordered true
::hints
