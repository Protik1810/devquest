=== lesson sql-relationships | Keys and relationships | 55
## Why data is split into tables

Imagine storing orders in one big table, with the customer's name, email and city repeated on every order. When Ada changes her email, you'd have to update every one of her orders, and if one update is missed, the data contradicts itself. Relational design avoids that by storing **each fact once**: customers in `customers`, orders in `orders`, and a **reference** from each order to its customer.

That reference is a **foreign key**: `orders.customer_id` holds the `id` of a row in `customers`. The database enforces it: an order can't point to a customer who doesn't exist.

```sql shop
SELECT id, customer_id, status FROM orders WHERE customer_id = 1;
```

Ada (customer 1) has three orders. To see her name next to them, you **join** the tables (next lesson).

## The three kinds of relationship

| Relationship | Example | How it's stored |
|---|---|---|
| **one-to-many** | a customer has many orders; an order has one customer | a foreign key on the "many" side: `orders.customer_id` |
| **many-to-many** | an order contains many products; a product appears in many orders | a **junction table** with two foreign keys: `order_items(order_id, product_id)` |
| **one-to-one** | a user and their profile settings | a foreign key that's also unique (often the primary key itself) |

The junction table often carries information about the relationship itself: `order_items` stores the `quantity` and the `unit_price` at the time of the order.

A table can also refer to **itself**. In the company database, `employees.manager_id` holds another employee's `id`; in the shop, `categories.parent_id` points to the parent category (Computers is inside Electronics). These **self-references** model hierarchies, and Module 6 shows how to walk them with recursive queries.

## Primary keys: natural or surrogate?

A primary key must be **unique** and **never NULL**, and should **never change**, because other tables refer to it.

- A **natural key** is a real-world value: an ISBN, a country code (`'UK'`), an email address.
- A **surrogate key** is a meaningless number or UUID generated by the database: `id integer GENERATED ALWAYS AS IDENTITY`.

Most tables use surrogate keys, because real-world values change (people change emails; even "permanent" codes get reorganised) and can be long. Junction tables often use a **composite key** made of their two foreign keys: `PRIMARY KEY (order_id, product_id)`, which also prevents the same product appearing twice in one order.

## Entity-relationship diagrams

Database designs are drawn as **ER diagrams**: a box per table listing its columns, and lines between related tables, with "crow's feet" marking the "many" end:

```
customers 1 ──< orders 1 ──< order_items >── 1 products >── 1 categories
     1                                          1
     └────────────────< reviews >───────────────┘
```

Read `customers 1 ──< orders` as "one customer has many orders". Tools such as dbdiagram.io, pgAdmin and DBeaver draw these diagrams from a real database.

=== lesson sql-join | Inner joins | 75
## Joining two tables

A **join** combines rows from two tables that belong together. To show each order with its customer's name:

```sql shop
SELECT orders.id, customers.name, orders.status
FROM orders
JOIN customers ON customers.id = orders.customer_id;
```

`JOIN ... ON condition` pairs every order with every customer for which the condition is true: here, the customer whose `id` equals the order's `customer_id`. (`JOIN` means `INNER JOIN`; both spellings are common.)

Because both tables have an `id` column, the column names are **qualified** with their table: `orders.id`. Writing out table names gets long, so queries use short **table aliases**:

```sql shop
SELECT o.id AS order_id, c.name AS customer, o.ordered_at
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id
WHERE c.country = 'UK'
ORDER BY o.ordered_at;
```

(The `AS` is optional for tables: `FROM orders o`.) Every other clause (`WHERE`, `GROUP BY`, `ORDER BY`) works on the joined rows as if they were one wide table.

## How a join works

Conceptually, a join considers **every pair** of rows (each order with each customer: 20 × 12 = 240 pairs) and keeps the pairs where `ON` is true. The database doesn't really build all pairs (it uses indexes, hash tables or sorting, Module 7), but the result is the same. Two consequences:

- A row with **no match** disappears from an inner join: an order whose customer didn't exist (impossible here thanks to the foreign key), or, joining the other way, a customer with no orders.
- A row with **several matches** appears **several times**: Ada has three orders, so she appears three times. This is correct, but it's the cause of a very common bug: summing values after a join that duplicated them.

## Joining many tables

Joins chain. To list what each order contained, with product names:

```sql shop
SELECT o.id AS order_id, c.name AS customer, p.name AS product, oi.quantity, oi.unit_price
FROM orders o
JOIN customers c ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id
WHERE o.id <= 3
ORDER BY o.id, p.name;
```

Follow the foreign keys: orders → customers, orders → order_items → products. Each `JOIN` adds one table and the condition that connects it.

## Joins and aggregates together

Most real reports join, then group:

```sql shop
SELECT c.name, count(*) AS orders, sum(o.shipping) AS shipping_paid
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY orders DESC, c.name;
```

```sql shop
SELECT cat.name AS category, sum(oi.quantity * oi.unit_price) AS revenue
FROM order_items oi
JOIN products p ON p.id = oi.product_id
JOIN categories cat ON cat.id = p.category_id
GROUP BY cat.name
ORDER BY revenue DESC;
```

Grouping by `c.id` (the primary key) as well as `c.name` keeps two customers with the same name apart.

## Join conditions other than equality

`ON` can be any condition. A **non-equi join** matches ranges, for example giving each product a price band from a table of bands:

```sql shop
SELECT p.name, p.price, b.label
FROM products p
JOIN (VALUES ('budget', 0, 50), ('standard', 50, 250), ('premium', 250, 100000)) AS b(label, low, high)
  ON p.price >= b.low AND p.price < b.high
ORDER BY p.price;
```

(`VALUES` creates a small inline table, here named `b` with three columns. It's handy for lookup lists that aren't worth a real table.)

## USING and NATURAL JOIN

When the joined columns have the **same name** in both tables, `USING (column)` is a shorthand: `JOIN order_items USING (order_id)`. **`NATURAL JOIN`** joins on all columns with the same names automatically: avoid it, because adding an unrelated column with a common name (`id`, `created_at`, `name`) silently changes the join.

## The old comma syntax

You'll see joins written with commas and the condition in `WHERE`, the style before 1992:

```sql shop
SELECT o.id, c.name
FROM orders o, customers c
WHERE c.id = o.customer_id AND o.id <= 3;
```

It works, but mixing join conditions with filters makes queries harder to read, and forgetting the condition gives every combination of rows. Prefer explicit `JOIN ... ON`.

=== lesson sql-outer-joins | Outer, self and cross joins | 75
## Keeping rows without a match: LEFT JOIN

An inner join drops customers who have never ordered. To list **every** customer, with their orders if any, use a **`LEFT JOIN`** (short for `LEFT OUTER JOIN`): it keeps every row of the left table, and fills the right side with `NULL`s where there's no match.

```sql shop
SELECT c.name, o.id AS order_id, o.status
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
ORDER BY c.name, o.id;
```

Hedy Lamarr and Guido van Rossum appear with `NULL` order columns: they have no orders.

**`RIGHT JOIN`** keeps every row of the right table instead (so `A RIGHT JOIN B` equals `B LEFT JOIN A`; most people always write `LEFT JOIN` and order the tables accordingly), and **`FULL JOIN`** keeps unmatched rows from both sides.

## Counting with outer joins

"Number of orders per customer, including zero" is a classic:

```sql shop
SELECT c.name, count(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY orders, c.name;
```

Note `count(o.id)`, not `count(*)`: a customer without orders still has one joined row (with `NULL`s), which `count(*)` would count as 1. `count(o.id)` skips the `NULL`.

## Finding rows with no match (anti-join)

Customers who have never ordered: left join, then keep the rows where the right side is missing:

```sql shop
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

This pattern is called an **anti-join**. The next lesson shows an equivalent with `NOT EXISTS`.

## The ON versus WHERE trap

With outer joins, **where** you put a condition matters:

```sql shop
-- Intended: every customer, with their cancelled orders if any. But WHERE removes customers without one!
SELECT c.name, o.id AS cancelled_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.status = 'cancelled';
```

`WHERE` runs after the join: rows where `o.status` is `NULL` (customers with no matching order) fail the condition and disappear, turning the left join into an inner join. Put conditions about the **right** table in `ON`, so they decide what matches:

```sql shop
SELECT c.name, o.id AS cancelled_order
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'cancelled'
ORDER BY c.name;
```

The rule: in a `LEFT JOIN`, conditions on the right table go in `ON`; conditions on the left table go in `WHERE`.

## Self joins

A table can be joined **to itself**, with two different aliases. In the company database, each employee's `manager_id` points to another employee:

```sql company
SELECT e.name AS employee, e.title, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id
ORDER BY m.name NULLS FIRST, e.name;
```

`e` plays the employee, `m` the manager. The `LEFT JOIN` keeps the CEO, who has no manager.

## Cross joins

**`CROSS JOIN`** pairs every row with every row (the **Cartesian product**): 5 sizes × 3 colours = 15 variants. It's rarely what you want by accident (it's what happens when you forget a join condition), but useful on purpose, for example to build every combination and then fill it in:

```sql shop
SELECT s.status, y.year
FROM (SELECT DISTINCT status FROM orders) s
CROSS JOIN (VALUES (2025), (2026)) AS y(year)
ORDER BY s.status, y.year;
```

=== lesson sql-subqueries | Subqueries | 80
## A query inside a query

A **subquery** is a `SELECT` in parentheses, used inside another statement. It lets you answer questions in steps. Which products cost more than the average?

```sql shop
SELECT name, price
FROM products
WHERE price > (SELECT avg(price) FROM products)
ORDER BY price;
```

The inner query runs first and returns one value (about 223.82), which the outer query compares with. A subquery that returns exactly **one value** is a **scalar subquery**, and can appear anywhere a value can: in `WHERE`, in `SELECT`, in a calculation.

## Subqueries that return a list: IN

A subquery returning one column of many rows works with `IN`:

```sql shop
SELECT name
FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE status = 'cancelled');
```

"Customers whose id is among the customer ids of cancelled orders." The same question could be a join; with `IN`, a customer appears **once** even if they cancelled several orders, while a join would repeat them.

## EXISTS and NOT EXISTS

**`EXISTS (subquery)`** is true when the subquery returns at least one row. Inside it, you can refer to the outer query's row:

```sql shop
SELECT p.name
FROM products p
WHERE EXISTS (SELECT 1 FROM reviews r WHERE r.product_id = p.id AND r.rating = 5)
ORDER BY p.name;
```

For each product, the subquery checks whether a five-star review for **this** product exists. (`SELECT 1` is a convention: `EXISTS` only cares whether rows exist, not what they contain.)

A subquery that refers to the outer row is **correlated**: conceptually it runs once per outer row (the planner usually turns it into an efficient join).

**`NOT EXISTS`** is the safe way to find rows **without** a match. Remember the `NOT IN` trap with `NULL`s (Module 2)? `NOT EXISTS` doesn't have it:

```sql shop
SELECT c.name
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
```

Prefer `NOT EXISTS` over `NOT IN (subquery)` whenever the subquery's column could contain `NULL`.

~~~check

+ If the subquery returns a NULL, NOT IN returns no rows at all
- NOT EXISTS is shorter
- NOT IN doesn't support subqueries
- NOT EXISTS sorts the result

~~~

## Correlated scalar subqueries

A correlated subquery in `SELECT` computes a value per row:

```sql shop
SELECT c.name,
       (SELECT max(o.ordered_at) FROM orders o WHERE o.customer_id = c.id) AS last_order
FROM customers c
ORDER BY last_order DESC NULLS LAST;
```

And comparing each row with its own group, "products priced above the average **of their category**":

```sql shop
SELECT p.name, p.category_id, p.price
FROM products p
WHERE p.price > (SELECT avg(p2.price) FROM products p2 WHERE p2.category_id = p.category_id)
ORDER BY p.category_id, p.price;
```

## Subqueries in FROM (derived tables)

A subquery in `FROM` acts as a temporary table, with an alias. It's how you aggregate in two steps, for example "the average number of orders per customer":

```sql shop
SELECT round(avg(order_count), 2) AS average_orders
FROM (
  SELECT customer_id, count(*) AS order_count
  FROM orders
  GROUP BY customer_id
) AS per_customer;
```

It's also the clean fix for the join fan-out bug: aggregate each table **before** joining, so nothing is duplicated:

```sql shop
SELECT c.name, totals.goods
FROM customers c
JOIN (
  SELECT o.customer_id, sum(oi.quantity * oi.unit_price) AS goods
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  GROUP BY o.customer_id
) AS totals ON totals.customer_id = c.id
ORDER BY totals.goods DESC
LIMIT 5;
```

Module 6 introduces **CTEs** (`WITH ... AS`), which give such steps names and make long queries much more readable.

## ANY and ALL

`x > ALL (subquery)` is true when `x` is greater than every value; `x = ANY (subquery)` is the same as `IN`. They're rare in practice (`max`/`min` usually say it more clearly), but you'll meet them in existing code.

=== lesson sql-set-ops | Combining results: UNION, INTERSECT, EXCEPT | 55
## Stacking results

Joins combine tables **side by side**; set operations combine query results **one under the other**. The queries must return the same number of columns, with compatible types:

```sql shop
SELECT name, 'customer' AS kind FROM customers WHERE country = 'NL'
UNION
SELECT name, 'product' AS kind FROM products WHERE price > 400
ORDER BY kind, name;
```

| Operation | Result |
|---|---|
| `A UNION B` | rows in A or B, **without duplicates** |
| `A UNION ALL B` | all rows of A, then all rows of B, duplicates kept |
| `A INTERSECT B` | rows in both |
| `A EXCEPT B` | rows in A that aren't in B (Oracle calls it `MINUS`) |

Column names come from the first query, and an `ORDER BY` at the end sorts the combined result.

## UNION versus UNION ALL

`UNION` removes duplicates, which requires sorting or hashing all rows. When duplicates are impossible or wanted, **`UNION ALL`** is faster and says what you mean. A common use is building one timeline from several tables:

```sql shop
SELECT ordered_at::date AS day, 'order #' || id AS event FROM orders WHERE customer_id = 1
UNION ALL
SELECT created_on, 'review of product ' || product_id FROM reviews WHERE customer_id = 1
ORDER BY day;
```

## INTERSECT and EXCEPT

```sql shop
-- customers who have both ordered and reviewed
SELECT customer_id FROM orders
INTERSECT
SELECT customer_id FROM reviews
ORDER BY customer_id;
```

```sql shop
-- products that were ordered but never reviewed
SELECT product_id FROM order_items
EXCEPT
SELECT product_id FROM reviews
ORDER BY product_id;
```

Unlike `NOT IN`, `EXCEPT` treats `NULL`s as equal to each other, so it has no `NULL` trap. Both also remove duplicates (`INTERSECT ALL` and `EXCEPT ALL` keep them).

+ 2
- 0
- It's an error
> UNION ALL keeps duplicates; UNION would return it once.
~~~
