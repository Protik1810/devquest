=== module Module 3 · Summarising data

=== lesson sql-agg | Aggregates and GROUP BY | 75
## From rows to answers

Questions about data are usually about **many rows at once**: how many customers? what's the average price? how much did we sell? **Aggregate functions** turn a set of rows into one value:

```sql shop
SELECT count(*) AS products,
       min(price) AS cheapest,
       max(price) AS dearest,
       round(avg(price), 2) AS average_price,
       sum(stock) AS items_in_stock
FROM products;
```

| Function | Returns |
|---|---|
| `count(*)` | the number of rows |
| `count(column)` | the number of rows where the column **isn't NULL** |
| `count(DISTINCT column)` | the number of different non-NULL values |
| `sum(x)`, `avg(x)` | total and mean of the non-NULL values |
| `min(x)`, `max(x)` | smallest and largest (works for numbers, text and dates) |

Aggregates **ignore NULLs** (except `count(*)`, which counts rows). That's usually what you want, but be aware of it:

```sql shop
SELECT count(*) AS customers,
       count(email) AS with_email,
       count(DISTINCT country) AS countries
FROM customers;
```

`avg(rating)` over reviews where some ratings were NULL would average only the known ratings. And an aggregate over **no rows** returns `NULL` (except `count`, which returns 0): `sum(x)` of nothing is `NULL`, so write `COALESCE(sum(x), 0)` when you need a number.

`WHERE` filters rows **before** they're aggregated:

```sql shop
SELECT count(*) AS delivered_orders
FROM orders
WHERE status = 'delivered';
```

## GROUP BY: one result row per group

**`GROUP BY`** splits the rows into groups that share the same value, and computes the aggregates for **each group**:

```sql shop
SELECT status, count(*) AS orders
FROM orders
GROUP BY status
ORDER BY orders DESC;
```

Think of it as sorting the rows into piles (one per status), then summarising each pile into one row. You can group by several columns (one group per combination) and by expressions:

```sql shop
SELECT order_id,
       count(*) AS lines,
       sum(quantity) AS items,
       sum(quantity * unit_price) AS goods_total
FROM order_items
GROUP BY order_id
ORDER BY order_id;
```

```sql shop
SELECT date_trunc('month', ordered_at)::date AS month, count(*) AS orders
FROM orders
GROUP BY date_trunc('month', ordered_at)
ORDER BY month;
```

## The GROUP BY rule

In a grouped query, every column in `SELECT` must either be **in the `GROUP BY`** or **inside an aggregate**. This fails:

```sql shop
-- error: which name should the group show? There are several per country.
SELECT country, name, count(*)
FROM customers
GROUP BY country;
```

Each country group contains several customers, so "the name" of a group has no single value. The error message (`column "customers.name" must appear in the GROUP BY clause or be used in an aggregate function`) is one you'll meet often; the fix is to decide what you mean: group by name too, or aggregate it (`min(name)`, `string_agg(name, ', ')`, `count(name)`).

(MySQL's old default mode silently picked an arbitrary name from the group. That "worked", and produced wrong reports for years in many companies; since MySQL 5.7 the `ONLY_FULL_GROUP_BY` mode rejects it too. PostgreSQL does allow other columns of a table when you group by its **primary key**, because they're then guaranteed to have one value per group.)

~~~check
? Which query is valid?
- `SELECT country, city, count(*) FROM customers GROUP BY country;`
+ `SELECT country, count(DISTINCT city) FROM customers GROUP BY country;`
- `SELECT name, count(*) FROM customers;`
- `SELECT country, name FROM customers GROUP BY country;`
> Every selected column must be grouped or aggregated.
~~~

## HAVING: filtering groups

`WHERE` can't use aggregates, because it runs before grouping. To filter **groups**, use **`HAVING`**, which runs after:

```sql shop
SELECT customer_id, count(*) AS orders
FROM orders
WHERE status <> 'cancelled'
GROUP BY customer_id
HAVING count(*) >= 2
ORDER BY orders DESC, customer_id;
```

Read it as: take orders, drop cancelled ones (`WHERE`), group by customer, keep customers with at least two orders (`HAVING`).

## The complete processing order

You now know all the main clauses. Logically, a query is processed in this order:

1. `FROM` (and joins, Module 4): which rows exist;
2. `WHERE`: keep matching rows;
3. `GROUP BY`: form groups;
4. `HAVING`: keep matching groups;
5. `SELECT`: compute the output columns (and aggregates);
6. `DISTINCT`;
7. `ORDER BY`;
8. `LIMIT` / `OFFSET`.

It explains most "why doesn't this work?" questions: `WHERE` (step 2) runs before groups exist (step 3) and before aggregates are computed, and only `ORDER BY` comes late enough to use `SELECT` aliases. (PostgreSQL relaxes this slightly by letting `GROUP BY` refer to output column names or positions, as in `GROUP BY 1`.)

## Joining text: string_agg

`string_agg(expression, separator)` concatenates the values in each group, which is perfect for readable reports:

```sql shop
SELECT country, string_agg(name, ', ' ORDER BY name) AS customers
FROM customers
GROUP BY country
ORDER BY country;
```

(MySQL calls it `GROUP_CONCAT`, SQL Server `STRING_AGG` too.) Similarly, `array_agg` collects the values into an array.

count(*) vs count(col) :: count(*) counts rows; count(col) counts non-NULL values; count(DISTINCT col) distinct ones.
GROUP BY :: One output row per group of equal values; aggregates are computed per group.
GROUP BY rule :: Every selected column must be grouped or aggregated (or functionally dependent on a grouped primary key).
WHERE vs HAVING :: WHERE filters rows before grouping; HAVING filters groups after aggregation.
Logical order :: FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.

=== lesson sql-grouping | Conditional aggregates and subtotals | 70
## Several counts in one pass: FILTER

Often you want several counts side by side ("how many orders of each status, per customer?"). Instead of several queries, put the condition **inside** the aggregate. The standard SQL way is **`FILTER`**:

```sql shop
SELECT customer_id,
       count(*) AS orders,
       count(*) FILTER (WHERE status = 'delivered') AS delivered,
       count(*) FILTER (WHERE status = 'cancelled') AS cancelled,
       sum(shipping) FILTER (WHERE status <> 'cancelled') AS shipping_paid
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
```

Databases without `FILTER` (MySQL, SQL Server) use a `CASE` inside the aggregate, which you'll see in a lot of existing code:

```sql shop
SELECT customer_id,
       sum(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) AS delivered,
       count(CASE WHEN status = 'cancelled' THEN 1 END) AS cancelled
FROM orders
GROUP BY customer_id
ORDER BY customer_id;
```

(`count(CASE ... THEN 1 END)` works because a `CASE` without `ELSE` gives `NULL`, which `count` skips.) Turning row values into columns like this is called **pivoting**.

## Percentages and ratios

Combining aggregates gives ratios. Remember integer division (Module 1): cast or multiply by `100.0` first.

```sql shop
SELECT count(*) FILTER (WHERE status = 'cancelled') AS cancelled,
       count(*) AS total,
       round(100.0 * count(*) FILTER (WHERE status = 'cancelled') / count(*), 1) AS cancel_rate_percent
FROM orders;
```

## DISTINCT inside aggregates

`count(DISTINCT x)` counts different values; `sum(DISTINCT x)` and `string_agg(DISTINCT x, ...)` also exist:

```sql shop
SELECT count(DISTINCT customer_id) AS customers_who_ordered,
       count(DISTINCT date_trunc('month', ordered_at)) AS active_months
FROM orders;
```

## Subtotals and grand totals: ROLLUP, CUBE and GROUPING SETS

Reports often need totals at several levels: per category and month, per category, and overall. **`GROUPING SETS`** computes several groupings in one query:

```sql shop
SELECT status, extract(year FROM ordered_at) AS year, count(*) AS orders
FROM orders
GROUP BY GROUPING SETS ((status, year), (status), ())
ORDER BY status NULLS LAST, year NULLS LAST;
```

Each grouping set produces its own rows; the columns not in a set are `NULL` in those rows (so a row with `year` NULL is a per-status subtotal, and the row with both NULL is the grand total). Two shortcuts:

- **`ROLLUP (a, b)`** means `GROUPING SETS ((a, b), (a), ())`: a hierarchy of subtotals, like the subtotal lines of a spreadsheet;
- **`CUBE (a, b)`** means every combination: `(a, b), (a), (b), ()`.

```sql shop
SELECT extract(year FROM ordered_at) AS year,
       extract(quarter FROM ordered_at) AS quarter,
       count(*) AS orders,
       sum(shipping) AS shipping
FROM orders
GROUP BY ROLLUP (year, quarter)
ORDER BY year NULLS LAST, quarter NULLS LAST;
```

When a grouping column can itself contain `NULL`, you can't tell a real `NULL` from a subtotal's `NULL`; the function **`GROUPING(column)`** returns 1 for subtotal rows, so you can label them:

```sql shop
SELECT CASE WHEN GROUPING(status) = 1 THEN 'ALL' ELSE status END AS status,
       count(*) AS orders
FROM orders
GROUP BY ROLLUP (status)
ORDER BY GROUPING(status), status;
```

These features come from **data warehousing** (OLAP: online analytical processing), where reports summarise huge fact tables along many "dimensions"; the analytics capstone returns to them.
