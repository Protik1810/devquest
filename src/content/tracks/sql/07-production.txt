## All or nothing

Moving money between two accounts is two updates: take from one, add to the other. If the program crashes between them, money vanishes. A **transaction** groups statements so that they all happen, or none do:

```sql empty
CREATE TABLE accounts (id integer PRIMARY KEY, owner text NOT NULL, balance numeric(10, 2) NOT NULL CHECK (balance >= 0));
INSERT INTO accounts VALUES (1, 'Ada', 100), (2, 'Grace', 50);

BEGIN;
UPDATE accounts SET balance = balance - 30 WHERE id = 1;
UPDATE accounts SET balance = balance + 30 WHERE id = 2;
COMMIT;

SELECT * FROM accounts ORDER BY id;
```

- **`BEGIN`** starts a transaction;
- **`COMMIT`** makes all its changes permanent and visible to others, at once;
- **`ROLLBACK`** cancels all of them, as if they never happened:

```sql empty
CREATE TABLE accounts (id integer PRIMARY KEY, owner text NOT NULL, balance numeric(10, 2) NOT NULL);
INSERT INTO accounts VALUES (1, 'Ada', 100), (2, 'Grace', 50);

BEGIN;
DELETE FROM accounts;
SELECT count(*) AS inside_the_transaction FROM accounts;
ROLLBACK;

SELECT count(*) AS after_rollback FROM accounts;
```

Without `BEGIN`, PostgreSQL runs each statement in its own transaction (**autocommit**). If any statement in a transaction fails, PostgreSQL marks the whole transaction as failed: every following statement is refused until `ROLLBACK`. That's deliberate: you can't accidentally commit half a job.

## ACID

Transactions give four guarantees, known as **ACID**:

| | Guarantee |
|---|---|
| **Atomicity** | all of the transaction's changes happen, or none |
| **Consistency** | it moves the database from one valid state to another: every constraint holds at commit |
| **Isolation** | concurrent transactions don't see each other's unfinished work |
| **Durability** | once committed, changes survive crashes (PostgreSQL writes them to its write-ahead log first) |

## Savepoints

A **savepoint** marks a point inside a transaction you can roll back to, without abandoning the whole transaction:

```sql empty
CREATE TABLE log (id integer PRIMARY KEY, message text);

BEGIN;
INSERT INTO log VALUES (1, 'kept');
SAVEPOINT before_risky_part;
INSERT INTO log VALUES (2, 'undone');
ROLLBACK TO SAVEPOINT before_risky_part;
INSERT INTO log VALUES (3, 'also kept');
COMMIT;

SELECT * FROM log ORDER BY id;
```

## Concurrency: many users at once

A busy database runs hundreds of transactions at the same time. PostgreSQL uses **MVCC** (multi-version concurrency control): an update writes a new version of the row instead of overwriting it, so **readers never wait for writers and writers never wait for readers**. Each transaction sees a consistent **snapshot** of the data. (Old row versions are cleaned up later by **VACUUM**, which runs automatically.)

Two writers updating the **same row** do wait for each other: the second blocks until the first commits or rolls back.

## Isolation levels

How much transactions can see of each other is set by the **isolation level**. The SQL standard defines four, by the anomalies they prevent:

| Level | Dirty read | Non-repeatable read | Phantom read | Serialization anomaly |
|---|---|---|---|---|
| Read uncommitted | possible (not in PostgreSQL) | possible | possible | possible |
| **Read committed** (PostgreSQL's default) | no | possible | possible | possible |
| Repeatable read | no | no | no in PostgreSQL | possible |
| Serializable | no | no | no | no |

- **Dirty read**: seeing another transaction's uncommitted changes.
- **Non-repeatable read**: reading the same row twice in one transaction and getting different values, because someone committed in between.
- **Phantom read**: running the same query twice and getting new rows.
- **Serialization anomaly**: the combined result is impossible in any one-at-a-time order.

The famous bug of read committed is the **lost update**. Two clerks sell the last items in stock at the same time:

| Time | Transaction A | Transaction B |
|---|---|---|
| 1 | `SELECT stock ...` → 1 | |
| 2 | | `SELECT stock ...` → 1 |
| 3 | `UPDATE ... SET stock = 0` (computed in the app: 1 − 1) | |
| 4 | `COMMIT` | `UPDATE ... SET stock = 0` (also 1 − 1) |
| 5 | | `COMMIT`: two items sold, stock says 0, one item is oversold |

Three standard fixes:

1. **Let the database do the arithmetic, atomically, with a guard**: `UPDATE products SET stock = stock - 1 WHERE id = 7 AND stock >= 1` (and check that one row was updated). This is usually the best.
2. **Lock the row** when reading it: `SELECT ... FOR UPDATE` makes the second transaction wait until the first commits, then read the new value.
3. **Optimistic locking**: store a `version` number and update with `WHERE id = 7 AND version = 3`; if no row changed, someone else got there first, so reload and retry. Common in ORMs and web applications.

Stricter isolation (`BEGIN ISOLATION LEVEL SERIALIZABLE`) prevents such anomalies automatically, at the cost of having to **retry** transactions that the database aborts with a serialization failure (error 40001).

## Deadlocks

If A locks row 1 then wants row 2, while B holds row 2 and wants row 1, both wait forever: a **deadlock**. PostgreSQL detects it and aborts one of them (error 40P01). Prevent deadlocks by always locking rows in the same order (for example, by id), and keep transactions **short**: never wait for user input inside one.

=== lesson sql-indexes | Indexes and query performance | 90
## Why queries get slow

On 20 rows, every query is instant. On 20 million, a query that reads the whole table (a **sequential scan**) can take seconds. An **index** is a separate data structure, sorted by one or more columns, that lets the database jump straight to the matching rows, like the index at the back of a book.

This example builds a table of 200,000 events, then runs the same query before and after creating an index. **`EXPLAIN ANALYZE`** shows the **plan** the database chose and how long each step took:

```sql empty
CREATE TABLE events (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, user_id integer NOT NULL, kind text NOT NULL, created_at timestamptz NOT NULL);
INSERT INTO events (user_id, kind, created_at)
SELECT (i * 7919) % 5000, (ARRAY['view', 'click', 'buy'])[1 + i % 3], timestamptz '2026-01-01' + i * interval '1 minute'
FROM generate_series(1, 200000) AS i;
ANALYZE events;

EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 42;
```

`Seq Scan on events` with `Rows Removed by Filter: 199960`: the database read every row to find 40. Now with an index:

```sql empty
CREATE TABLE events (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, user_id integer NOT NULL, kind text NOT NULL, created_at timestamptz NOT NULL);
INSERT INTO events (user_id, kind, created_at)
SELECT (i * 7919) % 5000, (ARRAY['view', 'click', 'buy'])[1 + i % 3], timestamptz '2026-01-01' + i * interval '1 minute'
FROM generate_series(1, 200000) AS i;
CREATE INDEX events_user_id_idx ON events (user_id);
ANALYZE events;

EXPLAIN ANALYZE SELECT * FROM events WHERE user_id = 42;
```

The plan now uses `events_user_id_idx`, and the execution time drops by a factor of about a hundred. On a real server with millions of rows and data on disk, the difference is between milliseconds and minutes.

## How a B-tree index works

The default index type is a **B-tree**: a balanced tree of sorted keys, a few levels deep even for billions of rows, where each leaf points to rows in the table. Finding one value takes a handful of page reads instead of all of them. Because it's sorted, a B-tree helps with:

- equality: `WHERE user_id = 42`;
- ranges: `WHERE created_at >= '2026-03-01' AND created_at < '2026-04-01'`, `BETWEEN`, `<`, `>`;
- prefix matches: `WHERE name LIKE 'Ada%'` (with the right operator class);
- sorting: `ORDER BY created_at DESC LIMIT 10` can read the index in order and stop early;
- `min` and `max`.

It doesn't help with `LIKE '%ada%'` (no fixed prefix), functions of the column (`WHERE lower(email) = ...`, unless you index that expression), or conditions that match most of the table (reading the index and then most rows would be slower than one sequential scan, so the planner rightly ignores the index).

## Reading plans

`EXPLAIN` shows the plan without running the query; `EXPLAIN ANALYZE` runs it and adds real times and row counts. The common nodes:

| Node | Means |
|---|---|
| `Seq Scan` | reads the whole table |
| `Index Scan` | walks the index, fetching matching rows |
| `Index Only Scan` | answers from the index alone, without touching the table |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | collects matching row locations from the index, then reads them in physical order (good for medium-sized results) |
| `Nested Loop`, `Hash Join`, `Merge Join` | join algorithms |
| `Sort`, `HashAggregate`, `Limit` | as named |

The planner chooses using **statistics** about each column (collected by `ANALYZE`, which runs automatically). When estimated rows (`rows=40`) and actual rows are very different, the statistics are stale or the query is hard to estimate: a common cause of bad plans.

## Multi-column, expression and partial indexes

```sql empty
CREATE TABLE events (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, user_id integer NOT NULL, kind text NOT NULL, created_at timestamptz NOT NULL);
INSERT INTO events (user_id, kind, created_at)
SELECT (i * 7919) % 5000, (ARRAY['view', 'click', 'buy'])[1 + i % 3], timestamptz '2026-01-01' + i * interval '1 minute'
FROM generate_series(1, 200000) AS i;
CREATE INDEX events_user_time_idx ON events (user_id, created_at DESC);
ANALYZE events;

EXPLAIN ANALYZE
SELECT * FROM events WHERE user_id = 42 ORDER BY created_at DESC LIMIT 5;
```

- A **multi-column** index on `(user_id, created_at)` serves "this user's latest events" directly: filter on the first column, read in the order of the second. Column order matters: it also serves queries on `user_id` alone, but not on `created_at` alone (like a phone book sorted by surname, then first name).
- An **expression index** indexes a computed value: `CREATE INDEX ON customers (lower(email))` serves `WHERE lower(email) = 'ada@example.com'`.
- A **partial index** covers only some rows: `CREATE INDEX ON orders (ordered_at) WHERE status = 'pending'` is small and fast for "pending orders" queries.
- A **unique index** enforces uniqueness (that's how `UNIQUE` and primary keys are implemented).

Other index types serve other data: **GIN** for arrays, `jsonb` containment and full-text search; **GiST** for ranges, geometry and exclusion constraints; **BRIN** for huge, naturally ordered tables (logs by time); hash for equality only.

## The cost of indexes

Indexes aren't free: every `INSERT`, `UPDATE` and `DELETE` must update every index on the table, and each takes disk space. So:

- index columns used in frequent `WHERE`, `JOIN` and `ORDER BY` clauses, **foreign keys** in particular (PostgreSQL doesn't index them automatically; joins and parent deletes need them);
- don't index everything "just in case";
- measure with `EXPLAIN ANALYZE` before and after, on realistic data;
- on a live production table, use `CREATE INDEX CONCURRENTLY`, which doesn't block writes while it builds;
- find slow queries with the `pg_stat_statements` extension and the slow query log (`log_min_duration_statement`).

=== lesson sql-catalog | The system catalog | 55
## The database describes itself

Every database keeps a description of its own structure, the **system catalog**, stored in tables you can query with ordinary SQL. Tools like `psql`'s `\d`, pgAdmin and ORMs read it to show tables, generate code and compare schemas.

There are two views of it:

- **`information_schema`**: the SQL standard's catalog, available (with variations) in PostgreSQL, MySQL, SQL Server and others. Portable, but slower and less detailed.
- **`pg_catalog`**: PostgreSQL's own catalog tables (`pg_class`, `pg_attribute`, `pg_constraint`, `pg_index`...), complete and fast, but specific to PostgreSQL.

## Tables, columns and constraints

```sql shop
SELECT table_name, column_name, data_type, is_nullable, column_default
FROM information_schema.columns
WHERE table_schema = 'public' AND table_name = 'products'
ORDER BY ordinal_position;
```

```sql shop
SELECT tc.table_name, tc.constraint_name, tc.constraint_type
FROM information_schema.table_constraints tc
WHERE tc.table_schema = 'public'
ORDER BY tc.table_name, tc.constraint_type;
```

Foreign keys, with the columns they connect:

```sql shop
SELECT kcu.table_name, kcu.column_name, ccu.table_name AS references_table, ccu.column_name AS references_column
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu ON kcu.constraint_name = tc.constraint_name
JOIN information_schema.constraint_column_usage ccu ON ccu.constraint_name = tc.constraint_name
WHERE tc.constraint_type = 'FOREIGN KEY'
ORDER BY kcu.table_name, kcu.column_name;
```

## PostgreSQL's catalog

`pg_catalog` answers questions the standard views can't: sizes, indexes and their definitions, statistics.

```sql shop
SELECT c.relname AS table_name,
       c.reltuples::bigint AS estimated_rows,
       pg_size_pretty(pg_total_relation_size(c.oid)) AS total_size
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE n.nspname = 'public' AND c.relkind = 'r'
ORDER BY pg_total_relation_size(c.oid) DESC;
```

```sql shop
SELECT tablename, indexname, indexdef FROM pg_indexes WHERE schemaname = 'public' ORDER BY tablename;
```

Handy functions: `pg_get_constraintdef(oid)` and `pg_get_indexdef(oid)` return definitions as SQL; `pg_typeof(x)` shows a value's type; `obj_description` and `col_description` read **comments** you attach with `COMMENT ON TABLE products IS '...'`, which is a simple way to document a schema inside the database itself.

The statistics views (`pg_stat_user_tables`, `pg_stat_user_indexes`) show how often each table is scanned and each index is used: an index with zero scans after months in production is a candidate for removal.

=== lesson sql-security | Security: roles, privileges and SQL injection | 85
## Least privilege

A database often holds a company's most valuable and sensitive data. The first rule of database security is **least privilege**: every person and program gets exactly the access it needs, and nothing more. The web application doesn't need to drop tables; the reporting tool doesn't need to see password hashes; the intern doesn't need production at all.

## Roles, GRANT and REVOKE

PostgreSQL manages access with **roles**. A role can log in (a user) or not (a group of privileges), and roles can be members of other roles.

```sql shop
CREATE ROLE reporting NOLOGIN;
GRANT SELECT ON products, categories, orders, order_items TO reporting;
GRANT SELECT (id, name, country) ON customers TO reporting;

SET ROLE reporting;                       -- act as that role, to test
SELECT name, country FROM customers LIMIT 3;
```

```sql shop
-- error: reporting may not read the email column
CREATE ROLE reporting NOLOGIN;
GRANT SELECT (id, name, country) ON customers TO reporting;
SET ROLE reporting;
SELECT name, email FROM customers;
```

| Statement | Effect |
|---|---|
| `CREATE ROLE app LOGIN PASSWORD '...'` | a role that can connect |
| `GRANT SELECT, INSERT, UPDATE ON orders TO app` | table privileges (also `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER`) |
| `GRANT SELECT (col1, col2) ON t TO r` | column privileges |
| `GRANT USAGE ON SCHEMA s TO r` | needed to see objects in a schema |
| `GRANT reporting TO alice` | role membership: alice gets reporting's privileges |
| `REVOKE INSERT ON orders FROM app` | take a privilege away |
| `ALTER DEFAULT PRIVILEGES ...` | privileges for tables created in the future |

A typical production setup: an **owner** role that runs migrations (and owns the tables), an **application** role with only `SELECT`, `INSERT`, `UPDATE` and `DELETE` on the tables it uses, and a **read-only** role for analysts, connected to a replica. Nobody uses the superuser for daily work.

Views (Module 6) add finer control: grant access to a view that shows only some rows or columns, without granting access to the table behind it.

## Row-level security

**Row-level security** (RLS) filters which **rows** each role or user may see or change, enforced by the database for every query. Multi-tenant applications use it so that one customer's data can never leak to another, even if the application has a bug:

```sql shop
CREATE ROLE web_app NOLOGIN;
GRANT SELECT ON orders TO web_app;

ALTER TABLE orders ENABLE ROW LEVEL SECURITY;
CREATE POLICY customer_sees_own_orders ON orders
  FOR SELECT
  USING (customer_id = current_setting('app.customer_id')::integer);

SET app.customer_id = '1';                -- the application sets this per request
SET ROLE web_app;
SELECT id, customer_id, status FROM orders;
```

Only Ada's three orders are visible to `web_app`, whatever the query says. (Table owners and superusers bypass RLS unless it's forced.)

## SQL injection

The most important security rule for application developers: **never build SQL by concatenating user input into a string.** Consider a login check built like this (shown in JavaScript):

```
const sql = "SELECT * FROM users WHERE email = '" + email + "' AND password_hash = '" + hash + "'";
```

If someone types the email `' OR 1=1 --`, the query becomes:

```
SELECT * FROM users WHERE email = '' OR 1=1 --' AND password_hash = '...'
```

`OR 1=1` makes the condition true for every row, and `--` comments out the password check: the attacker logs in as the first user, often an administrator. With other inputs, attackers can read any table (`' UNION SELECT ...`), modify data, or worse. **SQL injection** has been one of the most common and damaging web vulnerabilities for over twenty years.

The fix is **parameterized queries** (prepared statements): the SQL text and the values travel separately, so values are never interpreted as SQL:

```
// node-postgres
await client.query("SELECT * FROM users WHERE email = $1 AND password_hash = $2", [email, hash]);
```

```
# Python, psycopg
cur.execute("SELECT * FROM users WHERE email = %s AND password_hash = %s", (email, hash))
```

You can see the same mechanism in SQL itself with `PREPARE`, where the input stays a value even when it looks like SQL:

```sql shop
PREPARE find_customer(text) AS SELECT id, name FROM customers WHERE email = $1;
EXECUTE find_customer('ada@example.com');
```

```sql shop
PREPARE find_customer(text) AS SELECT id, name FROM customers WHERE email = $1;
EXECUTE find_customer(''' OR 1=1 --');
```

The attack string is simply an email address nobody has: no rows. Rules of thumb:

- always use parameters for values; never format them into the SQL string yourself;
- identifiers (table or column names) can't be parameters: if users choose them (a sort column), pick from an **allow-list** in code;
- inside PostgreSQL functions that build SQL dynamically, use `format('... %I ... %L', identifier, literal)`, which quotes safely (next lesson);
- ORMs and query builders parameterize for you, until you use their "raw SQL" escape hatch carelessly.

~~~check
? Which is the right defence against SQL injection?
- Removing quotes from user input
- Checking input with a regular expression
+ Parameterized queries, with values sent separately from the SQL
- Hiding error messages
> Escaping and filtering are fragile; parameters are structural.
~~~

## More protection

- **Passwords** are never stored in plain text: store a slow, salted hash (bcrypt, scrypt, Argon2) computed by the application.
- **Encryption in transit**: require TLS (`sslmode=require`) for connections over a network.
- **Encryption at rest**: disk or cloud-provider encryption; column-level encryption (`pgcrypto`) for especially sensitive fields.
- **Network**: the database port should never be open to the internet; only application servers connect.
- **Auditing**: log connections and changes to sensitive tables (with triggers, next lesson, or the `pgaudit` extension).
- **Backups** are copies of all your data: protect them as carefully as the database.
- Privacy laws (GDPR and others) also govern what you may store, for how long, and how users can see or delete it.

=== lesson sql-functions | Functions, procedures and triggers | 85
## Code inside the database

Databases can run code: **functions** you call from queries, **procedures** you call to perform work, and **triggers** that run automatically when data changes. The book calls this "stored procedural SQL"; every major database has it, with different languages: PostgreSQL's **PL/pgSQL**, Oracle's PL/SQL, SQL Server's T-SQL, MySQL's stored procedures.

## SQL functions

The simplest function is a named, parameterized query:

```sql shop
CREATE FUNCTION customer_spend(p_customer integer) RETURNS numeric
LANGUAGE sql STABLE
AS $$
  SELECT COALESCE(sum(oi.quantity * oi.unit_price), 0)
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  WHERE o.customer_id = p_customer AND o.status <> 'cancelled'
$$;

SELECT name, customer_spend(id) AS spent FROM customers ORDER BY spent DESC LIMIT 4;
```

- `$$ ... $$` quotes the body (so it can contain single quotes);
- `STABLE` tells the planner the function doesn't modify data and returns the same result within a query (`IMMUTABLE` for pure calculations, `VOLATILE`, the default, for anything else);
- functions can **return tables**, and then behave like parameterized views:

```sql shop
CREATE FUNCTION products_under(max_price numeric)
RETURNS TABLE (name text, price numeric)
LANGUAGE sql STABLE
AS $$
  SELECT name, price FROM products WHERE price <= max_price ORDER BY price
$$;

SELECT * FROM products_under(40);
```

## PL/pgSQL

For logic with variables, conditions and loops, use **PL/pgSQL**:

```sql shop
CREATE FUNCTION loyalty_tier(p_customer integer) RETURNS text
LANGUAGE plpgsql STABLE
AS $$
DECLARE
  spent numeric;
BEGIN
  SELECT COALESCE(sum(oi.quantity * oi.unit_price), 0) INTO spent
  FROM orders o JOIN order_items oi ON oi.order_id = o.id
  WHERE o.customer_id = p_customer AND o.status <> 'cancelled';

  IF spent >= 1000 THEN
    RETURN 'gold';
  ELSIF spent >= 250 THEN
    RETURN 'silver';
  ELSE
    RETURN 'bronze';
  END IF;
END;
$$;

SELECT name, loyalty_tier(id) AS tier FROM customers ORDER BY id LIMIT 6;
```

PL/pgSQL has `DECLARE`d variables, `IF`/`ELSIF`/`ELSE`, `CASE`, `LOOP`, `WHILE`, `FOR row IN SELECT ... LOOP`, `RAISE EXCEPTION 'message'` to fail with an error, and `EXCEPTION WHEN ...` blocks to catch errors.

## Procedures

A **procedure** (`CREATE PROCEDURE`, called with `CALL`) performs work rather than returning a value, and, unlike a function, can `COMMIT` inside its body, which suits long batch jobs:

```sql shop
CREATE PROCEDURE cancel_stale_orders(older_than interval)
LANGUAGE plpgsql
AS $$
BEGIN
  UPDATE orders SET status = 'cancelled'
  WHERE status = 'pending' AND ordered_at < timestamp '2026-03-31' - older_than;
  RAISE NOTICE 'cancelled % orders', (SELECT count(*) FROM orders WHERE status = 'cancelled');
END;
$$;

CALL cancel_stale_orders(interval '30 days');
SELECT id, status FROM orders WHERE id IN (17, 19);
```

## Dynamic SQL, safely

Sometimes a function must build SQL at run time (a table name chosen by a parameter). Use `EXECUTE` with **`format`**, whose `%I` quotes identifiers and `%L` quotes literals, so a malicious name can't inject SQL (the previous lesson):

```sql shop
CREATE FUNCTION row_count(table_name text) RETURNS bigint
LANGUAGE plpgsql
AS $$
DECLARE n bigint;
BEGIN
  EXECUTE format('SELECT count(*) FROM %I', table_name) INTO n;
  RETURN n;
END;
$$;

SELECT t, row_count(t) FROM unnest(ARRAY['customers', 'orders', 'reviews']) AS t;
```

## Triggers

A **trigger** runs a function automatically **before** or **after** each `INSERT`, `UPDATE` or `DELETE` on a table. Classic uses: maintaining `updated_at` columns, audit logs, enforcing rules that constraints can't express, and keeping denormalized data in sync.

```sql shop
ALTER TABLE products ADD COLUMN updated_at timestamptz;

CREATE FUNCTION touch_updated_at() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at := timestamptz '2026-03-15 12:00+00';   -- in real code: now()
  RETURN NEW;
END;
$$;

CREATE TRIGGER products_touch
BEFORE UPDATE ON products
FOR EACH ROW EXECUTE FUNCTION touch_updated_at();

UPDATE products SET price = 26.99 WHERE id = 2;
SELECT id, name, price, updated_at FROM products WHERE id IN (1, 2);
```

In a row trigger, **`NEW`** is the row being written (a `BEFORE` trigger can change it) and **`OLD`** the row before the change. Returning `NULL` from a `BEFORE` trigger skips the change for that row.

An **audit log** with an `AFTER` trigger:

```sql shop
CREATE TABLE price_history (product_id integer, old_price numeric, new_price numeric, changed_at timestamptz DEFAULT now());

CREATE FUNCTION log_price_change() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF NEW.price IS DISTINCT FROM OLD.price THEN
    INSERT INTO price_history (product_id, old_price, new_price) VALUES (OLD.id, OLD.price, NEW.price);
  END IF;
  RETURN NULL;          -- the return value of an AFTER trigger is ignored
END;
$$;

CREATE TRIGGER products_price_history
AFTER UPDATE OF price ON products
FOR EACH ROW EXECUTE FUNCTION log_price_change();

UPDATE products SET price = price * 1.1 WHERE category_id = 7;
SELECT product_id, old_price, round(new_price, 2) AS new_price FROM price_history;
```

~~~check

+ Assign to NEW.column and RETURN NEW
- UPDATE the table again inside the trigger
- Assign to OLD.column
- Return the new value
> NEW is the row about to be stored.
~~~

## When to put logic in the database

Database code runs next to the data (no network round-trips) and applies to **every** program that uses the database. But it's harder to test, version and debug than application code, and it ties you to one database product. A balanced approach used by many teams:

- **constraints** for every rule the schema can express;
- **triggers** for small, mechanical jobs (timestamps, audit trails) that must never be forgotten;
- **functions** for reusable queries and calculations that benefit from running in the database;
- **business workflows** in application code, inside transactions.

Keep database code in migrations, like the schema.

## Cursors

Programs written in the 1980s and 1990s used **embedded SQL** (SQL written inside C or COBOL and translated by a precompiler) and processed results row by row through **cursors**. Cursors still exist: inside a transaction, `DECLARE c CURSOR FOR SELECT ...` then `FETCH 100 FROM c` reads a huge result in batches without loading it all into memory, and drivers use them for streaming. PL/pgSQL's `FOR row IN SELECT ... LOOP` uses a cursor behind the scenes.

## From code to database

Applications talk to databases through a **driver** (also called a client library): `psycopg` for Python, `pg` (node-postgres) or `postgres.js` for Node.js, JDBC for Java, Npgsql for C#, `pgx` for Go. They all work the same way: open a connection, send SQL with **parameters**, receive rows.

```
# Python, psycopg 3
import psycopg

with psycopg.connect(os.environ["DATABASE_URL"]) as conn:
    with conn.transaction():
        conn.execute("UPDATE accounts SET balance = balance - %s WHERE id = %s", (40, 1))
        conn.execute("UPDATE accounts SET balance = balance + %s WHERE id = %s", (40, 2))
    rows = conn.execute("SELECT owner, balance FROM accounts ORDER BY id").fetchall()
```

```
// TypeScript, node-postgres
const { rows } = await pool.query<{ id: number; name: string }>(
  "SELECT id, name FROM customers WHERE country = $1 ORDER BY name",
  [country],
);
```

Notice the three habits: parameters for every value, transactions for multi-step changes, and the connection URL from an environment variable.

## Connection pools

Opening a database connection takes time (tens of milliseconds) and each PostgreSQL connection is a server process using memory, so a server handles hundreds of connections, not tens of thousands. Applications therefore keep a **pool** of open connections and lend them to requests. Size it modestly (often 10 to 20 per application instance); for many instances or serverless functions, a pooler such as **PgBouncer** sits in between.

## ORMs and query builders

**ORMs** (object-relational mappers) map tables to classes: SQLAlchemy and Django ORM (Python), Prisma, Drizzle and TypeORM (TypeScript), Hibernate (Java), Entity Framework (C#), ActiveRecord (Ruby). **Query builders** (Knex, Kysely, jOOQ) build SQL from code without hiding it.

They save a lot of repetitive code and handle parameters for you, but they generate SQL you should still understand, because the classic performance bug is theirs to make: the **N+1 query problem**.

```
orders = Order.objects.all()            # 1 query
for order in orders:
    print(order.customer.name)          # 1 query per order: N more queries
```

With 1,000 orders that's 1,001 round-trips to the database instead of one join. Every ORM has a fix (`select_related`/`prefetch_related` in Django, `include` in Prisma, `joinedload` in SQLAlchemy, `JOIN FETCH` in Hibernate), and query logs or APM tools reveal the problem. Knowing SQL is what lets you notice it.

## Operating a database

Running a production database involves more than queries:

- **Backups**: `pg_dump` makes logical backups (SQL or a compact archive) of a database; physical backups with **point-in-time recovery** (continuous archiving of the write-ahead log, with tools like pgBackRest or a cloud provider's feature) let you restore to any moment, for example to just before a bad `DELETE`. A backup you've never restored is a hope, not a backup: test restores regularly.
- **Replication**: **streaming replicas** receive every change from the primary, giving a hot standby for failover and read-only copies for reports and analytics. Replication is asynchronous by default (a replica can lag slightly).
- **Scaling**: first, better queries and indexes; then bigger hardware ("vertical"), read replicas, caching (Redis), **partitioning** large tables by time or key (`PARTITION BY RANGE`), and finally **sharding** across servers (Citus, or application-level), which adds a lot of complexity. Distributed SQL databases (CockroachDB, YugabyteDB, Spanner) and two-phase commit (`PREPARE TRANSACTION`) handle transactions spanning machines.
- **Monitoring**: connections, slow queries (`pg_stat_statements`), replication lag, disk space, table bloat, and long-running transactions (which block VACUUM).
- **Upgrades** to new major versions with `pg_upgrade` or logical replication.

Managed services (AWS RDS and Aurora, Google Cloud SQL, Azure, Neon, Supabase) do much of this for you, but you still own the schema, queries, indexes and data.

## Analytics and data warehouses

Production databases are optimised for many small transactions (**OLTP**). Heavy analysis runs better elsewhere: a **data warehouse** (Snowflake, BigQuery, Redshift, ClickHouse, DuckDB) stores data in **columns** rather than rows, which makes scanning and aggregating billions of rows fast. Data is copied there regularly (**ETL/ELT** pipelines, often managed with dbt, which is mostly SQL), and modelled as **star schemas**: a central **fact** table of events (sales, page views) surrounded by **dimension** tables (date, product, customer, store). The SQL you've learned, especially joins, grouping, `ROLLUP` and window functions, is exactly what analysts write there. The analytics capstone practises it.

CREATE PROCEDURE place_order(p_order integer, p_customer integer, p_product integer, p_quantity integer)
LANGUAGE plpgsql
AS $$
BEGIN
  INSERT INTO orders (id, customer_id, ordered_at, status, shipping)
  VALUES (p_order, p_customer, timestamp '2026-03-20 09:00', 'pending', 4.99);

  INSERT INTO order_items (order_id, product_id, quantity, unit_price)
  SELECT p_order, id, p_quantity, price FROM products WHERE id = p_product;

  UPDATE products SET stock = stock - p_quantity
  WHERE id = p_product AND stock >= p_quantity;
  IF NOT FOUND THEN
    RAISE EXCEPTION 'not enough stock';
  END IF;
END;
$$;

CALL place_order(21, 1, 3, 2);

DO $$
BEGIN
  CALL place_order(22, 2, 12, 1);
EXCEPTION WHEN others THEN
  RAISE NOTICE '%', SQLERRM;
END;
$$;
