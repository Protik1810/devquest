=== module Capstone projects

=== lesson sql-capstone-design | Capstone 1: design and build a library database | 400
A public library wants to replace its spreadsheets with a database. In this capstone you go through the whole job a backend developer or database engineer does: turn requirements into a schema, load and query it, then put the library's rules into the database so no program can break them.

## The requirements

The librarian explains:

- "We have **books** (title, publication year, an ISBN that's unique). A book can have **several authors**, and an author writes several books."
- "For popular books we own several **copies**. Each copy has a barcode and a condition: `good`, `worn` or `damaged`."
- "**Members** have a name, a unique email and a membership date."
- "Members borrow **copies**, not books. A **loan** records the copy, the member, when it was borrowed, when it's due back, and when it was returned (empty while it's out)."
- "A copy can only be on one active loan at a time, and a member can have at most **3** active loans."

## How a task like this is approached

1. **Find the entities and relationships**: books, authors (many-to-many with books, so a junction table), copies (one book has many copies), members, loans (connecting a member and a copy).
2. **Choose keys and types**, and write every rule the schema can express as a constraint.
3. **Load realistic data** and check that the reports people need are easy to write.
4. **Rules that span rows** (one active loan per copy, three per member) need more than column constraints: a partial unique index and a function or trigger.
5. **Test the rules by trying to break them**, as the checker does.
--- goals
- turn written requirements into a normalized schema with keys and constraints
- model a many-to-many relationship with a junction table
- write reports with joins, outer joins and aggregation over the new schema
- enforce cross-row business rules with partial unique indexes and PL/pgSQL

**Step 1: the schema.** Create these tables, with exactly these names and columns (types are up to you, as long as they fit the data):

- `authors (id, name)`: name required;
- `books (id, title, published_year, isbn)`: title required; ISBN required and unique; the year, if given, between 1450 and 2100;
- `book_authors (book_id, author_id)`: the junction table, each pair at most once; deleting a book deletes its rows here;
- `copies (id, book_id, barcode, condition)`: barcode required and unique; condition required, one of `good`, `worn`, `damaged`, default `good`;
- `members (id, name, email, joined_on)`: name and email required, email unique, `joined_on` defaulting to today;
- `loans (id, copy_id, member_id, borrowed_on, due_on, returned_on)`: all required except `returned_on`; `due_on` after `borrowed_on`; `returned_on`, if set, not before `borrowed_on`. A copy or member with loans can't be deleted.

All `id` columns are integer primary keys that the database numbers automatically **unless an id is given** (use `GENERATED BY DEFAULT AS IDENTITY`). The checker inserts data and tries to break each rule.

       (SELECT string_agg(a.name, ', ' ORDER BY a.name)
        FROM book_authors ba JOIN authors a ON a.id = ba.author_id

CREATE UNIQUE INDEX loans_one_active_per_copy ON loans (copy_id) WHERE returned_on IS NULL;

CREATE FUNCTION check_loan_limit() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF NEW.returned_on IS NULL
     AND (SELECT count(*) FROM loans WHERE member_id = NEW.member_id AND returned_on IS NULL) >= 3 THEN
    RAISE EXCEPTION 'member % already has 3 active loans', NEW.member_id;
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER loans_limit
BEFORE INSERT ON loans
FOR EACH ROW EXECUTE FUNCTION check_loan_limit();
::reference
CREATE UNIQUE INDEX ON loans (copy_id) WHERE returned_on IS NULL;
CREATE FUNCTION check_loan_limit() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE active int;
BEGIN
  SELECT count(*) INTO active FROM loans WHERE member_id = NEW.member_id AND returned_on IS NULL;
  IF active >= 3 AND NEW.returned_on IS NULL THEN RAISE EXCEPTION 'member % already has 3 active loans', NEW.member_id; END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER loans_limit BEFORE INSERT ON loans FOR EACH ROW EXECUTE FUNCTION check_loan_limit();

--- cards
Requirements to schema :: Nouns become tables, facts become columns, many-to-many becomes a junction table, rules become constraints.
Partial unique index :: CREATE UNIQUE INDEX ... ON loans (copy_id) WHERE returned_on IS NULL — unique among active rows only.
Cross-row rules :: Limits like "at most 3 active loans" need a trigger (or a locked check in a transaction).
Breaking your own rules :: Test a schema by attempting every invalid change and checking it's rejected.

=== lesson sql-capstone-analytics | Capstone 2: business analytics | 400
The shop's managers want answers. In this capstone you work as a **data analyst**: you take business questions, turn them into precise definitions, and answer them with SQL, the daily work of analysts, data scientists and product engineers. The last step builds a small **star schema**, the shape data warehouses use.

## How analysts approach a question

1. **Pin down the definitions.** "Revenue" for whom: goods only, or with shipping? Are cancelled orders included? By order date or delivery date? Write the definition down; different answers to the same question usually come from different definitions.
2. **Check the grain**: what does one row of the answer represent (a month, a customer, a product per month)?
3. **Build in steps** with CTEs, checking each intermediate result.
4. **Sanity-check** totals against simple queries (does the monthly revenue add up to the total?).

In this capstone, **revenue** means the goods value (`quantity × unit_price`) of orders that **weren't cancelled**, counted in the month the order was placed.
--- goals
- turn business questions into precise SQL definitions
- build multi-step analyses with CTEs and window functions
- measure growth, retention and contribution
- reshape operational data into a star schema and summarise it with ROLLUP

::prompt
**Monthly revenue with growth.** For every month with non-cancelled orders, return `month` (first day of the month, as a date), `orders` (number of non-cancelled orders), `revenue`, `previous_revenue` (the previous month **in the list**, NULL for the first) and `growth_percent` (change from the previous month in percent, rounded to 1 decimal, NULL for the first). Order by month.
::dataset shop
::starter
SELECT date_trunc('month', ordered_at)::date AS month
FROM orders;
::solution
WITH monthly AS (
  SELECT date_trunc('month', o.ordered_at)::date AS month,
         count(DISTINCT o.id) AS orders,
         sum(oi.quantity * oi.unit_price) AS revenue
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status <> 'cancelled'
  GROUP BY 1
)
SELECT month, orders, revenue,
       lag(revenue) OVER (ORDER BY month) AS previous_revenue,
       round(100 * (revenue - lag(revenue) OVER (ORDER BY month)) / lag(revenue) OVER (ORDER BY month), 1) AS growth_percent
FROM monthly
ORDER BY month;
::reference
WITH r AS (SELECT o.id, date_trunc('month', o.ordered_at)::date AS month, (SELECT sum(quantity * unit_price) FROM order_items WHERE order_id = o.id) AS goods FROM orders o WHERE o.status <> 'cancelled'),
     m AS (SELECT month, count(*) AS orders, sum(goods) AS revenue FROM r GROUP BY month)
SELECT m.month, m.orders, m.revenue, p.revenue AS previous_revenue, round((m.revenue / p.revenue - 1) * 100, 1) AS growth_percent
FROM m LEFT JOIN LATERAL (SELECT revenue FROM m m2 WHERE m2.month < m.month ORDER BY m2.month DESC LIMIT 1) p ON true ORDER BY 1;
::ordered true
::hints
- Aggregate per month in a CTE first; count orders with `count(DISTINCT o.id)`, because joining the items repeats each order.
- `lag(revenue) OVER (ORDER BY month)` is the previous month's revenue.

**Repeat customers.** For each customer who has placed at least one non-cancelled order, return `name`, `first_order` (the date, as a date, of their first non-cancelled order), `orders` (non-cancelled orders), `lifetime_value` (their revenue) and `segment`: `loyal` with 3 or more orders, `returning` with 2, `one-time` with 1. Order by `lifetime_value` descending, then name.
::dataset shop
::starter
SELECT c.name
FROM customers c;
::solution
WITH per_order AS (
  SELECT o.id, o.customer_id, o.ordered_at, sum(oi.quantity * oi.unit_price) AS goods
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.status <> 'cancelled'
  GROUP BY o.id
),
per_customer AS (
  SELECT customer_id, min(ordered_at)::date AS first_order, count(*) AS orders, sum(goods) AS lifetime_value
  FROM per_order
  GROUP BY customer_id
)
SELECT c.name, p.first_order, p.orders, p.lifetime_value,
       CASE WHEN p.orders >= 3 THEN 'loyal' WHEN p.orders = 2 THEN 'returning' ELSE 'one-time' END AS segment
FROM per_customer p
JOIN customers c ON c.id = p.customer_id
ORDER BY p.lifetime_value DESC, c.name;
::reference
SELECT c.name, min(o.ordered_at)::date AS first_order, count(DISTINCT o.id) AS orders, sum(oi.quantity * oi.unit_price) AS lifetime_value,
       CASE count(DISTINCT o.id) WHEN 1 THEN 'one-time' WHEN 2 THEN 'returning' ELSE 'loyal' END AS segment
FROM customers c JOIN orders o ON o.customer_id = c.id AND o.status <> 'cancelled' JOIN order_items oi ON oi.order_id = o.id
GROUP BY c.id, c.name ORDER BY 4 DESC, 1;
::ordered true
::hints
- Compute each order's goods value first, then aggregate per customer: two CTEs keep the counting honest.
- `CASE WHEN orders >= 3 THEN 'loyal' WHEN orders = 2 THEN 'returning' ELSE 'one-time' END`.

::prompt
**Category contribution (Pareto).** Rank the **top-level** categories (Electronics, Home, Books; a product's top-level category is its category's parent, or the category itself if it has no parent) by revenue. Return `category`, `revenue`, `share_percent` (of total revenue, 1 decimal) and `cumulative_percent` (running share in revenue order, 1 decimal), ordered by revenue descending. Products without a category are left out.
::dataset shop
::starter
SELECT name FROM categories WHERE parent_id IS NULL;
::solution
WITH top_level AS (
  SELECT c.id, COALESCE(parent.name, c.name) AS category
  FROM categories c
  LEFT JOIN categories parent ON parent.id = c.parent_id
),
revenue AS (
  SELECT t.category, sum(oi.quantity * oi.unit_price) AS revenue
  FROM order_items oi
  JOIN orders o ON o.id = oi.order_id AND o.status <> 'cancelled'
  JOIN products p ON p.id = oi.product_id
  JOIN top_level t ON t.id = p.category_id
  GROUP BY t.category
)
SELECT category, revenue,
       round(100 * revenue / sum(revenue) OVER (), 1) AS share_percent,
       round(100 * sum(revenue) OVER (ORDER BY revenue DESC) / sum(revenue) OVER (), 1) AS cumulative_percent
FROM revenue
ORDER BY revenue DESC;
::reference
WITH RECURSIVE tree AS (SELECT id, name AS root FROM categories WHERE parent_id IS NULL UNION ALL SELECT c.id, t.root FROM categories c JOIN tree t ON c.parent_id = t.id),
r AS (SELECT t.root AS category, sum(oi.quantity * oi.unit_price) AS revenue FROM order_items oi JOIN orders o ON o.id = oi.order_id JOIN products p ON p.id = oi.product_id JOIN tree t ON t.id = p.category_id WHERE o.status <> 'cancelled' GROUP BY t.root)
SELECT category, revenue, round(revenue * 100 / (SELECT sum(revenue) FROM r), 1) AS share_percent,
       round((SELECT sum(revenue) FROM r r2 WHERE r2.revenue >= r.revenue) * 100 / (SELECT sum(revenue) FROM r), 1) AS cumulative_percent
FROM r ORDER BY 2 DESC;
::ordered true
::hints
- The categories are only two levels deep: `COALESCE(parent.name, c.name)` after a self join gives the top level (a recursive CTE works for any depth).
- Window functions over the per-category result give the shares: `sum(revenue) OVER ()` and `sum(revenue) OVER (ORDER BY revenue DESC)`.

=== lesson sql-capstone-solo | Capstone 3: build it from a spec | 450
As in the other courses, the last capstone gives you a **specification** and nothing else. You design the schema details and the code, test your own work, and submit. Hidden checks then test every rule.

## The product: meeting room bookings

A company wants a database for booking its meeting rooms. Applications of all kinds (a web app, a Slack bot, the reception desk's tablet) will use it, so **every rule must be enforced by the database itself**.

### Tables (names and columns are part of the spec)

- **`rooms (id, name, capacity, floor)`**: `name` required and unique; `capacity` a required integer of at least 1; `floor` a required integer.
- **`people (id, name, email)`**: both required; `email` unique **ignoring case** (`Ada@X.dev` and `ada@x.dev` are the same person).
- **`bookings (id, room_id, person_id, starts_at, ends_at, attendees, title)`**: `starts_at` and `ends_at` are required `timestamptz` values with `ends_at` after `starts_at`; `attendees` a required integer of at least 1; `title` required.

All `id` columns are integer primary keys, generated automatically when not given.

### Rules

1. A booking's room and person must exist. **Deleting a person deletes their bookings**; deleting a room that has bookings is **refused**.
2. A booking lasts **at most 8 hours**.
3. `attendees` may not exceed the room's `capacity`.
4. Bookings of the **same room** may not **overlap** (a booking ending at 10:00 and another starting at 10:00 don't overlap). Bookings of different rooms may.
5. Rules 3 and 4 also apply when a booking is **changed** (`UPDATE`), not only when it's created.

Rules 3 and 4 span tables or rows: use a trigger (in production PostgreSQL, rule 4 is usually an **exclusion constraint**, `EXCLUDE USING gist (room_id WITH =, tstzrange(starts_at, ends_at) WITH &&)`, which needs the `btree_gist` extension; DevQuest's PostgreSQL doesn't include extensions, so write a trigger).

### A function for the booking screen

**`free_rooms(p_from timestamptz, p_to timestamptz, p_attendees integer)`** returns a table `(name text, capacity integer, floor integer)` of the rooms that can hold `p_attendees` people and have **no booking overlapping** the period, ordered by `capacity`, then `name` (the smallest suitable room first).

## How to approach it

1. Write the three tables with every constraint you can express declaratively (rules 1 and 2, the case-insensitive email via a unique index on `lower(email)`).
2. Write one trigger function for rules 3 and 4, firing `BEFORE INSERT OR UPDATE`; raise an exception when a rule is broken.
3. Write `free_rooms` as a SQL function with `NOT EXISTS`.
4. Test with your own inserts: overlapping and touching bookings, a booking moved by an `UPDATE`, too many attendees, a 9-hour meeting.

📚 **Go deeper:** PostgreSQL documentation, "Range Types" and "Exclusion Constraints"; *SQL: The Complete Reference*, chapter 11 ("Business Rules").

CREATE TABLE bookings (
  id        integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  room_id   integer NOT NULL REFERENCES rooms (id) ON DELETE RESTRICT,
  person_id integer NOT NULL REFERENCES people (id) ON DELETE CASCADE,
  starts_at timestamptz NOT NULL,
  ends_at   timestamptz NOT NULL,
  attendees integer NOT NULL CHECK (attendees >= 1),
  title     text NOT NULL,
  CHECK (ends_at > starts_at),
  CHECK (ends_at - starts_at <= interval '8 hours')
);

CREATE FUNCTION check_booking() RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  IF NEW.attendees > (SELECT capacity FROM rooms WHERE id = NEW.room_id) THEN
    RAISE EXCEPTION 'room % holds fewer than % people', NEW.room_id, NEW.attendees;
  END IF;
  IF EXISTS (
    SELECT 1 FROM bookings b
    WHERE b.room_id = NEW.room_id
      AND b.id IS DISTINCT FROM NEW.id
      AND b.starts_at < NEW.ends_at
      AND NEW.starts_at < b.ends_at
  ) THEN
    RAISE EXCEPTION 'room % is already booked at that time', NEW.room_id;
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER bookings_check
BEFORE INSERT OR UPDATE ON bookings
FOR EACH ROW EXECUTE FUNCTION check_booking();

CREATE FUNCTION free_rooms(p_from timestamptz, p_to timestamptz, p_attendees integer)
RETURNS TABLE (name text, capacity integer, floor integer)
LANGUAGE sql STABLE
AS $$
  SELECT r.name, r.capacity, r.floor
  FROM rooms r
  WHERE r.capacity >= p_attendees
    AND NOT EXISTS (
      SELECT 1 FROM bookings b
      WHERE b.room_id = r.id AND b.starts_at < p_to AND p_from < b.ends_at
    )
  ORDER BY r.capacity, r.name
$$;
::reference
CREATE TABLE rooms (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, name text NOT NULL UNIQUE, capacity int NOT NULL CHECK (capacity > 0), floor int NOT NULL);
CREATE TABLE people (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, name text NOT NULL, email text NOT NULL);
CREATE UNIQUE INDEX ON people (lower(email));
CREATE TABLE bookings (id int GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY, room_id int NOT NULL REFERENCES rooms, person_id int NOT NULL REFERENCES people ON DELETE CASCADE, starts_at timestamptz NOT NULL, ends_at timestamptz NOT NULL CHECK (ends_at > starts_at AND ends_at <= starts_at + interval '8 hours'), attendees int NOT NULL CHECK (attendees > 0), title text NOT NULL);
CREATE FUNCTION bk() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  PERFORM 1 FROM rooms WHERE id = NEW.room_id AND capacity >= NEW.attendees;
  IF NOT FOUND THEN RAISE EXCEPTION 'too many attendees'; END IF;
  PERFORM 1 FROM bookings WHERE room_id = NEW.room_id AND id <> COALESCE(NEW.id, -1) AND tstzrange(starts_at, ends_at) && tstzrange(NEW.starts_at, NEW.ends_at);
  IF FOUND THEN RAISE EXCEPTION 'overlap'; END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER bk BEFORE INSERT OR UPDATE ON bookings FOR EACH ROW EXECUTE FUNCTION bk();
CREATE FUNCTION free_rooms(p_from timestamptz, p_to timestamptz, p_attendees int) RETURNS TABLE (name text, capacity int, floor int) LANGUAGE sql AS $$
  SELECT name, capacity, floor FROM rooms r WHERE capacity >= p_attendees AND id NOT IN (SELECT room_id FROM bookings WHERE tstzrange(starts_at, ends_at) && tstzrange(p_from, p_to)) ORDER BY capacity, name $$;

=== lesson sql-whats-next | What's next after SQL | 50
## You've learned SQL

You can now query data precisely (filtering, `NULL` logic, sorting, functions and dates), summarise it (aggregates, `GROUP BY`, `FILTER`, `ROLLUP`), combine tables (joins, subqueries, set operations), design databases that protect themselves (types, constraints, normalization, migrations), write the advanced queries analysts and engineers use daily (CTEs, recursion, window functions, views, JSON), and run SQL in production (transactions, indexes and plans, the catalog, security, functions and triggers, drivers and operations). That covers what most developers ever need, and more than many use.

## Where to go from here

- **Use it from code**: connect the database to a Python, JavaScript or TypeScript project with a driver, then try an ORM (SQLAlchemy, Prisma, Drizzle) and watch the SQL it generates.
- **Run a real server**: install PostgreSQL locally or with Docker, load a public dataset (the "Pagila" DVD rental database, or open government data), and practise `EXPLAIN ANALYZE` on bigger tables.
- **Specialise**: DevQuest's **PostgreSQL** and **MySQL** tracks cover each product's specifics; the **MongoDB** and **Redis** tracks show the NoSQL side; the System Design track covers replication, sharding and caching at scale.
- **Analytics and data engineering**: dbt, DuckDB, and a cloud warehouse (BigQuery or Snowflake have free tiers); the Data & AI career path builds on this course.
- **Other languages**: DevQuest teaches one language at a time. Next in the order is **Java**, whose JDBC and JPA/Hibernate will look familiar now.

## Keep your skills alive

- Before writing a complex query, write down what one result row means and how each number is defined.
- Read the plan (`EXPLAIN ANALYZE`) of any query that runs often, and check your indexes.
- Put every rule the database can enforce into the schema.
- Never concatenate user input into SQL.
