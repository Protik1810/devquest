## CREATE TABLE

A table is defined with **`CREATE TABLE`**: its name, then each column's name, **type** and optional **constraints**:

```sql empty
CREATE TABLE books (
  id         integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title      text NOT NULL,
  isbn       char(13) UNIQUE,
  pages      integer,
  price      numeric(8, 2) NOT NULL DEFAULT 0,
  published  date,
  in_print   boolean NOT NULL DEFAULT true,
  added_at   timestamptz NOT NULL DEFAULT now()
);

INSERT INTO books (title, isbn, pages, price, published)
VALUES ('The Pragmatic Programmer', '9780135957059', 352, 44.95, '2019-09-13');

SELECT * FROM books;
```

- **`GENERATED ALWAYS AS IDENTITY`** makes the database number the rows (1, 2, 3...). It's the standard form; older PostgreSQL code uses `serial`, MySQL `AUTO_INCREMENT`, SQL Server `IDENTITY(1,1)`.
- **`DEFAULT`** gives a value when an `INSERT` doesn't provide one.
- Constraints (`NOT NULL`, `UNIQUE`, `PRIMARY KEY`) are the next lesson's subject.

`DROP TABLE books;` deletes a table and all its data, immediately and without a recycle bin: in production, think twice. `CREATE TABLE IF NOT EXISTS` and `DROP TABLE IF EXISTS` avoid errors in setup scripts.

## Choosing types

The type of a column is a promise about every value it will ever hold. Choosing well prevents bad data and wasted space:

| Data | Type | Notes |
|---|---|---|
| whole numbers | `integer` (±2.1 billion), `bigint` (±9.2 × 10¹⁸), `smallint` | ids of busy tables need `bigint` |
| money, exact decimals | `numeric(p, s)` | `numeric(10, 2)`: 10 digits, 2 after the point. Exact. |
| measurements, science | `double precision` (`float8`), `real` | **approximate**: never for money |
| text | `text`, `varchar(n)`, `char(n)` | in PostgreSQL `text` is as fast as `varchar`; use `varchar(n)` only when a limit is a real rule. `char(n)` pads with spaces |
| yes/no | `boolean` | `true`, `false` (and `NULL`) |
| dates and times | `date`, `timestamptz`, `interval` | Module 2 |
| identifiers from elsewhere | `uuid` | `gen_random_uuid()` makes one |
| documents | `jsonb` | Module 6 |
| binary data | `bytea` | files usually belong in object storage, with only their path in the database |

Why not floats for money? Binary floating point can't represent most decimals exactly:

```sql empty
SELECT 0.1::double precision + 0.2::double precision AS float_sum,
       0.1::numeric + 0.2::numeric AS numeric_sum,
       (0.1::double precision + 0.2::double precision) = 0.3 AS float_equal;
```

The float sum is `0.30000000000000004`, so equality fails. `numeric` is exact (but slower, which never matters for money).

PostgreSQL also has types few databases offer: arrays (`text[]`), ranges (`daterange`), network addresses (`inet`), geometric types, and user-defined enums and composite types (Module 6).

## Naming conventions

- `snake_case`, lower case, no quotes: `order_items`, `created_at`;
- tables in the plural (`customers`) or singular (`customer`): pick one per project (this course uses plural);
- `id` for the primary key, `<thing>_id` for foreign keys (`customer_id`);
- timestamps as `<event>_at` (`shipped_at`), dates as `<event>_on`, booleans as `is_x`/`has_x` or an adjective (`in_print`);
- avoid reserved words (`user`, `order`, `group`).

## Creating tables from queries

`CREATE TABLE ... AS SELECT` creates a table from a query's result (handy for snapshots and reports, though it copies no constraints):

```sql shop
CREATE TABLE uk_customers AS
SELECT id, name, city FROM customers WHERE country = 'UK';

SELECT * FROM uk_customers;
```

**Temporary tables** (`CREATE TEMP TABLE`) disappear at the end of the session, which suits intermediate results in long scripts.

## Rules the database enforces

Application code has bugs, data gets imported from spreadsheets, and several programs often share one database. **Constraints** are rules the database itself enforces on every change, whoever makes it, so bad data simply can't get in. They're the last line of defence, and the most reliable one.

| Constraint | Rule | Error code when broken |
|---|---|---|
| `NOT NULL` | a value is required | 23502 |
| `UNIQUE` | no two rows have the same value(s) | 23505 |
| `PRIMARY KEY` | `UNIQUE` + `NOT NULL`: the row's identity | 23505 / 23502 |
| `FOREIGN KEY` | the value must exist in another table | 23503 |
| `CHECK (condition)` | the condition must not be false | 23514 |

The shop database is full of them. Try breaking each rule:

```sql shop
-- error: violates the foreign key (there is no customer 99)
INSERT INTO orders (id, customer_id, ordered_at, status) VALUES (100, 99, now(), 'pending');
```

```sql shop
-- error: violates the CHECK constraint on status
INSERT INTO orders (id, customer_id, ordered_at, status) VALUES (100, 1, now(), 'lost');
```

```sql shop
-- error: violates the UNIQUE constraint on email
UPDATE customers SET email = 'ada@example.com' WHERE id = 2;
```

Read the `DETAIL` line of each error: PostgreSQL names the constraint and the offending value.

## Declaring constraints

Constraints can be written on a column, or separately at the end of the table (needed when they involve several columns). Giving them **names** makes errors and later changes clearer:

```sql empty
CREATE TABLE members (
  id       integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email    text NOT NULL UNIQUE,
  nickname text NOT NULL,
  born_on  date CHECK (born_on > '1900-01-01'),
  club     text NOT NULL,
  CONSTRAINT members_nickname_per_club UNIQUE (club, nickname)
);

INSERT INTO members (email, nickname, club) VALUES ('a@x.dev', 'ace', 'chess'), ('b@x.dev', 'ace', 'go');
SELECT * FROM members;
```

`UNIQUE (club, nickname)` allows the same nickname in different clubs, but not twice in one club.

A subtlety: `UNIQUE` allows several `NULL`s, because `NULL`s aren't equal to each other. (PostgreSQL 15 added `UNIQUE NULLS NOT DISTINCT` when you want at most one.) And a `CHECK` passes when its condition is **unknown**: `CHECK (born_on > '1900-01-01')` accepts a `NULL` birth date. Combine it with `NOT NULL` when the value is required.

## Foreign keys and what happens on delete

A foreign key decides what happens when the referenced row is deleted or its key changes:

| Option | When the customer is deleted, their orders... |
|---|---|
| `ON DELETE NO ACTION` / `RESTRICT` (default) | ...block the delete (error 23503) |
| `ON DELETE CASCADE` | ...are deleted too |
| `ON DELETE SET NULL` | ...keep existing, with `customer_id` set to NULL |
| `ON DELETE SET DEFAULT` | ...get the column's default |

```sql empty
CREATE TABLE authors (id integer PRIMARY KEY, name text NOT NULL);
CREATE TABLE posts (
  id        integer PRIMARY KEY,
  author_id integer NOT NULL REFERENCES authors (id) ON DELETE CASCADE,
  title     text NOT NULL
);
INSERT INTO authors VALUES (1, 'Ada'), (2, 'Grace');
INSERT INTO posts VALUES (1, 1, 'Notes'), (2, 1, 'Poetry'), (3, 2, 'Bugs');

DELETE FROM authors WHERE id = 1;
SELECT * FROM posts;
```

Choose deliberately: `CASCADE` suits data that only makes sense with its parent (an order's items), `RESTRICT` protects important history (orders of a customer), and `SET NULL` keeps rows whose link is optional. Index foreign key columns too (Module 7): PostgreSQL doesn't do it automatically, and deletes on the parent need it.

## Constraints and business rules

Constraints express rules that can be checked **on one row** (CHECK), between rows of one table (UNIQUE) or between tables (FOREIGN KEY). Rules that need more ("an order can't contain more items than are in stock", "a room can't be double-booked") need other tools: PostgreSQL's **exclusion constraints** (`EXCLUDE USING gist (room WITH =, during WITH &&)` prevents overlapping bookings), triggers (Module 7), or application logic inside transactions. A practical rule: put every rule the database **can** enforce into the schema, and only the rest into code.

=== lesson sql-write | Changing data: INSERT, UPDATE, DELETE | 80
## INSERT

```sql shop
INSERT INTO customers (id, name, email, city, country, joined_on)
VALUES (13, 'Frances Allen', 'fran@example.com', 'Schenectady', 'US', '2026-03-10');

SELECT * FROM customers WHERE id = 13;
```

Always **list the columns**: the statement then keeps working when columns are added, and columns you leave out get their default (or `NULL`). Several rows can go in one statement, which is much faster than one statement per row:

```sql shop
INSERT INTO categories (id, name, parent_id)
VALUES (8, 'Garden', NULL), (9, 'Tools', 8);

SELECT * FROM categories ORDER BY id;
```

`INSERT ... SELECT` copies the result of a query into a table:

```sql shop
CREATE TABLE vip_customers (customer_id integer PRIMARY KEY, since date NOT NULL);

INSERT INTO vip_customers (customer_id, since)
SELECT customer_id, min(ordered_at)::date
FROM orders
GROUP BY customer_id
HAVING count(*) >= 3;

SELECT * FROM vip_customers;
```

## RETURNING

PostgreSQL's **`RETURNING`** clause returns rows from `INSERT`, `UPDATE` and `DELETE`, typically to get generated ids without a second query:

```sql empty
CREATE TABLE notes (id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY, body text NOT NULL, created_at timestamptz NOT NULL DEFAULT now());

INSERT INTO notes (body) VALUES ('first'), ('second') RETURNING id, body;
```

(SQL Server has `OUTPUT`; MySQL has `LAST_INSERT_ID()`; SQLite and MariaDB support `RETURNING` too.)

## UPDATE

```sql shop
UPDATE products
SET price = round(price * 0.9, 2), stock = stock + 5
WHERE category_id = 5
RETURNING name, price, stock;
```

`SET` lists the new values, which can use the old ones (`stock + 5`). **`WHERE` decides which rows change.** Without it, **every row** changes:

```sql shop
-- Oops: no WHERE. Every customer is now in London.
UPDATE customers SET city = 'London';
SELECT DISTINCT city FROM customers;
```

That mistake is famous for a reason. Habits that prevent it: write the `WHERE` first; run the same `WHERE` in a `SELECT` before updating; work inside a transaction you can roll back (Module 7); and never run ad-hoc updates on production without a reviewed script.

To update using values from another table, PostgreSQL has `UPDATE ... FROM` (SQL Server is similar; MySQL uses `UPDATE ... JOIN`):

```sql shop
-- Mark products as discontinued (stock 0) if they belong to the Books category
UPDATE products p
SET stock = 0
FROM categories c
WHERE c.id = p.category_id AND c.name = 'Books'
RETURNING p.name, p.stock;
```

## DELETE

```sql shop
DELETE FROM reviews
WHERE rating <= 2
RETURNING id, product_id, rating;
```

The same warning applies: `DELETE FROM reviews;` with no `WHERE` empties the table. **`TRUNCATE reviews;`** empties a table much faster (it doesn't go row by row), which suits staging tables, not everyday work. Related rows elsewhere are protected by foreign keys: deleting a customer who has orders fails unless the foreign key cascades.

Many applications never really delete important rows: they **soft delete** by setting a `deleted_at` timestamp and filtering it out, which keeps history and allows undo.

## Upsert: INSERT ... ON CONFLICT

"Insert this row, or update it if it already exists" is called an **upsert**. PostgreSQL (and SQLite) write it as `INSERT ... ON CONFLICT`:

```sql shop
INSERT INTO products (id, name, category_id, price, stock, added_on)
VALUES (2, 'Wireless Mouse', 2, 22.99, 10, '2025-03-15'),
       (16, 'USB-C Hub', 2, 34.50, 25, '2026-03-12')
ON CONFLICT (id) DO UPDATE
SET price = excluded.price,
    stock = products.stock + excluded.stock
RETURNING id, name, price, stock;
```

`ON CONFLICT (id)` names the unique column that may clash; `excluded` is the row that couldn't be inserted. Product 2 is updated (new price, stock added); product 16 is inserted. `ON CONFLICT DO NOTHING` simply skips duplicates. (MySQL: `INSERT ... ON DUPLICATE KEY UPDATE`.)

The standard SQL statement for the same job is **`MERGE`** (PostgreSQL 15+, SQL Server, Oracle), which compares a source with a target and says what to do for matched and unmatched rows:

```sql shop
MERGE INTO products AS p
USING (VALUES (9, 25.00), (99, 10.00)) AS changes (id, new_price)
ON p.id = changes.id
WHEN MATCHED THEN UPDATE SET price = changes.new_price
WHEN NOT MATCHED THEN DO NOTHING
RETURNING merge_action(), p.name, p.price;
```

Unlike a read-then-write in application code ("SELECT; if missing INSERT else UPDATE"), an upsert is **atomic**: two requests arriving at the same moment can't both insert.

=== lesson sql-design | Designing a database: normalization | 80
## From a spreadsheet to tables

Most databases start as someone's spreadsheet. Here's one for a training company, as a table:

```sql empty
CREATE TABLE bookings_sheet (
  booking_id int, student text, student_email text, course text, course_fee numeric, trainer text, trainer_phone text, booked_on date
);
INSERT INTO bookings_sheet VALUES
  (1, 'Ada', 'ada@x.dev', 'SQL Basics', 300, 'Edgar', '555-0101', '2026-02-01'),
  (2, 'Ada', 'ada@x.dev', 'Advanced SQL', 450, 'Edgar', '555-0101', '2026-03-01'),
  (3, 'Bob', 'bob@x.dev', 'SQL Basics', 300, 'Edgar', '555-0101', '2026-02-03'),
  (4, 'Cy', 'cy@x.dev', 'Data Modelling', 400, 'Margaret', '555-0199', '2026-02-10');
SELECT * FROM bookings_sheet;
```

It works, until it doesn't:

- **Update anomaly**: Edgar's phone number is stored three times; change one and the data contradicts itself.
- **Insertion anomaly**: you can't record a new course until someone books it (there's no row to put it in).
- **Deletion anomaly**: delete Cy's booking and you lose the fact that Margaret teaches Data Modelling.

**Normalization** is the process of splitting tables so that every fact is stored **once**, which removes these anomalies.

## The normal forms

The rules are called **normal forms**. In practice, aim for the third:

- **First normal form (1NF)**: every column holds **one** value (no lists like `'SQL, Python'` in a cell, no `phone1`, `phone2`, `phone3` columns), and every row is unique (it has a key).
- **Second normal form (2NF)**: in a table with a composite key, every column depends on the **whole** key, not part of it. In an `enrolments(student_id, course_id, course_fee)` table, the fee depends on the course alone: it belongs in `courses`.
- **Third normal form (3NF)**: no column depends on another **non-key** column. In `courses(id, name, trainer, trainer_phone)`, the phone depends on the trainer, not on the course: it belongs in `trainers`.

A memorable summary (from Bill Kent): every non-key column must provide a fact about **the key, the whole key, and nothing but the key**. (Boyce-Codd normal form, BCNF, tightens 3NF for some rare cases with several overlapping candidate keys.)

## The normalized design

Each **thing** (entity) gets a table, and relationships become foreign keys:

```sql empty
CREATE TABLE trainers (id integer PRIMARY KEY, name text NOT NULL, phone text);
CREATE TABLE courses  (id integer PRIMARY KEY, name text NOT NULL UNIQUE, fee numeric(8, 2) NOT NULL,
                       trainer_id integer NOT NULL REFERENCES trainers (id));
CREATE TABLE students (id integer PRIMARY KEY, name text NOT NULL, email text NOT NULL UNIQUE);
CREATE TABLE bookings (id integer PRIMARY KEY,
                       student_id integer NOT NULL REFERENCES students (id),
                       course_id integer NOT NULL REFERENCES courses (id),
                       booked_on date NOT NULL,
                       UNIQUE (student_id, course_id));

SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' ORDER BY table_name;
```

Edgar's phone is now stored once; a course can exist without bookings; deleting a booking deletes only the booking. A join (or a **view**, Module 6) rebuilds the spreadsheet whenever someone wants it.

## A design process

1. **List the things** the system is about (nouns in the requirements: student, course, trainer, booking).
2. **List their facts** (attributes), and choose a key for each.
3. **Find the relationships** and their cardinality (one-to-many, many-to-many), adding junction tables for many-to-many.
4. **Check the normal forms**: does any column describe something other than its table's key?
5. **Add the rules** as constraints (Module 5): required values, uniqueness, valid ranges.
6. **Test it with real questions**: can every report and screen be built with joins?

## When to denormalize

Normalization optimises for **correct writes**. Sometimes reads matter more, and you deliberately store a fact twice: a cached `order_total` on `orders`, a counter of reviews on `products`, a reporting table rebuilt nightly. That's **denormalization**, and it's legitimate when you know what you're trading: you must keep the copies in sync (with triggers, application code or materialized views, Modules 6 and 7). Note that `order_items.unit_price` in the shop **isn't** a denormalization: the price at the time of the order is a different fact from the product's current price.

=== lesson sql-alter | Changing a schema: ALTER TABLE and migrations | 65
## Schemas evolve

Applications change, and their tables must change with them, usually while the database is full of data and in use. **`ALTER TABLE`** changes an existing table:

```sql shop
ALTER TABLE customers ADD COLUMN phone text;
ALTER TABLE customers ADD COLUMN marketing_opt_in boolean NOT NULL DEFAULT false;
ALTER TABLE products RENAME COLUMN added_on TO listed_on;
ALTER TABLE products ALTER COLUMN stock SET DEFAULT 10;
ALTER TABLE products ADD CONSTRAINT products_name_unique UNIQUE (name);

SELECT column_name, data_type, column_default
FROM information_schema.columns
WHERE table_name IN ('customers', 'products')
ORDER BY table_name, ordinal_position;
```

| Change | Statement |
|---|---|
| add a column | `ADD COLUMN name type [constraints]` |
| remove a column | `DROP COLUMN name` (its data is gone) |
| rename | `RENAME COLUMN a TO b`, `RENAME TO new_table` |
| change a type | `ALTER COLUMN c TYPE new_type [USING expression]` |
| defaults | `ALTER COLUMN c SET DEFAULT x` / `DROP DEFAULT` |
| required | `ALTER COLUMN c SET NOT NULL` / `DROP NOT NULL` |
| constraints | `ADD CONSTRAINT name ...` / `DROP CONSTRAINT name` |

Adding a `NOT NULL` column to a table with rows needs a default (or the existing rows would break the rule). Changing a type converts every value, with `USING` for conversions PostgreSQL can't guess:

```sql shop
ALTER TABLE orders ALTER COLUMN status TYPE varchar(12);
ALTER TABLE customers ALTER COLUMN joined_on TYPE timestamptz USING joined_on::timestamptz;
SELECT name, joined_on FROM customers LIMIT 3;
```

## Backfilling data

A new required column is often added in three steps: add it as nullable, fill it in (**backfill**), then make it required:

```sql shop
ALTER TABLE orders ADD COLUMN items_count integer;

UPDATE orders o
SET items_count = (SELECT coalesce(sum(quantity), 0) FROM order_items oi WHERE oi.order_id = o.id);

ALTER TABLE orders ALTER COLUMN items_count SET NOT NULL;
SELECT id, items_count FROM orders ORDER BY id LIMIT 5;
```

## Migrations

In a team, schema changes are never typed by hand into production. They're written as **migrations**: numbered SQL files (or code) kept in Git, applied in order by a tool that records which ones already ran:

```
migrations/
  0001_create_customers.sql
  0002_create_orders.sql
  0003_add_phone_to_customers.sql
```

Tools include Flyway and Liquibase (any language), Alembic (Python), Prisma Migrate and Knex (Node.js), Rails and Django migrations. Every developer's database, the test database and production all get the same changes in the same order. Good migrations:

- are **small** and do one thing;
- are **never edited** after they've run anywhere (fix mistakes with a new migration);
- are tested on a copy of production data when they touch big tables;
- come with a way back when possible ("down" migrations), although on real data the honest fix is often a new forward migration.

## Changing a live database safely

Some changes lock a table or break the running application. Renaming a column, for example, breaks every query of the old code still running during a deployment. The safe pattern is **expand and contract**:

1. **Expand**: add the new column (or table) next to the old one; the code writes to both.
2. **Migrate**: backfill old rows; switch reads to the new column.
3. **Contract**: once no code uses the old column, drop it in a later release.

Also be careful with operations that rewrite or lock a big table (changing a type, adding a constraint that must check every row): PostgreSQL offers gentler forms, such as adding a constraint `NOT VALID` and validating it later, and `CREATE INDEX CONCURRENTLY` (Module 7).

~~~check

~~~
