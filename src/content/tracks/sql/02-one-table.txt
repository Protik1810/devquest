=== lesson sql-where | Filtering rows: WHERE | 60
## Choosing rows

`SELECT` chooses columns; **`WHERE`** chooses rows. It keeps only the rows for which a condition is true:

```sql shop
SELECT name, price
FROM products
WHERE price < 50;
```

Comparison operators:

| Operator | Means |
|---|---|
| `=` | equal (one `=`, not two) |
| `<>` or `!=` | not equal (`<>` is the standard form) |
| `<`, `<=`, `>`, `>=` | less, less or equal, greater, greater or equal |

They work on numbers, text (alphabetical order) and dates:

```sql shop
SELECT name, joined_on
FROM customers
WHERE joined_on >= '2025-09-01';
```

The date is written as a string in ISO format (`'YYYY-MM-DD'`); PostgreSQL converts it to a date because it's compared with a date column.

## Combining conditions: AND, OR, NOT

```sql shop
SELECT name, price, stock
FROM products
WHERE price < 100 AND stock > 0;
```

`AND` needs both conditions to be true; `OR` needs at least one; `NOT` reverses a condition. When you mix `AND` and `OR`, **`AND` is evaluated first**, exactly like `*` before `+` in arithmetic. That causes real bugs:

```sql shop
-- Intended: cheap products in category 2 or 3. Actually: (category 2) OR (category 3 AND cheap)
SELECT name, category_id, price
FROM products
WHERE category_id = 2 OR category_id = 3 AND price < 100;
```

The Laptop costs 1299, yet it's in the result. Add parentheses to say what you mean:

```sql shop
SELECT name, category_id, price
FROM products
WHERE (category_id = 2 OR category_id = 3) AND price < 100;
```

Whenever a condition mixes `AND` and `OR`, use parentheses, even when they aren't needed: the next reader will thank you.

## Shortcuts: IN and BETWEEN

```sql shop
SELECT name, country
FROM customers
WHERE country IN ('NL', 'AT');
```

`IN (list)` means "equal to any of these", and replaces a chain of `OR`s. `NOT IN` is the opposite (but beware of `NULL` in the list, next lesson).

```sql shop
SELECT name, price
FROM products
WHERE price BETWEEN 40 AND 60;
```

`BETWEEN a AND b` includes **both ends**: it means `price >= 40 AND price <= 60`. For dates and times, a half-open range is usually safer: `ordered_at >= '2026-01-01' AND ordered_at < '2026-02-01'` catches every moment of January, while `BETWEEN '2026-01-01' AND '2026-01-31'` misses everything after midnight on the 31st when the column is a timestamp.

## Pattern matching: LIKE and ILIKE

`LIKE` compares text with a pattern, where `%` matches any sequence of characters (including none) and `_` matches exactly one character:

```sql shop
SELECT name FROM products WHERE name LIKE '%Mouse%';
```

| Pattern | Matches |
|---|---|
| `'A%'` | starts with A |
| `'%er'` | ends with er |
| `'%o%'` | contains o |
| `'_a%'` | a as the second letter |

`LIKE` is case-sensitive in PostgreSQL; **`ILIKE`** is the case-insensitive version (PostgreSQL only; elsewhere write `LOWER(name) LIKE '%mouse%'`). For complex patterns, PostgreSQL also supports **regular expressions** with `~` (and `~*` ignoring case), the same regex language you met in the Python and JavaScript courses:

```sql shop
SELECT name, email FROM customers WHERE email ~ '^[a-g]';
```

~~~check
? Which condition finds products whose name contains "desk" in any capitalisation?
- `name = '%desk%'`
- `name LIKE 'desk'`
+ `name ILIKE '%desk%'`
- `name IN ('desk')`
> % wildcards only work with LIKE/ILIKE; ILIKE ignores case.
~~~

## How a query is processed

It helps to know the order in which the database logically handles the clauses you've seen, which is **not** the order you write them:

1. `FROM`: take the table;
2. `WHERE`: keep the matching rows;
3. `SELECT`: compute the output columns;
4. `ORDER BY` and `LIMIT` (next lessons).

That's why you **can't** use a `SELECT` alias in `WHERE`: when `WHERE` runs, the alias doesn't exist yet.

```sql shop
-- error: the alias doesn't exist when WHERE runs (fix: WHERE price * stock > 5000)
SELECT name, price * stock AS stock_value
FROM products
WHERE stock_value > 5000;
```

=== lesson sql-null | NULL and three-valued logic | 65
## NULL means "unknown"

Some values are missing: Linus Torvalds has no email address in the shop database, and one customer has no city. SQL represents a missing or unknown value with **`NULL`**:

```sql shop
SELECT name, email, city FROM customers WHERE id IN (5, 10, 11);
```

`NULL` isn't zero, an empty string or `false`. It's the absence of a value, and that has surprising consequences.

## Comparisons with NULL are unknown

What is `NULL = 'London'`? We don't know the city, so we can't say: the answer is neither true nor false but **unknown** (which SQL also writes as `NULL`). Even `NULL = NULL` is unknown: two unknown values aren't known to be equal.

```sql empty
SELECT NULL = 1 AS a, NULL = NULL AS b, NULL <> 1 AS c, 1 + NULL AS d, 'x' || NULL AS e;
```

All five results are `NULL`. **Almost any expression involving `NULL` gives `NULL`.**

And `WHERE` only keeps rows where the condition is **true**: unknown rows are dropped. So this finds nobody, even though two customers have no email:

```sql shop
SELECT name FROM customers WHERE email = NULL;
```

To test for missing values, SQL has special operators:

```sql shop
SELECT name FROM customers WHERE email IS NULL;
```

`IS NULL` and `IS NOT NULL` always give true or false, never unknown.

## Three-valued logic

Because conditions can be true, false or unknown, SQL uses **three-valued logic**:

| `a` | `b` | `a AND b` | `a OR b` | `NOT a` |
|---|---|---|---|---|
| true | unknown | unknown | **true** | false |
| false | unknown | **false** | unknown | true |
| unknown | unknown | unknown | unknown | unknown |

The rule of thumb: if the answer could go either way depending on the unknown value, it's unknown; if it's decided regardless (`false AND anything`, `true OR anything`), it's decided.

The classic trap: rows with `NULL` disappear from **both** a condition and its opposite.

```sql shop
SELECT
  (SELECT count(*) FROM customers WHERE city = 'London') AS in_london,
  (SELECT count(*) FROM customers WHERE city <> 'London') AS not_in_london,
  (SELECT count(*) FROM customers) AS everyone;
```

2 + 9 is 11, but there are 12 customers: the customer with no city is in neither group. If "not in London" should include unknown cities, say so: `WHERE city <> 'London' OR city IS NULL`, or use PostgreSQL's (and the standard's) `city IS DISTINCT FROM 'London'`, which treats `NULL` as an ordinary comparable value.

~~~

## The NOT IN trap

`NOT IN` with a list containing `NULL` returns **no rows at all**: `x NOT IN (1, NULL)` means `x <> 1 AND x <> NULL`, and `x <> NULL` is always unknown.

```sql shop
SELECT name FROM products WHERE category_id NOT IN (2, 3, NULL);
```

This bites hardest with subqueries (`NOT IN (SELECT ...)`) when the subquery can return a `NULL`. Module 4 shows the safe alternative, `NOT EXISTS`.

## Replacing NULL: COALESCE and NULLIF

**`COALESCE(a, b, ...)`** returns the first argument that isn't `NULL`. It's how you show a default:

```sql shop
SELECT name,
       COALESCE(email, '(no email)') AS email,
       COALESCE(city, 'unknown city') AS city
FROM customers;
```

**`NULLIF(a, b)`** does the opposite: it returns `NULL` when `a = b`. Its classic use is avoiding division by zero, because dividing by `NULL` gives `NULL` instead of an error:

```sql shop
SELECT name, price, stock, round(price / NULLIF(stock, 0), 2) AS price_per_unit_in_stock
FROM products;
```

## Where NULLs come from, and when to allow them

`NULL` appears when a column has no value (an optional email), when outer joins find no match (Module 4), and from aggregates over no rows (Module 3). Good table design (Module 5) decides deliberately which columns may be `NULL`: allow it only when "unknown" or "not applicable" is a real possibility, and mark everything else `NOT NULL`.

=== lesson sql-sorting | Sorting and paging | 55
## ORDER BY

Rows in a table have **no order**. Without `ORDER BY`, a database returns rows in whatever order is convenient, and that order can change from one run to the next (as data changes, or when the planner picks another plan). If the order matters, say so:

```sql shop
SELECT name, price
FROM products
ORDER BY price;
```

`ASC` (ascending, the default) and `DESC` (descending) set the direction for each column. With several columns, later ones break ties:

```sql shop
SELECT name, country, joined_on
FROM customers
ORDER BY country, joined_on DESC;
```

Customers are grouped by country (A to Z), and within each country the most recent first.

You can sort by an expression or by a `SELECT` alias (unlike `WHERE`, `ORDER BY` runs **after** `SELECT`):

```sql shop
SELECT name, price * stock AS stock_value
FROM products
ORDER BY stock_value DESC;
```

## Where do NULLs go?

In PostgreSQL, `NULL`s sort as if they were larger than every value: last in ascending order, first in descending order. You can choose explicitly:

```sql shop
SELECT name, city
FROM customers
ORDER BY city NULLS FIRST;
```

Databases disagree here (MySQL and SQL Server put `NULL`s first in ascending order), so write `NULLS FIRST` or `NULLS LAST` whenever it matters.

## LIMIT and OFFSET

**`LIMIT n`** returns at most `n` rows, which together with `ORDER BY` answers "top N" questions:

```sql shop
SELECT name, price
FROM products
ORDER BY price DESC
LIMIT 3;
```

`LIMIT` without `ORDER BY` returns some arbitrary rows: almost always a bug.

**`OFFSET n`** skips rows first, which gives simple **pagination**: page 3 with 5 rows per page is `LIMIT 5 OFFSET 10`.

```sql shop
SELECT id, name
FROM products
ORDER BY id
LIMIT 5 OFFSET 10;
```

The standard SQL spelling is `OFFSET 10 ROWS FETCH FIRST 5 ROWS ONLY`, which PostgreSQL, Oracle and SQL Server understand. SQL Server also has `SELECT TOP 5 ...`, and older Oracle code uses `ROWNUM`.

~~~check
? Why is `SELECT * FROM products LIMIT 5` without ORDER BY a problem?
- It returns an error
+ Which 5 rows come back isn't defined and can change between runs
- It always returns the last 5 rows
- LIMIT needs OFFSET
> Tables are unordered; only ORDER BY defines an order.
~~~

## Ties and stable pages

If two rows have the same sort value, their relative order isn't defined either, so a page boundary can fall between them differently each time: a row can appear on two pages, or on none. Make the order **unique** by adding a tie-breaker, usually the primary key:

```sql shop
SELECT name, price
FROM products
ORDER BY price DESC, id;
```

## Keyset pagination

`OFFSET` gets slow for deep pages (the database still reads and discards all the skipped rows), and rows inserted while a user is paging shift everything. Large applications use **keyset pagination** (also called "seek" or cursor pagination): remember the last row of the previous page, and ask for rows after it:

```sql shop
-- page 1: the 5 most expensive; the last one was the Office Chair (229.00, id 11)
SELECT id, name, price
FROM products
WHERE (price, id) < (229.00, 11)
ORDER BY price DESC, id DESC
LIMIT 5;
```

`(price, id) < (229.00, 11)` is a **row comparison**: rows with a lower price, or the same price and a lower id. With an index on `(price, id)`, every page is fast, however deep. APIs expose this as a "next page cursor".

=== lesson sql-expressions | Expressions, functions and CASE | 70
## Built-in functions

SQL comes with hundreds of functions. You call them like in any language: `name(arguments)`. The most useful ones, grouped:

**Text:**

```sql shop
SELECT name,
       upper(name) AS shouting,
       length(name) AS characters,
       left(name, 3) AS first_three,
       replace(name, ' ', '_') AS slug,
       split_part(email, '@', 2) AS email_domain
FROM customers
WHERE id <= 4;
```

| Function | Does |
|---|---|
| `lower(s)`, `upper(s)`, `initcap(s)` | change case |
| `length(s)` | number of characters |
| `trim(s)`, `ltrim`, `rtrim` | remove surrounding spaces (or other characters) |
| `substring(s from 2 for 3)`, `left(s, n)`, `right(s, n)` | parts of a string |
| `position('x' in s)`, `strpos(s, 'x')` | where a substring starts (0 if absent) |
| `replace(s, from, to)` | replace every occurrence |
| `split_part(s, sep, n)` | the n-th field |
| `concat(a, b, ...)`, `concat_ws(sep, a, b, ...)` | join strings, **ignoring NULLs** (unlike `\|\|`) |
| `format('%s has %s items', a, b)` | printf-style formatting |
| `lpad(s, n, '0')`, `rpad` | pad to a length |

**Numbers:**

```sql shop
SELECT name, price,
       round(price * 0.85, 2) AS discounted,
       ceil(price) AS rounded_up,
       floor(price / 100) * 100 AS price_band,
       price % 10 AS last_digits
FROM products
WHERE id <= 5;
```

`round(x, 2)` rounds to 2 decimals; `abs`, `power`, `sqrt`, `mod` (or `%`), `greatest(a, b, ...)` and `least(...)` do what their names say. `random()` returns a number between 0 and 1.

## Types and casting

Every value has a **type**, and an expression's type decides what you can do with it. Converting between types is called **casting**. Standard SQL writes `CAST(x AS type)`; PostgreSQL also has the shorter `x::type`:

```sql empty
SELECT CAST('42' AS integer) + 1 AS a,
       '3.14'::numeric * 2 AS b,
       42::text || ' apples' AS c,
       '2026-03-15'::date + 10 AS d,
       round(7::numeric / 2, 1) AS e;
```

A cast that can't work fails with an error (`'abc'::integer` gives `invalid input syntax for type integer`), which is what you want: bad data should be noticed, not silently turned into 0 (as MySQL does in some modes).

## CASE: if-then-else in SQL

**`CASE`** chooses a value based on conditions, checked in order; the first true one wins:

```sql shop
SELECT name, price,
       CASE
         WHEN price >= 300 THEN 'premium'
         WHEN price >= 50 THEN 'standard'
         ELSE 'budget'
       END AS price_band
FROM products;
```

Without `ELSE`, unmatched rows give `NULL`. The short form compares one expression with several values:

```sql shop
SELECT id,
       CASE status
         WHEN 'pending' THEN 'Waiting for payment'
         WHEN 'paid' THEN 'Being prepared'
         WHEN 'shipped' THEN 'On its way'
         WHEN 'delivered' THEN 'Delivered'
         ELSE 'Cancelled'
       END AS customer_message
FROM orders
ORDER BY id
LIMIT 6;
```

`CASE` works anywhere an expression does: in `SELECT`, `WHERE`, `ORDER BY` (for custom sort orders) and inside aggregate functions (Module 3).

## Custom sort orders

`CASE` in `ORDER BY` sorts by business rules rather than alphabetically:

```sql shop
SELECT id, status
FROM orders
ORDER BY CASE status WHEN 'pending' THEN 1 WHEN 'paid' THEN 2 WHEN 'shipped' THEN 3 ELSE 4 END, id;
```

=== lesson sql-dates | Dates and times | 65
## Date and time types

| Type | Holds | Example |
|---|---|---|
| `date` | a calendar day | `2026-03-15` |
| `time` | a time of day | `14:30:00` |
| `timestamp` | date and time, **without** a time zone | `2026-03-15 14:30:00` |
| `timestamptz` | an exact moment in time, shown in the session's time zone | `2026-03-15 14:30:00+00` |
| `interval` | a duration | `3 days 04:00:00` |

**Store moments as `timestamptz`.** Despite its name, it doesn't store a time zone: it stores an absolute moment (in UTC) and converts to and from the session's time zone. A plain `timestamp` is just a date and a time with no zone, so "10:15" is ambiguous when your users are in different countries. (The shop's `orders.ordered_at` uses `timestamp` to keep the examples simple; Module 5 discusses this choice.)

Write literals in ISO 8601 format: `'2026-03-15'`, `'2026-03-15 14:30'`, `'2026-03-15T14:30:00Z'`. Other formats (`'03/15/2026'`) depend on settings and are ambiguous (is `03/04` March or April?).

## The current date and time

```sql empty
SELECT current_date, now(), now() AT TIME ZONE 'Asia/Tokyo' AS tokyo_time;
```

`now()` (or `current_timestamp`) returns the time the current **transaction** started: it stays the same for every row of a query, which keeps results consistent.

## Date arithmetic

```sql shop
SELECT id, ordered_at,
       ordered_at + interval '14 days' AS return_deadline,
       ordered_at::date AS order_day,
       date '2026-04-01' - ordered_at::date AS days_before_april
FROM orders
WHERE id >= 17;
```

- `date + integer` adds days; `date - date` gives a number of days;
- `timestamp + interval` adds a duration (`interval '1 month'`, `'2 hours'`, `'1 year 6 months'`);
- `timestamp - timestamp` gives an interval; `age(a, b)` gives it in years, months and days.

## Taking dates apart

```sql shop
SELECT id, ordered_at,
       extract(year FROM ordered_at) AS year,
       extract(month FROM ordered_at) AS month,
       extract(dow FROM ordered_at) AS weekday,
       date_trunc('month', ordered_at) AS month_start,
       to_char(ordered_at, 'DD Mon YYYY HH24:MI') AS pretty
FROM orders
WHERE id <= 5;
```

- `extract(field FROM value)` gives one part: `year`, `quarter`, `month`, `day`, `dow` (day of week, 0 = Sunday), `hour`, `epoch` (seconds since 1970)...
- `date_trunc('month', ts)` cuts a timestamp down to the start of its month (or `'day'`, `'week'`, `'year'`, `'hour'`): essential for "per month" reports (Module 3).
- `to_char(value, format)` formats for display (PostgreSQL and Oracle; MySQL uses `DATE_FORMAT`, SQL Server `FORMAT`). Formatting is usually better done in the application, which knows the user's language.

## Filtering by date

To get everything in one month, compare with a **half-open range** rather than taking the column apart:

```sql shop
SELECT id, ordered_at
FROM orders
WHERE ordered_at >= '2026-01-01' AND ordered_at < '2026-02-01';
```

This is correct for timestamps (it includes 31 January at 23:59) and, unlike `WHERE extract(month FROM ordered_at) = 1`, it can use an index on `ordered_at` (Module 7).

~~~check
? Which condition reliably selects all orders placed in March 2026, on a timestamp column?
- `ordered_at BETWEEN '2026-03-01' AND '2026-03-31'`
+ `ordered_at >= '2026-03-01' AND ordered_at < '2026-04-01'`
- `ordered_at = '2026-03'`
- `ordered_at LIKE '2026-03%'`
> BETWEEN with a date stops at midnight on the 31st.
~~~

## Generating series of dates

`generate_series` produces a row for every step, which is how you build calendars and fill gaps in reports (a month with no orders still needs a row):

```sql empty
SELECT day::date
FROM generate_series(date '2026-03-01', date '2026-03-07', interval '1 day') AS day;
```
