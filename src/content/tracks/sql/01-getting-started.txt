## Why databases exist

Almost every application stores data: users, orders, messages, sensor readings. You could keep it in files (the Python and JavaScript courses did, with JSON), but as soon as an application is real, files break down:

- **Several users at once**: two people buying the last ticket at the same moment must not both succeed.
- **Crashes**: a power cut halfway through saving must not leave half an order behind.
- **Size**: finding one customer among ten million shouldn't mean reading ten million lines.
- **Questions nobody planned for**: "which customers in Boston spent more than $500 last year?" should need one short query, not a new program.
- **Rules**: every order must belong to an existing customer, prices can't be negative, emails must be unique.

A **database management system** (DBMS) is software that solves all of these: it stores data safely, lets many programs read and change it at the same time, keeps it consistent, and answers questions about it quickly.

## The relational model

In 1970, Edgar F. Codd, a researcher at IBM, proposed storing data as **relations**: what we now call **tables**. Each table holds one kind of thing; each **row** is one thing (one customer); each **column** is one fact about it (its name, its city). Every row is identified by a **primary key** (usually an `id` column), and tables point to each other with **foreign keys**: an order row stores the `id` of its customer.

Here is part of the shop database used throughout this course:

```sql shop
SELECT * FROM customers;
```

Press **▶ Run**: that query asks the database for every column (`*`) of every row in the `customers` table, and the database answers with a table. This course runs **real PostgreSQL** inside DevQuest; every example works on a fresh copy of a sample database, so experiment freely: press **✎ Edit**, change things and run again. Nothing you do can break it.

The relational model's great idea is that you describe **what** data you want, not **how** to find it. The database works out the "how" (which files to read, which indexes to use, in which order) by itself.

## SQL: the language of relational databases

**SQL** (Structured Query Language, pronounced "S-Q-L" or "sequel") was created at IBM in the 1970s to work with relational data, and it became an ANSI/ISO standard in 1986. Fifty years later it's still the most widely used way to work with data, and one of the most valuable skills for any developer, analyst or data scientist.

SQL is **declarative**: a query states the result you want.

```sql shop
SELECT name, city
FROM customers
WHERE country = 'UK';
```

Compare that with the loop, the condition and the list you would write in Python or JavaScript to do the same thing. The database's **query planner** turns the SQL into an efficient plan, and it can change that plan as the data grows, without any change to your query.

SQL has several parts, which this course covers in turn:

| Part | Statements | Used for |
|---|---|---|
| Queries | `SELECT` | reading data (most of what you'll write) |
| Data manipulation (DML) | `INSERT`, `UPDATE`, `DELETE` | changing data |
| Data definition (DDL) | `CREATE`, `ALTER`, `DROP` | creating tables and other objects |
| Data control (DCL) | `GRANT`, `REVOKE` | permissions |
| Transaction control | `BEGIN`, `COMMIT`, `ROLLBACK` | grouping changes |

## Which database? Dialects

Every major database speaks SQL, with its own extensions and small differences, called **dialects**:

| Database | Typical use |
|---|---|
| **PostgreSQL** | general purpose; the most standards-compliant open-source database, and the most popular among developers |
| **MySQL** / MariaDB | web applications (WordPress, many startups) |
| **SQLite** | a database in a single file, built into phones, browsers and apps |
| **SQL Server** | Microsoft and enterprise environments |
| **Oracle** | large enterprises and banks |
| Snowflake, BigQuery, Redshift | analytics on huge datasets ("data warehouses") |

The core you'll learn (`SELECT`, joins, grouping, `INSERT`, `CREATE TABLE`, transactions) works almost everywhere. This course uses PostgreSQL, and notes the differences you'll meet in the others, such as `LIMIT` versus SQL Server's `TOP`.

## Not only relational

You'll also hear of **NoSQL** databases: document stores (MongoDB), key-value stores (Redis), wide-column stores (Cassandra) and graph databases (Neo4j). They trade some of the relational model's guarantees for flexibility or scale in specific situations, and DevQuest has tracks on MongoDB and Redis. Relational databases remain the default choice for most applications, and PostgreSQL itself can store documents too (Module 6).

## SELECT and FROM

A query starts with **`SELECT`**, the columns you want, then **`FROM`**, the table:

```sql shop
SELECT name, price
FROM products;
```

- Columns come back in the order you list them.
- `SELECT *` returns all columns. It's handy for exploring, but in application code list the columns you need: the query stays clear, sends less data, and doesn't break when someone adds a column.
- SQL **keywords** aren't case-sensitive (`select` works), but writing them in capitals is a strong convention that makes queries easy to read. Table and column names are written in lower case.
- Spaces and line breaks don't matter: put each clause on its own line once queries grow.
- A statement ends with a **semicolon** `;`, which you need when you run several statements together.

## Expressions and aliases

A `SELECT` list can contain **expressions**, not just columns. **`AS`** gives a result column a name (an **alias**):

```sql shop
SELECT name,
       price,
       price * 1.2 AS price_with_tax,
       stock * price AS stock_value
FROM products;
```

Without `AS`, PostgreSQL names a computed column `?column?`, which is useless to whoever reads the result. Aliases that contain spaces or capitals need double quotes: `AS "Stock value"`.

Strings are written in **single quotes**, and `||` joins them:

```sql shop
SELECT name || ' (' || country || ')' AS customer
FROM customers;
```

A single quote inside a string is written twice: `'Chef''s Knife'`. **Double quotes** are only for names (`"Stock value"`), never for strings: this is one of the most common beginner mistakes, and MySQL's habit of accepting `"text"` as a string doesn't help.

## Removing duplicates: DISTINCT

```sql shop
SELECT DISTINCT country
FROM customers;
```

`DISTINCT` removes duplicate rows from the result: four countries instead of twelve customers. With several columns, it removes rows where **all** the listed columns are the same.


## SELECT without a table

PostgreSQL can evaluate expressions without any table, which makes it a handy calculator for trying things out:

```sql empty
SELECT 2 + 3 * 4 AS answer, 'Hello' || ', SQL' AS greeting, 7 / 2 AS integer_division, 7 / 2.0 AS decimal_division;
```

Note `7 / 2` is `3`: dividing two integers gives an integer in PostgreSQL (and SQL Server), while MySQL gives `3.5000`. Make one side a decimal (`2.0`) when you want a fractional result.

## Client and server

A database like PostgreSQL runs as a **server**: a program that owns the data files and listens for connections, usually on port 5432 (MySQL: 3306, SQL Server: 1433). Everything else is a **client** that connects, sends SQL and receives results:

- **`psql`**, PostgreSQL's command-line client;
- graphical tools: **pgAdmin**, **DBeaver**, **DataGrip**, TablePlus, the database panels in VS Code;
- your applications, through a **driver** (Module 7);
- DevQuest, which here runs PostgreSQL inside the app itself, compiled to WebAssembly.

A connection needs a **host**, **port**, **database name**, **user** and **password**, often written as one **connection URL**:

```
postgres://shop_app:secret@localhost:5432/shop
```

Never put real passwords in code or commit them to Git: use environment variables (`DATABASE_URL`) or a secret manager.

## Installing PostgreSQL

- **Windows / macOS**: the installers from postgresql.org (they include pgAdmin), or Postgres.app on macOS.
- **Linux**: `sudo apt install postgresql` (Debian, Ubuntu) or your distribution's package.
- **Docker**, the most common choice for development, because every project can have its own version:

```
docker run --name shop-db -e POSTGRES_PASSWORD=dev -p 5432:5432 -d postgres:18
```

- **Hosted**: Neon, Supabase, AWS RDS, Google Cloud SQL and Azure give you a managed server with backups.

## psql essentials

```
psql postgres://postgres:dev@localhost:5432/postgres
```

Inside `psql`, SQL statements end with `;`, and backslash commands (not SQL; only `psql` understands them) explore the database:

| Command | Does |
|---|---|
| `\l` | list databases |
| `\c shop` | connect to the database `shop` |
| `\dt` | list tables |
| `\d customers` | describe a table: columns, types, keys, indexes |
| `\x` | toggle expanded display (one column per line, for wide rows) |
| `\i file.sql` | run the SQL in a file |
| `\timing` | show how long each statement takes |
| `\?` / `\h SELECT` | help on psql commands / on an SQL statement |
| `\q` | quit |

The same information is available with plain SQL from the **system catalog**, which works in any client. You'll explore it in Module 7; here's a taste:

```sql shop
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public';
```

## Databases, schemas and tables

A PostgreSQL **server** (also called a cluster) holds several **databases**; each database contains **schemas** (namespaces, `public` by default); each schema contains **tables** and other objects. So the full name of a table is `database.schema.table`, and you can write `public.customers` in a query. MySQL has no separate schema level (its "schema" means a database), and SQL Server uses `dbo` as the default schema.

## Scripts and comments

SQL is usually kept in `.sql` files: schema definitions, seed data, migrations (Module 5) and reports. Comments make them readable:

```sql shop
-- A line comment
SELECT name, price   /* a block comment
                        can span lines */
FROM products
WHERE price > 300;
```

When a script holds several statements, clients run them in order. In DevQuest the result shown is that of the **last** statement that returns rows.

=== lesson sql-errors | Reading SQL errors | 50
## Errors tell you exactly what's wrong

When PostgreSQL can't run a statement, it stops and explains why. Reading those messages calmly is half of working with databases. A message has up to four parts, as `psql` and DevQuest show them:

```
ERROR: column "nme" does not exist (line 1)
HINT: Perhaps you meant to reference the column "products.name".
```

- **ERROR**: what went wrong;
- the **position** (DevQuest shows the line);
- **DETAIL**: the specific values involved, when relevant;
- **HINT**: a suggestion, when PostgreSQL has one.

Run each of these to see the messages, then fix them (the fixes are in the comments):

```sql shop
-- error: a misspelt column (fix: name)
SELECT nme, price FROM products;
```

```sql shop
-- error: a misspelt table (fix: customers)
SELECT name FROM customer;
```

```sql shop
-- error: a string in double quotes is a column name (fix: 'UK')
SELECT name FROM customers WHERE country = "UK";
```

```sql shop
-- error: ORDER without BY (fix: ORDER BY price)
SELECT name, price FROM products ORDER price;
```

That last one shows a classic: a **syntax error** is reported where the parser got confused, which is often just **after** the real mistake. The message points at `price`, but the problem is the missing `BY` before it. When the message says `syntax error at or near "X"`, look at what comes right before `X`.

## The most common errors

| Message | Usual cause |
|---|---|
| `column "x" does not exist` | a typo, a column of another table, or a string written in double quotes |
| `relation "x" does not exist` | a misspelt table, a table in another schema, or a table not created yet ("relation" means table) |
| `syntax error at or near "x"` | a missing comma, parenthesis or keyword just before `x`, or a reserved word used as a name |
| `operator does not exist: integer = text` | comparing values of different types (quote numbers only as text, not as numbers) |
| `column "x" must appear in the GROUP BY clause or be used in an aggregate function` | Module 3 explains this one |
| `duplicate key value violates unique constraint` | inserting a value that must be unique, twice (Module 5) |
| `null value in column "x" violates not-null constraint` | a required value is missing |
| `division by zero` | exactly that |

```sql shop
-- error: comparing a number with text (fix: WHERE id = 3)
SELECT name FROM customers WHERE id = 'three';
```

## A statement either works completely or not at all

When a statement fails, **nothing** it would have done happens. In a script, PostgreSQL stops at the first failing statement; statements before it have already run (unless they're inside a transaction, Module 7). So when you fix an error in a script, check whether the earlier statements already ran.

~~~check
? `syntax error at or near "FROM"` in `SELECT name price, FROM products`. Where's the mistake?
+ The stray comma before FROM (and the missing comma between name and price)
- FROM is misspelt
- The table doesn't exist
- price is not a column
> The parser reports where it got stuck: look just before that word.
~~~

## Reserved words and quoting names

Some names clash with SQL keywords: a column named `order`, `user` or `group` causes syntax errors. You can quote it (`"order"`), but it's better to choose another name (`orders`, `customer`, `team`). Quoted names are also **case-sensitive**: `"Customers"` and `customers` are different tables in PostgreSQL, which is why lower-case, unquoted, `snake_case` names are the convention.
